# 二期写作与证据风格指南

二期章节面向已经会写一点 Python、但还没有把 AI Infrastructure 看成一个完整系统的读者。目标不是把一期内容改长，而是让读者能从小例子走到数学、论文、源码和实验，并且知道结论的边界。模板和检查器只冻结接口；可学性仍由作者和审阅者负责。

## 1. 先解决读者的问题

每个新概念按“问题 → 直觉 → 最小例子 → 正式定义 → 机制 → 边界 → 练习”推进。开头先描述两个请求、一块内存、一个批次或一次失败。术语第一次出现时用生活化或运行时例子解释，再给英文名、符号和实现名。前一节的概念在下一节继续使用，避免一段话塞进十个新名词。
检查器只把开头的三个概念里程碑视为“问题 → 心智模型 → 机制”；标题、前置说明、本章地图和正文导言不算 substantive section，最小例子或正式定义可以放在心智模型与机制之间。这个宽检查保护新人路径，不替代对后续边界、实验和练习的教师评审。

可以这样开头：

> 两个请求同时到达时，第二个请求没有变慢，为什么 p95 却突然变大？先画出等待区间，再决定要不要引入排队论。

不要这样开头：

> 本章全面介绍调度、批处理、KV cache、并行和可观测性体系。

前一种写法给读者一个可回答的问题；后一种是目录，不是教学。

## 2. 允许教师的声音

像耐心的老师在白板旁讲解。允许短句、提问、停顿、反例和“这里暂时不展开”。多写“先看一个只有两个请求的例子”“这里容易误解的一点是”“如果把这个假设拿掉，结论会怎样”。少用“赋能、体系化、全面覆盖、值得注意的是、在此基础上、从而实现”等没有信息量的连接词，也不要让每段都变成同样的三句模板。

一个小节至少要回答一个具体困惑，展示一个可复算的例子，说明正式机制，给出系统对应关系，并承认一个失败边界。复杂章节再加论文谱系、源码导读和实验；不要为满足数量把它们硬挤在同一段。

## 3. 数学先算数，后写符号

公式出现前先说明“为什么需要它”。用实际数字算一次，然后推广为符号。每个变量都要有含义、单位、来源和有效范围；说明假设以及假设失效后的变化。不要把符号堆成装饰，也不要把一个 toy model 的结果写成生产承诺。

建议顺序：

1. 描述要估计的量和观测单位
2. 给出最小数字例子，展示中间步骤
3. 写一般公式，逐个定义变量
4. 用边界值或反例检查公式
5. 指向实验，说明哪些量真实测到、哪些只是推断

## 4. 论文是一次失败后的选择

每篇论文都回答五件事：

1. 当时的系统哪里慢、错或贵
2. 作者观察到的关键瓶颈是什么
3. 核心想法如何用直觉和至多一页公式解释
4. 实验在其硬件和数据上证明了什么、不能证明什么
5. 今天的实现保留了什么、改变了什么，后来有哪些负结果或替代设计

区分“论文测到了 X”和“我们可以迁移机制 Y”。论文结果必须注明 workload、硬件、软件版本、重复次数和统计口径；如果原文没有给出，就写“未报告”，不要补猜。

## 5. 源码导读是受限的阅读任务

在链接前先给任务：例如“找出一次请求何时从 waiting 变成 running”。注明仓库、tag/commit、目录和与版本相关的差异。只展示 20–40 行关键代码或更小片段；逐行解释输入、状态变化、异常路径和指标。固定版本的源码链接不能用 `main` 代替；若只能从当前 `main` 发现线索，标成待验证，不能当作证据。

## 6. 实验记录能被别人复现

实验记录至少包含：

- 基线、变量、控制变量和研究问题
- 硬件、OS、驱动、框架/编译器版本、commit/tag
- 输入数据、数据分布、随机种子和预热策略
- 完整命令、环境变量（脱敏）、原始输出和 artifact 路径
- 重复次数、聚合方法、p50/p95/p99、吞吐、TTFT、ITL/TPOT、显存/KV 使用率中相关指标
- 误差来源、置信或不确定性说明，以及结果不能推断的部分

目标 GPU、RDMA 或多机不可用时，应提供 CPU 或仿真 fallback，并在标题或结果旁明确“这是解释性模型，不是硬件等价 benchmark”。先保证控制变量和原始输出，再谈漂亮图表。

## 7. 内容标签与证据清单

正文可以用自然语言表明证据类型，不要求每段都插入标签。统一分类为：

- `fact` 事实：可由来源直接核对的陈述
- `definition` 定义：约定一个量或术语的含义
- `derivation` 推导：从已说明假设逐步得到的结果
- `paper_result` 论文结果：原论文测得的结果和条件
- `source_observation` 源码观察：在固定版本中看到的路径或数据结构
- `experiment_measurement` 实验测量：本项目实验的原始观察和统计方法
- `inference` 推断：由证据支持但不是直接观察的结论
- `design_judgment` 设计判断：明确是取舍或推荐，而非自然定律
- `unverified_hypothesis` 未验证假设：可测试、暂未验证的解释

每章在 `docs/phase2/evidence/` 放同名 JSON manifest。顶层字段是 `manifest_version`、`chapter_id` 和 `entries`。每条 entry 必须有 `claim`、`type`、`source_url`、`version`、`experiment_id`、`limitation` 和 `review_date`：

- `claim` 只写一个可审阅的陈述，不写整段摘要
- `source_url` 使用论文、规范、官方文档、仓库或本实验记录的稳定 URL；只能用 `http`/`https`
- `version` 写 commit、release/tag、论文版本或 RFC；`main`、`latest` 等分支名不算固定版本
- `experiment_id` 写可重跑实验标识；不是实验的条目填 `null`
- `limitation` 诚实说明硬件、数据、因果或迁移边界，不能写成空泛的“需要更多研究”
- `review_date` 用 `YYYY-MM-DD`，记录最近一次核对来源和断言的日期

Manifest 是证据地图，不是把所有链接堆在文末的参考文献表。一个论文结果可以有一个条目；一个结论若同时依赖源码和实验，就拆成可分别复核的条目。

## 8. 前置依赖与版本

二期 frontmatter 的固定字段为 `phase`、`chapter_number`、`level`、`prerequisites`、`learning_objectives`、`paper_count`、`source_commits`、`lab_paths`、`last_verified`，并保留一期的 `id`、`title`、`description`、`slug`、`sidebar_position` 以便迁移期间继续构建。`source_commits` 和 `lab_paths` 是列表，即使目前只有一项也不要偷偷改回单数；旧 UI 需要时暂时同步 `source_commit` 和 `lab_path`。

`chapter_number` 使用 1–40 的稳定编号；`level` 使用 `foundation`、`core`、`systems`、`advanced`、`frontier` 或 `capstone`。前置项写稳定 id，不写标题和 branch。`last_verified` 是最近一次人工核对教学、源码和证据的日期；它不是构建时间戳。

## 9. 反例和失败诊所

每章至少保留一个反例或失败现象。推荐结构：

1. 观察到什么（含原始指标或命令）
2. 哪些解释看起来合理
3. 最小排查如何区分它们
4. 哪个证据支持或推翻了假设
5. 修复、回滚和剩余风险

把“指标正常”也当成需要解释的现象：平均吞吐变好可能掩盖了 p99 变坏；缓存命中率上升可能来自更短的请求；固定随机种子不能消除异步归约差异。失败记录比无条件成功更能帮助读者迁移方法。

## 10. 审阅清单（不替代教师评审）

- 新人能否在前三节不依赖框架名读懂问题、直觉和数字例子？
- 每个公式是否定义变量、单位、假设，并有一次数字代入？
- 论文结果是否保留硬件、数据和统计条件，且没有被写成生产保证？
- 源码入口是否固定到 tag/commit，并注明版本敏感的路径和异常分支？
- 实验是否包含基线、控制变量、命令、重复、分位数、原始输出和限制？
- 至少两个方案的边界是否用同一工作负载和单位比较？
- 失败诊所是否提供可执行的排查路径，而不是“注意性能问题”？
- 证据 manifest 的每条 claim 能否由读者独立打开、重跑或判断其限制？
- 是否删掉重复总结、空泛连接词和为了凑字符数而加的段落？

检查器只能发现缺字段、坏日期、未固定版本、断开的 JSON 和开头教学顺序缺失；它不能替作者判断解释是否诚实、例子是否合适或因果链是否成立。
