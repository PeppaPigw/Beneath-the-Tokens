# 第23章　AI Infra 成本、容量规划、能耗与碳治理

> 一次模型调用的价格不是 GPU 小时价格。它还包括排队造成的空转、权重和数据的存储、跨区域流量、平台团队的固定成本、备用容量、失败重试，以及电力和硬件制造的环境代价。本章把这些支出和影响放进同一个可审计模型：先定义功能单位，再测量资源和质量，最后用容量、预算和碳约束做决策。数字是事实、测量、推断还是设计判断，会明确标注；没有测量证据时，不把估算写成精确账单。

本章使用“事实、机制、测量、推断、设计判断”五类证据标记。**事实**来自标准、论文或供应商文档；**机制**是根据调度器、计费和功率遥测还原的因果链；**测量**只对声明环境中的实验负责；**推断**由测量与公式计算；**设计判断**是在目标、风险和预算清楚时的工程选择。云厂商价格、GPU型号和电网碳强度会变化，示例价格仅用于演示方法，生产预算必须用带日期、区域和承诺类型的报价快照。

## 23.1 为什么要把成本、容量与碳放在一起

AI 系统的资源曲线通常呈现“固定底座加峰值弹性”。模型权重常驻在对象存储和缓存，控制面、日志、监控和最小副本在低流量时仍运行；流量上涨时才增加 GPU、副本、网络和电力。只看平均利用率会掩盖尖峰延迟，只看峰值会买下长期闲置的容量，只看云账单又会遗漏企业自建机房的折旧、运维和电力。

成本和碳还会互相影响。把任务搬到低碳区域可能增加跨区流量和延迟；使用抢占式实例可降低价格和嵌入式碳摊销，却需要保存检查点并承受重算；提高批大小通常提升每 GPU 的吞吐，但会增加排队等待和单请求尾延迟。工程目标不是寻找一个永远最小的数字，而是在用户 SLO、数据驻留、安全、预算和碳约束下找可解释的折中。

本章的心智模型是四层账本：

1. **工作负载层**：请求、token、样本、训练步、检索条目或输出视频帧等功能单位。
2. **资源层**：GPU/CPU 秒、显存、存储字节月、网络字节、队列等待和失败重算。
3. **财务层**：按量价、承诺折扣、折旧、人员、软件许可、设施和风险缓冲。
4. **环境层**：电能、PUE、位置或时间相关碳强度，以及设备制造的隐含碳。

任何报告都应能从单位经济学回溯到作业 ID、租户、区域、时间窗和采样误差。若无法回溯，就只能称为“方向性估计”，不能拿来做精细归因或对外环境声明。

## 23.2 定义功能单位和成本边界

### 23.2.1 选择单位，而不是先选价格

训练可以使用“每有效训练 token”“每完成一轮数据集”“每达到目标验证损失的 GPU 小时”；在线推理可以使用“每百万输入加输出 token”“每千个成功请求”“每生成一张图”；批处理可以使用“每百万行”“每个视频分钟”。单位必须能被业务和财务同时理解。若只用“每 GPU 小时”，容易奖励把批次拆成更多小时而忽略吞吐和质量。

定义功能单位 (U) 后，记录完成数量 (Q_U)、资源消耗 (R_i) 和质量门槛 (G)。例如，只有通过离线评测且没有数据质量告警的训练轮才计入“有效训练轮”；被抢占而重算的步数要计入总资源，却不能计入有效产出。在线服务应把超时、策略拒答和错误 schema 从成功分母中排除或单独分类，避免用低质量响应稀释单位成本。

### 23.2.2 账本边界和时间窗口

建议为每个账本写出四个边界：

- **时间边界**：账单周期、训练项目生命周期或滚动 30 天窗口。跨窗口的预留实例和设备折旧要按使用小时摊销。
- **范围边界**：是否包含共享控制面、数据湖、网络出口、客服与值班；是否包含硬件制造的隐含碳。
- **归属边界**：直接租户标签、共享集群按 GPU 秒或峰值预留分摊、无法归属的公共成本进入平台池。
- **质量边界**：成功输出、重试输出、缓存命中和降级输出分别如何计数。

边界变化必须版本化。将“日志成本不算在模型项目”改成“日志按字节分摊”会改变历史趋势；应在报告中标注生效日期，并在仪表盘上保留旧口径以便重述，而不是静默重写。

### 23.2.3 直接、共享和机会成本

直接成本容易分配：带租户标签的 GPU 运行秒、对象存储桶费用和专属数据库。共享成本包括调度器、监控、镜像仓库、机房网络、SRE 值班和安全扫描。机会成本表示为了低延迟保留的峰值容量在低峰期无法出售给其他团队的收入或替代用途；它不是云账单上的一行，但在容量决策中应被显式写出。

一个可解释的总成本模型为：

\[
C_{total}=C_{compute}+C_{storage}+C_{network}+C_{platform}+C_{people}+C_{facility}+C_{risk}
\]

其中风险项可包含价格波动、故障重算和容量短缺的预算缓冲。单位成本为 (C_U=C_{total}/Q_U)。公式不要求所有团队都使用同一套分摊权重，但权重必须公开、稳定，并能在季度复盘时修改。

## 23.3 GPU 与加速器成本模型

### 23.3.1 从标价到有效 GPU 小时

云 GPU 的“每小时价格”只是起点。有效小时成本还要考虑折扣、承诺、空转、失败和多租户碎片：

\[
C_{gpu,eff}=\frac{P_{on-demand}\times H_{bill}\times (1-d_{commit}) + C_{egress}+C_{support}}{H_{useful}}
\]

其中 (H_{useful}) 是产生合格功能单位的 GPU 小时，而不是实例计费小时；(d_{commit}) 是承诺折扣。若一台 8 卡节点只有 5 卡被作业使用，剩余卡被拓扑、显存或配额限制占用，闲置部分应进入碎片损失，不应在“GPU 利用率 62.5%”后就宣称资源充分利用。

自建集群可用年化成本转换：

\[
C_{hour,owned}=\frac{C_{capex}/L + C_{maintenance}+C_{power}+C_{space}+C_{staff}}{H_{available}}
\]

(L) 为折旧年数，(H_{available}) 是考虑维护、升级和故障后的可用小时。折旧不等于现金流，财务模型应同时展示现金流、会计折旧和边际成本，避免用一个数字回答三个不同问题。

### 23.3.2 利用率的三种含义

“GPU 利用率”至少有三层：

1. **分配利用率**：被调度器分配的卡小时除以可供卡小时，反映容量是否卖出。
2. **忙碌利用率**：SM、张量核心或内存引擎处于活动的时间比例，反映设备是否在工作。
3. **有效产出利用率**：合格 token、样本或请求数除以理论或基线吞吐，反映工作是否有价值。

NVIDIA DCGM 文档提醒，某个活动比例可能是少量 SM 长时间活动，也可能是全部 SM 短时间活动，单一百分比不能解释瓶颈；应同时记录 SM active、张量管线、显存带宽、功率和 PCIe/NVLink 流量。因而报告中应至少给出分配、忙碌和有效产出三列，并注明采样周期。

### 23.3.3 低利用率的诊断树

当忙碌利用率低时，先不要立即增加 GPU。可按以下顺序排查：

- 输入管道是否缺数据、解压或 tokenization 占满 CPU；
- 数据并行是否因最慢 worker（straggler）等待；
- 批大小、序列长度和 padding 是否导致显存碎片；
- 通信是否受 PCIe、NVLink、RDMA 或跨区带宽限制；
- 内核是否频繁同步，导致 GPU 间隙；
- 调度器是否把短作业塞进不适合的节点，形成碎片；
- 监控采样是否过粗，遗漏了短时突发。

每个改动都要同时观察吞吐和尾延迟。把功率上限拉高可能提升吞吐，却可能违反机架供电或碳预算；把批大小加倍可能降低每 token 成本，却让 P99 超出用户 SLO。优化的目标函数必须含质量和服务约束。

### 23.3.4 多租户分摊

共享 GPU 可按三种主方法分摊：按实际 GPU 秒、按保留峰值、按加权资源消耗。按实际秒简单但会奖励高峰抢占；按峰值保留能反映机会成本，却可能惩罚低流量团队；加权方法可把显存、网络和 CPU 与卡秒组合，但需要稳定的权重。推荐同时发布“直接使用费”和“容量保留费”，并给出共享平台费的分配规则。禁止把个人或团队的环境、健康、绩效等敏感数据作为成本惩罚依据。

## 23.4 排队理论与容量规划

### 23.4.1 从峰值并发到服务率

设到达率为 \(\lambda\)（请求/秒），每个 worker 的服务率为 \(\mu\)，并行 worker 数为 \(c\)。利用率近似为 \(\rho=\lambda/(c\mu)\)。当 \(\rho\) 接近 1 时，平均等待和尾延迟会急剧上升，即使平均 GPU 利用率看起来“很高”。在线推理通常需要为突发和重试留出余量，目标 \(\rho\) 可能在 0.5–0.8 之间，具体值要由压测和 SLO 决定，不能把经验值当作规范。

对到达和服务时间近似随机的场景，可用 Erlang-C 估计多服务台队列等待概率：

\[
P(wait)=\frac{\frac{a^c}{c!}\frac{c}{c-a}}{\sum_{k=0}^{c-1}\frac{a^k}{k!}+\frac{a^c}{c!}\frac{c}{c-a}},\quad a=\lambda/\mu
\]

平均排队等待约为 \(W_q=P(wait)/(c\mu-\lambda)\)。模型假设先进先出、无限队列和独立服务时间；长上下文、优先级、批处理和抢占会破坏假设。因此它是容量初筛，不是尾延迟的证明。生产决策要用带真实 trace 的离散事件仿真或压测校准。

### 23.4.2 训练容量：有效吞吐与检查点

训练作业的容量单位不只是卡数。若每步有效 token 为 (T)，每步耗时 (s)，则吞吐为 (T/s)。数据加载、通信、检查点和重算应纳入有效步时：

\[
s_{effective}=s_{compute}+s_{input}+s_{comm}+s_{checkpoint}+s_{recovery}
\]

检查点间隔过长，故障会造成更多重算；过短则增加对象存储、网络和同步开销。可用期望重算成本粗估 (C_{recovery}\approx p_{fail}\times t_{since\_checkpoint}\times C_{cluster})，再与检查点成本比较。这里的故障概率需用历史测量，不能直接套供应商宣传的可用率。

### 23.4.3 头寸、缓冲与可用区

容量计划至少分三层：基线容量（覆盖 P50）、弹性容量（覆盖已知峰值）、恢复容量（覆盖节点故障、升级和供应中断）。缓冲不应只写百分比，还要写触发条件和释放条件：队列深度超过阈值连续五分钟扩容，低于阈值并且冷却十分钟缩容；恢复容量在演练中验证能否在 RTO 内获得。跨区域复制和数据驻留会减少可用的候选容量，必须在“有效容量”而非物理总卡数中反映。

### 23.4.4 预留、抢占和混合池

按量、预留、节省计划、抢占/Spot 或 TPU Flex-start 等选项的组合取决于作业可中断性：

- 在线关键路径使用稳定的基线池，避免把用户 SLO 绑定到可撤回容量；
- 可恢复训练和批推理使用抢占池，要求频繁、可校验的检查点；
- 实验作业使用排队公平和预算上限，允许延迟换取低价；
- 混合池要防止“便宜卡”因驱动、显存或拓扑不兼容而产生隐性重构成本。

每种池都要记录中断率、启动延迟、失败重算和真实单位成本。只有在这些数据稳定后，才扩大抢占比例。

### 23.4.5 容量计划工作表

一次可审计的容量评审可以按下面的顺序进行。第一步是冻结工作负载假设：每秒请求数的 P50、P95 和突发持续时间，输入与输出 token 的分布，缓存命中率，模型和 tokenizer 版本，允许的批处理窗口，以及关键路径的 P99 延迟。没有这些假设，直接说“需要一百张卡”没有可复核含义。第二步是测量基线：在代表性的序列长度和数据分片上，记录每卡有效 token/s、显存峰值、节点功率、通信占比和失败率。第三步是画出阶梯式容量曲线，将每增加一个副本带来的服务率提升、启动延迟和成本写在同一张图上。

第四步是加入非理想因素。节点升级、驱动重启、网络维护、配额等待、抢占中断和慢 worker 都会降低可用容量。可以定义有效容量系数 (a)，其中 (a=0.85) 表示在时间窗口内只有 85% 的物理卡小时能完成合格工作；有效卡数为 (N_{effective}=N_{physical}\times a)。系数不是常数，应从过去 30 至 90 天的作业和维护记录估计，并按区域与池类型分开。第五步是做敏感性分析：把流量、服务率、故障率和价格分别上调或下调，观察 SLO、预算和碳区间是否仍可接受。若一个小幅变化就让计划失效，应先解决供给和架构风险，而不是把缓冲写成更大的百分比。

容量评审还要回答“何时不扩容”。当排队增加但有效产出没有增加时，扩容可能只是把瓶颈从 GPU 移到数据管道、网络或后处理。可以把吞吐拆成最小值：

\[
T_{e2e}=\min(T_{GPU},T_{input},T_{network},T_{storage},T_{postprocess})
\]

若 (T_{input}) 是最小项，增加 GPU 只会提高闲置和功率。评审记录应包含瓶颈证据、候选修复、预计收益、验证窗口和停止条件。停止条件很重要，例如“GPU 忙碌率达到 70% 但 P99 不得超过 2 秒”“每增加一张卡的有效 token/s 提升低于 5% 时停止横向扩展”。这样可以防止容量采购替代性能工程。

### 23.4.6 优先级、饥饿与公平

成本最低的排队策略不一定对组织公平。若所有作业按先到先服务，长训练会阻塞短实验；若只按业务优先级，低优先级作业可能永久饥饿。建议为队列定义最大等待时间和配额份额，采用带老化的优先级：等待越久，优先级逐步提升，但不能突破生产安全上限。每个租户要看到自己的等待分布、抢占次数和被拒绝原因，而不是只看到一个“容量不足”。公平策略也要防止团队通过拆分作业或伪造标签获得更高优先级，调度器应按受控项目和历史消耗校验。

## 23.5 成本分摊、标签与 FinOps 治理

### 23.5.1 最小可审计标签

每个作业或请求至少带：`org`、`team`、`project`、`environment`、`model_version`、`workload_type`、`region`、`cost_center`、`data_class` 和 `owner`。标签来自受控枚举，禁止用户把自由文本放进高基数字段。缺失标签的资源进入隔离账单池并触发修复，不应默默分到“平台”来掩盖问题。个人姓名、健康、绩效和其他敏感信息不应成为成本标签。

### 23.5.2 共享成本的透明分配

平台池可按“直接卡秒 + 峰值保留 + 网络字节 + 存储字节月 + 请求数”加权。发布权重、样例计算和误差带，允许团队重现账单。对内部计费，先采用 showback（展示成本）观察行为，再逐步采用 chargeback（实收费）；过早收费会导致团队规避标签、压缩质量或重复建设私有集群。

### 23.5.3 单位经济学仪表盘

最低仪表盘建议包括：每成功请求成本、每百万 token 成本、每有效训练步成本、GPU 分配/忙碌/有效利用率、P50/P95/P99 延迟、队列等待、失败重算比例、缓存命中率、存储与出口成本、每功能单位电能和碳强度。所有指标注明时间窗、区域、模型版本、采样率和数据延迟。成本与碳数据通常滞后于请求数据，要通过版本化快照连接，不要用当天部分账单与完整请求量直接相除。

### 23.5.4 预算护栏和异常检测

预算不是事后报警。为项目设月度软阈值、硬阈值和应急豁免流程：软阈值触发建议优化，硬阈值暂停非关键实验或降低并发，豁免需要写明负责人、期限和回退条件。异常检测可使用滚动中位数与 MAD，避免单个大训练作业把均值拉高；同时保留业务发布日、竞赛和数据回灌等已知事件，减少误报。自动关停必须有检查点和保护白名单，不能因时钟或标签错误删除生产实例。

### 23.5.5 一个可复核的成本演算例

假设一个团队运行四卡节点，账面按每卡每小时 2.4 美元计费。一个 24 小时窗口里，节点启动 20 小时，实际执行合格训练 12 小时，重算 2 小时，等待输入和排队 6 小时。若按账单，计算成本是 \(4\\times20\\times2.4=192\) 美元；若按合格训练，直接有效成本是 \(192/12=16\) 美元/有效 GPU 小时；若把重算也视为必要投入，按 14 小时合格加重算工作摊销，则是 13.71 美元/工作 GPU 小时。三个数字都可能有用，但回答的是不同问题。报告必须写清分母，否则“成本下降”可能只是把失败和等待移出分母。

继续假设这 12 小时产生 6000 万有效 token，输入缓存命中节省了 10% 计算，但增加了 200 GB 月存储和读取费用。可以同时展示每百万 token 的计算、存储、网络和平台分项，再展示含共享费的全成本。若换模型后 token 数增长而质量下降，单位 token 成本下降不代表单位合格答案成本下降。建议为每个项目保留“产出定义”字段，记录质量评测版本、阈值和抽样误差。

共享平台费通常按月结算，不能把当月全额分给恰好在月末运行的大作业。一个简单方法是按同一窗口的直接 GPU 秒、峰值保留、对象存储字节月和日志字节做权重；另一个方法是为每个租户建立容量承诺，未使用部分仍由承诺方承担。无论采用哪种方法，都要提供分摊前后的总额对账，保证各租户之和等于平台账单加内部允许的舍入误差。财务审计人员应能用作业清单和权重重算出同一结果。

## 23.6 云与自建：比较的是风险调整后的总拥有成本

### 23.6.1 云模式的优点与隐藏项

云的优点是按需扩缩、全球区域、托管控制面和快速试错。隐藏项包括跨区流量、日志摄取、快照、IP、负载均衡、支持计划、最小计费粒度、配额等待、GPU 供应中断和出口锁定。报价页面常按区域、操作系统、承诺和计费单位区分，不能拿一个公开数字代替项目报价。估算表应保存抓取日期、SKU、区域、货币和折扣条件。

### 23.6.2 自建模式的优点与隐藏项

自建可控制拓扑、数据驻留、功率上限和长期利用，但需要承担采购提前期、备件、网络、机房电力、冷却、固件、驱动、值班和资产处置。容量一旦买下，低谷闲置也要付折旧；高峰缺货时再买机器来不及。要把采购等待造成的延期成本和人员机会成本纳入风险场景，而不是只比较电费与云 GPU 单价。

### 23.6.3 风险调整比较表

| 维度 | 云按量/承诺 | 自建/托管 | 需要的证据 |
|---|---|---|---|
| 现金流 | 低前置，按账单付费 | 高前置，折旧与备件 | 财务报价、付款条款 |
| 供给 | 区域配额和抢占风险 | 采购周期和故障备件 | 历史供给、中断记录 |
| 利用率 | 可缩容但有最小粒度 | 低谷也承担折旧 | 分时利用率 trace |
| 数据与网络 | 区域、出口、锁定 | 自控网络与合规 | 数据分类、流量测量 |
| 运维 | 托管部分控制面 | 自负硬件和软件栈 | 值班工时、MTTR |
| 能耗与碳 | 可取区域电力数据，粒度不一 | 可测电表，需核算制造碳 | 电表、PUE、供应商数据 |

推荐用三种情景（低、中、高负载）和至少一个供应中断情景跑模型，输出总成本分布而不是单点。若某方案只有在 95% GPU 利用率且没有故障时才便宜，就应视为风险较高的方案。

## 23.7 能耗测量：从 GPU 功率到机房电表

### 23.7.1 测量层级

能耗测量有五个层级，不能混写：

1. 芯片或板卡功率：如 DCGM 的板卡瓦特字段，适合定位内核和作业差异。
2. 节点功率：包含 CPU、内存、风扇、磁盘和电源损耗。
3. 机架或房间电表：包含交换机、存储和冷却。
4. 设施总表：用于 PUE（总设施能耗 / IT 设备能耗）。
5. 电网与生命周期：加入位置/时间碳强度和硬件制造隐含碳。

若只能拿到板卡功率，报告应明确这是下界；不能乘一个未经验证的固定倍数后宣称精确总功耗。可通过短时并行采样把 GPU 时间戳与作业 ID 对齐，再用节点电表抽样校准。采样频率过低会错过功率峰值，频率过高又会增加监控开销，需记录采样间隔和聚合方法。

### 23.7.2 功率、能量与性能的关系

功率 (P(t)) 的积分是能量：

\[
E=\int_{t_0}^{t_1}P(t)dt\approx\sum_i P_i\Delta t_i
\]

能量并不等于功率峰值乘总时长，尤其是训练中的通信、检查点和数据加载阶段。可报告“每百万 token 焦耳”“每有效样本瓦时”“每完成训练步焦耳”，并同时给出吞吐和质量。仅降低功率上限可能让作业耗时更长，总能量反而增加，因此要比较 (E) 和完成时间，而不是只看瞬时瓦特。

### 23.7.3 PUE 与边界

PUE = 设施总能耗 / IT 设备能耗。若只有 GPU 功率，先不要直接套用数据中心 PUE；应说明 IT 分母是否包含 CPU、网络和存储。云用户通常拿不到专属机房电表，只能使用供应商区域或实例级估算，并标注不确定性。自建机房可按月读取总表和 IT 表，按区域、租户和作业时间分配；冷却系统的季节变化要纳入时间序列。

### 23.7.4 测量校准与数据质量

功率数据进入账本前应经过校准。先选一段没有发布、迁移或故障的稳定窗口，同时采集 GPU 遥测、节点 IPMI 或 BMC、电源分配单元和房间电表。把各层信号按时间戳对齐，检查采样时钟漂移、缺失值和异常尖峰。若板卡功率之和与节点电表长期相差一倍以上，先检查是否重复计算电源转换损耗、是否漏采 CPU 和风扇、是否把多个节点误归到同一作业。校准结果应给出比例和区间，不能只保留一个“经验修正系数”。

作业归属还需要时间窗口规则。一个作业启动和结束可能跨越采样桶，按启动时间归属会把尾部功率错误分配给下一个作业；按 GPU 进程 ID 归属又可能在容器重启后丢失。推荐保留原始样本，使用区间相交比例分配，并把无法归属的部分放入共享池。任何插值、平滑和异常剔除都要记录方法和版本，确保环境审计或账单争议时可以重算。

当功率遥测中断时，预算控制器不应假设功率为零。可以进入保守估计状态，使用最近稳定区间的上界，并在数据恢复后重述窗口；如果估计误差超过阈值，则暂停对外碳声明，只发布“数据不完整”。这类做法比填入一个看似精确的平均数更诚实，也能防止监控故障掩盖成本和过热风险。

## 23.8 碳估算：运营碳、隐含碳和不确定性

### 23.8.1 软件碳强度公式

Green Software Foundation 的 Software Carbon Intensity（SCI）将软件碳强度写成：

\[
SCI=\frac{(E\times I)+M}{R}
\]

其中 (E) 是软件消耗的能源，(I) 是区域或时间相关碳强度，(M) 是硬件制造等隐含排放按生命周期摊销后的份额，(R) 是功能单位。公式的价值在于强迫团队披露边界；它不提供某个云区域的“真实碳数”。

运营碳可近似为 (C_{operational}=E_{IT}\times PUE\times I)。若使用电力市场的小时级碳强度，必须保存时间戳、来源、单位和是否为位置法或市场法。可再生能源凭证不等于物理电网在该小时无排放，市场法和位置法应并列展示，避免双重宣称。

### 23.8.2 隐含碳摊销

硬件制造碳可按设备生命周期 (L) 和有效使用小时摊销：

\[
M_{job}=M_{embodied}\times\frac{h_{job}}{L\times h_{available}}\times f_{allocation}
\]

制造商环境产品声明的边界、回收假设和地区电力不同，不能跨品牌直接比较。没有可靠数据时，给出区间（例如低、中、高情景）并说明来源，而不是伪造精确值。重复购买最新 GPU 也会产生升级和报废的额外隐含碳，资产处置与再利用策略要纳入年度报告。

### 23.8.3 碳估算的不确定性传播

若能耗、PUE、碳强度都有误差，可用区间传播：(E\in[E_l,E_u])、(I\in[I_l,I_u])、(PUE\in[p_l,p_u])，则运营碳区间为 ([E_l p_l I_l, E_u p_u I_u])（在变量非负且独立的保守估计下）。若变量相关，应用抽样或相关系数而不是简单相乘。报告中同时给出点估计和 5–95% 区间，解释主要不确定性来自功率采样、区域因子还是隐含碳数据。

### 23.8.4 碳感知调度

碳感知调度可以延后可中断训练、选择低碳区域或降低批处理功率，但约束包括数据驻留、延迟、配额、价格和故障风险。调度器应把“碳预算”视为软约束，保留关键生产任务的可靠性余量。不要为了低碳把敏感数据复制到未经批准的区域，也不要把碳分数用于评价个人绩效；目标是改善系统设计，非制造惩罚性排名。

### 23.8.5 碳预算、声明和反弹效应

内部碳预算可以按项目、区域或功能单位设定，但必须先确定是“总量预算”还是“强度预算”。总量预算限制一个季度排放总吨数，适合控制规模增长；强度预算限制每百万 token 或每个有效训练轮的排放，适合跟踪效率。两者可能冲突：模型效率提高后，团队可能因为单位更便宜而扩大调用量，导致总排放反而上升，这就是反弹效应。报告应同时展示总量、单位强度、工作量和质量，不能只挑改善最大的指标。

对外环境声明需要定义主张的对象、周期、边界、数据来源和审计人。可以说“在指定窗口和边界内估算为某个区间”，不要说“模型是零碳”或“迁移区域必然减少排放”这种超出数据的结论。市场法、位置法、供应商产品碳因子和内部电表要分栏列出，并解释为何选用某一方法。若供应商数据只有年度平均，不能把它伪装成小时级实时因子；若硬件制造数据来自行业平均，也要标记为估算并给出敏感性。

碳预算控制器可以仿照财务预算：在接近阈值时提醒，超过软阈值时限制低优先级实验，超过硬阈值时要求负责人批准额外额度。关键生产和安全演练保留豁免，但豁免要有期限、原因和回顾日期。任何“买碳抵消”或可再生能源凭证都不能替代降低能源消耗和提高设备利用率；它们是另一种核算工具，需由环境与法务团队审核，不应由调度器自动宣称等价减排。

## 23.9 弹性、预算治理与变更控制

### 23.9.1 弹性策略的四个旋钮

弹性控制包括并发上限、批大小、队列优先级和实例池。每个旋钮都有成本、延迟和质量影响：

- 并发上限防止成本失控，却可能增加等待；
- 批大小提高吞吐，却可能恶化交互延迟；
- 优先级保证生产，却可能让实验长期饥饿；
- 弹性池降低闲置，却带来启动延迟和缓存冷启动。

治理时要把旋钮变更当作可审计配置，记录前后值、触发指标、负责人、有效期和回滚值。任何自动扩缩都应设置最大副本数、每小时预算上限和熔断；指标异常时应停止扩张并进入人工检查，而不是无限追赶排队。

### 23.9.2 预算与 SLO 联动

成本预算不能单独切断服务。应定义“预算—SLO 矩阵”：预算健康且 SLO 充足时可运行实验；预算超阈值但生产 SLO 紧张时先保护生产并削减低优先级；预算和 SLO 都超标时进入事故流程，冻结非必要发布，评估降级质量。错误预算和碳预算可共享相同的窗口和审计机制，但不要把它们相加成一个没有意义的分数。

### 23.9.3 账单异常响应

发现异常支出时，先确认是否为真实业务流量、重复重试、标签丢失、价格变化或供应商账单延迟。自动化动作应优先暂停新实验和降低并发，保留生产副本与检查点；删除对象、释放预留或修改网络路由属于高风险变更，应要求明确审批和回滚。事后要补充根因、检测延迟、误报率和预算护栏缺口。

### 23.9.4 把治理流程接到发布流程

成本和碳治理若只在月末财务会议出现，通常已经错过最便宜的修复时机。建议在模型或服务发布模板中加入资源预算、预计单位成本、峰值功率、区域与碳边界、回滚阈值和 owner。预发布压测生成一份短期成本与能耗基线；发布后 24 小时比较实际与基线，超过阈值就自动创建调查任务，而不是直接判定开发团队失责。对于训练项目，在提交作业时声明最大卡数、最长墙钟时间、检查点位置和可使用的抢占池，调度器据此进行准入。

季度复盘应检查三类变化：工作负载变化（token、序列长度、请求峰值）、平台变化（驱动、调度、硬件、区域）和会计变化（价格、汇率、折旧、共享费）。只有同时记录这三类变化，才能判断单位成本上升是模型变重、平台退化还是账务口径变化。复盘结论应转成下一季度可验证的假设，例如“把缓存命中率从 45% 提到 60% 可减少 8% GPU 小时，且 P99 不恶化”，并指定实验窗口与回滚条件。

### 23.9.5 审计与可重复性

每次成本或碳报告应保存输入快照、查询版本、汇率、价格条件、标签字典、过滤规则和生成时间。报告发布后不覆盖旧版本；若供应商补发账单或修正碳因子，保留差异和重述原因。审计抽样时，任选一个功能单位都应能追到作业日志、资源样本、账单行和质量结果。无法追溯的金额和排放应标记为估算，并从高风险决策的精细比较中排除。

## 23.10 失败案例与反模式

### 案例一：平均利用率 80%，P99 仍超时

团队把 GPU 平均忙碌率从 55% 提到 80%，但 P99 从 1.2 秒升到 4 秒。排查发现流量存在 10 秒微突发，队列在平均窗口中被平滑；重试请求又进入同一队列。修复方案是按秒记录到达率和服务率，设置突发并发上限、短队列超时和请求合并，而不是继续加压。验证指标包括队列等待 P99、重试率、有效 token/s 和 GPU 功率；平均利用率不再作为唯一成功标准。

### 案例二：便宜的抢占实例导致成本翻倍

批训练迁移到抢占池，账单单价下降 60%，但三周后有效训练轮成本上升。原因是检查点每两小时一次，抢占平均每小时发生一次，重算和对象存储出口吞噬折扣。修复包括缩短检查点间隔、压缩增量检查点、对中断率高的区域设置上限，并按“有效轮”而非“实例小时”重新计算。若中断率继续高于阈值，自动回退到稳定池。

### 案例三：自建 GPU 账面便宜，现金和碳都更高

采购模型按 95% 利用率估算，实际只有 38%，因为项目之间的显存和拓扑不兼容；机房电力容量按峰值签约，冷却和备件长期闲置。云按量在中低负载下更便宜，且区域电力因子更低。教训是使用分时 trace、并行利用率、故障和人员工时做风险调整 TCO，不能只比较电费与云标价。

### 案例四：碳报表因边界不一致而误导

一个团队把 GPU 板卡功率乘统一 PUE，再乘市场法碳因子，另一个团队用设施总表和位置法因子；两者都声称“每百万 token 碳排”。审计发现第一个遗漏 CPU、存储和隐含碳，第二个把可再生能源凭证当作物理零碳。修复后报告同时列出边界、公式、数据源、位置/市场法和区间，并禁止横向比较没有相同边界的数字。

## 23.11 可运行实验：标准库排队、成本与能耗估算

下面脚本只使用 Python 标准库，模拟到达、服务、弹性扩容和功率积分。它不替代 GPU 压测或电表；目标是让读者能复现“利用率、队列和单位成本不能只看一个数字”的机制。保存为 `ch23_cost_capacity_lab.py` 后运行 `python ch23_cost_capacity_lab.py --seed 7`。

```python
#!/usr/bin/env python3
"""Chapter 23 toy lab: queueing, autoscaling, cost and carbon.
Standard library only; no production billing or power API calls.
"""
import argparse
import math
import random
from dataclasses import dataclass


@dataclass
class Job:
    arrival: float
    service: float
    done: float | None = None


def poisson_arrivals(rate: float, horizon: float, rng: random.Random):
    t = 0.0
    out = []
    while t < horizon:
        t += rng.expovariate(rate)
        if t <= horizon:
            out.append(t)
    return out


def simulate(rate=3.0, base_workers=2, max_workers=6,
             service_rate=2.0, horizon=120.0, seed=7):
    rng = random.Random(seed)
    arrivals = poisson_arrivals(rate, horizon, rng)
    queue = []
    workers = [0.0] * base_workers
    jobs = []
    scale_events = []
    i = 0
    now = 0.0
    while i < len(arrivals) or queue or any(x > now for x in workers):
        next_arrival = arrivals[i] if i < len(arrivals) else math.inf
        next_done = min((x for x in workers if x > now), default=math.inf)
        now = min(next_arrival, next_done)
        if now == math.inf:
            break
        while i < len(arrivals) and arrivals[i] <= now:
            j = Job(arrivals[i], rng.expovariate(service_rate))
            queue.append(j)
            jobs.append(j)
            i += 1
        # Simple autoscaler: add one worker when queue persists; remove at idle.
        if queue and len(workers) < max_workers:
            free = sum(1 for x in workers if x <= now)
            if free == 0:
                workers.append(now)
                scale_events.append((now, len(workers), "scale_up"))
        for wi, available in enumerate(workers):
            if available <= now and queue:
                j = queue.pop(0)
                workers[wi] = now + j.service
                j.done = workers[wi]
        while len(workers) > base_workers and all(x <= now for x in workers[-1:]):
            workers.pop()
            scale_events.append((now, len(workers), "scale_down"))
    completed = [j for j in jobs if j.done is not None]
    waits = [j.done - j.arrival for j in completed]
    gpu_seconds = sum(j.service for j in completed)  # one toy worker = one GPU
    billed_seconds = sum(max(j.done, horizon) - j.arrival
                         for j in completed) if completed else 0.0
    return jobs, waits, gpu_seconds, billed_seconds, scale_events


def percentile(xs, p):
    if not xs:
        return float("nan")
    xs = sorted(xs)
    k = (len(xs) - 1) * p
    f, c = math.floor(k), math.ceil(k)
    return xs[f] if f == c else xs[f] + (xs[c] - xs[f]) * (k - f)


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--seed", type=int, default=7)
    ap.add_argument("--rate", type=float, default=3.0)
    args = ap.parse_args()
    jobs, waits, gpu_s, billed_s, events = simulate(rate=args.rate, seed=args.seed)
    # Illustrative assumptions, not vendor prices or grid factors.
    usd_per_gpu_hour = 2.40
    pue = 1.35
    watts_per_gpu = 320.0
    kgco2_per_kwh = 0.40
    useful = len(jobs)
    cost = gpu_s / 3600 * usd_per_gpu_hour
    kwh = gpu_s * watts_per_gpu / 1000 / 3600 * pue
    carbon = kwh * kgco2_per_kwh
    print(f"jobs={useful} p50_s={percentile(waits,.50):.3f} "
          f"p95_s={percentile(waits,.95):.3f} p99_s={percentile(waits,.99):.3f}")
    print(f"gpu_hours={gpu_s/3600:.3f} illustrative_cost_usd={cost:.2f}")
    print(f"facility_kwh={kwh:.3f} illustrative_kgco2={carbon:.3f}")
    print(f"scale_events={len(events)} first_events={events[:5]}")


if __name__ == "__main__":
    main()
```

实验解读：改变 `--rate` 观察队列等待和扩容事件；把 `service_rate` 降低模拟长上下文；把 `watts_per_gpu` 或 `pue` 改动后比较单位能耗。脚本中的成本、PUE 和碳因子是教学假设，不能复制到预算或环境披露。脚本还把每个 worker 当成一张同质 GPU，忽略显存、拓扑、冷启动和优先级；生产验证应导入真实到达 trace、DCGM/电表样本和账单快照。

### 23.11.1 实验失败模式

常见失败包括：速率设为零导致分位数是 NaN；把 `billed_seconds` 当作真实云计费而忽略最小计费粒度；用板卡瓦特乘 PUE 却重复计入节点功率；把模拟“完成的 job 数”当作业务成功而不做质量校验。遇到失败时先记录输入、随机种子、版本和停止条件，再修复模型；不要为了得到漂亮的曲线删掉异常样本。

## 23.13 练习

### 练习 A：从账单到每百万 token 成本

给定一个月：GPU 账单 18,000 美元、存储 2,000 美元、出口 1,200 美元、平台共享费 3,000 美元；成功输出 4.5e9 token，失败重算产生 20% GPU 时间。请计算直接单位成本和把重算摊回成功 token 后的有效单位成本。再说明若质量门槛提高导致成功 token 减少 10%，应如何更新分母。

### 练习 B：Erlang-C 与扩容阈值

请求到达率在低峰为 20/s、高峰为 50/s，每个 worker 服务率为 12/s。用不同 worker 数计算 \(\rho\) 和等待概率，给出一个满足 P95 等待小于目标的候选，并说明为什么要用真实 trace 校准。扩展脚本加入冷启动 30 秒，观察“理论可行但实际不可行”的场景。

### 练习 C：碳区间和调度

某批训练 IT 能耗测得 1,000–1,300 kWh，PUE 为 1.2–1.5，区域碳强度为 0.25–0.55 kgCO₂e/kWh。计算保守区间，并讨论把作业迁移到低碳区域后跨区网络和数据驻留带来的新边界。不得把市场法凭证直接当作物理零碳。

### 练习 D：云与自建 TCO 情景

构造低、中、高三种利用率曲线，加入采购提前期、故障备件、人员工时、承诺折扣和出口。输出现金流、会计折旧、边际成本和碳强度四张图，解释一个方案为什么在现金流上便宜、在风险调整后却不优。

### 练习 E：设计预算控制器

写出一个状态机：`normal → warn → throttle → freeze → recover`。为每条转移定义成本、队列、SLO 和回滚条件；考虑账单延迟、标签缺失和误报。禁止自动删除生产数据，要求所有不可逆动作进入人工审批。

## 23.15 安全边界与治理清单

成本和碳优化不能绕过安全边界。执行前检查：

- 数据驻留、跨区复制和出口是否符合合同、隐私和监管要求；
- 标签和账单是否泄露个人、客户或敏感项目名称；
- 预算自动化是否拥有释放实例、修改路由、删除数据或更改配额的权限；
- 功率和碳遥测是否含主机名、作业参数或可推断商业机密；
- 多租户调度是否通过显存清理、缓存隔离和网络策略防止侧信道；
- 外部基准、碳因子或价格页面是否经过版本固定和来源审查；
- 任何不可逆动作是否有人工确认、回滚和审计日志。

不要把碳分数、GPU 利用率或账单金额直接映射到个人绩效；资源差异可能由数据驻留、无障碍需求或安全隔离造成。不要为了追求低价安装未批准的驱动、关闭安全日志或绕过配额。实验只使用合成数据和可撤销资源，生产改动应走变更窗口和审批。

## 23.16 小结：把数字变成可执行决策

本章的核心不是某个固定的 GPU 单价或碳因子，而是一套可复核的工作流：先定义质量绑定的功能单位和边界，再测量分配/忙碌/有效利用率、队列、能量和账单；用排队和情景模型规划容量；用标签、共享池和版本化权重做成本分摊；用 PUE、时间/位置碳强度和隐含碳区间报告环境影响；最后把预算、SLO、弹性和安全护栏写成可回滚状态机。每个数字都带来源、时间、区域、版本和不确定性。

当模型、硬件、云价格和电网不断变化时，真正可持续的是证据链和反馈回路，而不是一张静态优化表。把实验脚本、账单快照、功率采样和决策记录一起保存，下一次扩容、迁移或碳盘查才能从事实出发，而不是从印象出发。
