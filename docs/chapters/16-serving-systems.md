# 第16章　模型服务系统：worker、路由、自动扩缩容与多租户

> 模型服务的难点是把一个会消耗大量计算和内存的程序，放进一个必须持续响应、可以升级、能够承受突发流量的系统里。请求的输入长度、输出长度、工具调用和取消时间都不确定；模型加载可能要数十秒甚至数分钟；同一批实例既要服务交互式流量，也要服务批处理任务。worker 池、路由、自动扩缩容、流式协议、预热、降级和租户隔离不是彼此独立的开关，而是一组相互约束的控制回路。本章用“每个请求都有预算和所有权”的视角，把这些机制串成一条可验证的服务路径。

本章先建立状态机和容量账本，再给出一个只用 Python 标准库的 CPU toy。toy 不模拟真实神经网络、GPU kernel、网络抖动或容器调度器，它只刻画排队、worker、token 逐步生成、流式发送、取消和简化扩缩容。它的用途是帮助读者验证不变量和观察尾延迟；生产系统仍需在目标模型、硬件、网络、租户流量和组织安全规则上重新测量。

## 16.1 从请求到响应：服务是一个有状态的生命周期

### 16.1.1 先画状态机，再选框架

一个可靠的模型请求至少经过接受、认证、准入、排队、分配 worker、加载或确认模型、预热、推理、流式发送、完成或取消、账单记录和清理这些阶段。每个阶段都应有明确的进入条件、离开条件、超时和资源所有者。例如，准入阶段只检查令牌、租户配额和估算预算，不应在还未决定是否接收时就分配大型 KV 缓冲区；推理阶段拥有模型上下文和输出缓冲区，断线后应由该阶段收到取消信号并释放资源；清理阶段必须幂等，因为网络超时和 worker 崩溃可能让同一个请求触发两次清理。

状态机的价值在于把“请求还在不在”与“资源是否已释放”分开。一个 HTTP 连接关闭，并不意味着 worker 已经停止计算；一个客户端收到错误，也不意味着模型上下文可以立即复用。建议为请求维护单调递增的阶段序号和取消代数。清理动作只有在观察到与当前代数相同的取消事件时才执行，迟到的事件不能误杀后来复用的请求 ID。

### 16.1.2 三本账：计算、内存、时间

服务端应同时维护三本账。计算账包括 CPU 时间、GPU 时间、每秒 token、批大小和工具执行时间；内存账包括模型权重、激活、KV、请求队列和序列化缓冲区；时间账包括排队、加载、预热、首 token、每 token 间隔、尾 token 和清理。只看 CPU 利用率会错过显存耗尽，只看显存会错过队列拥塞，只看平均延迟会错过少数租户的 p99。

每个请求在进入时获得一个估算预算，但预算不能被当作精确预言。输入 token 数通常可知，输出 token 数只能设置上限；工具调用、重试和降级会改变成本。准入应以保守上界加安全余量计算，并在运行中更新剩余预算。若预算即将耗尽，应先触发可解释的截断或降级，而不是突然抛出内部异常。

### 16.1.3 控制平面和数据平面

数据平面执行推理、发送 token 和管理本地资源，控制平面负责版本、路由、配额、扩缩容和开关。两者必须有故障隔离：控制平面短暂不可用时，数据平面应使用最近一次经过校验的配置继续服务一段时间；数据平面过载时，控制平面仍要能读取健康和容量状态以决定缩容、摘流或回滚。把所有决策都放进一个中心控制器会让中心故障变成全局故障。

控制配置需要版本号、发布时间、有效期和签名或完整性摘要。worker 接收配置后先校验模型版本、租户规则和采样限制，再原子切换；未知字段、缺失字段或版本回退都要拒绝。回滚不是简单地把一个字符串改回旧值，还要确认旧工件、tokenizer、运行时和安全策略仍在本地可用。

## 16.2 Worker 池：把并发和资源边界显式化

### 16.2.1 进程、线程、协程和设备 worker

CPU 推理可以使用多进程隔离地址空间，也可以在线程池中共享权重。进程池对内存泄漏和崩溃更有边界，但每个进程可能重复占用权重；线程池减少复制，却受解释器锁、底层算子线程数和共享状态竞争影响。协程适合网络等待和流式发送，不能自动让 CPU 计算并行。常见结构是“网络协程层 + 有界推理线程或进程池 + 单独的工具调用池”。

GPU 服务通常把一个或多个设备上下文分配给专用 worker，避免不同请求随意争用默认流。worker 内部可能有预填充队列、解码队列和复制队列，但每条队列都要有 token 或显存上限。若把设备 worker 包装成无界线程池，排队请求会先占用主机内存，最终以更高延迟和 OOM 的形式失败。

### 16.2.2 有界队列和背压

有界队列是服务的第一道保险。队列容量可以用请求数表示，也可以用估算 token、预计执行毫秒或显存页表示；对于输出长度差异很大的模型，token 预算通常比请求数更有意义。入队失败应返回明确的忙碌或稍后重试错误，并提供一个有界的重试建议，而不是让客户端无限重试。

队列应区分等待中的请求和已经占用资源的请求。一个请求入队时不能持有大型上下文对象或文件句柄；真正分配前还要再次确认预算。出队时使用租约，worker 在租约过期前定期续租，控制面可以据此判断 worker 是否卡死。租约不能只靠心跳包，因为进程可能仍发送心跳却已无法执行模型；应结合完成 token、设备事件或小型自检任务。

### 16.2.3 池的分层与隔离

把所有工作放进同一个池会让长上下文、批处理或工具调用阻塞交互请求。实用做法是按资源和 SLA 拆池：短响应交互池、长上下文池、离线批量池、工具调用池以及维护或预热池。每个池有独立的并发、队列、超时和优先级；池之间只通过受控令牌借用资源，借用必须有上限和回收时间。

租户隔离可以在池级、worker 级或设备分区级实现。池级隔离成本较低，适合防止单个租户挤占队列；worker 级隔离能减少内存和缓存串扰，但会降低总体利用率；硬件分区提供更强边界，代价是配置和调度复杂。隔离的强度应与数据敏感度和合同承诺匹配，不能用“所有租户共享”作为默认答案。

### 16.2.4 取消、超时和优雅关闭

取消分为排队取消、执行取消和发送取消。排队取消可直接移除租约；执行取消需要让模型循环在安全边界检查取消标记；发送取消则要停止写 socket 并释放发送缓冲区。取消检查太稀疏会浪费计算，太频繁会增加同步开销。对逐 token 生成，通常每个 token 或每个小批次检查一次即可；对长时间的单次算子，需要使用可中断的分块或设备事件。

优雅关闭分为停止接收、等待短请求、迁移或取消长请求、释放模型和确认退出。收到关闭信号后，路由器先摘除实例并等待连接排空；worker 继续处理已接收且未超时的请求，但为长请求设置最大排空窗口。超时后应发送可重试错误并清理上下文。直接杀进程会留下未结算计量、半截流和无法判断的外部工具状态。

## 16.3 路由：把请求送到有能力且值得信任的 worker

### 16.3.1 路由目标不是“最近的机器”

路由至少要满足四个条件：能力匹配、容量可用、数据边界合规和成本可接受。能力匹配包括模型与 tokenizer 版本、上下文上限、工具能力、量化格式和输出模式。容量可用包括当前队列、估算 KV、设备健康和排空状态。数据边界包括区域、租户隔离、数据驻留和审计要求。最后才是网络距离或价格。

请求中的模型别名不能直接信任为文件路径或容器标签。路由器应把别名解析成经过审核的能力描述，并缓存带版本的解析结果。若解析缓存过期，宁可暂时返回不可用，也不要把请求随机送到旧模型。能力描述还应列出禁用功能，例如某个低成本模型不允许工具调用或不支持结构化输出。

### 16.3.2 静态、负载感知和一致性哈希

轮询路由简单、易测，但在请求成本差异大时会把长请求集中到某个实例。最少队列或最少估算负载更适合交互流量，但依赖健康、队列和容量信号，信号陈旧时可能形成羊群效应。加权路由可以按设备规格和租户优先级分配，但权重应有边界，不能让高优先级永久挤压公共池。

一致性哈希适合需要缓存局部性的场景，例如共享前缀或本地权重分片。哈希键应是经过规范化且不包含秘密的标识，例如模型版本和匿名会话分区；不能把原始 prompt、邮箱或访问令牌作为键。实例扩缩容会改变哈希环，路由器要有迁移和失效策略，避免所有缓存同时失效导致热加载风暴。

### 16.3.3 跨区域、影子和金丝雀

跨区域路由首先遵守数据驻留和故障域规则，然后才考虑 RTT。跨区域重试可能重复计费、增加隐私暴露和造成输出顺序不一致。若请求允许跨区，授权和成本边界必须在请求级明确，并将跨区事件记录到审计。

影子流量只复制必要的脱敏输入和元数据，影子响应不可见也不应触发工具副作用。金丝雀流量要有固定比例、租户白名单、可撤销开关和比较窗口，比较指标包括质量代理、错误、首 token、p99、内存和成本。不能只看到吞吐提升就扩大比例；一旦发现跨租户、工具或安全策略异常，应立即停止并保留证据。

### 16.3.4 重试与对冲请求

重试只适用于可判断为暂时性且尚未产生不可逆副作用的错误。推理请求可能已经生成部分 token 或调用工具，盲目重试会重复输出、重复扣费或重复执行外部动作。请求应携带幂等键和尝试号；worker 在清理时记录已生成 token 数和工具状态，路由器据此决定是否允许重试。

对冲请求同时发到多个 worker 可以降低偶发尾延迟，却会把资源消耗翻倍，并放大设备抖动。适合对冲的前提是请求很短、操作幂等、成本有预算且只保留最先成功的一个结果。需要在固定等待阈值后才发第二份，并在首个结果到达时向其他 worker 发送取消。流式响应一般不适合对冲，因为首 token 已发送后很难合并两条不同的输出。

## 16.4 自动扩缩容：控制容量，而不是追逐噪声

### 16.4.1 用队列模型理解容量

对平均到达率 λ、平均服务率 μ 和实例数 c，粗略利用率可写成 ρ = λ/(cμ)。当 ρ 接近 1 时，平均延迟和尾延迟会非线性上升；目标通常不是把设备跑到满载，而是为长度长尾、故障和突发留出余量。对于 token 生成服务，λ 应按输入 token、输出 token 或估算计算量拆分，单看请求数会失真。

扩缩容信号可分为需求、拥塞和能力三类。需求包括到达率、token 速率和活跃会话；拥塞包括队列长度、排队时间、拒绝率和 p99；能力包括可用 worker、显存页、设备错误和模型加载状态。把多个信号合成为扩容建议时，要明确单位和时间窗口，避免一个异常指标让系统反复抖动。

### 16.4.2 反应式和预测式扩容

反应式策略根据最近窗口的队列或利用率增加实例，通常需要冷启动时间的数倍提前量。预测式策略使用历史周期、发布日历或已知批任务预热，但预测错误会浪费成本。稳健组合是：对突发采用快速但有限的反应式扩容，对可预测高峰提前启动，对无法满足容量的时段先启用排队和降级。

扩容决策应包含最小实例、最大实例、每次步长、冷却时间、启动预算和失败回退。冷却时间过短会振荡，过长会让排队持续；可以对扩容使用短窗口、对缩容使用长窗口，并在缩容前检查实例是否有流式长连接。一个实例进入排空后不应再被计入可用容量，除非它能接收新请求。

### 16.4.3 冷启动、预热和缩到零

模型加载是冷启动的主要成本。扩容器启动后经过镜像拉取、权重校验、内存映射、运行时初始化、预热和健康检查，才能加入路由池。把“进程端口打开”当作就绪会把冷实例暴露给真实请求，造成首请求超时。

缩到零可以节省成本，却增加首请求延迟和容量风险。适合离线或低频模型，不适合严格交互 SLO。若必须缩到零，应保留一个经过验证的快速恢复路径、明确的首请求预算和客户端可见的排队状态。缩容不能在设备故障或控制面失联时盲目发生，应先确认至少一个健康副本和可用工件。

### 16.4.4 稳定性和预算

扩缩容本身也消耗资源。大批实例同时加载权重，会争抢镜像仓库、网络和磁盘，甚至把健康实例挤垮。可以限制并行加载数、预留权重缓存、分批加入路由、在启动时随机抖动并设置加载预算。若加载失败，实例进入隔离状态并报告原因，不要立即无限重试。

把错误预算和容量预算联系起来：若队列 p99 连续超标，优先扩容或降级；若错误预算尚未使用完但内存风险高，应先限制长请求；若错误预算耗尽，可以临时降低非核心功能而保住核心 SLO。扩容不能替代修复泄漏、错误路由或不受控重试。

## 16.5 流式响应：从 token 生成到可取消的传输

### 16.5.1 流式协议的最小语义

流式接口应定义事件类型、顺序、终止标记、错误格式和重连语义。常见事件包括开始、文本增量、工具状态、用量、警告和结束；每个事件都有请求 ID、单调序号、模型版本和可选的校验摘要。客户端断开后，服务端不能假设客户端会回来，因此必须在有限时间内取消或转入明确的后台任务模式。

文本增量不应依赖客户端自行拼接 JSON 片段。若提供结构化输出，每个事件应是可解析的完整片段或带明确的增量协议；否则中途断线会留下无法恢复的半个对象。结束事件要说明完成、长度上限、内容过滤、取消、超时或内部错误，不能把所有情况都映射成“正常结束”。

### 16.5.2 背压和慢客户端

生成速度可能远快于客户端读取速度。如果发送队列无界，慢客户端会积累大量字符串和 token，占用内存；如果发送队列有界但没有策略，worker 会阻塞，拖累同池其他请求。建议为每个流设置有限缓冲区和最大滞留时间。达到阈值时，可以合并相邻文本增量、降低发送频率、暂停生成或断开并返回可重试错误。

背压策略必须与用户体验和计费一致。合并增量不应改变 token 计费，也不应破坏工具事件边界；暂停生成要记录暂停时长，防止 SLO 误判为模型变慢；主动断开要释放 KV 和计量租约。心跳只能说明连接还存在，不能替代对客户端消费速度的检查。

### 16.5.3 断线、重连和幂等

如果协议支持重连，客户端应携带最后确认的事件序号，服务端只在保留窗口内重放事件。重放缓存必须按租户和请求隔离，并设置容量与保留期；超出窗口则返回不可恢复，让客户端重新发起一个新的幂等请求。不要把完整输出永久保存在公共缓存里。

重连不等于重新执行模型。若请求仍在执行，服务端可以把流重新绑定到原上下文；若已完成，则只重放有限摘要或让客户端读取授权的结果对象。对包含工具调用的请求，重连流程必须识别工具是否已提交，避免再次执行。高风险工具操作应要求显式确认或交给独立事务系统。

## 16.6 模型加载、预热与版本切换

### 16.6.1 工件不可变和完整性检查

模型目录、权重分片、tokenizer、配置、量化参数和运行时镜像应作为版本化工件。加载前校验来源、摘要、大小、签名或可信清单，拒绝缺片、截断和未知文件。不要从请求字段拼接本地路径，也不要把下载目录直接挂入多租户 worker。工件通过校验后再复制或映射到只读位置，避免加载期间被替换。

加载日志记录版本、摘要、设备、内存预算和失败阶段，但不记录权重内容或用户 prompt。若加载使用远程对象存储，需限制凭据权限、设置超时和断点策略，并将下载与解压放到隔离的启动容器。网络异常时回退到已缓存且经过验证的版本，不要回退到“最新”或未审核的文件。

### 16.6.2 分阶段加载

可以把启动拆成工件发现、校验、权重映射、运行时构建、算子编译、静态预热、动态预热、健康探针和加入路由。每个阶段有超时和可观测事件。静态预热覆盖常见输入长度和批大小；动态预热覆盖流式、取消、长上下文和不同采样策略。预热请求使用合成数据，不应把真实租户内容发送到新实例。

健康探针分为存活、就绪和能力探针。存活只确认进程尚可响应；就绪确认模型、内存和关键依赖可用；能力探针确认声明的上下文长度、结构化输出、工具限制和版本一致。路由只看就绪和能力，不看单一的端口状态。预热失败时实例保持隔离，保留诊断并释放部分资源。

### 16.6.3 蓝绿、滚动与回滚

蓝绿切换同时保留旧池和新池，先让新池承接极小金丝雀，再逐步放量；成本较高但回滚快。滚动切换逐个替换实例，节省资源但容易在容量临界时导致排队。无论哪种方式，都要确保旧池在错误预算和长连接完成前不被过早删除。

回滚触发条件应包括错误率、p99、模型输出校验失败、内存增长、工具异常和跨租户告警。回滚动作是把路由指针切回已验证版本、停止新版本扩容、摘除异常实例并保留诊断；不要删除新工件或覆盖现场，否则无法复盘。若数据格式或缓存格式不兼容，应先清理或隔离缓存再恢复流量。

## 16.7 优雅降级：压力下仍保住核心路径

### 16.7.1 分级过载模式

可以定义正常、警戒、拥塞、紧急四个模式。正常模式提供完整上下文、工具和高质量模型；警戒模式限制新请求并缩短最大输出；拥塞模式暂停非核心工具、降低并发、启用较小模型或排队；紧急模式只接受健康检查、管理员或合同约定的核心租户。每个模式都有进入和退出阈值、最大持续时间和用户可见错误。

降级顺序应优先移除高成本且可选的功能，例如扩展检索、长历史、非必要工具和多候选采样；不能先删除系统安全指令或租户隔离。若使用小模型回退，应明确标记模型版本和能力差异，不能让用户误以为仍是原模型。结构化输出失败时可以返回可解析的错误对象，不要拼接一个看似成功的半截 JSON。

### 16.7.2 限流、排队和拒绝

限流有租户级、模型级、区域级和全局级。令牌桶适合控制平均速率，漏桶适合平滑处理，带并发上限的信号量适合限制活跃请求。只限制请求数无法防止长上下文占满内存，需结合 token、预计毫秒和 KV 估算。拒绝响应提供可重试与不可重试的分类、建议等待时间和关联 ID；不要返回内部队列长度或其他租户信息。

排队不是无限容忍。一个请求等待超过其 SLO 后，即使最终成功也会消耗更多资源和重试流量。系统可以设置最大排队时间，到期后快速拒绝并保留计量。对批处理，可以把请求转入离线队列并给出完成窗口；对交互流量，应避免把长批处理藏在同一队列里。

### 16.7.3 优雅停止和故障域

实例故障时，路由器先停止发送新请求，再等待短时间让活跃请求完成；长流根据剩余预算迁移、断开或降级。迁移要求请求状态可序列化且模型版本兼容，不能把任意内存指针复制到另一台机器。若不可迁移，宁可返回明确可重试错误，也不要静默重放。

故障域包括进程、主机、设备、机架、区域和控制面。副本分散在不同故障域才能降低相关故障；但跨区副本可能增加成本和隐私边界。容量规划要假设至少一个故障域不可用，并验证剩余容量能否服务核心租户。把所有副本放在同一共享磁盘或同一网络交换机上，不算真正的高可用。

## 16.8 SLO、观测和错误预算

### 16.8.1 SLI 不能只报平均延迟

交互模型至少需要首 token 延迟、流式 token 间隔、完整响应延迟、错误率、取消率和拒绝率。批处理需要作业完成时间、吞吐、重试和成本。基础设施还要有队列等待、worker 利用率、模型加载时间、显存或页水位、网络发送缓冲和清理延迟。每个指标都注明分母、窗口、租户和模型版本。

p50 反映典型用户，p95 和 p99 揭示尾部，但尾部样本很少，必须同时看样本量和长尾原因。将排队、prefill、decode、发送和客户端确认拆成子区间，才能决定是扩容、优化模型还是修复慢客户端。不要把超时请求从分母中排除，也不要把拒绝当作成功的零延迟。

### 16.8.2 SLO 与错误预算

例如可以为核心交互路径设定月度成功率和首 token p95，但具体数值要由产品和合同决定。错误预算是允许的失败量，包含内部错误、超时、明确拒绝和超过延迟目标的请求；是否把客户端取消计入要提前声明。预算消耗过快时，暂停高风险发布、收紧长请求、增加容量或启用降级；预算恢复后再逐步放宽。

SLO 不能被单一租户的大流量稀释。应分别报告全局、租户、模型和区域视图，采用最小样本门槛和隐私保护的聚合。租户合同若不同，容量预留和预算也应不同，但规则要可解释、可审计。不要用隐含的行业或姓名特征做优先级。

### 16.8.3 追踪、日志和指标的边界

每个请求生成不可预测的关联 ID，跨路由、worker、模型版本、流事件和计量系统传递。日志记录阶段、持续时间、错误类别、资源摘要和配置摘要，不记录完整 prompt、输出、访问令牌或工具参数。需要采样文本时，先脱敏和加密，限制访问、保留期和审批，并让用户或租户规则覆盖默认设置。

指标标签数量必须有限。将用户 ID、文档标题或原始模型别名直接作为标签会导致高基数和隐私泄露。可用租户哈希、合同等级和长度桶等受控标签；原始关联 ID放在追踪系统而非公开指标。告警应包含可操作的下一步，例如队列超阈值、页泄漏、加载失败或租户拒绝，而不是泛化的“服务异常”。

## 16.9 多租户：公平、隔离和可计量

### 16.9.1 租户边界和信任域

租户标识必须在认证后由服务端确定，不能信任请求体中的字符串。每个请求携带租户策略快照，包括允许的模型、区域、最大上下文、工具和数据保留。快照在路由、worker、日志和计量中保持一致，策略变更只影响新请求或明确的重验证点。

共享权重通常可以接受，因为权重本身不是某租户数据；KV、前缀缓存、检索结果、工具凭据、流事件和调试样本必须按信任域隔离。线程局部变量、对象池和序列化缓冲区也可能残留数据，worker 在租户切换或请求完成时清理并在测试中验证。只依赖代码审查而不做跨租户泄露测试是不够的。

### 16.9.2 配额、预算和公平队列

配额可以按请求数、并发、输入 token、输出 token、设备秒和费用表示。硬配额保护全局资源，软配额允许在低负载时借用；借用要有上限、过期时间和回收规则。公平队列可使用加权轮询、最小剩余服务或按租户虚拟时间的调度。高权重不应绕过安全检查、数据驻留或最大上下文。

建议同时观察租户的获得服务量和被拒绝量，记录配额拒绝、全局背压和模型不支持三类原因。若一个租户持续在低负载时获得更高吞吐，可能是权重或缓存局部性的结果，应在合同和监控中解释。计量要在请求结束或可靠的中间检查点落账，取消请求也应按已消耗资源计费或明确不计费。

### 16.9.3 noisy neighbor 和缓存污染

长上下文租户可能占满页池，突发工具调用可能占满线程池，慢客户端可能占满发送缓冲。隔离池、并发上限、最大上下文和发送背压可以减轻 noisy neighbor；必要时对高风险租户使用专用实例或硬件分区。共享前缀缓存要限制容量和信任域，避免一个租户的热门模板驱逐其他租户或让其测出命中时序。

测试时构造“安静租户 + 恶意长请求 + 慢客户端 + 大量取消”的组合，而不是只做平均混合流量。验证安静租户的 p95、拒绝率、页水位和计量是否仍在承诺内。任何租户级保护都要有管理员可见的解释和审计记录，不能只给出不可诊断的 429。

### 16.9.4 多租户运维权限

运维人员和自动化也属于租户边界的一部分。查看 prompt、输出、调试流和缓存页应采用最小权限、临时授权和审计。紧急调试可以使用脱敏样本或合成重放，不应默认打开全量内容。删除租户数据、导出账单和改变配额是高影响操作，需要明确授权、双人或分步确认以及可回滚记录。

## 16.10 标准库 CPU serving toy：可运行的 worker、流式与扩缩容模型

下面的 toy 使用 `queue`、`threading`、`time`、`dataclasses` 和 `collections`，模拟一个有界请求队列、可取消的逐 token worker、按租户配额、流式事件和简化自动扩缩容。它不加载真实模型，`infer_one` 用 CPU 计算和短暂睡眠模拟一个 token 的成本。代码中的日志只输出长度和 ID，不输出 prompt 内容。

```python
from __future__ import annotations
from dataclasses import dataclass, field
from queue import Queue, Full, Empty
from threading import Thread, Event, Lock
from collections import defaultdict, deque
import hashlib, random, time

@dataclass
class Request:
    rid: str
    tenant: str
    prompt_tokens: int
    max_new: int
    cancel: Event = field(default_factory=Event)
    created: float = field(default_factory=time.monotonic)

class Worker:
    def __init__(self, wid: int, inbox: Queue, events: Queue, stop: Event, quotas):
        self.wid, self.inbox, self.events, self.stop = wid, inbox, events, stop
        self.quotas = quotas
        self.thread = Thread(target=self.run, name=f"worker-{wid}", daemon=True)
        self.active = None

    def start(self):
        self.thread.start()

    def infer_one(self, req: Request, step: int) -> str:
        # 伪造少量 CPU 工作；生产实现应替换为真实模型调用
        h = hashlib.sha256(f"{req.rid}:{step}".encode()).digest()
        _ = sum(h[i] * (i + 1) for i in range(len(h)))
        time.sleep(0.003 + 0.001 * min(req.prompt_tokens, 64) / 64)
        return f"t{h[0] % 97:02d}"

    def run(self):
        while not self.stop.is_set():
            try:
                req = self.inbox.get(timeout=0.05)
            except Empty:
                continue
            self.active = req
            started = time.monotonic()
            try:
                self.events.put(("start", req.rid, self.wid, req.tenant))
                # prompt 阶段只模拟固定成本，真实系统需检查预算和模型版本
                time.sleep(0.001 * min(req.prompt_tokens, 128))
                for step in range(req.max_new):
                    if req.cancel.is_set():
                        self.events.put(("cancelled", req.rid, self.wid, step))
                        break
                    token = self.infer_one(req, step)
                    self.events.put(("token", req.rid, self.wid, step, token))
                else:
                    self.events.put(("done", req.rid, self.wid, req.max_new,
                                     time.monotonic() - started))
            finally:
                self.active = None
                self.inbox.task_done()

class ToyServer:
    def __init__(self, max_queue=32, min_workers=1, max_workers=4):
        self.inbox = Queue(maxsize=max_queue)
        self.events = Queue()
        self.stop = Event()
        self.lock = Lock()
        self.workers = []
        self.min_workers, self.max_workers = min_workers, max_workers
        self.quotas = defaultdict(lambda: {"active": 0, "limit": 2})
        self.records = {}
        for _ in range(min_workers):
            self._add_worker()

    def _add_worker(self):
        w = Worker(len(self.workers), self.inbox, self.events, self.stop, self.quotas)
        self.workers.append(w)
        w.start()

    def submit(self, req: Request) -> bool:
        with self.lock:
            q = self.quotas[req.tenant]
            if q["active"] >= q["limit"]:
                self.events.put(("reject", req.rid, "tenant_quota"))
                return False
            q["active"] += 1
            self.records[req.rid] = req
        try:
            self.inbox.put_nowait(req)
            self.events.put(("accepted", req.rid, req.tenant))
            return True
        except Full:
            with self.lock:
                self.quotas[req.tenant]["active"] -= 1
                self.records.pop(req.rid, None)
            self.events.put(("reject", req.rid, "queue_full"))
            return False

    def cancel(self, rid: str):
        req = self.records.get(rid)
        if req:
            req.cancel.set()

    def finish_record(self, rid: str):
        req = self.records.pop(rid, None)
        if req:
            with self.lock:
                self.quotas[req.tenant]["active"] -= 1

    def autoscale_once(self):
        queued = self.inbox.qsize()
        alive = sum(w.thread.is_alive() for w in self.workers)
        if queued > alive and len(self.workers) < self.max_workers:
            self._add_worker()
            self.events.put(("scale", "up", len(self.workers), queued))
        elif queued == 0 and alive > self.min_workers:
            # toy 不在线杀线程，只报告可排空的候选
            self.events.put(("scale", "down_candidate", alive, queued))

    def drain_events(self):
        out = []
        while True:
            try: out.append(self.events.get_nowait())
            except Empty: return out

    def shutdown(self):
        self.stop.set()
        for w in self.workers: w.thread.join(timeout=1)

def demo():
    random.seed(7)
    s = ToyServer(max_queue=5, min_workers=1, max_workers=3)
    for i in range(12):
        tenant = "gold" if i % 3 == 0 else "free"
        r = Request(f"r{i}", tenant, 20 + i, 4 + i % 4)
        s.submit(r)
        s.autoscale_once()
        if i == 5: s.cancel("r2")
        time.sleep(0.004)
    deadline = time.monotonic() + 3
    while time.monotonic() < deadline and s.records:
        for e in s.drain_events():
            if e[0] in {"done", "cancelled", "reject"}:
                if e[0] != "reject": s.finish_record(e[1])
            print(e)
        s.autoscale_once()
        time.sleep(0.01)
    s.shutdown()

if __name__ == "__main__": demo()
```

运行时使用 Python 3.10 或更新版本。输出会显示接受、拒绝、worker 开始、token、取消和完成事件。可以观察到三个不变量：队列满时新请求被拒绝而不会无限堆积；租户的 `active` 不超过配额；取消后 worker 在下一次 token 边界停止。toy 的自动缩容只报告候选，因为在线停止线程需要排空和租约协议，故意没有用不安全的强杀。

为了做可比实验，可修改四个变量：队列容量、worker 上限、每租户并发上限和 `infer_one` 的模拟成本。每次记录随机种子、请求序列、接受与拒绝原因、首 token 时间、完成时间、取消延迟和队列长度。不要把这个 toy 的 token/秒当作任何真实模型的性能；它只用于验证队列和状态机的关系。

可以进一步添加：带序号的流事件和客户端读取延迟、基于 token 预算的准入、租户加权轮询、模拟模型加载状态、断线取消、错误预算以及分阶段预热。每个新增功能先写不变量，再写测试；例如“断线后最长 100 毫秒内释放记录”或“路由到能力不匹配的 worker 永远不会发生”。

## 16.11 失败案例：系统如何一步步失控

### 案例一：重试风暴掩盖了队列满

一次发布使首 token p99 超时，客户端把所有超时都当作可重试，并以固定 100 毫秒重试。服务端新请求更多，队列更长，超时更多，形成正反馈。根因不是单个 worker 变慢，而是错误分类和客户端重试策略没有预算。

修复包括：区分排队超时、模型错误和不可重试的策略拒绝；响应中提供有界的 `retry_after`；客户端使用带抖动的指数退避和幂等键；服务端对每租户重试流量设上限；在达到错误预算时优先停止非核心流量。复盘指标要包含原始请求与重试请求的比例，否则会误以为到达率没有变化。

### 案例二：扩容同时加载导致全局雪崩

监控发现队列升高，自动扩容一次启动二十个实例。所有实例同时下载和解压权重，争抢共享存储、网络和磁盘，健康实例的延迟反而飙升。部分新实例在半加载状态被路由，返回大量超时。

修复是限制并行加载、预热完成后再加入路由、使用分批和随机抖动、为工件缓存设置容量、把“进程活着”和“模型可服务”分开探针，并为加载失败设置隔离状态。扩容控制器应把加载中的实例排除在可用容量外，只有通过能力探针才算新增容量。

### 案例三：流式断线造成隐形 worker 泄漏

移动网络频繁断线，网关关闭 socket，却没有向推理 worker 传播取消。worker 继续生成到最大长度，发送队列堆满，KV 和计量租约直到超时才释放。总体 QPS 看似正常，但活跃请求和内存逐小时上升。

修复包括端到端取消链、发送缓冲上限、最后读取时间、每 token 取消检查和清理幂等性。告警同时看连接数、活跃推理、未确认事件和 KV 页，不能只看 HTTP 连接。应加入断线、慢读、代理重置和客户端主动取消的测试。

### 案例四：路由缓存过期把请求送到旧版本

路由器缓存模型别名到实例集合的映射，控制平面发布新 tokenizer 后只更新了部分节点。旧实例仍能加载权重，却使用不同 tokenization，结构化输出失败率上升。因为健康探针只检查进程和权重，异常直到业务指标恶化才被发现。

修复是把 tokenizer、模板、安全策略和权重绑定成同一个能力版本；路由器在切换时校验版本摘要；能力探针发出一小段合成结构化请求；缓存失效采用版本号而不是时间猜测。回滚时保留旧版本完整工件和兼容的缓存策略。

### 案例五：共享前缀缓存导致租户信息侧漏

工程师为降低首 token 延迟，用系统提示文本做全局缓存键。两个租户的文本相同，但一个租户拥有额外工具权限，导致 KV 前缀被错误共享。攻击者通过测量命中与未命中的时间差，推断另一个租户是否使用某模板。

修复是把权限域、模型和策略版本纳入缓存键；对敏感租户关闭跨域共享；限制命中统计的精度和访问；对时序差异做必要的抖动和容量隔离。缓存测试应覆盖相同文本、不同权限、不同区域和不同版本，而不是只验证命中率。

### 案例六：缩容打断了长流和工具事务

自动缩容只看 CPU 利用率，认为低负载实例可以立即终止。一个长流正在等待工具结果，另一个流刚发送半个结构化对象；进程被杀后客户端收到截断，工具状态却已经提交。重试重新执行工具，造成重复副作用。

修复是按活跃租约和阶段排空，缩容前停止接收新请求；长流超过排空窗口要发送明确错误并记录工具提交状态；不可幂等的工具必须有事务 ID 和服务端去重。缩容指标应同时考虑活跃请求、流式连接、工具状态和剩余错误预算。

## 16.12 六个理解检查（附答案）

### 检查 1：为什么队列必须有界？

答案：无界队列把拥塞从可见的拒绝变成不可见的内存增长和尾延迟，最终可能让整个进程 OOM。队列有界后，系统可以在已知容量内接受请求，并向客户端返回可重试或不可重试的明确结果。容量单位应与请求成本相关，长短请求混合时仅按请求数仍可能失真。

### 检查 2：为什么“端口打开”不能作为模型实例就绪？

答案：进程可能尚未校验和映射权重、编译算子、完成预热或确认显存预算。此时接收真实请求会把冷启动延迟暴露给用户，甚至在加载期间 OOM。应分开存活、就绪和能力探针，只有通过模型、版本、内存和关键路径检查的实例才加入路由。

### 检查 3：什么时候重试会造成重复副作用？

答案：请求已经生成部分结果、调用外部工具、扣费或写入状态后，客户端或路由器看见超时就重试，可能再次执行同一动作。解决办法是幂等键、尝试号、工具事务 ID、记录已提交状态，并只对确认的暂时性且无副作用错误重试。流式响应尤其不能默认对冲。

### 检查 4：自动扩缩容为什么容易振荡？

答案：指标有采样延迟，实例有冷启动时间，扩容动作又会改变队列和利用率；若扩缩容窗口、冷却时间过短，控制器会在未观察到上一次动作效果前再次反向操作。通常对扩容使用较快窗口、对缩容使用较慢窗口，设置步长、最小实例、排空状态和稳定时间，并把加载中的实例排除在可用容量外。

### 检查 5：流式服务为什么必须实现背压？

答案：生成速度可能大于客户端读取速度。无界发送缓冲会占用内存并拖累 worker；没有取消传播则断线客户端仍消耗模型资源。有限缓冲、合并增量、暂停或断开策略能把慢客户端成本限定在预算内，同时必须保持事件顺序、计量和结构化边界。

### 检查 6：多租户公平是否等于所有租户完全相同的配额？

答案：不一定。合同、数据敏感度和服务等级可能需要不同的容量和优先级，但规则必须可解释、可审计，并且不能绕过安全、数据驻留和最大资源上限。公平性应同时观察获得的服务量、等待时间、拒绝原因和全局资源状态，防止高权重租户永久挤压其他租户。

## 16.13 练习

1. **队列容量实验**：扩展 toy，使请求成本按输入 token 和最大输出 token 估算。比较固定请求数队列与 token 预算队列在长尾流量下的 p95、p99、拒绝率和内存上界。
2. **租户公平调度**：实现加权轮询或虚拟完成时间队列。构造一个持续满载的金牌租户和多个突发免费租户，报告每个租户的等待时间、获得 token 数、拒绝原因和最大连续服务轮次。
3. **流式背压**：加入模拟慢客户端和有限发送缓冲。分别测试合并增量、暂停生成和断开策略，检查断线后资源释放时间、事件序号连续性和计量一致性。
4. **扩缩容控制器**：增加启动延迟、加载失败概率、冷却窗口和排空时间。比较只看 CPU、只看队列以及需求加拥塞双信号的控制器，记录振荡次数、过载时间和实例成本。
5. **模型切换演练**：为 toy 增加模型能力版本和就绪探针，模拟 tokenizer 不匹配、权重摘要错误、预热超时和回滚。验证旧池未被过早删除，新池未通过能力检查时不会接流量。
6. **故障注入**：随机杀 worker、延迟事件、重复取消和断开 socket。要求请求清理幂等、租户 active 计数最终归零、队列不会永久卡死，并给每次故障保留最小可重放记录。
7. **SLO 预算**：为首 token、完整响应、拒绝和取消定义窗口与分母。构造一小时突发，比较立即拒绝、有限排队和小模型降级对错误预算、用户可见延迟和成本的影响。
8. **隐私边界审计**：检查日志、指标、事件缓存、共享前缀和追踪标签，列出可能包含 prompt、输出、租户标识或工具参数的位置。为每项添加脱敏、最小权限、保留期和删除验证。
9. **优雅关闭**：实现停止接收、排空短请求、取消超时长请求和确认工具状态。验证重复关闭信号、控制面失联和实例崩溃时仍能释放所有本地资源。

每份练习报告包含随机种子、软件版本、配置、负载生成规则、原始事件摘要、p50/p95/p99、最大值、拒绝类别和失败样本。不要只给一张吞吐图；解释控制器为何作出每次扩缩容或降级决定，并指出 toy 与真实 GPU、网络和模型之间的差距。

## 16.14 来源地图与进一步阅读

来源可以按“算法、运行时、可靠性、租户和安全”五条线阅读。算法线复习 Transformer 推理、批处理和 KV 管理；运行时线阅读服务框架的 worker、动态批处理、健康探针和模型仓库约束；可靠性线阅读 SLO、错误预算、背压、优雅关闭和分布式重试；租户线关注公平队列、配额、数据驻留和计量；安全线关注供应链、日志最小化、提示注入、侧信道和事件响应。不同来源的实验硬件、模型长度、批大小和错误定义不同，不能直接横向比较“提升百分比”。

- **Attention Is All You Need**：<https://arxiv.org/abs/1706.03762>。确认 Transformer 层结构、因果注意力与序列并行化基础。
- **Orca：A Distributed Serving System for Transformer-Based Generative Models**：<https://www.usenix.org/conference/osdi22/presentation/yu>。讨论迭代级调度、请求级调度和生成服务的系统权衡。
- **vLLM 与 PagedAttention**：<https://arxiv.org/abs/2309.06180>、<https://docs.vllm.ai/>。参考分页 KV、连续批处理和服务端配置边界。
- **Ray Serve 文档**：<https://docs.ray.io/en/latest/serve/>。查看部署副本、路由、批处理和扩缩容的工程接口，注意其版本差异。
- **KServe 文档**：<https://kserve.github.io/website/>。了解模型服务 CRD、预测协议、就绪检查和推理图的常见形态。
- **NVIDIA Triton Inference Server 文档**：<https://docs.nvidia.com/deeplearning/triton-inference-server/>。核对动态批处理、模型仓库和健康端点，不能替代目标模型压测。
- **OpenTelemetry Traces**：<https://opentelemetry.io/docs/concepts/signals/traces/>。建立跨网关、路由、worker、流事件和计量的关联追踪。
- **Google SRE Workbook**：<https://sre.google/workbook/>。参考 SLI、SLO、错误预算、过载和发布控制的实践。
- **RFC 9457 Problem Details**：<https://www.rfc-editor.org/rfc/rfc9457>。为可重试、不可重试、限流和容量错误设计机器可读的错误对象。
- **NIST AI RMF**：<https://www.nist.gov/itl/ai-risk-management-framework>。将可靠性、隐私、治理和事件响应纳入上线检查。
- **OWASP LLM Top 10**：<https://owasp.org/www-project-top-10-for-large-language-model-applications/>。识别提示注入、敏感信息泄露、供应链和过度代理风险。

建立内部来源表时记录来源版本、访问日期、支持的主张、适用模型/硬件、实验设置、未覆盖边界和本地复现实验。把“论文提出的算法”“框架提供的接口”“本章 toy 的观察”和“尚待验证的工程假设”分开写。某个框架支持动态批处理，不等于它在你的租户流量上满足 p99；某个云服务承诺可用性，也不等于模型输出质量或工具幂等已经解决。

## 16.15 安全边界与上线清单

模型服务把用户数据、模型工件和运维权限放在同一条生命周期里，以下边界必须在设计、测试和上线后持续验证：

- **身份与租户边界**：租户身份由认证上下文确定，策略快照贯穿路由、worker、缓存、日志和计量。请求体中的租户字段只能作为显示信息，不能决定权限。
- **工件完整性边界**：模型、tokenizer、模板、量化配置和运行时按版本绑定，加载前校验摘要和来源，失败时隔离，不从未知路径或未审核下载物中恢复。
- **数据机密边界**：日志、指标、追踪、流事件缓存和调试样本不得默认包含完整 prompt、输出、令牌、工具凭据或跨租户上下文。采样需脱敏、最小权限、保留期和删除验证。
- **资源可用性边界**：所有队列、发送缓冲、KV 或上下文池、重试和对冲都有上限；过载时优先拒绝或降级，不允许无限排队和无限重试。
- **流式完整性边界**：事件有顺序、终止和错误语义；断线传播取消；结构化输出不返回无法解析的半片；重连不重复工具副作用。
- **多租户公平边界**：配额、权重和隔离规则可解释可审计，不能依据受保护或无关属性做隐藏优先级。紧急通道也不能绕过合法性、数据驻留和安全策略。
- **控制平面边界**：配置带版本、摘要和有效期，worker 原子切换并保留回滚；控制面失联时只使用最近一次校验配置，不能接受任意推送。
- **发布和回滚边界**：新版本先预热、能力探针和金丝雀，再逐步放量；异常时摘流并保留现场，不覆盖损坏工件或审计记录。
- **运维权限边界**：查看用户内容、导出账单、修改配额、改变数据驻留和删除缓存都是受控动作，使用临时最小权限、审计和分步确认。

上线前逐项验证：队列有界且拒绝可解释；worker 租约和取消最终一致；流式慢客户端不会无限占内存；模型工件可验证且预热合成；就绪和能力探针有效；扩缩容有冷却、并行加载上限和排空；SLO 分段且含拒绝与超时；租户配额、公平和隔离经过恶意长请求测试；重试有幂等键和预算；工具事务可去重；日志和追踪完成脱敏；回滚开关经过演练；故障域容量能承受至少一个域不可用；所有动态优化都能安全关闭。

## 16.16 小结：服务系统是一组带预算的控制回路

worker 池决定并发边界和资源所有权，有界队列把背压变成可观测的协议；路由器根据能力、容量、合规和成本把请求交给正确的实例；自动扩缩容要同时看需求、拥塞、冷启动和故障余量，不能追逐单一噪声指标。流式响应需要事件顺序、背压、断线取消和幂等重连，模型加载需要不可变工件、分阶段预热、能力探针和可回滚切换。

优雅降级不是偷偷换模型，而是在明确模式和用户可见边界内，先移除可选成本、保住安全与核心能力。SLO 要拆成首 token、间隔、完整响应、拒绝和清理等可操作指标，并与错误预算和发布策略相连。多租户系统要把身份、配额、缓存、日志、计量和运维权限视为同一个信任边界。

最终，可靠的模型服务能回答这些问题：请求为什么被接收或拒绝，在哪个队列等待，使用了哪个模型和版本，何时首 token，慢在模型还是网络，断线后资源多久释放，租户如何获得公平服务，扩容为何发生，降级为何触发，以及出现错误时怎样在不泄露数据、不重复副作用的前提下回滚。把这些答案固化进状态机、toy 实验、指标、审计和演练，才能从“模型能响应”走向“服务可运营、可解释、可恢复”。
