# 第5章　GPU 架构与 CUDA 执行：从线程束到可观测内核

> GPU 性能不是“把程序搬到显卡上”就自动产生的加速。真正决定结果的是：工作如何切成线程，线程如何成束执行，数据如何经过寄存器、缓存、显存和主机互联，以及我们是否能够用计时器和计数器验证假设。本章把 CUDA 当作一个可测量的执行系统，而不是一组神奇的 API。

## 5.1 先建立一张可检查的地图

本章围绕一个问题展开：给定一个计算任务，如何判断它应该在 CPU、单 GPU 还是多 GPU 上执行，并且能解释性能结果？答案需要同时看五个尺度：

1. **指令尺度**：一个线程执行哪些标量指令，寄存器如何分配。
2. **线程束尺度**：32 个线程组成的 warp 是否走相同控制流，访存是否合并。
3. **线程块尺度**：一个 block 如何使用共享内存、同步屏障和资源配额。
4. **SM 尺度**：流式多处理器（SM）如何驻留多个 block，如何在延迟和吞吐之间调度。
5. **系统尺度**：CPU、GPU 显存、PCIe/NVLink、网络和存储如何组成端到端路径。

[事实] CUDA 的编程模型把网格（grid）映射到设备，网格由线程块（block）组成，线程块由线程组成。硬件实际以 warp 为基本调度和发射单位，常见 NVIDIA 架构中一个 warp 包含 32 个线程。

[机制] “一个线程”是程序员容易理解的抽象，“一个 warp”是性能分析必须面对的现实。若同一 warp 的线程执行不同分支，硬件通常要按路径分别执行，再屏蔽不属于该路径的线程，产生分支发散。若线程对连续地址发起访问，硬件可将请求合并为较少的内存事务；若地址离散，事务数上升，带宽利用率下降。

[设计判断] 先画数据路径再讨论优化。最少要标出：输入何时在 CPU 内存、何时进入显存、在哪个 kernel 中读写、何时回到 CPU，以及每个边界是否发生隐式同步。只盯 kernel 内部的微秒数，可能忽略了毫秒级的数据搬运。

## 5.2 CPU 与 GPU：两种不同的并行契约

CPU 面向通用控制流和低延迟单线程。现代 CPU 通常拥有少量高性能核心，每个核心有较大的乱序执行窗口、分支预测、缓存层次和复杂一致性协议。它擅长指针追踪、分支密集、数据规模较小、延迟敏感或需要调用大量系统服务的工作。

GPU 面向高吞吐。一个 GPU 包含许多 SM，每个 SM 维护大量线程上下文，以线程束为单位发射指令。单个线程的寄存器数量、缓存容量和控制流能力通常不如 CPU 核心，但同时驻留的线程数更多，可以在某个 warp 等待内存时切换到另一个就绪 warp。

| 维度 | CPU | GPU |
|---|---|---|
| 主要目标 | 单线程低延迟、复杂控制 | 大规模数据并行吞吐 |
| 并行粒度 | 核心、SIMD 向量、任务线程 | warp、block、grid |
| 缓存与分支 | 缓存较大，分支预测复杂 | 缓存较小，warp 分支需一致 |
| 内存访问 | 随机访问容忍度相对高 | 需要合并、对齐和高并行度 |
| 启动成本 | 函数调用开销低 | kernel 启动与同步有固定成本 |
| 适合工作 | 解析、调度、稀疏控制、短任务 | 矩阵、卷积、规整向量、批处理 |

[事实] GPU 不是 CPU 的“更多核心版本”。它们在内存系统、执行宽度、上下文管理和同步语义上都不同。将串行循环直接复制到 kernel 并不能保证加速。

[机制] GPU 隐藏内存延迟依赖足够多的独立 warp。若每个 block 只使用很少线程，或寄存器/共享内存占用过高导致可驻留 block 数低，SM 没有足够工作可切换，内存延迟就会暴露。反过来，盲目增加线程也可能让寄存器压力升高、occupancy 下降。

[设计判断] 选择设备时先问“并行性和数据重用在哪里”，再问“峰值 FLOPS 有多少”。一个分支复杂且输入很小的任务，CPU 可能更快；一个可批处理的 GEMM，即使单次延迟不敏感，也常由 GPU 获得数量级吞吐优势。

## 5.3 SM、线程块与 warp 的执行模型

### 5.3.1 SM 是资源池而非一个核心

一个 SM 可以看成四类资源的组合：算术流水线、寄存器文件、共享内存/L1 缓存、warp 调度器。一个 thread block 被分配到单个 SM 上执行，不能跨 SM 直接共享共享内存或同步。网格中的不同 block 通常可以独立执行，因此硬件可以把它们分发到多个 SM。

每个 block 占用的资源包括线程数、寄存器数、共享内存字节数和架构相关的调度槽位。资源不足时，block 不能驻留，表现为并行度下降。`cudaOccupancyMaxActiveBlocksPerMultiprocessor` 等 API 可估算理论 occupancy，但 occupancy 只是“可驻留线程数相对上限”，不等于有效吞吐。

### 5.3.2 warp 发射与分支发散

一个 warp 通常以单指令多线程（SIMT）方式执行。线程拥有独立寄存器和程序计数器语义，但指令发射在 warp 级别。伪代码：

```cpp
if (threadIdx.x % 2 == 0) {
    a = expensive_path(x);
} else {
    b = other_path(y);
}
```

同一 warp 中一半线程走 `expensive_path`，另一半走 `other_path`，硬件往往需要串行执行两条路径，再用活跃掩码屏蔽无关线程。对于偶发分支影响可能很小，但在深层循环、长延迟函数或不规则输入下，发散会显著增加执行时间。

[机制] 分支代价与 warp 内分歧比例、路径长度、编译器优化和缓存命中相关。不能用“有 if 就一定慢”替代测量。若分支发生在不同 warp 之间而不是同一 warp 内，通常不会形成同样的发散。

### 5.3.3 block 形状与边界处理

二维矩阵常使用 `dim3 block(16, 16)` 或 `32×8` 等形状。选择时要考虑：线程数是否为 warp 大小的整数倍、x 维是否对应连续地址、共享内存 tile 是否对齐、边界条件是否导致大面积无效线程。一个边界检查示例：

```cpp
int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
if (row < M && col < N) {
    C[row * N + col] = A[row * K + k] * B[k * N + col];
}
```

[安全边界] 任何索引计算都要检查整数溢出、负值转换和维度乘积。越界写可能破坏其他线程的数据，甚至表现为“下一次 kernel 才崩溃”。开发阶段可启用 `compute-sanitizer`，不要把“没有立刻报错”当作安全证明。

## 5.4 内存层次：从寄存器到主机内存

### 5.4.1 寄存器

寄存器是线程私有、延迟最低的存储，但数量有限。编译器根据变量活跃范围和优化级别分配寄存器。若 kernel 需要太多寄存器，可能发生 register spilling，把局部变量放到 local memory；local memory 名称容易误导，它通常位于显存，访问代价高于寄存器。

可以使用编译输出查看寄存器数量，例如 `nvcc --ptxas-options=-v`。减少寄存器占用的方法包括缩短变量生命周期、拆分 kernel、调整循环展开和数据类型；`__launch_bounds__` 或 `-maxrregcount` 应谨慎使用，因为强行限制寄存器可能增加 spilling。

### 5.4.2 共享内存与 bank conflict

共享内存位于 SM，供同一 block 的线程显式协作。典型用途是把全局内存中的 tile 搬入共享内存，重复使用以降低显存流量。共享内存被划分为多个 bank；若同一 warp 的线程访问不同 bank，访问可并行；多个线程冲突访问同一 bank 时，可能被拆成多次事务。

常见的转置优化是在 tile 的一维增加 padding：

```cpp
__shared__ float tile[32][33]; // 33 避免某些列访问的 bank 对齐冲突
```

[机制] 共享内存容量大、延迟低并不等于“随便用”。过大的 tile 会限制每个 SM 可驻留 block 数，过小的 tile 则减少数据重用。应同时观察共享内存吞吐、bank conflict 指标和实际 kernel 时间。

### 5.4.3 L1/L2/纹理与只读路径

现代 NVIDIA GPU 通常在 SM 附近有 L1/共享内存可配置区域，并有跨 SM 的 L2 缓存。只读数据可能通过只读缓存或纹理路径受益，具体行为依架构和编译器变化。L2 命中可以减少显存事务，但随机访问、工作集过大或多流互相驱逐都会降低命中率。

[设计判断] 不要把缓存命中率单独当成成功指标。命中率提升但请求数量也增加时，总时间可能不降；反之，命中率不高但访存并行度足够，内核仍可能接近带宽上限。

### 5.4.4 全局内存与合并访问

全局内存位于 GPU 显存，容量大、带宽高但延迟高。一个 warp 访问连续且对齐的元素，硬件可将访问合并为少量事务。以下模式通常不理想：

```cpp
// 线程 x 访问跨步地址，可能造成大量事务
float v = data[(threadIdx.x * stride) % n];
```

常见改进是让 x 维线程对应连续元素，将转置或聚合放到共享内存，并确保基址对齐。对于结构体数组和数组结构体，要根据访问字段选择布局；只使用其中一个字段时，结构体数组可能带来不必要流量。

### 5.4.5 统一内存与页迁移

Unified Memory (`cudaMallocManaged`) 简化了主机和设备的地址管理，但页面可能在 CPU 与 GPU 之间迁移。首次访问缺页、交替访问和多 GPU 竞争会造成隐式迁移与同步。`cudaMemPrefetchAsync`、`cudaMemAdvise` 可提供提示，但仍应通过事件计时和迁移统计验证。

[安全边界] 统一内存不是“无限安全内存”。指针生命周期、并发访问、主机线程是否在 GPU 使用时修改数据，都需要遵守 CUDA 的同步规则。析构仍在 kernel 使用中的对象可能导致未定义行为。

## 5.5 主机到设备：PCIe、NVLink 与拓扑

一次 GPU 推理通常包含：CPU 解码与预处理、主机内存到显存的 H2D 拷贝、若干 kernel、设备间通信（可选）、显存到主机的 D2H 拷贝。端到端时间可粗略写为：

`T_total = T_cpu + T_H2D + T_kernel + T_D2H + T_sync + T_queue`。

PCIe 是主机与 GPU 的常见互联，带宽受代际、链路宽度、拓扑和其他设备争用影响。NVLink 提供 GPU-GPU 或 GPU-CPU 的更高带宽和更低协议开销，但具体代际、桥接方式和 P2P 支持差异很大。多 GPU 系统还可能经过 PCIe switch 或 CPU root complex，路径不同会导致显著差异。

[事实] `cudaMemcpy` 是同步拷贝语义之一；`cudaMemcpyAsync` 可以在满足条件时与主机或其他工作重叠，通常需要页锁定（pinned）主机内存。异步不意味着立刻完成，也不意味着可以安全地重用源缓冲区。

[机制] H2D/D2H 拷贝是否能与 kernel 重叠，取决于设备支持的 copy engine 数量、流、内存类型、依赖关系和默认流语义。若主机线程在提交后马上读取结果，隐式同步会消除重叠收益。

一个可复现的带宽实验要记录：

- 数据大小与方向（H2D、D2H、D2D、P2P）
- pageable 还是 pinned 内存
- 传输次数、是否预热、是否使用同一 stream
- 计时边界是 API 返回、event 还是端到端可见结果
- PCIe/NVLink 拓扑、GPU 时钟和温度

不要将 `nvidia-smi` 显示的链路速率直接当作实际有效带宽。协议开销、事务大小、分段和并发请求都会影响有效吞吐。

## 5.6 occupancy、延迟隐藏与实际吞吐

Occupancy 常定义为某个 SM 上活跃线程数与最大可支持线程数的比值。它受以下资源约束：

- 每个 block 的线程数和每个 SM 的最大线程数
- 每个 block 的寄存器总量与寄存器文件容量
- 每个 block 的共享内存字节数与共享内存容量
- block 数量、warp 数量和架构限制

高 occupancy 有助于隐藏内存延迟，但并非越高越好。一个计算密集 kernel 可能在 50% occupancy 时已经完全利用算术流水线；提高到 100% 只会牺牲寄存器重用或增加调度压力。一个访存延迟高的 kernel 可能需要更高并行度，但应先修正合并访问和工作集重用。

[设计判断] 把 occupancy 当成诊断线索，不是目标函数。优化报告至少同时给出：kernel 时间、有效带宽或 FLOP/s、占用率、寄存器数、共享内存、分支效率和内存合并指标。

一个简单的并发估算：若每个 block 使用 `R` 个寄存器、`S` 字节共享内存、`T` 个线程，SM 资源上限分别为 `R_sm`、`S_sm`、`T_sm`，则由资源决定的最大驻留 block 数可近似写为：

`B_active = min(floor(R_sm / (R*T)), floor(S_sm / S), floor(T_sm / T), B_arch)`。

该式忽略架构细节，只用于识别主要限制项。实测应以 occupancy calculator、编译器报告和 profiler 为准。

## 5.7 kernel、stream、event 与同步

### 5.7.1 kernel 是设备端工作提交单元

Kernel 调用将网格配置和参数提交给 GPU。提交本身有固定开销，短小 kernel 可能被启动开销主导。把多个逐元素操作融合为一个 kernel 可减少启动次数和中间写回，但融合会增加寄存器压力、降低复用或让代码难以维护，因此需要测量。

### 5.7.2 stream 是有序队列

同一 CUDA stream 中的操作通常按提交顺序执行。不同 stream 的操作可能并发，前提是没有数据依赖且硬件资源允许。默认流（legacy default stream）与其他流可能有隐式同步规则；`cudaStreamNonBlocking` 可用于创建不与默认流发生某些隐式同步的流。

示例流水线：

```cpp
for (int i = 0; i < batches; ++i) {
    int s = i % 2;
    cudaMemcpyAsync(d_x[s], h_x[s], bytes, cudaMemcpyHostToDevice, streams[s]);
    kernel<<<grid, block, 0, streams[s]>>>(d_x[s], d_y[s]);
    cudaMemcpyAsync(h_y[s], d_y[s], bytes, cudaMemcpyDeviceToHost, streams[s]);
}
```

双缓冲只有在 `h_x[s]`、`h_y[s]` 是 pinned、缓冲区生命周期覆盖异步操作且主机不提前重用时才可能实现重叠。

### 5.7.3 event 是设备时间线上的标记

`cudaEventRecord` 在 stream 中插入标记，`cudaEventElapsedTime` 可测量两个 event 之间的设备时间。相比主机墙钟，event 更适合测量 kernel 或拷贝的设备时间，但它不自动包含主机排队、初始化或外部同步。首次调用可能触发上下文创建，实验需预热并报告是否排除初始化。

### 5.7.4 同步语义与隐式等待

- `cudaDeviceSynchronize()` 等待设备上此前提交的工作全部完成，简单但粗粒度。
- `cudaStreamSynchronize(stream)` 只等待指定流。
- `cudaEventSynchronize(event)` 等待某个里程碑。
- `cudaMemcpy`（同步版本）可能对相关流产生同步。
- 内存分配、释放、某些库调用可能隐式同步，需查看文档与 profiler。

[安全边界] 错误检查应紧邻异步调用。常用宏：

```cpp
#define CUDA_CHECK(call) do { \
  cudaError_t e = (call); \
  if (e != cudaSuccess) { \
    fprintf(stderr, "%s:%d: %s\n", __FILE__, __LINE__, cudaGetErrorString(e)); \
    exit(EXIT_FAILURE); \
  } \
} while (0)
```

kernel 启动后还应调用 `cudaGetLastError()` 检查配置错误，并在调试模式用 `cudaDeviceSynchronize()` 把异步错误定位到最近的调用。生产路径可使用更细粒度的错误传播，不必每个 kernel 都强制全设备同步。

## 5.8 CUDA Graphs：减少提交开销而不是改变算法

当同一个执行拓扑反复运行时，可以先捕获 kernel、拷贝和事件，再实例化 CUDA Graph，后续通过 `cudaGraphLaunch` 重放。Graph 适合稳定的 batch 形状、固定内存布局和重复的流水线；对于每次依赖关系都变化的请求，捕获和更新成本可能抵消收益。

典型流程：

1. 在捕获流上执行一次代表性工作。
2. `cudaStreamEndCapture` 得到 graph。
3. `cudaGraphInstantiate` 创建可执行实例。
4. 重复 `cudaGraphLaunch`。
5. 输入地址或标量变化时，更新节点参数或重新构建。

[机制] Graph 减少主机到驱动的逐 kernel 提交与依赖管理开销，不能自动减少 kernel 内部计算和显存流量。若瓶颈在带宽或算术单元，Graph 可能几乎没有收益。

[设计判断] 先用 event 和 profiler 证明“提交开销占比足够大”，再引入 Graph。Graph 会增加生命周期和参数更新复杂度，需配套回退路径。形状、指针、stream、设备变化时应明确是否允许重捕获。

## 5.9 性能剖析：从时间线到 Roofline

### 5.9.1 工具分层

- `nvidia-smi`：查看设备、进程、显存、温度和时钟，适合健康检查，不适合解释单个 kernel 的瓶颈。
- Nsight Systems：看 CPU/GPU 时间线、stream、拷贝、同步和跨线程关系，回答“时间花在哪里”。
- Nsight Compute：看单 kernel 的指令、缓存、吞吐、occupancy、分支、访存事务，回答“为什么这个 kernel 慢”。
- CUDA events：在代码中做轻量、可重复的局部计时。
- Compute Sanitizer：检查越界、竞态、初始化和同步错误，优先用于调试版本。

剖析时先建立基线：固定输入、固定 batch、预热次数、重复次数、GPU 持久化状态和环境变量。记录 P50、P95、P99，而不是只记录一次最好结果。

### 5.9.2 Roofline 衔接

第4章介绍 Roofline：性能上限由计算峰值与内存带宽共同决定。对 GPU kernel，算术强度定义为：

`AI = FLOPs / Bytes_moved`。

若 `AI × memory_bandwidth` 小于峰值 FLOP/s，内核倾向于内存受限；若高于计算峰值，倾向于计算受限。实际分析还需考虑缓存层次、指令混合、张量核心利用率、稀疏性和有效而非理论字节数。

[机制] 一个 kernel 的理论 FLOP 数不等于硬件实际发射的指令数。融合可能增加算术重用、提高 AI；但若增加寄存器 spilling，实际内存流量反而上升。Profiler 中的 dram throughput、L2 hit rate、sm throughput、tensor pipe utilization 应结合时间线解释，不能孤立排名。

[设计判断] 把 Roofline 用作“下一步实验选择器”：

- 内存受限：先做合并访问、重用、数据布局、压缩和融合。
- 计算受限：检查指令类型、精度、张量核心利用率、展开和数学库。
- 两者都低：可能是 occupancy、分支发散、同步、启动或依赖链问题。
- 时间线显示拷贝占主导：先做流水线、批处理、pinned 内存、P2P 或减少往返。

## 5.10 CPU fallback：先保证正确，再比较速度

GPU 不是所有环境都可用：CI 机器、无驱动容器、用户本地笔记本、低功耗边缘设备都需要 CPU fallback。Fallback 不应只是“删掉 CUDA 分支”，而应拥有相同的数值契约、输入验证和错误传播。

推荐接口：

```python
def matmul(x, w, *, device="auto"):
    if device == "auto":
        device = "cuda" if cuda_available() else "cpu"
    if device == "cuda":
        return cuda_matmul(x, w)
    return cpu_matmul(x, w)
```

实验步骤：

1. 生成固定随机种子和多个矩阵形状，包含小尺寸、非对齐尺寸和空维度错误用例。
2. CPU 使用单线程和多线程两种基线，记录线程数、BLAS 库和频率。
3. GPU 预热后用 event 计时 kernel，再测端到端 CPU→GPU→CPU。
4. 比较绝对误差、相对误差、P50/P95、吞吐和能耗（若可测）。
5. 当 GPU 不可见、显存不足或 kernel 返回错误时，验证 fallback 是否能够给出明确诊断。

伪代码：

```python
try:
    y = model_gpu(x)
except (CudaUnavailable, OutOfMemoryError):
    log.warning("GPU path unavailable; using CPU fallback")
    y = model_cpu(x)
```

[安全边界] 不要捕获所有异常并静默回退。越界写、错误模型权重或数据损坏不应被伪装成“GPU 不可用”。只对已识别、可恢复的错误回退，并保留原始错误码、设备信息和输入摘要。

## 5.11 实验一：测量 kernel 与端到端路径

下面实验只需要一个向量加法 kernel；没有 GPU 时可运行 CPU 版本并记录“不可用”结果。实验目的不是得到某个厂商数字，而是练习边界定义。

### 5.11.1 CUDA 代码框架

```cpp
__global__ void axpy(const float* x, float* y, float a, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) y[i] = a * x[i] + y[i];
}

int main() {
    int n = 1 << 24;
    size_t bytes = n * sizeof(float);
    float *h_x, *h_y, *d_x, *d_y;
    cudaHostAlloc(&h_x, bytes, cudaHostAllocDefault);
    cudaHostAlloc(&h_y, bytes, cudaHostAllocDefault);
    cudaMalloc(&d_x, bytes); cudaMalloc(&d_y, bytes);
    // 初始化、预热、event 计时、错误检查省略
}
```

记录四组时间：初始化、H2D、kernel、D2H，以及总墙钟。用数据量除以 H2D 时间估算有效带宽，用 `2n` 次浮点运算除以 kernel 时间估算 FLOP/s。向量加法通常是内存受限，故 FLOP/s 看起来很低并不代表代码错误。

### 5.11.2 实验矩阵

- `n`：从 `2^10` 到 `2^26`，观察启动开销和带宽饱和。
- block：64、128、256、512，观察线程数与边界损失。
- 主机内存：pageable 与 pinned。
- stream：单流与双流，比较拷贝和 kernel 重叠。
- 计时：event、主机 monotonic clock、Nsight 时间线。

输出表格至少包含：环境、驱动、CUDA 版本、GPU 名称、时钟、输入大小、预热次数、重复次数、P50/P95、错误检查结果。不要只贴一个“最快 ms”。

## 5.12 实验二：用 CPU fallback 验证故障路径

构造四个场景：

1. 正常 GPU：设备可见，结果与 CPU 在容差内一致。
2. 无设备：设置 `CUDA_VISIBLE_DEVICES` 为空或在无 GPU 主机运行，程序明确选择 CPU。
3. 显存不足：请求一个超过预算的大张量，捕获可恢复的 OOM，释放缓存后重试小任务或回退。
4. 内核配置错误：故意设置非法 block 维度，仅在测试环境验证错误被报告，不能把它当作回退触发条件掩盖。

[机制] OOM 回退前要考虑输入是否包含敏感数据、CPU 是否有足够内存和时间、请求是否超过 SLO。回退可能保护可用性，却让延迟增加几个数量级。

[设计判断] 服务端应暴露“路径标签”（gpu、cpu_fallback、rejected）和回退原因的枚举，而不是只返回一个总延迟。这样容量规划才不会把 CPU 回退误当成 GPU 性能。

## 5.13 故障案例：从症状到证据链

### 案例 A：GPU 利用率低但延迟很高

症状：`nvidia-smi` 显示 20% 利用率，P99 从 80 ms 升到 600 ms。错误判断是“GPU 不够快”。时间线显示每个请求都在 CPU 排队，并且每次 kernel 前有小的 H2D 拷贝；请求粒度太小，启动与同步占主导。

修复路径：批处理相邻请求；使用 pinned 内存与双流；合并逐元素 kernel；减少每请求的全设备同步；将预处理放到 GPU 或提前缓存。验证指标：拷贝次数、kernel 数、GPU 空闲间隔、P50/P99 和 CPU 排队时间。

### 案例 B：occupancy 100% 但速度不快

症状：工具报告 occupancy 100%，但内核只达到理论带宽的 35%。进一步检查发现线程访问跨步地址，dram 事务数高，L2 命中低。

修复路径：重排数据布局，让连续线程访问连续地址；使用 tile 与共享内存；减少无效边界线程。occupancy 可能降到 75%，但有效带宽上升到 85%。这说明 occupancy 不是最终目标。

### 案例 C：双流没有重叠

症状：代码使用两个 stream，时间线仍显示 H2D、kernel、D2H 串行。检查发现主机缓冲区是 pageable，且循环中调用了 `cudaDeviceSynchronize()`；某个库在默认流提交了工作，触发隐式同步。

修复路径：改为 pinned 双缓冲；按 stream 使用事件建立依赖；删除不必要的全设备同步；确认库的 stream 设置。不要在没有证据时反复增加 stream 数量。

### 案例 D：升级驱动后结果随机错误

症状：同一输入偶尔出现 NaN，重跑又正常。Compute Sanitizer 报告越界写，根因是 block 尺寸改变后索引计算使用了 32 位乘法溢出；旧版本的内存布局让错误暂未暴露。

修复路径：使用 64 位索引或显式检查乘积；在 CI 中跑边界尺寸和 sanitizer；将驱动升级视为暴露未定义行为的机会，而不是简单回滚。若必须回滚，记录风险并安排修复。

## 5.14 六个理解检查（含答案）

**检查 1：为什么同样是 1024 个线程，分成 32×32 和 128×8 的 block，性能可能不同？**  
答案：线程总数相同，但 x 维连续访存、共享内存 tile 形状、边界线程分布、warp 到二维坐标的映射不同。32×32 让一个 warp 可能覆盖一整行，128×8 则形成不同的跨行模式；实际要用 profiler 验证合并访问和 bank conflict。

**检查 2：occupancy 从 50% 提到 100% 一定更快吗？**  
答案：不一定。若瓶颈是算术流水线或内存事务质量，增加驻留线程不会解决问题；为了提高 occupancy 而限制寄存器可能引入 spilling。应比较 kernel 时间、吞吐和资源指标。

**检查 3：`cudaMemcpyAsync` 调用返回后，能否立即重用主机缓冲区？**  
答案：只有在确认拷贝完成并且缓冲区是可安全异步使用的情况下。通常需要 pinned 内存、事件或 stream 同步；API 返回不代表 DMA 已完成。

**检查 4：为什么把三个 kernel 融合后反而变慢？**  
答案：融合可能减少启动和中间写回，但增加寄存器活跃范围、降低 occupancy、造成分支发散或增加指令依赖。应使用时间线和 Nsight Compute 分解收益与代价。

**检查 5：PCIe 带宽高于单次 H2D 测得带宽，是否说明实验有 bug？**  
答案：不一定。标称带宽是链路理论值，实际有效带宽受协议、事务、页锁定、大小、拓扑和并发影响。需要报告测量边界和数据大小，而不是直接比较两个数字。

**检查 6：CPU fallback 是否可以捕获所有 CUDA 异常后继续？**  
答案：不可以。只对明确可恢复且不代表数据损坏的错误回退；越界、竞态、非法访问和模型不一致应失败并报警。否则会掩盖严重缺陷并造成不可预测的结果。

## 5.17 安全边界与运行手册

GPU 调试也有安全边界。以下规则适用于个人实验、共享服务器和生产推理：

1. **权限最小化**：容器只映射需要的 GPU，不授予不必要的宿主机设备节点；不要把 `/dev/mem` 或整套主机目录暴露给实验容器。
2. **资源配额**：设置显存、进程、batch、kernel 超时和请求并发上限；对多租户使用 MIG、MPS 或调度器时遵守管理员策略。
3. **数据隔离**：显存释放不等于敏感数据瞬间消失。复用缓冲区前按组织政策清理，日志不要写入原始输入或完整张量。
4. **驱动变更**：升级驱动、CUDA、固件前记录版本、回滚路径和兼容矩阵，在隔离节点验证。
5. **错误处理**：区分 OOM、设备丢失、非法访问、超时和用户取消；保留错误码与时间线摘要，避免无限重试。
6. **确定性声明**：并行归约和库算法可能有非确定性；若任务需要可复现，设置确定性选项并接受性能代价。
7. **外部代码**：不要直接运行来源不明的 PTX、插件或自定义算子。审查编译脚本、动态库路径和网络访问权限。
8. **健康检查**：温度、功率、ECC、XID 错误、时钟和 PCIe 重传异常应纳入监控。健康异常时先隔离节点，再继续压测。

任何 GPU 优化提交都应附一页说明：

- 目标：延迟、吞吐、成本还是能耗？SLO 是什么？
- 工作负载：输入分布、batch、并发、序列长度和数据类型。
- 基线：硬件、驱动、CUDA、库版本、编译选项和计时边界。

## 5.19 本章小结

GPU 加速的核心不是某个魔法数字，而是一条可验证的因果链：任务有足够并行性；线程被组织成高效 warp 和 block；访存合并且有合理重用；SM 有足够工作隐藏延迟；stream 和 event 表达真实依赖并允许合法重叠；主机互联与数据搬运不吞掉收益；profiler 把时间线和瓶颈证据暴露出来；CPU fallback 和错误边界让系统在无 GPU、OOM 和驱动异常时仍可解释。只要坚持“定义边界—测量—提出假设—改动—复测”，GPU 就不再是黑盒，而是可以被工程化管理的执行资源。

## 5.21 从算法到网格：一个矩阵乘法推导

设 `A` 的形状为 `M×K`，`B` 的形状为 `K×N`，目标是计算 `C=A×B`。最直接的实现让每个线程负责一个 `C[row,col]`：线程循环 `k=0..K-1`，读取 `A[row,k]` 和 `B[k,col]`，累加到寄存器。该实现容易理解，却有两个问题：同一行的线程重复读取 A，同一列的线程重复读取 B；当 K 较大时，显存流量和延迟都很高。

分块实现把 A、B 的子矩阵搬入共享内存。一个 `T×T` 的线程块共同加载两个 tile，每个线程计算一个输出元素。加载后，线程在 K 维循环中复用 tile 数据，因此算术强度提高。边界 tile 需要填零或使用条件分支，分支位置和无效线程比例应纳入测量。

推导时可先算理想流量。朴素版本大约为每个输出元素读取 `2K` 个元素并写回一个元素，总字节数接近 `M×N×(2K+1)×sizeof(float)`；分块版本每个 tile 的元素被 T 个线程复用，理想全局读量接近 `M×K + K×N` 个元素，显著下降。真实实现还会有缓存命中、写回、边界填充、寄存器和同步成本，所以理想值只是上限。

Tensor Core 路径还要满足数据布局、维度对齐、数据类型和累加精度要求。把 FP32 改为 TF32、FP16 或 BF16 可能提高吞吐，但会改变数值误差和可复现性。评审中应给出准确率或误差预算，不能只报告“快了多少”。

## 5.22 数值一致性与归约陷阱

GPU 上的浮点归约通常改变加法顺序。浮点加法不满足严格结合律，因此 CPU 顺序累加和 GPU 分层归约可能有微小差异。对于长序列、极端尺度或迭代算法，误差可能被放大。可采用更高精度累加、Kahan 变体、确定性算法或固定归约树，但每种方案都有性能代价。

原子操作也有语义边界。`atomicAdd` 可避免写冲突，却可能成为热点；不同线程更新同一地址的顺序通常不保证。若结果必须确定，考虑分块局部累加后再按固定顺序归约。若只需统计近似值，原子路径可能是合理折中，但要在接口文档中写出误差与非确定性。

NaN、Inf 和次正规数会影响分支、数学函数和性能。测试应包含零、负值、极大值、极小值、NaN、Inf 和空张量。不要在生产中通过“把 NaN 变成零”掩盖模型或数据问题；至少应计数、告警并提供采样诊断。

## 5.23 多流流水线的依赖图

多流不是“开更多线程”这么简单。可将流水线画成有向无环图：输入准备节点 → H2D 节点 → 预处理 kernel → 主计算 kernel → 后处理 kernel → D2H 节点。边表示数据依赖，资源标记表示 copy engine、SM、L2 和主机线程。只有不共享写入缓冲区、没有边依赖的节点才可并行。

事件用于表达跨流依赖：流 A 完成 H2D 后记录 event，流 B 等待该 event 再启动 kernel。主机轮询 event 可能浪费 CPU；阻塞等待则降低忙等开销但增加调度延迟。服务端通常采用事件回调、线程池或异步任务系统，避免一个请求线程长时间占用。

构建流水线时要计算缓冲区生命周期。若批次 i 的 D2H 尚未完成，批次 i+2 不能覆盖相同输出缓冲区。环形缓冲区大小至少覆盖“在途批次”数量，并根据最慢阶段的服务时间调整。缓冲区太小导致等待，太大则增加显存和 pinned 内存压力。

## 5.24 资源预算：显存、workspace 与碎片

显存峰值不只包括模型权重。预算应拆为权重、激活、输入输出、临时 workspace、通信缓冲、CUDA context、allocator 元数据和碎片。对动态 batch，峰值与最大序列长度共同决定。分配器可能保留已释放区块以便复用，`nvidia-smi` 显示的已用显存不一定等于当前张量总和。

建议在实验中记录三组数：分配前、峰值、释放后；同时记录逻辑张量字节数和驱动报告。若峰值接近上限，优先减小 batch、采用分块、降低精度或复用缓冲区，而不是简单捕获 OOM 后无限重试。重试会放大排队并可能使所有请求一起失败。

多进程共享 GPU 时，context 和 allocator 都有额外成本。MPS、MIG、进程独占模式和调度器的行为不同，不能把某一模式的显存数字迁移到另一模式。容器重启、进程崩溃和设备重置可能释放 context，但正在运行的请求会失败，服务需要幂等重试策略。

## 5.25 编译、架构与可移植性

CUDA 二进制通常包含针对一个或多个计算能力的 SASS，以及可由驱动 JIT 编译的 PTX。只包含旧架构 SASS 可能无法在新 GPU 上运行或无法使用新特性；只包含 PTX 则可能增加首次启动 JIT 延迟。发布包应明确支持的计算能力、驱动最低版本和是否需要联网下载组件。

编译选项会影响性能和调试：`-O3`、快速数学、融合、循环展开和寄存器限制都可能改变数值与资源使用。开发阶段保留带行号的调试信息，并在 CI 中运行至少一个 debug 配置和一个发布配置。不要把 `-use_fast_math` 当作默认万能开关，它会改变舍入和特殊值处理。

自定义算子必须测试不同架构。warp shuffle、异步拷贝、Tensor Core 等指令可能有架构前提。使用条件编译和 capability 查询，并为不支持的设备提供清晰错误或 CPU/库函数回退。回退路径不是降低质量，而是使发布范围可控。

## 5.26 从实验到生产 SLO

实验中的 kernel 加速要经过四道门才能成为生产优化。第一道是正确性：随机输入、边界输入、长序列和异常输入通过；数值误差符合契约。第二道是稳定性：在目标驱动、温度、并发和持续运行时性能不漂移，XID、ECC、非法访问为零。第三道是容量：在真实到达分布和突发下，P95/P99、显存峰值、CPU 利用率和队列长度满足 SLO。第四道是可回退：GPU 不可见、OOM、设备丢失、升级不兼容时，服务有明确策略和告警。

SLO 报告应区分冷启动与热路径。首次加载权重、CUDA context、JIT、Graph 捕获和缓存预热可能花费数百毫秒或更久。若用户经常触发冷启动，平均热路径结果无法代表体验。可在调度层预留温热实例，也可把冷启动作为单独预算并限制其发生频率。

持续压测要设置停止条件：温度达到阈值、错误率超过阈值、显存碎片超过预算、P99 连续若干窗口超标时自动停止。压测脚本应尊重共享集群配额，不得通过提高功率限制、禁用安全监控或绕过调度器获得“漂亮”数字。

## 5.27 故障演练剧本

**设备丢失**：模拟驱动重置或拔掉可热插拔设备（仅在隔离环境），确认服务检测到 `cudaErrorDeviceLost`，停止向该实例派发新请求，保存最小诊断信息并迁移到健康设备。不要在设备丢失后继续复用上下文。

**显存泄漏**：运行固定请求数，观察已分配和保留显存曲线。若每个请求后只增长不下降，使用分配器统计、对象生命周期和 profiler 定位。测试取消、异常和超时路径，因为泄漏常出现在成功路径之外。

**非法访问**：在测试 kernel 中写越界索引，使用 Compute Sanitizer 确认能被捕获；验证生产构建仍通过边界检查，而不是依赖 sanitizer 常驻。报告线程、地址、调用栈和可复现输入。

**版本不匹配**：在 CI 中组合最小驱动、目标驱动和容器 CUDA 版本，执行一组 smoke tests。版本错误应在启动探针中明确报告，而不是等第一条用户请求失败。

这些演练的目标不是制造中断，而是验证告警、隔离、回退和恢复链路。每次演练都应记录开始条件、预期信号、实际信号、恢复时间和遗留风险。

## 5.28 术语速查与最小复盘模板

- **SM**：流式多处理器，承载 warp 调度、算术流水线、寄存器与共享内存等资源。
- **warp**：硬件常见的 32 线程执行组，是分支发散和访存合并分析的基本单位。
- **block**：程序员定义的线程协作单元，驻留在单个 SM 上，可使用共享内存和块内同步。
- **occupancy**：活跃线程或 warp 与硬件上限的比例，用来估计延迟隐藏能力，不能单独代表性能。
- **coalescing**：将一个 warp 的连续访存合并为较少事务的过程，受地址对齐、数据宽度和架构影响。
- **pinned memory**：页锁定主机内存，便于 DMA 和异步拷贝，但会消耗主机资源，不能无限分配。
- **P2P**：设备间点对点访问，是否可用取决于拓扑、驱动和权限；不可用时可能绕经主机内存。
- **Graph replay**：重放已实例化的 CUDA Graph，减少重复提交开销，但要求拓扑和参数更新策略明确。

复盘时写下五句话：任务的并行维度是什么；最贵的一次数据搬运在哪里；当前证据支持内存受限还是计算受限；回退和错误分类如何工作；下一次实验要改变哪个变量以及预期看到什么信号。若无法写出第五句，说明优化仍停留在猜测阶段。

本章与第4章的衔接点是“把 Roofline 和排队模型连接起来”：Roofline 估计单个 kernel 的服务时间下界，排队模型估计到达率和并发下的等待时间；只有同时控制二者，才能把微秒级优化转化为稳定的端到端 SLO。后续章节将把这些 GPU 机制放进模型服务、批处理和多租户调度场景中。

## 5.29 小型决策案例：把测量结果变成选择

假设一项图像预处理任务在 CPU 上平均 4 ms、P99 7 ms；初版 GPU 路径的 kernel 只有 0.4 ms，但 H2D、D2H 和同步后端到端平均 6 ms、P99 18 ms。若只比较 kernel，会得出十倍加速；若比较用户可见时间，GPU 反而更差。正确的决策取决于请求是否可以批处理、数据是否已经在显存、是否允许异步返回，以及 CPU 是否有其他工作可并行。

第一种方案是保留 CPU：当输入小、请求稀疏、GPU 需要频繁唤醒时，CPU 更符合低延迟目标。第二种方案是把预处理和后续模型推理放到同一个 GPU 流程，避免往返；这需要验证模型输入格式和内存布局。第三种方案是批量化多个请求，用 pinned 内存和双流隐藏拷贝，牺牲一点单请求等待换取更高吞吐。第四种方案是混合调度，按大小和队列深度选择 CPU 或 GPU，并设定切换迟滞，避免请求在两个设备之间抖动。

写决策记录时，必须列出被放弃的方案和理由。例如“只看 occupancy 未采用”，因为时间线显示主导成本是 H2D；“强制 Graph 未采用”，因为 batch 形状变化导致重捕获频繁；“无限 CPU 回退未采用”，因为高峰期会耗尽 CPU 并污染尾延迟。这样后续成员能复查判断，而不必重新猜测。

当测量结果不稳定时，先检查环境而不是立刻改代码：GPU 时钟是否被功耗限制，是否有其他进程抢占，输入是否触发不同分支，内存分配器是否处于冷状态，主机线程是否被调度到不同核心。将这些变量固定或记录后再比较，才能避免把环境噪声误认为优化收益。
