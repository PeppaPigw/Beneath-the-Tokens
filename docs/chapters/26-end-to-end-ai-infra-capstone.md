# 第26章　AI Infra 端到端 Capstone：从需求到架构、训练、推理、运维与复盘

> 真正的 AI Infra 专家不是把十个组件拼在一起的人，而是能在不确定信息下把“我们想要一个智能功能”变成可测量的契约，说明数据怎样流过每个边界，证明系统在容量、故障、安全和成本约束下仍然可操作，并在证据不足时拒绝上线。本章把全书的概念收束为一个可交付项目。我们为一家虚构的“工单助手”公司设计从需求、数据、训练、模型注册、推理服务、Kubernetes 编排、可观测性、可靠性、安全、成本到发布和复盘的闭环，再用 CPU-only toy 重现关键状态。所有产能数字都只是教学参数，除非另有说明，不代表任何生产保证。

本章沿用全书证据标记。**事实**是规范、论文、官方文档或源代码直接支持的行为；**机制**是根据数据流、状态转移和调用关系还原出的因果链；**测量**是在声明环境中运行实验得到的结果；**推断**是由测量和公式推出来但仍依赖假设的结论；**设计判断**是在目标、风险和预算明确时的推荐。读者必须在 ADR、发布单和复盘中写清楚标签。一个绿色 CI、一次成功的本地请求或一个 CPU toy 的 40 次样本，都不能单独证明生产系统的可用性、质量或安全。

## 26.1 为什么需要端到端 Capstone

### 26.1.1 局部最优会制造全局失败

在前面的章节中，我们分别讨论了训练调度、数据格式、推理批处理、GPU 编排、可观测性、可靠性、安全和成本。真实项目却不会按照章节边界出故障。数据团队可能为了提高召回率把文本切得更长，导致推理 KV cache 超过容量；平台团队可能为了提高利用率把不同租户放到同一批次，违反数据隔离；模型团队可能更新 tokenizer，却忘记在服务镜像中同步；成本团队可能压低副本数，让尾延迟和重试放大。每个局部决定在自己的仪表盘上看起来合理，合在一起却使用户得不到可解释的结果。

端到端 Capstone 的意义是强迫我们写出跨边界不变量。例子包括：请求中携带的模型版本必须能在审计日志中解析；训练产生的 tokenizer 摘要必须与注册表和服务启动检查一致；一个输入只能产生一次有副作用的审计写入；达到容量上限时系统必须拒绝或降级，而不是无界排队；回滚必须同时恢复模型、提示模板、检索索引和策略版本。**设计判断**：如果一个不变量无法由至少一个自动检查和一个运行时观测支持，就把它标为未证实风险，而不是把它写进“已完成”清单。

### 26.1.2 “成功”不是返回 HTTP 200

工单助手的一次调用包含身份校验、输入审查、检索历史工单、模型生成答案、敏感信息过滤、引用检查、写入审计记录和流式返回。HTTP 200 只说明网关形成了一个响应，不说明答案引用了新数据、不说明模型没有泄露别的租户、不说明审计写入只发生一次，也不说明用户在预算时间内看到首个 token。我们把业务成功定义为复合事件：

- 请求被正确租户接受，策略检查通过或给出明确拒绝；
- 在首 token 和完整响应时限内返回结构合法的答案；
- 检索新鲜度和引用覆盖率满足阈值，若降级则显式标记；
- 输出通过安全分类和格式校验，无法自动判定时转人工；
- 审计事件以幂等键写入，模型、提示、索引和策略版本可追溯。

其中“质量满足阈值”通常需要采样评估，无法对每个请求实时证明。我们因此把实时 SLO 和离线质量门分开：实时层保证可达性、时限、格式、策略和审计完整性；质量层通过黄金集、人工抽样和回归评估提供统计证据。混淆两者会让团队在一次小样本通过后宣称“模型可靠”。

### 26.1.3 学习边界与交付姿态

本章的项目规模被故意压缩到一个团队四到六周可以完成的范围：一个文本模型、一个检索源、两个租户、单区域 Kubernetes、CPU 回退路径、少量 GPU 预算、有限的工具调用。你要练的是推理过程和证据闭环，不是复制某家云厂商的生产模板。若读者把示例的 QPS、p95 或恢复时间直接写入合同，属于证据越界。

## 26.2 Capstone 项目规格：工单助手

### 26.2.1 用户、场景与非目标

**用户**：支持工程师在公司内部控制台输入一段客户工单，系统检索已授权的知识和历史解决方案，生成带引用的建议回复。租户 A、B 的数据严格隔离。支持工程师可以接受、编辑或拒绝答案，最终发送由人工完成。

**目标**：在工作日高峰提供稳定的首 token 延迟，答案结构化、可追溯、能说明引用来源，故障时安全降级。模型可以是小型开源指令模型或教学 stub；质量不以“像人”衡量，而以引用覆盖率、结构合法率和人工抽样为主。

**非目标**：不自动向客户发送邮件，不作医疗、金融、法律或人事决定，不执行任意代码，不允许模型越权读取租户外的数据，不把本章的 toy 延迟当成规模承诺。任何自动外发都需要额外的人审和业务批准。

### 26.2.2 用户旅程和接口契约

把一次请求写成显式状态机：`RECEIVED → AUTHORIZED → RETRIEVED → GENERATED → VALIDATED → AUDITED → STREAMED`。任一状态失败都必须进入有界的 `REJECTED` 或 `DEGRADED`，不能静默跳过审计。状态事件至少包含 `request_id`、`tenant_id` 的不可逆摘要、模型版本、提示版本、索引版本、策略版本、输入和输出 token 桶、开始/结束时间、结果类别和错误类别。原始工单只在有权限的存储中保留，指标中不得出现完整文本。

输入 JSON 的最小字段是 `ticket_id`、`text`、`locale` 和 `requested_output`；输出 JSON 包含 `answer`、`citations`、`confidence_band`、`degraded`、`model_version` 和 `audit_id`。客户端重试时必须重用 `idempotency_key`。服务端返回 `429` 表示容量或租户配额拒绝，`503` 表示依赖暂时不可用，`422` 表示格式或策略拒绝；不要用统一的 500 隐藏不同的恢复语义。

### 26.2.3 SLO、质量门和错误预算

给出一个教学基线，实际项目须用业务数据校准：在每个滚动 30 天窗口内，纳入 SLO 的请求中，99.5% 应在 2 秒内产生首 token，99% 在 12 秒内完成，99.9% 审计事件可检索，99.5% 响应满足 JSON schema。纳入请求不包括显式策略拒绝、客户端在发送前取消和演练流量；排除项必须可审计，不能在事故后追加。

设窗口中的纳入请求数为 (N)，完成且满足实时契约的请求数为 (S)，实时错误预算为 (B=N-S)。若可用性目标为 (p=0.995)，则预算比例 (e=1-p=0.005)，预算请求数 (B_{max}=N e)。例如 N=1,000,000 时，预算为 5,000 个请求。质量抽样另设置信区间和样本量，不把 100 个黄金样本的通过率直接当作百万请求质量。

错误预算要绑定行动：预算消耗超过 25% 时冻结非必要变更并提高采样；超过 50% 时暂停高风险发布，优先修复尾延迟和重复副作用；超过 75% 时进入事故模式，允许只做回滚和容量修复；窗口结束时若预算剩余，可安排受控优化实验。阈值是**设计判断**，必须在团队评审中确认。预算只能约束纳入范围内的错误，不能掩盖安全事故、跨租户泄露或不可恢复的数据损坏。

### 26.2.4 约束、假设和未知量

规格文件必须列出假设：高峰到达率 20 请求/秒、平均输入 600 token、平均输出 180 token、最长上下文 4,000 token；租户 A 占 70%，B 占 30%；检索延迟在 p95 为 120 ms；模型副本每个能稳定处理 2 请求/秒。上述数字是**教学假设**。未知量包括峰值突发形状、引用质量、模型冷启动时间、跨区域恢复时间、GPU 抢占概率和真实人工审核耗时。未知量不能被“预计”替代，要放进风险账本并指定验证实验和截止日期。

## 26.3 端到端架构与边界

### 26.3.1 控制平面和数据平面

数据平面路径是：入口网关 → 身份与策略 → 请求路由 → 检索服务 → 推理服务 → 输出校验 → 审计写入 → 流式响应。控制平面管理模型和 tokenizer 注册、提示模板、索引构建、Kubernetes 部署、配额、证书、密钥、观测规则和发布状态。控制平面暂时不可用时，已运行的数据平面应继续使用最后一个经过签名和校验的配置一段时间；新模型、新租户和新索引必须暂停。这个“冻结而不是盲目追新”的模式把控制平面故障的影响限制在变更速度，而不是立即影响所有在线请求。

每个边界声明四件事：输入和版本、超时和取消语义、失败类别、数据保留。检索服务必须接受 deadline 和租户过滤器，不能仅依赖调用方的 HTTP header；推理服务必须知道剩余预算，避免在网关已超时后继续占用 GPU；审计写入必须支持幂等键和重复检测；网关必须传播 trace 采样决策但不把完整 prompt 放入 trace。

### 26.3.2 数据流和版本流

离线数据流从授权工单和知识库导出开始，经过脱敏、去重、语言检测、切分、质量检查和清单发布，生成对象存储中的不可变分片、元数据和删除索引。索引构建读取同一清单，写临时索引，完成校验后发布 manifest。训练或提示优化读取清单摘要，输出模型、tokenizer、配置、评估报告和许可证信息，注册表只允许不可变版本。线上请求携带的索引版本、模型版本和策略版本写入审计，便于回答“为什么这个用户在 14:03 得到这句话”。

版本流与数据流要分开但可关联。索引可以每天更新，模型可能每两周更新，策略可能随法规在数小时内更新。把它们塞进一个“发布版本”字符串会丢失回滚粒度；把它们完全独立又难以重现。推荐使用包含四个引用的 release manifest，并用签名或至少校验和保护：`model_ref`、`tokenizer_ref`、`index_ref`、`policy_ref`。服务启动时检查四者兼容，不兼容则拒绝变为 Ready。

### 26.3.3 资源舱壁和租户隔离

租户 A 的突发不能占满租户 B 的队列、KV cache 或审计配额。入口按租户令牌桶限流，检索和推理各有并发上限，长上下文请求进入独立队列或使用更低优先级，审计写入使用有界缓冲并在超限时阻止“成功”响应。Kubernetes 层用 namespace、NetworkPolicy、ServiceAccount 和资源配额隔离；应用层仍需执行租户过滤，因为网络隔离不等于查询结果隔离。

资源舱壁有代价：总利用率可能下降、短请求不能完全共享批次、调度复杂度增加。**设计判断**：对可能包含敏感数据的租户优先选择硬隔离；对同信任域的租户可以共享模型权重，但仍要隔离缓存键、日志索引和配额。任何“为了 GPU 利用率暂时关闭过滤”的建议都应被视为阻断上线的安全风险。

## 26.4 从需求到容量：用数字检查架构

### 26.4.1 到达率、服务率和排队

设平均到达率为 λ（请求/秒），单副本服务率为 μ（请求/秒），副本数为 (c)，利用率近似为 ρ=λ/(cμ)。当 ρ 接近 1，尾延迟会对突发和服务时间方差高度敏感；因此不能以平均利用率 100% 作为目标。教学基线中 λ=20、μ=2，至少需要 10 个副本才能覆盖平均流量，若目标峰值利用率 0.65，还需 (c ≥ 20/(2×0.65) ≈ 16) 个副本，再加故障余量和滚动发布余量。这里没有计算 batching、缓存、token 长度和 GPU 共享，数字只用来发现明显不可能的计划。

Little 定律 (L=λ W) 连接并发数 L、到达率 λ 和平均等待时间 W。若系统允许最多 100 个在途请求，平均处理时间 0.5 秒，理论稳态吞吐约为 200 请求/秒，但尾延迟和错误会随突发上升；不能把公式当作压测结果。对流式生成，还应分别建模首 token 服务时间和每 token 服务时间，短请求与长请求混合时要按长度分桶。

### 26.4.2 Token、显存与成本

设输入 token 数为 (T_{in})，输出 token 数为 (T_{out})，每 token 计算成本和显存占用取决于模型、精度、批次和 KV cache。容量账本至少记录最大上下文、并发序列数、每序列页数、权重驻留、临时激活、通信缓冲和碎片余量。不要只拿模型参数乘字节数；量化权重、运行时工作区、CUDA graph、通信和 allocator 碎片都可能成为峰值。

成本模型把固定成本、变动成本和风险成本分开。固定成本包括节点、控制面和日志存储；变动成本包括 GPU 秒、CPU 秒、对象存储、跨区流量和外部模型调用；风险成本包括错误重试、空转保温副本、数据恢复和事故值班。每个请求写出估算的 GPU 毫秒和 token，按租户汇总，与财务账单抽样对账。**测量**必须声明价格区域、折扣、空闲时间和是否包含网络费用，不能把公开列表价当成最终成本。

### 26.4.3 容量实验设计

实验要逐层加压：固定输入输出长度测试单副本服务率；固定到达率增加并发观察 p50/p95/p99；混合长度测试 KV 竞争；故障中减少一个副本测量错误预算消耗；滚动发布同时观测 Ready 时间和队列积压。每次改变一个主要变量，记录版本、随机种子、请求分布、暖机策略和清理动作。CPU toy 只能验证状态逻辑和计数关系，不能测 GPU kernel、网络拓扑或真实模型质量。

## 26.5 数据、训练和评估闭环

### 26.5.1 数据契约和血缘

数据契约写明来源、授权、字段、保留期、删除传播、质量阈值、schema 版本和责任人。原始工单进入受控区域后先脱敏，生成训练视图和检索视图；两者不能因为“都是文本”而共享同一权限。每个分片 manifest 包含 URI、大小、行数、校验和、schema、语言分布、脱敏规则版本和父数据集引用。重复检测既用于节省成本，也用于防止同一答案同时出现在训练集和评估集造成虚假的高分。

血缘必须可从线上答案反向追到索引文档，再追到清洗规则和原始授权批次；若删除请求发生，能找到受影响的索引、缓存、训练派生物和备份。删除链路往往比写入链路复杂，必须成为阶段门的一部分。**设计判断**：在不能完成删除传播证明前，宁可把数据限制在检索而不是训练，并在产品规格中明确这个限制。

### 26.5.2 训练与提示优化的可复现性

Capstone 不要求训练大模型，但要求把训练或提示优化当作可重放作业：配置、代码提交、依赖锁文件、随机种子、数据 manifest、机器资源、日志、检查点 manifest 和评估集都进入实验记录。训练器在开始时打印输入摘要，结束时写出最佳 checkpoint 和停止原因。中断恢复要验证模型、优化器、学习率调度、数据游标和随机状态是否一致；只恢复权重不一定等价于继续训练。

模型注册阶段至少检查结构、许可证、tokenizer 兼容、恶意代码风险、偏差和安全回归。模型分数低于门槛不等于不能部署，可以只做离线分析；分数通过也不等于可以自动外发。训练数据中若有用户敏感信息，评估报告必须说明是否做了成员推断、记忆泄露或提示注入测试。

### 26.5.3 离线评估和在线质量

黄金集按语言、长度、租户策略、难度和拒答场景分层。报告均值之外，还要给置信区间、最差分层、格式合法率、引用覆盖率和安全误拒/漏拒。在线只采样经过授权的匿名事件，使用影子流量或人工审核比较新旧版本。若新模型使引用覆盖率提高但首 token p99 超预算，应按规格讨论是否降级，而不是只看单一分数。

## 26.6 推理、发布和 Kubernetes 运行面

### 26.6.1 推理路径和超时预算

把总 deadline (D) 分给身份与策略 (d_a)、检索 (d_r)、模型首 token (d_p)、生成 (d_g)、校验与审计 (d_v)，并为网络与排队保留余量 (d_q)，要求 (D ≥ d_a+d_r+d_p+d_g+d_v+d_q)。服务收到 deadline 后向下游传播剩余时间，不能每层重新从零计时。重试只在可安全重试的错误类别进行，使用指数退避和抖动，并受每请求重试预算限制。模型生成已经消耗大量 token 后再重试，可能比快速降级更糟。

流式响应需要定义取消语义：客户端断开时取消生成、释放 KV 页并记录取消原因；若取消未传播，后端会继续工作，指标却把请求当作成功。首 token、每 token 间隔和完整响应分开计量。对于检索失败，可返回带 `degraded=true` 的无引用模板或转人工；对于策略服务失败，默认拒绝而不是绕过。

### 26.6.2 Kubernetes 对象与升级顺序

教学部署可包含 Deployment、Service、ConfigMap、Secret、HorizontalPodAutoscaler、PodDisruptionBudget、NetworkPolicy 和 ServiceAccount。生产集群需根据版本和插件验证字段语义，不能从示例复制资源限制。启动探针覆盖模型加载和 tokenizer 检查；就绪探针覆盖可接受请求的条件；存活探针避免在长 GC 或 GPU 暂时繁忙时误杀。模型 Pod 使用明确的 requests/limits、拓扑约束和节点标签，避免在不兼容 GPU 上调度。

升级顺序是先发布兼容的 schema 与观测，再预热新模型副本，执行影子或小流量，确认错误预算和质量门，逐步切换路由，最后清理旧版本。回滚不仅是镜像回退，还要恢复模型、tokenizer、提示、索引和策略 manifest。若新旧版本共享缓存，必须验证缓存键包含版本，否则回滚可能继续返回新模型的结果。

### 26.6.3 发布策略和停止条件

Capstone 采用四阶段：离线验证、影子流量、5% 金丝雀、全量。每阶段有自动停止条件：SLO 预算消耗速率超过基线两倍、跨租户过滤失败、审计写入缺口、质量分层显著回归、成本每请求超过上限、或观测管道丢失。停止条件触发时先冻结流量，再保存证据和回滚，而不是继续“看一会儿”。**事实**：许多编排器提供滚动更新机制；**设计判断**：机制是否足以满足模型版本与数据版本一致性，必须由团队额外验证。

## 26.7 可观测性、可靠性、安全与成本的共同闭环

### 26.7.1 一套跨组件的证据语义

统一事件字段：`trace_id`、`span_id`、`request_id`、时间、租户策略域、阶段、结果类别、错误类别、版本四元组、资源桶和幂等键摘要。metrics 聚合低基数维度，logs 保存离散事实，traces 关联时序，profiles 解释资源成本。高基数原文和敏感字段进入受控存储，且有保留期。每条 SLO 规则都指向一个查询、一个告警阈值和一个运行手册步骤；否则告警只是噪声。

观测自身也有容量和安全预算。日志管道拥塞时优先保留安全、审计和错误事件，丢弃调试采样；指标后端不可用时应用仍应能完成关键请求，但应发出观测缺失告警。不要把用户提示词放进 label，也不要把密码、token、完整客户工单写进 trace。观测系统能看见更多，不代表任何人都应该能看见。

### 26.7.2 可靠性机制

重试、超时、熔断、舱壁、限流、优雅降级和检查点共同构成恢复层。每个机制都写出状态和边界：什么错误可重试，多少次，何时打开熔断，半开如何探测，降级结果如何标记，幂等键存多久，检查点 manifest 怎样原子发布。对审计写入使用幂等键，避免“客户端超时但服务器成功”造成重复；对模型生成不要盲目重试所有 5xx，因为 GPU 队列可能因此雪崩。

灾备文档写明 RTO、RPO、依赖顺序、密钥和 DNS、数据驻留、恢复演练证据。恢复一个服务但没有模型权重、tokenizer 或策略版本，不算恢复。每次故障演练都记录预期影响、停止条件、操作权限、回滚和清理；CPU toy 的故障注入不会触及真实租户或真实凭证。

### 26.7.3 安全和供应链门

身份层采用最小权限服务账号和短期凭证，密钥不进镜像、不进日志。镜像、模型、tokenizer、索引和配置都要有来源、校验和、许可证和漏洞扫描记录。构建环境固定依赖并生成 SBOM，部署前验证签名或哈希。模型输入可能包含提示注入，工具调用采用显式允许列表、参数 schema、沙箱和人工批准；模型生成的“请上传密钥”不是授权。

租户隔离要覆盖缓存、向量过滤、对象路径、日志、备份和支持工程师查询。应急调试需要 break-glass 流程、审批、时间限制和事后审计。对高影响领域，系统只能提供辅助建议，必须保留人工决定权。安全门失败时，任何“为了上线先关掉过滤器”的变更都应被拒绝并记录为阻断风险。

### 26.7.4 成本闸门

每个阶段提交成本估算与实际账单抽样。容量计划包含常态、副本故障、滚动发布、峰值突发和灾备保留。设置单租户 token 配额、最大上下文、最大生成长度和并发上限；超过限制时返回可解释的 429 或转人工。缓存和批处理可以降低单位成本，但可能增加数据新鲜度风险、租户混淆风险和尾延迟。成本下降只有在 SLO、质量和安全证据不退化时才算成功。

## 26.8 项目规格包、阶段门与证据账本

### 26.8.1 交付物目录

每组学生或工程团队必须提交一个可从干净检出复现的目录，至少包含：

1. `brief.md`：用户旅程、非目标、假设、SLO、预算、负责人。
2. `architecture.md`：控制面/数据面、依赖图、数据流、版本流、故障边界。
3. `contracts/`：请求 schema、错误语义、幂等、超时、租户过滤和删除契约。
4. `data-card.md` 与 `manifest.json`：来源、授权、质量、脱敏、血缘、保留期。
5. `model-card.md`、评估报告和注册 manifest：模型、tokenizer、提示、索引、策略引用。
6. `deploy/`：Kubernetes 资源或 CPU fallback 配置，含资源、探针、PDB、网络策略。
7. `runbook.md`、`rollback.md`、`chaos-plan.md`：告警、止损、恢复、演练和清理。
8. `capacity.csv`、`risk.csv`、`evidence.csv`：容量、风险和证据账本。
9. `postmortem.md`：时间线、影响、根因、促成因素、修复、验证和未决行动。
10. `ch26_capstone_lab.py` 的运行输出与环境摘要，标明这是教学模拟。

### 26.8.2 阶段门 G0 至 G5

**G0 需求门**：通过标准是用户旅程可测试，非目标清楚，SLO 有分母和排除项，风险负责人已命名。证据是 brief、接口草案和一次威胁建模。若仍在争论“智能”含义，不得进入实现。

**G1 数据门**：通过标准是授权、脱敏、质量、血缘、删除和 manifest 可验证。证据是数据卡、质量报告、抽样和删除演练。缺失删除传播时，只允许使用合成或低敏感数据。

**G2 模型门**：通过标准是代码、数据、配置、依赖、随机种子和检查点可重放；离线质量和安全回归满足门槛。证据是实验记录、评估报告、模型卡、检查点校验和。一次 notebook 成功运行不足以过门。

**G3 服务门**：通过标准是请求契约、超时、重试、幂等、容量、探针、观测、降级和回滚通过测试。证据是负载报告、故障注入、仪表盘截图或查询、回滚日志。CPU toy 可证明状态逻辑，不可证明 GPU 产能。

**G4 安全与成本门**：通过标准是身份、隔离、秘密、供应链、滥用控制、成本上限和数据驻留有责任人。证据是扫描报告、最小权限检查、成本模型、账单抽样和 break-glass 审计。

**G5 运行门**：通过标准是金丝雀、全量、值班轮换、灾备演练和复盘模板就绪。证据是发布记录、错误预算决策、RTO/RPO 演练、行动项追踪。若没有人知道告警响起后做什么，不能称为“可运营”。

### 26.8.3 三本账：容量、风险、证据

容量账本列出资源、需求、余量、测量来源、增长假设和触发阈值。例如 GPU 副本、CPU、显存、对象存储、索引大小、队列并发、日志写入和跨区流量。每行注明是测量还是推断，避免把估算伪装成事实。

一个最小的容量账本可以先长这样，数值是教学假设，`来源` 列不能省略：

| 资源 | 基线需求 | 目标余量 | 来源标签 | 触发动作 |
|---|---:|---:|---|---|
| 推理副本 | 峰值 20 req/s ÷ 2 req/s/副本 = 10 | 故障 1 副本、发布 2 副本 | 推断，待压测 | 利用率连续 10 分钟 >0.65，扩容 |
| KV cache | 4,000 token 上下文、每副本 32 并发 | 20% 碎片余量 | 测量，短请求覆盖不足 | 超过 80% 拒绝长上下文并告警 |
| 审计队列 | 20 事件/s | 5 分钟缓冲 | 设计判断 | 积压 >3 分钟，停止宣称完整成功 |
| 日志写入 | 每请求约 2 KB，峰值 40 req/s | 2 倍突发 | 估算 | 采样调试日志，保留安全与审计事件 |

风险账本不只记录“风险存在”，还要记录怎样知道它发生以及谁负责关闭。示例：

| 风险 | 影响/可能性 | 早期信号 | 缓解与应急 | 负责人/截止 |
|---|---|---|---|---|
| tokenizer 与模型不兼容 | 错答、启动失败/中 | 启动兼容性检查、格式错误率 | 禁止 Ready；回滚完整 manifest | 模型负责人 / G2 |
| 索引过期 | 引用错误/高 | 新鲜度 SLI、版本不匹配 | 切换旧索引并标记降级；重建后原子发布 | 数据负责人 / 每日 |
| 写后超时造成重复审计 | 合规与成本/中 | 幂等冲突率、物理/逻辑计数差 | 相同键写后查询；未知状态转人工 | 服务负责人 / G3 |
| 日志包含工单原文 | 隐私泄露/中 | 敏感字段扫描、抽样审计 | 脱敏、缩短保留期、撤销调试权限 | 安全负责人 / G4 |

证据账本把发布主张拆成可以被第三方复核的条目：

| 主张 | 标签 | 证据位置 | 覆盖范围 | 缺口/有效期 |
|---|---|---|---|---|
| 40 个请求中同键只写一次 | 测量 | `ch26_capstone_lab.py` 输出 | CPU toy、固定种子 | 不覆盖分区数据库，需集成测量 |
| p95 首 token <2 s | 测量 | 压测报告链接和查询 | 2,000 个短请求、暖机后 | 长上下文和节点故障未覆盖 |
| 探针不会误杀长生成 | 设计判断 | runbook 条款 | 目标 K8s 版本待演练 | 需在 GPU 节点注入 OOM |
| 删除传播到索引和缓存 | 未知→待验证 | 删除演练记录 | 合成数据 | 备份和跨区副本尚未验证 |

账本中的“未知”是有效状态。只有补上可重放的实验、审查记录或生产观测，才能将它改为“部分证实”或“已证实”；不能通过把文字改成绿色来关闭风险。

风险账本列出风险描述、影响、可能性、检测信号、缓解、应急、负责人、截止日期和残余风险。示例：模型更新与 tokenizer 不兼容；检索索引过期；客户端重试产生重复审计；日志泄露敏感文本；GPU 抢占导致 RTO 超时；供应链包被替换。风险关闭必须有证据链接，不能只写“已关注”。

证据账本把每个主张绑定到测试、文档或实验：主张、标签（事实/测量/推断/设计判断）、证据位置、环境、版本、有效期、审查人和缺口。若“p95 小于 2 秒”只在 100 个短请求上测量，证据条目必须写明覆盖不足。发布委员会根据证据账本决定“已证实、部分证实、未知、阻断”，而不是根据演示效果决定。

## 26.9 CPU-only 可运行实验

### 26.9.1 实验目的和边界

仓库中的 `ch26_capstone_lab.py` 是 L0/L1 教学模拟，使用 Python 3.11+ 标准库，不需 GPU、容器、网络或外部服务，预计运行少于 2 秒。它模拟四件事：有限重试和熔断、检索降级、按幂等键写审计、带临时文件和 manifest 的检查点发布/恢复，并输出 G0-G4 阶段门和摘要。脚本明确打印 `teaching_simulation: true`。它不能证明真实模型质量、Kubernetes 调度、GPU 显存、网络尾延迟、供应商可用性、合规或生产成本。

运行命令：

```bash
python3 ch26_capstone_lab.py --requests 40 --seed 7 --fault all
```

参数 `--fault` 可选 `none`、`retrieval`、`model`、`audit`、`checkpoint`、`all`；`--seed` 固定随机序列，`--requests` 改变样本数。先运行 `none` 建立基线，再运行单一故障，最后运行 `all`。保存完整 JSON 输出、Python 版本、操作系统、提交哈希和命令行，不要只复制屏幕上的几个数字。

### 26.9.2 代码机制

`run_requests` 为每个请求分配逻辑 ID。检索故障允许最多两次重试，第三次转为有界降级；模型故障重试三次后失败并让熔断器累计失败；审计写入使用 `req-{id}` 幂等键，即便模拟客户端在模糊超时后再次提交，物理写入也只增加一次。熔断器在连续失败达到阈值时进入 OPEN，冷却后 HALF_OPEN，成功则回到 CLOSED。结果同时记录逻辑成功、降级、重试、延迟和物理写次数，帮助比较“请求看似成功”和“副作用发生几次”。

`checkpoint_drill` 先写 `*.tmp`，再通过同一文件系统的替换操作发布 manifest。故障模式在 step=30 发布前退出，恢复器只接受有完整校验字段的最终 manifest，并回退到最新完整 step。这个过程展示原子发布和 RPO 的概念，但不覆盖对象存储一致性、跨区域复制、进程崩溃时的 fsync 语义、分片 checkpoint 或密钥可用性。

### 26.9.3 预期观察与解释

基线运行应显示失败为 0 或接近 0、降级为 0、重试很少，物理审计写数等于逻辑成功数。`retrieval` 会增加延迟和 `degraded` 数，但不应增加重复审计。`model` 会出现失败，连续失败可能打开熔断，后续请求收到 `circuit_open`，说明熔断限制了依赖风暴，却不等于系统可用。`audit` 会增加逻辑重试，但物理写数仍不超过每个幂等键一次。`checkpoint` 应恢复到 step=20，RPO 以 step 差表示。具体数字随随机种子和参数变化，不能在文档中承诺固定值。

示例输出（仅为一次本地测量，不能当作规范）可能包含：请求 40、成功 34、失败 6、降级 12、重试 61、物理审计写 34、熔断最终 CLOSED；检查点发布 [10,20]、有效 [10,20]、恢复 step=20。若读者看到不同数字，先检查 Python 版本、命令、随机种子和脚本是否被修改，再解释机制。测量的价值在于比较干预前后方向，而不是背诵数字。

### 26.9.4 扩展实验

(1) 把熔断阈值从 3 改为 1、5，比较误熔断和失败放大；记录允许请求数和错误预算。

(2) 令审计写入在“写后响应丢失”时重试，比较有无幂等键的物理写入次数；用同一请求 ID 重放 100 次。

(3) 将 checkpoint 临时文件写入半截 JSON，验证恢复器拒绝损坏 manifest；再加入校验和字段，比较恢复行为。

(4) 增加两个租户和每租户令牌桶，观察高流量租户是否能耗尽共享队列；写出舱壁代价。

(5) 把模型服务时间从常数改成长尾分布，绘制 p50、p95、p99 和重试率，说明为什么平均值不能代表 SLO。

(6) 将 `--requests` 增至 10,000，测量 CPU 时间和 JSON 大小；这只是模拟规模，不是生产压测。

## 26.10 故障演练剧本

每个演练先写稳态假设、影响范围、授权、停止条件和清理步骤，演练后把结果放入证据账本。未经批准不得在真实租户、真实凭证或共享生产集群注入故障。

### 演练 A：检索索引过期

稳态假设是索引版本与发布 manifest 相同，文档新鲜度小于 24 小时。将检索服务切换到旧索引，保持模型和策略不变，观察引用覆盖率、新鲜度、降级标记、缓存命中和审计版本。成功标准不是“HTTP 200”，而是系统检测版本不匹配或明确标记降级，且不会把旧引用伪装成新引用。恢复动作是重新构建、校验并原子发布索引，逐步切回。

失败案例：团队只监控检索延迟，旧索引更小所以 p99 变好，事故持续三天。复盘根因是没有把新鲜度和索引版本纳入业务 SLI。修复包括版本检查、引用时间戳、过期告警和金丝雀查询；保留延迟指标，但不再把它当作完整健康证明。

### 演练 B：模型副本 OOM 或长尾

稳态假设是长上下文请求的显存峰值在容量账本内。使用合成的超长输入或 CPU toy 的长尾服务时间注入，观察 admission control、队列长度、取消传播、p99、重试率和 GPU 页池。停止条件包括错误预算消耗超过演练预算、队列超过上限、日志管道拥塞或任何跨租户信号。

恢复动作是拒绝超长请求、切换小模型或摘要模式、扩容兼容节点、回收泄漏副本，最后验证取消后的资源已释放。不要通过无限增加超时或关闭内存限制“修复”问题。复盘要回答：哪一个长度桶越界？探针为何没有提前发现？容量模型是否包含 allocator 碎片？

### 演练 C：审计写入超时与重复

稳态假设是一次逻辑请求至多有一个审计事件。让存储在写入成功后丢弃响应，客户端按相同幂等键重试；再用不同键重试，比较结果。成功标准是同键只产生一条物理记录，事件状态可以从 `UNKNOWN` 查询为 `COMMITTED` 或 `NOT_COMMITTED`，而不是盲目再写。若审计无法确认，系统应把答案标记为未完成或转人工，不能宣称完整成功。

失败案例：团队把每个 HTTP 500 都重试三次，月末审计记录数比工单数多 2.4 倍。根因是把传输失败等同于业务未执行，且没有幂等键。修复是幂等表、写后查询、有限重试和重复率指标。教学脚本只验证键集合逻辑，不能证明数据库唯一约束在分区和复制故障下的行为。

### 演练 D：控制平面不可用

短时间阻断配置发布和扩缩容通道，保持已运行数据平面。观察现有副本是否继续服务、证书和密钥何时过期、旧配置是否被清理、告警是否能通知值班。成功标准是服务在声明的冻结窗口内继续满足降级 SLO，新部署和高风险变更被拒绝，恢复后控制面不会覆盖人工修复。

失败案例：控制面恢复时自动把过期的 ConfigMap 推回所有副本，导致安全策略回退。根因是没有不可变 release manifest 和版本单调性检查。修复包括签名版本、回滚保护、双人审批和恢复演练。

### 演练 E：跨租户数据访问尝试

在隔离环境中发送带有租户 A ID 但查询过滤器指向 B 的请求，检查授权、向量过滤、缓存、日志和审计。成功标准是请求被拒绝，响应不透露 B 是否存在，日志不包含 B 的原文，告警能关联到策略版本。任何真实数据泄露都应立即停止实验并按安全事件流程处理；不要为了“验证监控”复制真实客户文本。

## 26.11 失败诊所：看似合理的方案为何失败

### 案例 1：只追求平均延迟

方案把平均响应时间从 1.8 秒降到 1.2 秒，宣布性能提升。实际上长上下文 p99 从 8 秒升到 40 秒，客户端超时后后台生成仍继续，GPU 利用率和成本上升。错误是优化平均值而忽视尾部、取消和 token 长度分层。修复是按输入/输出长度分桶，分别预算 TTFT、ITL、完整响应和取消清理。

### 案例 2：把重试当可靠性

团队给检索、模型和审计各加三次重试，短暂网络抖动时成功率看似提高，但队列和 GPU 负载成倍增长，依赖恢复后仍被重试风暴压垮。正确做法是传播 deadline，按错误类别决定是否重试，使用指数退避、抖动、重试预算和熔断；对副作用使用幂等键。重试是资源放大器，不是免费可用性。

### 案例 3：蓝绿发布但版本不完整

蓝色和绿色 Deployment 同时存在，路由切换很快；但两者共享提示模板和 Redis 缓存，绿色模型读取了蓝色索引的 embedding，质量下降且无法复现。修复是将模型、tokenizer、提示、索引和策略作为 release manifest 的引用集合，缓存键包含所有兼容版本，路由切换前执行跨版本集成查询。

### 案例 4：安全扫描通过却仍会泄露

镜像漏洞扫描全绿，但支持工程师可通过 debug endpoint 读取完整 prompt，且日志保留 90 天。扫描只覆盖已知依赖漏洞，不覆盖权限、数据最小化、日志策略和业务越权。修复需要威胁建模、动态授权测试、敏感字段检测、break-glass 审计和保留期验证。

### 案例 5：成本优化破坏恢复

为了省 GPU 费用，把副本降至刚好覆盖平均流量，且关闭 warm standby。节点故障时恢复需 25 分钟，超过 RTO；自动扩容还因模型下载和镜像拉取拥塞无法及时启动。成本决策必须把故障余量、缓存、镜像和模型预热纳入容量模型，比较常态节省与错误预算和停机损失。

### 案例 6：演示通过等于可交付

Demo 使用 20 条精心挑选的短工单，固定模型、固定索引、无并发、无拒答。上线后出现长文本、注入、删除请求、租户切换和客户端取消，所有未测状态都暴露。Capstone 要求阶段门、故障演练和证据账本，就是为了让团队正视未覆盖空间。

## 26.12 取舍与被拒绝的替代方案

**单体服务 vs 多服务**：单体降低网络和发布复杂度，适合早期验证；但租户隔离、独立扩容和故障舱壁较弱。Capstone 选择逻辑分层、物理上可先单体的模块化实现，并要求契约先于拆分。

**同步检索 vs 异步队列**：同步路径简单、用户反馈快；异步适合长任务和批量重建，但需要状态、重试、重复消费和通知。在线答案使用同步并设 deadline，索引构建和评估使用异步作业。

**共享大模型 vs 每租户模型**：共享权重成本低、运维简单，但策略和质量边界更难；每租户模型隔离强却带来显存、发布和评估成本。教学项目共享模型权重，按租户隔离缓存、过滤和配额，不把共享视为无条件安全。

**缓存答案 vs 不缓存**：缓存可降低延迟和成本，但会带来新鲜度、撤回和租户混淆风险。只有当缓存键包含租户、策略、模型、索引和输入规范化摘要，且有 TTL 与删除传播，才允许在低风险查询启用。

**CPU fallback vs 直接失败**：CPU fallback 提高可达性，却可能质量较低、成本高或泄露更多上下文。仅对明确允许的降级场景启用，响应必须标记并纳入质量 SLO；安全和审计依赖失败时直接拒绝或转人工。

**供应商托管服务 vs 自建**：托管服务可能提供更快上线和专业运维，但数据驻留、版本锁定、退出路径和账单可见性要审查。自建不自动更安全，需承担补丁、容量、值班和灾备。Capstone 要求在架构决策记录中写出数据、故障、成本和退出的比较，而不是按流行程度选工具。

## 26.13 论文、标准和仓库的综合阅读

阅读一个系统不从项目名开始，而从机制问题开始：请求如何进入、状态在哪里、资源怎样计量、失败如何传播、版本怎样回滚、证据是什么。对论文，先读问题定义、工作负载、基线、故障假设和评价指标，再读实现细节；对仓库，先找配置 schema、测试、错误处理、发布脚本和默认值，再看 README 的性能数字。性能图上的提升如果没有硬件、批次、输入长度、软件版本和成本，就不能直接迁移到本项目。

把来源分为四类：规范和标准回答语义，官方文档回答接口和版本行为，成熟实现与测试回答机制，事故报告回答真实失败模式。每个来源在证据账本中写“它支持什么”和“它不支持什么”。例如 Kubernetes 探针文档能支持探针状态语义，不能单独证明模型质量；一篇批处理论文能支持某种吞吐机制，不能证明你的 tokenizer、GPU 和租户流量会得到同样增益。

## 26.14 理解检查（含答案）

### 检查一：为什么 HTTP 200 不足以计算业务成功？

**答案**：200 只说明传输层形成响应，无法证明策略通过、引用新鲜、输出结构合法、审计只写一次或质量满足门槛。业务成功必须按事先定义的复合事件计数，并声明分母和排除项。

### 检查二：SLO 为 99.5%，本月纳入请求 2,000,000，错误预算是多少？

**答案**：误差比例 (e=1-0.995=0.005)，预算 (B_{max}=2,000,000×0.005=10,000) 个请求。预算只适用于纳入范围的实时契约错误，不包括跨租户泄露等必须单独阻断的安全事件。

### 检查三：为什么平均利用率 100% 不是容量目标？

**答案**：当 ρ 接近 1，任何服务时间方差、突发、故障或滚动发布都会使队列和尾延迟急剧上升，还没有故障余量。应按目标峰值、SLO、批处理和降级策略确定利用率上限，并用测量校准。

### 检查四：写入超时后为什么不能无脑重试审计？

**答案**：超时只说明调用方未知提交结果，服务器可能已经成功写入。无幂等键的重试会产生重复副作用；应使用幂等键、写后查询或唯一约束，并把 UNKNOWN 状态纳入恢复语义。

### 检查五：模型回滚为什么可能仍返回新模型结果？

**答案**：共享缓存键、提示模板、索引或路由状态可能仍引用新版本。回滚必须恢复完整 release manifest，清理或隔离缓存，并验证跨版本集成查询和审计版本。

### 检查六：CPU toy 证明了哪些事，没证明哪些事？

**答案**：它证明了在给定代码和随机种子下，有限重试、熔断、幂等集合和临时文件发布的状态转移可被观察。它没有证明真实模型质量、GPU 产能、Kubernetes 调度、对象存储一致性、网络故障率、供应商 SLA 或生产合规。

## 26.15 练习：从回忆到独立交付

1. **回忆**：列出工单助手一次请求的八个阶段，并为每阶段写一个可观测事件和一个可取消点。
2. **推导**：高峰 35 请求/秒、单副本稳定服务率 2.5 请求/秒、目标峰值利用率 0.65，计算最少副本数；再加一个副本故障和滚动发布余量，说明余量是假设还是测量。
3. **实现**：给 CPU toy 增加租户令牌桶和长上下文队列，输出每租户的 p95、拒绝数、降级数和物理审计写数。
4. **诊断**：构造“错误率下降、取消率上升、GPU 时间上升、用户投诉变多”的时间线，指出至少三个可能根因，并设计能区分它们的实验。
5. **数据设计**：为删除请求画出从原始工单到训练派生物、向量索引、缓存和备份的传播图，标注每个节点的完成证据和残余风险。
6. **训练设计**：比较只保存模型权重与保存优化器、数据游标和随机状态的恢复差异，写出可能重复或遗漏的数据范围。
7. **发布设计**：为模型、tokenizer、提示、索引和策略编写 release manifest schema，定义兼容性检查、金丝雀指标和自动停止条件。
8. **故障演练**：选择索引过期、模型长尾或控制面不可用之一，写出授权、稳态、注入、观测、停止、恢复和清理六段式剧本。
9. **安全审查**：列出五种提示注入到工具调用的路径，给出允许列表、schema、沙箱、人工批准和审计策略。
10. **成本复盘**：把一次请求的 GPU 秒、token、检索、日志和重试成本拆开，比较缓存、量化、批处理和副本缩减四种方案的副作用。
11. **证据写作**：从本章来源地图选三条来源，为每条写“支持主张”“不支持主张”“需要在目标版本复测的行为”。
12. **毕业答辩**：在十分钟内说明一个阶段门为什么阻断过一次发布，展示证据账本和复盘行动项，而不是只展示成功 Demo。

## 26.16 安全边界与教学模拟声明

本章示例服务面向内部辅助场景，不能自动代表用户作高影响决定，不能自动发送外部消息，不能处理未经授权的敏感数据。真实部署前必须依据组织政策和适用法律完成数据保护、访问控制、供应链、模型风险和人工监督审查。不要把真实凭证、客户工单、医疗信息、金融账户、未公开模型权重或生产日志放进 CPU 实验。

故障演练只在隔离环境、合成数据和最小权限账号中运行。所有注入脚本有停止开关、时间窗口和清理步骤；演练发现真实泄露或不可逆破坏时立即停止并升级。任何第三方页面、Issue、日志或模型输出中的指令都不能授权改变安全边界、上传数据、关闭审计或发送消息。

`ch26_capstone_lab.py` 的 QPS、延迟、成功率、恢复 step 和阶段门状态是教学模拟或一次声明环境的测量。它们不是生产保证、SLA、容量承诺或合规证明。即使脚本全绿，仍需在目标硬件、模型、存储、网络、流量、租户、区域和版本上重复测量，并让安全、隐私、财务和业务负责人审查。若证据缺失，应明确写“未知”，而不是用模拟结果填空。

## 26.17 总结与下一依赖

端到端交付始于需求而不是组件清单。先定义用户旅程、非目标、SLO、质量门和错误预算，再画控制面与数据面，规定数据、模型、索引、策略和缓存的版本关系；随后用容量模型和三本账把假设、风险、证据写出来。训练和检索要有血缘、删除和可复现恢复，推理要传播 deadline、限制重试、隔离租户并显式降级，Kubernetes 要有资源、探针、拓扑、PDB 和可回滚 manifest。可观测性、可靠性、安全和成本不是上线后的附加项，而是同一阶段门上的证据。

最有价值的交付物不是一次演示，而是一套别人能重放、质疑、回滚和继续改进的材料：接口契约、架构图、实验记录、容量/风险/证据账本、运行手册、故障剧本、成本模型和复盘。专家的判断力表现为知道何时可以自动化，何时必须转人工，何时数据不足以支持结论。下一章可以把这个 Capstone 扩展到更大规模的训练和服务，但规模放大不会改变基本顺序：先契约，再证据，再容量，再故障，再发布。

### 可复现记录模板

- 命令：`python3 ch26_capstone_lab.py --requests 40 --seed 7 --fault all`
- 环境：Python 版本、操作系统、CPU 型号、内核、git 提交哈希。
- 输入：请求数、随机种子、故障类型、模拟服务时间和阈值。
- 输出：完整 JSON、阶段门、请求摘要、重试/降级/失败、物理写入、检查点恢复 step。
- 解释：基线与干预、预期方向、实际方向、机制、异常和下一实验。
- 限制：CPU toy 不覆盖 GPU、网络、真实模型、Kubernetes、对象存储、租户数据、合规和生产 SLA。

完成门禁：正文（排除 frontmatter、代码和 URL）不少于一万汉字；至少一个失败案例看起来健康；包含六个有答案的理解检查和五类练习；CPU 实验从干净检出可运行并记录预期观察；阶段门、容量/风险/证据账本、发布、回滚、故障演练、安全边界和来源地图齐全；每项生产主张都标明事实、测量、推断或设计判断，并写出尚未证实的部分。
