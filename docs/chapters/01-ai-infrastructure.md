# 第1章　什么是 AI Infrastructure：从模型到可运行系统

> 本章给零基础读者一条通往专家的路线：先把“模型”放回真实系统，再用可观测的因果链解释速度、成本和故障。文中会明确标注事实、机制、测量、推断和设计判断，避免把经验当定律。

## 1.1 先问一个朴素问题：为什么“模型能跑”还不够

很多教程在最后一行代码打印出一个分类标签或一段文本，就宣布推理完成。真实团队却会继续追问：这段代码能不能同时服务一百个用户？高峰期的第九十九个请求要等多久？输入变长十倍，显存、内存和账单怎么变？模型权重更新后，旧请求会不会读到一半的新版本？某块加速卡降频时，系统会不会悄悄变慢而没有告警？

[事实] 模型文件、推理运行时、操作系统、网络、存储、监控和发布流程共同决定一次请求的结果与代价。仅仅验证“输出大致正确”，不能证明系统具备可用的延迟、吞吐、成本和可靠性。

[机制] 一个请求通常经历排队、鉴权、路由、数据预处理、批处理等待、模型前向计算、后处理、序列化和网络传输。任何一段都可能成为瓶颈；加速模型计算只会缩短其中一段，甚至会暴露下一段更慢的环节。

[设计判断] 学习 AI Infrastructure（AI 基础设施）时，最有效的起点不是背硬件型号，而是画出“请求从哪里来、经过哪些状态、最后在哪些计算单元上执行”的链路。沿链路提问，才能把抽象模型变成可运行、可测量、可诊断的服务。

本章的目标有四个：

这也是本章的问题动机：把“模型能运行”与“服务可承诺”之间的空白变成一组可观察、可实验、可复盘的工程问题。

1. 建立“模型到系统”的分层词汇，能区分控制面和数据面。
2. 用工作负载分类选择合理指标，知道何时关注首 token、何时关注总吞吐。
3. 用 Little's Law、Amdahl 定律和 Roofline 模型形成数量级直觉，并理解它们的边界。
4. 亲手设计一个 CPU 本地推理服务实验，记录数据、分析故障，而不是宣称未经测量的结果。

## 1.2 AI Infrastructure 的工作定义

[设计判断] 在本书中，AI Infrastructure 指“让模型在真实约束下持续运行的软硬件与操作系统”：它连接模型资产（权重、词表、配置、适配器）和用户可调用的接口（API、批处理、流式通道、作业队列）。它不等于 GPU 集群，也不等于某一家云厂商的产品目录。

可以把系统看成五层：

- **模型层**：网络结构、权重、分词器、提示模板、量化参数和安全策略。
- **运行时层**：算子实现、图优化、内存分配、批处理、并行策略、编译缓存。
- **资源层**：CPU、GPU、NPU、内存、显存、磁盘、网络、时钟和功耗。
- **平台层**：容器、编排、调度、服务发现、配置、身份、发布和回滚。
- **运维层**：指标、日志、追踪、告警、容量规划、事故响应和成本归因。

[事实] 这些层经常由不同团队维护，但请求的行为跨越所有层。一次延迟回归可能来自提示长度变化（模型层）、内核选择变化（运行时层）、CPU 降频（资源层）、节点亲和性变化（平台层）或采样器日志增加（运维层）。

[机制] 层次不是严格的单向流水线。运行时会反过来限制模型可用的精度与上下文长度；平台调度会改变批大小和并发度；运维采集会消耗 CPU 和网络。基础设施设计的难点在于这些反馈回路，而不是层名本身。

## 1.3 控制面与数据面：谁决定“做什么”，谁真正搬运数据

### 1.3.1 控制面

[定义] 控制面负责声明和改变系统状态：部署哪个模型版本、给多少副本、使用哪类硬件、何时扩缩容、如何分流流量、哪些指标触发回滚。它通常处理低频但影响范围大的操作。

典型控制面对象包括：模型注册表中的版本、服务部署规格、节点标签、队列优先级、限流规则、密钥和策略、发布批次。控制面故障常见表现是“新配置没有生效”“部分节点仍运行旧镜像”或“自动扩容反复抖动”。

### 1.3.2 数据面

[定义] 数据面负责处理用户实际请求：接收字节流、解析输入、排队、选择模型副本、执行前向计算、返回结果并记录请求级指标。它处在高频路径上，任何额外的锁、拷贝或网络跳转都会累积。

[机制] 控制面通过配置、调度和发布影响数据面；数据面通过健康状态、利用率和错误率反馈给控制面。两者的故障模式不同：控制面慢，可能导致新副本迟迟起不来；数据面慢，则用户直接看到延迟上升。把两类指标混在一张图上，排障时容易误判。

[测量] 建议至少分别记录：控制面变更延迟（从提交到生效）、数据面端到端延迟、请求排队时间、执行时间、错误码、当前模型版本和节点身份。仅有平均 CPU 利用率，无法证明控制面或数据面健康。

### 1.3.3 一个常见误区

[推断] 当“部署成功”页面显示绿色时，很多人推断服务已经可用。更谨慎的结论是：控制面已接受声明，仍需用真实或合成请求验证数据面路径，包括冷启动、热请求、并发、超时和回滚。

## 1.4 工作负载分类：同一个模型，也可能是不同的系统

分类的目的不是贴标签，而是决定资源配置、指标和故障预算。下面的轴可以组合使用。

### 1.4.1 在线与离线

- **在线请求**：每个请求有明确用户，关注端到端延迟、尾部延迟和错误率。交互式聊天还要区分首 token 延迟（TTFT）与后续 token 间隔（TPOT）。
- **离线批处理**：关注单位时间完成的样本或 token 数、总作业时长、失败重试和每条样本成本。允许更长排队换取更高批量效率。

[机制] 在线服务通常被尾部延迟约束；离线作业通常被总吞吐和资源利用率约束。用离线平均吞吐来推断在线 p99，会忽略排队和请求大小分布。

### 1.4.2 训练、微调与推理

- **训练**需要前向、反向和优化器状态，计算、内存和通信模式都比推理重。
- **微调**可能冻结大部分权重，改变的是梯度范围、检查点和数据管道。
- **推理**通常只做前向，但自回归生成会重复执行多轮小步骤，并受到 KV cache、批调度和上下文长度影响。

[事实] 训练和推理可以共享硬件，但不能假设共享同一套容量模型。训练峰值显存、检查点写入和跨卡通信可能远高于推理；推理则更容易受到请求到达随机性和尾延迟影响。

### 1.4.3 计算形态

- **密集张量计算**：矩阵乘法占比高，适合利用向量/矩阵单元。
- **内存受限**：算子每做一点计算就要搬运大量参数或激活，带宽比峰值算力更关键。
- **控制流与小算子**：分词、解码、后处理、条件分支可能由 CPU 和 Python 解释器主导。
- **通信受限**：多卡或多节点需要同步，链路带宽与延迟决定可扩展性。

[设计判断] 先用采样器或运行时剖析确认形态，再选硬件和优化。凭“这个模型很大”直接购买更大的卡，是成本高且不可验证的决策。

### 1.4.4 请求形状

记录至少三个变量：输入 token 数、输出 token 数、并发请求数。对视觉或多模态模型，还需记录图像分辨率、帧数和音频时长。相同平均值下，长尾请求会显著改变 p95/p99。

[测量] 负载生成器应保存每个请求的形状与结果，而不是只保存总 QPS。否则无法回答“是请求变长，还是系统变慢”。

## 1.5 四个核心指标：延迟、吞吐、成本、可靠性

### 1.5.1 延迟（Latency）

延迟是从一个明确定义的起点到终点的时间。常见口径有：客户端端到端、网关、排队、模型执行、首 token、每 token、总生成。必须写清时钟位置和是否包含网络。

[事实] 平均值不能描述尾部。一个服务平均 100 ms，可能有 1% 请求超过 2 s；这对用户体验和级联超时影响巨大。

[测量] 报告中至少给出 p50、p95、p99，并同时给出样本数、负载分布、预热方式、失败请求是否计入。百分位数不是“最大值”，不同窗口和聚合方法会得出不同结论。

### 1.5.2 吞吐（Throughput）

吞吐可以按请求/秒、样本/秒、token/秒或字节/秒计。必须说明是输入、输出还是总 token，以及系统是否在稳定状态。

[机制] 增大批大小常提高硬件利用率，却可能增加单请求等待。吞吐与延迟存在帕累托权衡，不存在对所有工作负载都最优的唯一批大小。

### 1.5.3 成本（Cost）

成本包括计算租用、存储、网络、日志、运维人力和失败重试。为了可比较，可按每千请求、每百万 token、每样本或每作业小时归一化。

[设计判断] “更快”不是自动“更便宜”。若加速卡价格和闲置时间增加，单位请求成本可能上升。成本模型应列出固定成本、随负载变化的成本、峰值冗余和迁移成本，并标明哪些是估算。

### 1.5.4 可靠性（Reliability）

可靠性是系统在指定条件下持续提供正确服务的能力。可观测近似包括成功率、可用性、超时率、重试率、错误预算消耗、数据正确性和恢复时间（MTTR）。

[事实] HTTP 200 不等于正确：可能返回截断、空结果或旧版本模型。应把协议成功、业务成功和质量校验分开记录。

[机制] 重试能掩盖瞬时错误，却也会放大流量；没有幂等键的写操作重试可能造成重复副作用。AI 推理多为读操作，但缓存写入、计费和工具调用仍需考虑幂等。

## 1.6 从请求到硬件的因果链

把一次请求拆成可测量的时间段，有助于避免“GPU 利用率不高，所以 GPU 不行”的跳跃结论。一个简化链路如下：

1. **接入**：DNS、TLS、负载均衡、身份验证。
2. **解析与预处理**：JSON 解码、分词、图像缩放、校验和。
3. **排队与调度**：选择副本、等待批次、优先级和限流。
4. **数据搬运**：CPU 内存到设备内存、张量布局转换、缓存查找。
5. **模型执行**：算子调度、矩阵乘法、归一化、注意力和采样。
6. **后处理**：解码、过滤、格式化、脱敏。
7. **返回**：序列化、压缩、网络发送、客户端读取。

[机制] 端到端延迟近似为各段服务时间与排队时间之和；并行部分不能简单相加，需要区分重叠、同步和最慢分支。一次额外内存拷贝可能与计算重叠，也可能因为同步点变成纯额外成本。

[测量] 给每段埋单调时钟时间戳，并携带 request_id、模型版本、节点、设备、输入/输出长度。先测热路径，再单独测冷启动；不要用日志时间戳替代高精度计时器。

[推断] 若 GPU 利用率低且排队时间高，可能是批调度或 CPU 预处理瓶颈；若 GPU 利用率高但 p99 突然升高，可能是显存压力、频率抖动或长请求挤占。以上是候选解释，必须通过实验或剖析验证。

## 1.7 三个定律与模型：建立直觉，也承认边界

### 1.7.1 Little's Law：系统里有多少工作

公式为：L = λW。L 是系统内平均工作量（例如在途请求数），λ 是长期平均到达率，W 是平均逗留时间。直觉是：每秒进入 λ 个请求，每个平均停留 W 秒，系统中平均就有 λ×W 个请求。

[事实] 该关系适用于满足稳定条件的队列系统，不要求服务时间服从特定分布，但需要使用一致的时间窗口和定义。

[例子] 若稳定地处理 20 请求/秒，平均端到端 0.5 秒，则在途请求平均约 10 个。若看到在途请求 50 个且到达率仍是 20，平均逗留时间应接近 2.5 秒，或系统尚未稳定。

[边界] 瞬时尖峰、丢弃请求、不断增长的队列和不一致采样会让直接套用产生误导。L 也不告诉你 p99、队列公平性或哪一段慢。

[测量] 可用请求计数器和并发仪表估算 L、λ、W，再检查三者是否近似满足关系。偏差是排查指标口径、异步任务和采样窗口的线索，而不是自动证明系统错误。

### 1.7.2 Amdahl 定律：局部加速的上限

若程序中可并行或可加速的比例为 p，加速倍数为 s，整体加速上限为：S = 1 / ((1-p) + p/s)。当 s 趋近无穷，S 不超过 1/(1-p)。

[机制] 如果 80% 时间在模型前向，剩余 20% 在预处理、排队和网络，即使前向无限快，端到端最多约 5 倍加速。这个结论提醒我们找“不可加速部分”。

[边界] p 不是固定常数；改变批大小、精度和并行策略会改变各段占比。并行还会引入同步、通信、内存和调度开销，实际加速可能低于公式。

[设计判断] 优化前先做时间分解。不要仅凭某个内核快了 2 倍就承诺端到端快 2 倍；应重新测量新的 p 和新增开销。

### 1.7.3 Roofline：算力还是带宽受限

Roofline 用算术强度（每搬运一个字节做多少计算）把性能上限画成两部分：内存带宽斜线和峰值算力水平线。算术强度低时，性能受带宽限制；达到“拐点”后，才受算力限制。

[事实] 这是对处理器、内存层次和某类内核的上限模型，不是完整的端到端服务模型。

[机制] 量化、融合算子和改善数据复用可能提高算术强度；但压缩会增加解码成本，融合可能降低可调试性。若请求很小，内核启动和调度开销可能主导，Roofline 的稳态假设不成立。

[测量] 需要收集实际 FLOP 估计、内存读写字节、设备带宽和利用率。不同计数器定义可能不一致，跨硬件比较时要注明工具和采样周期。

[边界] Roofline 不直接描述网络、排队、分支、缓存未命中、功耗降频或质量变化。它适合回答“某个算子大致受什么限制”，不适合单独回答“用户请求为什么慢”。

## 1.8 可运行实验：CPU 本地推理服务的最小设计

本实验刻意不依赖 GPU，目标是建立完整方法：定义假设、运行服务、生成负载、采集分段指标、比较变量、记录不确定性。实验结果必须由读者实际运行后填写，本文不预先声称任何数值。

### 1.8.1 实验问题与假设

问题 A：并发从 1 增加到 4 时，吞吐和 p95 如何变化？

问题 B：输入 token 数增加时，预处理和推理时间哪个增长更快？

问题 C：开启进程内缓存后，重复请求的延迟是否下降，内存是否上升？

[设计判断] 先写假设再跑实验，避免看到曲线后倒推故事。示例假设：在单核或受限 CPU 上，增加并发会先提高吞吐，超过某点后因上下文切换和排队使 p95 上升；长输入会增加分词和注意力计算时间，但增长关系需实测。

### 1.8.2 环境与固定变量

建议记录：操作系统版本、Python 版本、CPU 型号与逻辑核数、内存大小、线程环境变量、依赖版本、模型名称与哈希、量化/精度、输入输出长度、温度和随机种子。固定 CPU 频率策略（若权限允许），否则把频率变化作为限制写入报告。

为减少噪声：

- 预热若干请求后再计时，同时单独记录冷启动。
- 每个配置运行足够样本，随机化配置顺序。
- 不在同一机器上同时运行大型下载、编译或桌面任务。
- 记录错误、超时和重试，不把失败样本静默丢弃。

### 1.8.3 最小服务骨架

下面示例使用 FastAPI 接受文本，模型部分用可替换的 `predict` 占位函数。为了让实验可重复，先用确定性的字符计数和可控睡眠模拟推理，再替换为真实本地模型；替换后必须记录模型与运行时版本。

```python
# server.py
import os, time, uuid
from fastapi import FastAPI, Request
from pydantic import BaseModel

app = FastAPI()

class Query(BaseModel):
    text: str
    max_tokens: int = 32


def predict(text: str, max_tokens: int):
    # 设计判断：先用可控占位，验证链路和指标，再接入真实模型
    token_est = max(1, len(text) // 4)
    work_ms = min(200, 2 + token_est * 0.8 + max_tokens * 0.5)
    time.sleep(work_ms / 1000)
    return {"text": text[:80], "tokens": token_est + max_tokens}

@app.post("/infer")
def infer(q: Query, request: Request):
    rid = request.headers.get("x-request-id", str(uuid.uuid4()))
    t0 = time.perf_counter()
    t1 = time.perf_counter()
    result = predict(q.text, q.max_tokens)
    t2 = time.perf_counter()
    return {
        "request_id": rid,
        "result": result,
        "timing_ms": {
            "preprocess": (t1 - t0) * 1000,
            "inference": (t2 - t1) * 1000,
            "total": (t2 - t0) * 1000,
        },
    }
```

启动命令和依赖版本应写入实验记录。示例命令：

```bash
python -m venv .venv
. .venv/bin/activate
pip install fastapi uvicorn pydantic httpx
uvicorn server:app --host 127.0.0.1 --port 8000 --workers 1
```

[事实] 该骨架不是生产级推理服务器：没有认证、限流、模型加载、超时、优雅关闭或持久化。它只用于验证观测和负载实验。

### 1.8.4 负载生成与实验矩阵

可以写一个异步客户端，把每次请求的开始、首字节、结束、状态码、输入长度和输出长度保存为 JSONL。实验矩阵至少包含：并发 1、2、4、8；短文本约 32 字符、中等约 512 字符、长文本约 2048 字符；预热与冷启动两种；缓存关闭与开启两种。

[测量] 对每个格子报告：请求数 n、成功数、吞吐、p50/p95/p99、平均输入/输出长度、CPU 利用率、RSS 内存、失败类型。若 n 太小，p99 只有一个样本，结论应标注低置信度。

建议画三类图：

1. 并发—吞吐曲线，观察是否出现饱和。
2. 并发—p95 曲线，观察排队拐点。
3. 输入长度—分段耗时堆叠图，区分预处理与推理。

### 1.8.5 数据分析模板

先检查数据完整性：时间戳单调、request_id 唯一、失败是否有原因、客户端和服务端时钟是否同源。然后计算 Little's Law 的近似值，比较观测并发与 λ×W；若差异大，检查是否存在连接池、异步任务或窗口不一致。

再用 Amdahl 思路做“如果只优化某段”的情景分析。例如观测到推理占总时间 70%，把推理缩短一半的理想上限约为 1/(0.3+0.7/2)=1.54 倍；这只是基于当前分解的估算，优化后占比会改变。

最后记录不确定性：机器是否共用、CPU 频率是否锁定、模型是否产生随机输出、网络是否绕过本机环回、垃圾回收是否干扰。不要把一次运行的中位数写成普遍规律。

## 1.9 故障诊断案例：p99 飙升但平均值正常

### 现象

某文本生成服务的日报显示平均延迟从 180 ms 升到 190 ms，团队认为变化不大；用户却报告“偶尔卡住”。进一步查看发现 p99 从 600 ms 升到 4 s，超时率接近错误预算上限。

### 第一步：确认指标口径

[测量] 检查客户端、网关和模型服务是否使用同一请求集合，是否把超时请求排除，百分位数是否先按实例计算再平均。若口径不同，先修正仪表盘再讨论优化。

### 第二步：沿因果链分段

把总延迟拆为接入、排队、预处理、设备执行、后处理和返回。若只有排队 p99 上升，而设备执行分布稳定，优先调查调度和流量尖峰；若设备执行长尾同步上升，调查频率、内存和内核选择。

### 第三步：提出并验证候选机制

候选 1：发布了更长的默认上下文。验证：按输入 token 分桶比较延迟。

候选 2：批调度等待窗口从 2 ms 变成 20 ms。验证：读取运行时配置，做 A/B 实验。

候选 3：节点发生 CPU 降频。验证：关联频率、温度、功耗和实例标签。

候选 4：日志序列化在锁内执行。验证：采样剖析线程栈，临时降低日志级别并观察是否回落。

[推断] 在没有分段数据前，不能宣布“GPU 故障”或“网络问题”。每个候选都应有可证伪观测：若关闭日志后 p99 不变，则日志锁不是主要原因；若长输入桶仍稳定，则上下文变化解释不足。

### 第四步：缓解与复盘

短期可设置每请求最大上下文、限制批等待、隔离长请求队列、启用熔断和降级模型。长期需要容量模型、发布前基准、尾延迟回归门禁和按请求形状的 SLO。

[设计判断] 复盘应区分“触发因素”（例如配置改变）和“放大因素”（例如没有按长度分桶、告警只看平均值）。只修触发因素，系统仍可能在下一次不同事件中复发。

## 1.10 与传统软件工程、ML 工程的边界

### 1.10.1 与传统软件工程的交集

两者都关心接口、版本、测试、部署、可观测性、回滚、权限和事故响应。AI 基础设施不应成为跳过软件工程纪律的借口。

### 1.10.2 与传统软件工程的差异

[机制] AI 工作负载的资源需求常随输入形状变化，模型输出具有概率性或质量分布，算子可能受硬件精度和内存带宽影响。一个功能测试通过，不代表不同长度、语言、温度和并发下的质量与性能稳定。

### 1.10.3 与 ML 工程的交集

ML 工程关注数据集、训练、评估、特征、模型注册和实验追踪；AI Infrastructure 关注如何把这些产物可靠地服务化、批量化和治理化。边界不是组织名称，而是问题的主要约束。

例如，数据漂移导致准确率下降，通常首先是 ML 评估问题；模型加载时显存碎片导致 OOM，通常首先是基础设施问题；两者同时发生时，需要共享模型版本、请求样本和资源指标。

[设计判断] 交接契约应包含：模型输入输出 schema、最大形状、精度、随机性、质量门槛、资源画像、已知失败模式、回滚版本和观测字段。没有契约，基础设施团队只能猜模型行为，ML 团队也无法复现实服性能。

## 1.11 六道理解检查（含答案要点）

### 检查 1：控制面已显示部署成功，为什么仍需发送真实请求？

答案要点：部署成功只说明声明被接受或副本已创建；数据面可能有路由、鉴权、模型加载、超时和输出格式问题。要用健康检查与真实样本验证端到端路径，并记录模型版本。

### 检查 2：平均延迟下降，p99 上升，系统一定变差吗？

答案要点：不能只凭两个数字下结论。先确认样本量、请求形状和统计口径；可能是大多数短请求更快、少数长请求更慢。若业务受尾延迟 SLO 约束，p99 上升通常是风险信号，需要分桶与排队分析。

### 检查 3：GPU 利用率 30% 是否证明 GPU 浪费？

答案要点：不证明。可能 CPU 预处理、数据搬运、批等待、网络或内存带宽受限；也可能请求很小而内核启动占主导。应结合分段时间、带宽/算力计数器和并发曲线验证。

### 检查 4：Little's Law 能否直接预测 p99？

答案要点：不能。L=λW 描述平均量和稳定系统关系，不描述分布、尾部、优先级和丢弃。它可用于一致性检查和数量级估算，不能替代百分位测量。

### 检查 5：把前向计算加速十倍，端到端一定加速十倍吗？

答案要点：不一定。Amdahl 定律要求考虑不可加速部分、同步和新增开销。若前向只占 60%，理论上限约 2.5 倍，还可能更低。

### 检查 6：什么时候 Roofline 不适合解释整条请求链？

答案要点：当主要问题在网络、排队、控制流、内核启动、缓存和多阶段同步时；Roofline适合分析稳态内核的算力/带宽上限，不能单独解释端到端延迟或质量。

## 1.12 练习：从观察到决策

1. **画链路**：为一个聊天 API 画出接入、排队、预处理、推理、后处理和返回，给每段写两个可测指标。要求标出控制面改变会影响哪些段。
2. **做 Little's Law 检查**：在本地实验中记录 60 秒的到达率、平均延迟和并发，比较 λW 与观测并发，并解释差异来源。
3. **做 Amdahl 情景**：假设分词 15%、推理 65%、网络 20%，分别把推理加速 2 倍和 5 倍，计算理想端到端加速，再写出两个现实开销。
4. **做 Roofline 假设**：选择一个矩阵乘法和一个逐元素归一化算子，说明哪个更可能受算力或带宽限制，并列出需要采集的计数器。不要只依据算子名称下结论。
5. **设计尾延迟实验**：固定平均输入长度，改变长度方差，观察 p95/p99 是否变化。写出至少一个混杂变量与控制方法。
6. **故障报告**：模拟把批等待从 2 ms 改为 20 ms，写一页事故报告，必须区分事实、机制、推断、测量缺口和短期缓解。
7. **成本模型**：给本地 CPU、按小时计费的加速卡和托管 API 建立单位 token 成本表，标出固定成本、峰值冗余和不确定项。不得填入未经核实的价格。
8. **边界讨论**：选择一个“模型准确率下降”的事件，列出 ML 工程、基础设施、产品和数据治理各自需要提供的证据。

## 1.13 来源地图：如何把结论追溯到证据

本章不是把链接当装饰，而是给每类主张指定验证路径。阅读来源时，应记录版本、日期、适用硬件和实验条件。

### 事实来源

- Little 定律的排队论教材或原始论文：核对稳定条件、平均量定义和适用范围。
- Amdahl 关于并行处理能力的论文与体系结构教材：核对公式假设和不可并行部分。
- Roofline 模型论文及相关硬件性能工程文档：核对算术强度、带宽和峰值算力定义。
- 处理器、操作系统、容器和运行时官方文档：核对线程、频率、内存和调度语义。

可作为起点的公开来源链接（访问时仍需核对版本与上下文）：Little 原始论文 DOI https://doi.org/10.1287/opre.9.3.383；Amdahl 论文 DOI https://doi.org/10.1145/1465482.1465560；Roofline 论文 DOI https://doi.org/10.1145/1498765.1498785。

### 机制来源

- 推理运行时官方文档：批处理、KV cache、算子融合、量化和内存分配行为。
- 服务框架文档：超时、连接池、工作进程、流式响应和优雅关闭。
- 编排与调度文档：副本就绪、探针、滚动发布、亲和性和自动扩缩容。

### 测量来源

- 公开基准套件的测量协议：确认请求形状、预热、样本数和统计口径。
- 监控系统文档：计数器、直方图、百分位计算、采样和聚合方式。
- 硬件性能计数器指南：确认带宽、FLOP、频率和功耗指标的定义及误差。

### 推断与设计判断

- 推断必须链接到观测：日志、追踪、剖析、配置差异和可重复实验。
- 设计判断应写明目标函数和约束，例如“为满足 p99 SLO，宁可牺牲峰值吞吐”。这是团队选择，不是自然定律。
- 若来源只支持某一硬件、模型或版本，不应把结论推广到所有环境；应在报告中写出外推边界。

建议建立一个“主张—证据”表：主张文本、类型（事实/机制/测量/推断/设计判断）、来源链接或实验编号、环境、日期、复核人和失效条件。表格本身也是基础设施的一部分，因为它让下一次性能回归有可追溯的基线。

## 1.14 安全、隔离与变更管理也属于基础设施

性能讨论常把安全当成附录，但在可运行系统中，安全控制会改变数据路径、延迟和故障模式。[事实] 身份验证、授权、审计、输入限制、模型防护和机密管理都需要执行点；执行点越多，越要测量它们的时间和失败行为。

### 1.14.1 数据与模型的边界

[机制] 用户输入可能包含提示注入、超长内容、恶意序列化或个人信息。网关应先做大小、编码和内容策略检查，再进入分词和模型执行；这样可以避免把明显不合规的输入送到昂贵资源。检查本身也可能成为 CPU 瓶颈，因此要记录拒绝率、检查耗时和误拒绝样本。

模型权重、适配器、词表和配置应视为发布制品。下载或加载前校验来源、哈希和版本；运行时不要从用户可写路径加载可执行对象。[设计判断] 即使实验只在本机运行，也应在记录中写明信任边界：哪些文件由谁生成，哪些依赖来自何处，哪些权限是最小必需。

### 1.14.2 多租户与资源隔离

不同团队或用户共享节点时，缓存、临时文件、日志和内存都可能泄漏信息或互相争用。可采用进程/容器隔离、资源配额、队列优先级、请求超时和数据脱敏；但每项隔离都会增加调度、拷贝或运维复杂度。[测量] 应比较隔离前后的吞吐、p99、失败率和成本，而不是只看“安全开关是否打开”。

长请求尤其容易占满并发槽位。将短请求与长请求分队列，能降低交互式 p99，但可能降低总吞吐或增加调度公平性问题。应先定义 SLO 与优先级，再决定是否牺牲某类请求的等待时间。

### 1.14.3 变更与回滚

模型、运行时、驱动、内核、批策略和日志配置都可能改变性能。每次变更至少保留：变更前基线、变更内容、受影响工作负载、回滚版本、观测窗口和负责人。灰度发布时按用户或请求哈希稳定分流，避免同一请求在两套版本间随机切换。

[测量] 回滚不能只看实例恢复绿色，还要检查真实请求的质量、延迟、成本和错误预算是否回到基线附近。[推断] 如果回滚后 p99 仍高，触发因素可能已经留下队列、缓存或资源碎片，需要先清理状态再比较。

### 1.14.4 可持续性与功耗

功耗和散热会影响频率、容量和成本。报告可以记录设备功率、温度、频率和每请求能耗估算，但必须注明计量接口、采样频率和分摊方法。不要把某次峰值功率直接乘以全天时长，当作精确碳排或账单；那只是带有假设的估算。

## 1.15 从指标到容量：把一次实验变成运行承诺

实验的下一步不是立刻扩容，而是把用户期望写成可检查的服务目标。一个服务等级目标（SLO）至少要说明工作负载、时间窗口、统计口径和例外条件。例如，“在输入不超过 512 token、输出不超过 128 token 的在线请求中，滚动 30 天成功请求的 p95 端到端延迟小于 800 ms，且超时率低于 0.5%”。没有输入形状和窗口，数字看似精确，实际无法复现。

[事实] SLO 是目标，SLA 是对外承诺，错误预算是允许的失败额度。三者的法律和业务含义不同，团队不应把仪表盘上的单个阈值直接称为 SLA。

### 1.15.1 容量规划的四个步骤

第一步，建立需求分布，而不是只填一个峰值 QPS。记录一天内到达率、并发、输入输出长度、租户比例、优先级和突发持续时间。若只能拿到抽样数据，应写明抽样方法和可能遗漏的长尾。

第二步，测量单实例在不同并发和请求形状下的稳定区间。稳定区间意味着队列不会无限增长，错误率和 p99 没有持续发散。超过某个并发后，即使平均吞吐仍上升，也可能已经违反交互式 SLO。

第三步，加入冗余和故障假设。若要求任意一台机器下线后仍满足目标，容量不能只按平均需求计算；还要考虑发布期间的双版本副本、热点租户和硬件维修窗口。[设计判断] 冗余比例取决于故障分布、恢复时间和业务容忍度，不能从一个通用常数推导。

第四步，用压测和线上观测校正模型。把预测的并发、排队和成本与真实计数器对照，记录误差和原因。若模型持续偏低，先检查输入长度和重试是否漏计，再修改公式。

### 1.15.2 排队、限流与背压

[机制] 当到达率接近服务率时，等待时间对小幅流量变化非常敏感。无界队列会把过载转化成越来越长的延迟；有界队列会更快拒绝或降级，让系统保留可恢复性。两者没有普遍正确答案，要看请求是否可重试、是否有用户交互和是否存在副作用。

限流应说明维度：全局、租户、模型版本、IP、令牌或并发槽位。只按请求数限流可能让长请求占满资源；只按 token 限流又可能忽略分词和网络开销。实践中常用多维预算，并在拒绝响应中返回可解析的原因和重试建议。

背压是让上游感知下游拥塞的机制。流式响应可以在生成变慢时降低发送速率；批处理系统可以暂停拉取新任务；消息队列可以根据可见深度调节消费者。没有背压的重试风暴会形成正反馈：失败越多，重试越多，队列越长，最终拖垮健康副本。

### 1.15.3 降级与质量护栏

降级不是简单地换一个更小模型。候选方案包括限制最大输出、降低采样复杂度、使用缓存、改为异步通知、切换到规则系统或返回明确的稍后重试。每个方案都会改变质量、成本或用户承诺，应在实验中给出触发条件和退出条件。

[测量] 降级路径要单独计数：触发次数、持续时间、成功率、质量抽检和恢复时间。否则平均指标可能看起来变好，实际是大量请求被静默截断。质量护栏可以是格式校验、敏感内容过滤、置信度阈值或人工复核，但护栏本身的误报和漏报也要纳入评估。

### 1.15.4 一个可复用的运行记录模板

每次基准或事故都可以保存以下字段：

- 目标：要验证的假设或 SLO，成功与失败的判定方式。
- 范围：模型、运行时、硬件、软件版本、请求形状和流量回放时间。
- 操作：启动参数、环境变量、配置变更、压测脚本和随机种子。
- 观测：端到端与分段延迟、并发、吞吐、错误、资源、成本和质量。
- 结论：已证实事实、尚未证实的机制候选、推断、限制和下一步实验。
- 复现：命令、数据位置、依赖锁定文件、图表生成脚本和负责人。

[设计判断] 记录模板看起来繁琐，却能把“某次感觉变快了”变成可复核证据。随着系统扩大，最昂贵的不是多跑一次基准，而是无法解释回归、只能靠猜测扩容或回滚。

### 1.15.5 何时停止优化：用预算做取舍

优化没有天然终点。若 p99 已满足目标，继续压缩几十毫秒可能增加代码复杂度、升级风险和运维负担；若成本仍超预算，则应把优化目标改成单位请求成本，而不是盯着单实例吞吐。[设计判断] 停止条件应在实验开始前写出，例如“p95 低于目标 20%，且连续三次基准的结果差异小于 5%”。

把目标写成多维约束会更诚实：延迟上限、最低吞吐、单位成本、错误率、质量分数和变更风险。某项改动若只改善一个维度，必须说明牺牲了什么。例如增大批大小可能降低单位 token 成本，却让短请求等待更久；开启更激进量化可能减少内存，却引入质量回退和额外解码开销。

[机制] 资源争用会让局部优化在混合负载下失效。一个针对长输入调优的内核，可能挤占短请求的缓存；一个减少日志的配置，可能降低事故可见性。基准因此需要至少一个代表性混合场景，而不能只跑最容易的单一请求。

[测量] 对每项优化保留前后对照、置信区间或重复运行范围，并记录回滚演练是否成功。如果差异小于测量噪声，就把结论写成“尚未观察到稳定改善”，不要为了发布而挑选有利样本。

当结果冲突时，回到用户影响：是更多用户能在可接受时间内拿到正确结果，还是只有实验室里的单个请求更快？基础设施的最终价值是可预测地提供能力，而不是制造一个漂亮的峰值数字。

如果你刚接触这个领域，可以按三个循环推进。第一个循环只关注可见性：让请求拥有唯一标识，记录分段时间、输入形状和错误原因。第二个循环关注因果：一次只改变一个变量，用排队关系、加速上限和算术强度解释变化。第三个循环关注治理：把基准、回滚、预算、质量护栏和安全边界纳入发布流程。每完成一个循环，都应留下可复现的命令、原始数据和限制说明。这样即使换了模型、硬件或云环境，方法仍然成立；变化只会体现在新的测量和新的约束上。
持续复核这些证据，才能让系统在规模扩大后依然保持可解释性、可操作性和可恢复性。

## 1.16 本章小结

AI Infrastructure 的核心不是把模型放到更大的机器上，而是把请求、资源、策略和证据连接成可运行系统。控制面决定系统想要什么状态，数据面承担请求的真实代价；工作负载分类决定该看哪些指标；延迟、吞吐、成本和可靠性必须在同一约束下讨论。

Little's Law 帮你检查平均量是否自洽，Amdahl 定律提醒局部加速有上限，Roofline 帮你判断某个内核更像算力瓶颈还是带宽瓶颈。三者都不是端到端真相，必须配合分段测量和可复现实验。最后，先用 CPU 本地服务跑通观测链路，再逐步替换真实模型、增加并发和引入加速器。每一步都记录事实、机制、测量、推断和设计判断，才能从“能跑”走向“可解释、可运维、可扩展”。
