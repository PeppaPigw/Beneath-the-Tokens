# 第4章　性能数学：排队、Amdahl、Roofline 与成本模型

> 性能不是“快或慢”的形容词，而是一组带有单位、测量点和适用边界的关系。本章把系统性能写成可以计算、可以反驳、可以用实验校准的模型。公式不是为了制造精确幻觉，而是为了在买硬件、改批处理、定 SLO 之前先排除数量级错误。

## 4.1 为什么需要性能数学

在真实的 AI 服务里，最容易出现的争论往往不是算法对不对，而是“这个优化会不会让系统快一倍”“需要几张卡”“峰值流量能不能扛住”“云账单为什么突然涨了”。如果没有共同的量纲和测量点，讨论会退化成印象：看到 GPU 利用率 90% 就说算力不足，看到平均延迟下降就说 SLO 改善，看到一台机器处理过一万请求就说能够支持一万并发。

[事实] 任何性能结论都依赖工作负载、输入分布、并发度、软件版本、硬件状态和测量边界。改变其中一个条件，结论可能不再成立。

[机制] 性能模型把复杂系统压缩为少数变量，例如到达率 λ、并发数 L、响应时间 W、服务率 μ、计算量、内存带宽和单价。模型通常不精确，但它能揭示数量级、瓶颈位置和优化上限，再由实验填入真实常数。

[设计判断] 本章使用“模型 → 假设 → 实验 → 校准 → 决策”的循环。任何公式旁边都应写清：输入是什么、输出是什么、单位是什么、在哪些边界失效。这样即使模型不完美，也不会把错误的精确数当作承诺。

本章先约定四类指标：

1. **延迟（latency）**：一次请求从起点到终点所需时间，单位通常是 ms 或 s。
2. **吞吐（throughput）**：单位时间完成的请求、样本或 token 数，单位如 req/s、sample/s、token/s。
3. **并发（concurrency）**：同一时刻处于系统中的请求数，单位为请求。
4. **资源与成本**：CPU 秒、GPU 秒、GiB·s、kWh、货币/请求等可归因消耗。

不要把这些指标互换。10 req/s 是速率，10 个请求是数量，1 s 是时间；只有通过公式和测量边界，它们才会联系起来。

## 4.2 量纲纪律：先检查单位，再相信公式

### 4.2.1 基本单位表

可以用以下最小单位集合描述多数在线推理实验：

- 时间：s（秒）；毫秒必须在计算前转换为 0.001 s。
- 请求：req；它是计数单位，不应与字节混淆。
- token：tok；输入和输出都要分开记录。
- 数据量：B、KiB、MiB、GiB；明确使用十进制还是二进制前缀。
- 计算量：FLOP；算力是 FLOP/s。
- 功率：W = J/s；能量是 J 或 kWh。
- 货币：元、美元等，并记录计价周期。

[机制] 量纲分析最先捕捉“把 100 ms 当成 100 s”“把每小时价格除以请求数却漏掉小时到秒换算”这类错误。若等式两边单位不一致，公式必错；单位一致也不代表假设正确，但至少排除了低级错误。

### 4.2.2 服务时间、响应时间与排队时间

令 S 表示服务时间（服务器真正占用执行资源的时间），Q 表示排队等待时间，N 表示网络、序列化和客户端等额外时间，则端到端响应时间可以写为：

`W = Q + S + N`。

这不是物理定律，而是一个测量分解协议。某些系统把批处理等待算进 Q，某些系统把它归入 S；只要定义一致，就可以比较。报告中应同时给出 W、Q 和 S，否则“模型变快”可能只是排队变短，或者反过来。

### 4.2.3 边界与假设清单

每次建模前写一小段假设：

- 输入/输出 token 分布是否固定？是否有长尾？
- 请求到达是平稳、突发还是按批次到达？
- 资源是否独占？是否有多租户抢占、频率变化、热降频？
- 重试算不算新请求？超时请求是否仍占用资源？
- 数据从哪个时间点开始计时，到哪个时间点停止？
- 成本是按节点、按 GPU、按 vCPU·小时，还是按 token 计费？

[测量] 将这些假设写在实验记录中，后续才能解释模型与实测偏差。没有假设的数字只是一条孤立的日志。

## 4.3 Little’s Law：把吞吐、并发和延迟连接起来

### 4.3.1 公式与直觉

Little’s Law 写作：

`L = λ W`。

其中 L 是系统内平均请求数，λ 是长期平均到达率（req/s），W 是请求在系统内的平均停留时间（s）。在稳定系统中，长期完成率等于长期到达率，因此也可以用吞吐替代 λ。直觉是：如果每秒进入 20 个请求，每个请求平均停留 0.5 秒，那么系统中平均有 10 个请求。

[事实] Little’s Law 不要求队列是 M/M/1，也不要求服务时间服从某个分布。核心条件是观察窗口足够长、系统近似稳定、L、λ、W 的统计口径一致。

[机制] 公式把“容量”转换为并发预算。给定目标吞吐和目标平均延迟，可估算需要容纳的并发；反过来，固定并发和服务时间变化会改变可达吞吐。

### 4.3.2 在在线推理中的三种用法

**用法 A：从流量估算活动请求数。**

某 API 平均 50 req/s，端到端平均 W=0.4 s，则 L≈20。连接池、队列、线程数和显存中的 KV cache 至少要能覆盖这个数量级，另留出突发和重试余量。

**用法 B：从并发反推最大稳定吞吐。**

如果系统限制并发为 64，测得平均响应时间 0.8 s，稳定吞吐上限粗略为 λ≈64/0.8=80 req/s。这个数不是承诺，因为排队、限流和尾延迟可能先触发；但如果产品宣称 200 req/s，就需要立刻要求更多证据。

**用法 C：解释延迟为何随负载上升。**

在服务时间基本不变时，负载增加使系统内请求数增加，等待队列拉长，W 上升。若只优化内核把 S 从 100 ms 降到 80 ms，却让批处理等待增加 100 ms，端到端 W 可能反而变差。

### 4.3.3 稳定性边界与利用率

对单服务台，令服务率 μ=1/S，利用率 ρ=λ/μ=λS。若 ρ 接近 1，任何到达抖动都会放大等待时间；若 ρ≥1，长期队列无法稳定。工程上通常为突发、重试和故障保留余量，不能把 ρ=0.99 当作安全目标。

在理想 M/M/1 模型中，平均系统时间是 `W = 1/(μ-λ) = S/(1-ρ)`。当 ρ 从 0.5 升到 0.8，分母从 0.5 变为 0.2，延迟放大 2.5 倍；这解释了为什么容量“只多压一点”就出现雪崩。真实服务不是 M/M/1，但“接近饱和会非线性变慢”的方向通常成立。

[边界] M/M/1 假设泊松到达、指数服务时间、单服务台和无限队列。GPU 批调度、多副本、优先级、限流和长短请求混合都会改变常数。把公式当作上界直觉可以，把它当作精确 p99 预测则不可靠。

### 4.3.4 突发和变异性：为什么平均值不够

同样的平均 λ，如果请求成批到达，队列会比均匀到达更长。排队理论中，等待时间不仅取决于利用率，还取决于到达和服务时间的变异系数。Kingman 近似（单服务台、一般分布）常写成：

`Wq ≈ [ρ/(1-ρ)] × [(Ca² + Cs²)/2] × S`，

其中 Ca、Cs 是到达间隔和服务时间的变异系数，Wq 是平均排队时间。它提醒我们：降低长尾服务时间（Cs）或平滑请求突发（Ca）可能和提升平均算力同样重要。

### 4.3.5 排队预算反推容量

假设 API 的 SLO 是 p95≤800 ms，测得服务时间 p95 约 300 ms，网络与序列化预算 100 ms，则排队和调度只能使用约 400 ms 的预算。若压测显示 p95 排队已达 700 ms，应先扩容、限流或调整批策略，而不是继续优化矩阵乘法。

[设计判断] 把总延迟拆成“排队预算、服务预算、外围预算”，并为每段建立仪表盘，是比只看端到端 p99 更可执行的 SLO 方法。

## 4.4 延迟、吞吐与尾部：不要让平均数替你做承诺

### 4.4.1 百分位数的含义

p50 是一半请求不超过的延迟，p95 是 95% 请求不超过的延迟，p99 是 99% 请求不超过的延迟。p99 不是最大值，也不是“最慢的那个请求”。样本量 100 时，p99 只由极少数样本决定，置信区间很宽；样本量不足时，应报告样本数和不确定性。

[测量] 采集每个请求的时间戳，先按请求粒度计算 W，再计算百分位。不要先按实例求平均再平均，因为实例流量和长尾不同会导致加权错误。

### 4.4.2 流式生成的两个延迟

自回归生成至少有两个用户可感知指标：

- **TTFT（time to first token）**：请求进入到第一个输出 token 的时间，受排队、prefill、调度和首包网络影响。
- **TPOT/ITL（time per output token / inter-token latency）**：后续 token 的间隔，影响阅读流畅度。

总生成时间约为 `TTFT + (输出 token 数 - 1) × TPOT`。输入很长时，prefill 令 TTFT 增大；输出很长时，TPOT 累积。将两者平均成一个“响应时间”会掩盖不同优化策略的效果。

### 4.4.3 吞吐的口径陷阱

“token/s”可能表示设备总 token/s、每个请求 token/s、仅输出 token/s、输入加输出 token/s。报告时应写成“每 GPU、每实例、总集群；input/output 分开；是否包含 padding 和失败重试”。对批推理，还要区分有效样本吞吐和填充后的计算吞吐。

[失败模式] 用单请求低延迟模式测出的 token/s 去承诺高并发吞吐，常会失败；批大小改变了内存访问、调度和尾延迟。必须画出 batch size—throughput—p99 的曲线，而不是给一个点。

## 4.5 Amdahl、Gustafson：优化有上限，规模也会改变问题

### 4.5.1 Amdahl 定律

若程序中可被加速的部分占比 p，其他部分占比 1-p，加速倍数为 s，则整体加速比：

`Speedup = 1 / [(1-p) + p/s]`。

当 s→∞，最大加速比是 `1/(1-p)`。例如只有 70% 时间在 GPU 内核中，剩余 30% 在预处理、同步和网络；即使 GPU 部分无限快，整体最多约 3.33 倍。把 30% 优化到一半（s=2）时，整体只从 1 变为 `1/(0.3+0.35)=1.54` 倍。

[机制] Amdahl 让“先找占比最大且可优化的部分”变成计算，而不是口号。占比应基于目标工作负载测量，不能从代码行数推断。

### 4.5.2 多段流水线的串行瓶颈

若请求依次经过网关、排队、预处理、模型、后处理和网络，每段时间相加。并行化某段后，其他段和同步点仍在总路径上。将端到端延迟分解成时间占比，再套 Amdahl，能防止把优化收益重复计算。

### 4.5.3 Gustafson 定律

Amdahl 固定总问题规模；Gustafson 讨论固定时间、随资源扩大问题规模时的加速：

`Scaled Speedup = s - α(s-1)`，

其中 s 是处理器数（或并行扩展倍数），α 是串行部分在并行运行时间中的比例。它解释了为什么离线训练可以通过增加 GPU 同时处理更多样本、扩大 batch 或缩短 epoch，而不是只追求同一批数据更快完成。

[边界] Gustafson 不是对在线请求尾延迟的保证。在线服务的请求量、SLO、通信和成本会限制可扩展规模；扩大问题规模也可能引入数据通信、负载不均和调度开销。

### 4.5.4 实践：画出“占比—收益”曲线

用剖析器记录各阶段占比 p_i，假设每阶段分别有可实现的 s_i，计算新的总时间 `T' = Σ T_i/s_i`。同时对每个阶段写“可实现上限”和“验证实验”。如果模型依赖“把预处理完全移到 GPU”，要说明数据拷贝和内存占用会否抵消收益。

## 4.6 Roofline：算术强度决定更接近算力还是带宽

### 4.6.1 两条上限

Roofline 模型用峰值计算能力和内存带宽给出性能上限：

`Performance ≤ min(Peak FLOP/s, Bandwidth × Arithmetic Intensity)`。

算术强度（AI）是每搬运一个字节执行的 FLOP 数：

`AI = FLOP / Byte`。

当 AI 较低，性能受内存带宽约束；当 AI 足够高，才可能接近峰值算力。交叉点 `AI* = Peak FLOP/s ÷ Bandwidth` 把两种区域分开。

例如设备峰值 10 TFLOP/s、显存带宽 500 GB/s，则 AI*=20 FLOP/Byte。一个 AI=4 的算子带宽上限约 2 TFLOP/s；即使再增加计算单元也未必加速。一个 AI=40 的算子算力上限仍可能只有 10 TFLOP/s，接下来要查占用、指令效率和并行度。

### 4.6.2 如何估算算术强度

矩阵乘法 C=A×B，若 A、B、C 被理想复用，FLOP 数约 2MKN，字节数取决于元素精度和读写次数；真实 kernel 的字节数应由 profiler 或硬件计数器测得。逐元素加法通常每元素只做 1 次加法，却读写多个数组，AI 很低，常受带宽限制。

[测量] 不要用“理论读取一次”替代实际内存流量。缓存命中、融合算子、padding、布局转换和跨设备拷贝都会改变 Byte。先测 dram bytes、FLOP/s 和带宽，再把点放到 Roofline 图上。

### 4.6.3 LLM 推理中的 prefill 与 decode

LLM 的 prefill 对一整个输入序列做较大矩阵运算，批量和算术强度通常更高；decode 每轮只生成少量 token，却要读取权重和 KV cache，常更接近内存带宽或调度受限。长上下文会增加 KV cache 读写，长输出会重复 decode。仅看 GEMM 峰值无法预测端到端 tok/s。

[设计判断] 若模型处在带宽屋顶，量化、权重布局、KV cache 压缩和减少拷贝可能比增加 FLOP 更有效；若处在算力屋顶，融合 kernel、张量并行和更高效矩阵指令才可能奏效。必须用算术强度与计数器验证，而不是依据设备宣传峰值。

## 4.7 从请求到账单：成本与能耗模型

### 4.7.1 分层成本

把单请求成本拆成可归因项：

`C_req = C_compute + C_memory + C_network + C_storage + C_control + C_retry`。

计算成本可以写为 `C_compute = (GPU_seconds × price_GPU_sec) + (CPU_seconds × price_CPU_sec)`；若云平台按实例小时计费，则 `GPU_seconds = instance_count × elapsed_seconds × GPUs_per_instance`，并要考虑空闲时间。内存和存储可能按 GiB·hour、GB·month 或 I/O 次数收费；网络按区域、方向和字节计费。控制面和观测成本（日志、追踪、指标）在高 QPS 时不可忽略。

[量纲检查] “美元/小时 × 秒”必须再除以 3600 才是美元；“美元/百万 token × token”要除以 1,000,000。所有费率都标注含税、折扣、承诺用量、跨区流量和最低计费粒度。

### 4.7.2 摊销与利用率

若一张卡每小时 2 美元，实例每小时有效运行 3600 秒，但只有 40% 时间处理有效请求，则有效计算成本会被利用率放大约 2.5 倍。定义利用率 `u = busy_time / wall_time`，则在固定实例费率下，单位有效计算秒成本约为 `price_per_wall_sec / u`。

批处理可以提高 u 和吞吐，降低每 token 成本，却可能增加等待与尾延迟。成本优化不能只看单价，还要把 SLO 约束写入目标：在满足 p95≤X、错误率≤Y 的前提下最小化每百万 token 成本。

### 4.7.3 能耗与碳排

功率 P（W）在时间 t（h）内消耗能量 `E_kWh = P × t / 1000`。若有 GPU、CPU、内存和风扇功率，应分别采样并加总；机房 PUE（Power Usage Effectiveness）可近似为 `E_facility = E_IT × PUE`。碳排估算为 `CO2e = E_kWh × carbon_intensity`，其中碳强度随地点和时间变化。

[边界] 读取瞬时功率并不能代表整个作业能耗；采样频率太低会漏掉峰值，遥测本身也有开销。将能耗报告为范围（例如平均值±置信区间）比给出伪精确小数更诚实。

### 4.7.4 成本分配

多租户环境可按请求 token、GPU 时间、显存占用或优先级分配成本。每种分配都有争议：按 token 简单但忽略长上下文；按 GPU 时间公平但需要可靠追踪；按峰值显存能反映容量机会成本但难以解释。生产系统应保存 request_id、model_version、input_tokens、output_tokens、gpu_seconds、retry_count 等字段，并定期与账单对账。

## 4.8 一个贯穿示例：估算 LLM API 的容量与成本

假设某服务平均到达率 40 req/s，输入平均 800 token，输出平均 200 token；单请求实测服务时间 S=120 ms，外围网络与序列化 N=30 ms。目标是 p95≤500 ms，机器每小时 3 美元，实测在 batch=8 时每台机器可稳定处理 55 req/s，平均 GPU 利用率 65%。

**第一步：Little’s Law 粗估并发。** 若平均 W≈0.15 s，则 L≈40×0.15=6 个请求。高峰和长尾需留出更大并发容量，不能把 6 当连接池上限。

**第二步：利用率。** 以 S=0.12 s 计算单服务台的工作量 40×0.12=4.8，若一台机器可并行处理约 55 req/s，则粗略利用率 40/55≈0.73。留有 27% 余量，但突发、重试和节点故障可能消耗余量。

**第三步：实例数和成本。** 平均流量需要 40/55≈0.73 台，生产至少按故障域取 2 台；若按 2 台全天运行，月墙钟成本约 2×3×24×30=4320 美元，实际有效请求成本为 `4320 ÷ (40×60×60×24×30)`，还要加存储、网络、观测和空闲成本。

**第四步：token 成本。** 每请求 1000 token，月请求量约 40×2,592,000=103,680,000 req，对应约 103.68B token。若只按请求数分摊，会掩盖输入长度变化；应分别记录 input/output token，观察长上下文用户是否占用更高 GPU 秒。

**第五步：SLO 检查。** 即使平均 W=150 ms，p95 仍可能超过 500 ms。必须在 40 req/s、峰值流量、batch 变化和混合长度下压测，记录排队、TTFT、TPOT、p95/p99。若 p95 接近 500 ms，应通过限流、优先级或额外副本建立安全边界。

[推断] 这个示例的精确成本并不可靠，因为实例价格、利用率和 token 分布未给出完整范围；它的价值在于展示计算顺序和需要补齐的数据。

## 4.9 可运行测量实验：从公式到数据

下面实验只需要 Python 3 标准库和可选的 psutil。它不模拟真实神经网络，而是演示 Little’s Law、尾延迟和吞吐测量方法。运行前先记录 CPU 型号、Python 版本、操作系统、电源模式和 git 版本。

### 实验 A：固定服务时间，观察 Little’s Law

```python
# little_law.py
import concurrent.futures as cf
import time, statistics

SERVICE = 0.05       # 秒：模拟服务时间
N = 200               # 请求总数


def serve(i):
    start = time.perf_counter()
    time.sleep(SERVICE)
    end = time.perf_counter()
    return end - start

for workers in [1, 2, 4, 8, 16]:
    t0 = time.perf_counter()
    with cf.ThreadPoolExecutor(max_workers=workers) as ex:
        samples = list(ex.map(serve, range(N)))
    elapsed = time.perf_counter() - t0
    lam = N / elapsed
    w = statistics.mean(samples)
    # 这里的 L 用吞吐乘平均响应时间，是实验窗口内的近似
    print(f"workers={workers:2d} throughput={lam:6.1f} req/s "
          f"W={w*1000:6.1f} ms L≈{lam*w:5.2f}")
```

这个实验中的服务没有排队时间被记录到 samples，因为每个任务在提交后才开始计时。要测端到端 W，应在提交前记录时间戳，并把等待线程池的时间算进去。修改函数，让参数携带 arrival_time，再比较“服务时间”和“系统时间”，可直接看到排队贡献。

### 实验 B：突发到达与百分位

```python
# tail_latency.py
import concurrent.futures as cf
import random, statistics, time

def run(workers, burst):
    submit = time.perf_counter()
    def one(i):
        arrival = time.perf_counter()
        # 混合短请求与长请求，构造服务时间变异
        delay = 0.01 if i % 10 else 0.20
        time.sleep(delay)
        done = time.perf_counter()
        return done - arrival, done - submit
    with cf.ThreadPoolExecutor(max_workers=workers) as ex:
        rows = list(ex.map(one, range(burst)))
    return [w for _, w in rows]

def pct(xs, q):
    ys = sorted(xs)
    return ys[min(len(ys)-1, int(q*len(ys)))]

for workers in [2, 4, 8]:
    xs = run(workers, 100)
    print(workers, "p50/p95/p99(ms)=",
          *(round(pct(xs, q)*1000, 1) for q in (0.50, 0.95, 0.99)))
```

比较 workers 和 burst 的组合，观察 p99 是否比 p50 增长得更快。再把长请求比例从 10% 改成 1%，记录尾延迟变化。不要只记录平均值；把每个样本保存为 CSV，才能复查百分位计算。

### 实验 C：Roofline 风格的带宽/计算对比

```python
# roofline_toy.py
import time, math

N = 20_000_000

def memory_bound():
    a = bytearray(N)
    b = bytearray(N)
    t0 = time.perf_counter()
    for i in range(N):
        b[i] = (a[i] + 1) & 255
    return time.perf_counter() - t0

def compute_bound():
    x = 1.001
    t0 = time.perf_counter()
    acc = 0.0
    for _ in range(N):
        acc = acc * x + math.sin(x)
    return time.perf_counter() - t0, acc

print("memory seconds", memory_bound())
print("compute seconds", compute_bound()[0])
```

Python 循环会受到解释器和函数调用影响，所以这个实验不是硬件 Roofline 测量；它只是让读者体验“搬运少量数据”和“执行更多算术”耗时不同。严肃测量应使用 NumPy、编译语言或框架 profiler，记录 FLOP、dram bytes、频率和温度。

### 实验 D：成本与能耗采样

在允许读取遥测的机器上，每隔 1 秒记录 GPU/CPU 功率、作业状态、有效请求数和 token 数。完成作业后按时间积分功率，计算 kWh 和每百万 token 能耗。至少做三次重复，报告均值、标准差和环境温度；将空闲基线与运行功率分开，避免把整机待机功率误归因于模型。

[测量] 每个实验都应包括预热阶段、稳定阶段和冷却/清理阶段。把首次导入、编译缓存和频率爬升混入稳定样本，会高估长期性能。

## 4.10 失败案例：公式用错时会发生什么

### 案例一：用 Little’s Law 把平均值当峰值容量

团队看到 λ=100 req/s、W=100 ms，于是计算 L=10，并把连接池设为 10。高峰时请求成批到达，p99 服务时间是 500 ms，重试率上升，真实并发迅速超过 10；连接池限制导致更多排队和超时。修复方式是使用峰值或分位负载、观察窗口、重试预算和故障余量，给 L 设动态上限而非单个平均值。

### 案例二：Amdahl 的 p 来自代码行数

工程师估计“GPU 代码占 90%”，购买更大 GPU 后只快了 10%。剖析发现 90% 是代码行数，不是时间占比；实际 45% 时间在 CPU 预处理和 Python 调度，30% 在数据拷贝，只有 25% 在 GPU kernel。修复方式是用时间采样和请求级 trace 得到 p，再计算收益上限。

### 案例三：只看理论 FLOP 峰值

将模型从 A 卡迁移到峰值 FLOP 更高的 B 卡，decode tok/s 几乎不变。Roofline 计数器显示 decode 处于内存带宽屋顶，B 卡带宽只提升 5%，而 kernel 启动和 KV cache 访问成为主因。修复方向是权重/缓存量化、布局优化、融合小算子和减少同步，而不是再追逐峰值 FLOP。

### 案例四：平均延迟下降，p99 变坏

批大小从 1 增到 16，平均吞吐翻倍，平均延迟下降 10%；但长请求与短请求混在同一批，短请求等待最长序列完成，p99 从 400 ms 升到 2 s。修复方式包括长度分桶、最大批等待时间、优先级队列和分别报告短/长请求 SLO。

### 案例五：成本按请求数线性扩容，账单却超预算

模型输入长度从 1k 增到 8k，输出不变；请求数没变，GPU 时间和 KV cache 显著增加，账单翻倍。按请求计费的仪表盘未显示异常。修复方式是按 input/output token、GPU 秒和上下文桶分层归因，设置长上下文配额与告警。

### 案例六：能耗测量漏掉空闲与网络

只采样 GPU 芯片功率，忽略 CPU、内存、风扇和 PUE，得出每百万 token 能耗很低。迁移到另一个机房后，碳排估算反而更高。修复方式是统一测量边界，报告 IT 能耗和设施能耗两个口径，并记录地点、时段与碳强度来源。

## 4.11 六个理解检查（含答案）

### 检查 1：Little’s Law

系统平均吞吐 30 req/s，平均端到端延迟 200 ms。估算系统内平均请求数。

**答案：** 把 200 ms 转为 0.2 s，L=30×0.2=6 req。它是观察窗口内的平均并发，不是最大并发、线程数或 p99 并发。

### 检查 2：排队边界

服务时间 S=50 ms，单服务台到达率 λ=18 req/s。利用率是多少？如果到达率升到 21 req/s，会发生什么？

**答案：** ρ=λS。18×0.05=0.9，已很接近饱和；21×0.05=1.05，长期平均服务能力不足，队列不稳定，延迟和超时会不断上升。多核/多副本会改变服务率，但仍需检查每个服务台和调度策略。

### 检查 3：Amdahl 上限

有 40% 时间无法优化，剩余 60% 最多快 5 倍。整体最大加速比是多少？

**答案：** `1/(0.4+0.6/5)=1/0.52≈1.92`。即使可优化部分无限快，上限也只有 2.5 倍；5 倍只是局部加速，不是端到端承诺。

### 检查 4：Roofline 区域

设备峰值 8 TFLOP/s、带宽 400 GB/s，算子算术强度 5 FLOP/Byte。理论上限更接近哪一侧？

**答案：** 交叉点 AI*=8,000/400=20 FLOP/Byte。AI=5 小于 20，带宽上限为 400×5=2,000 GFLOP/s，即约 2 TFLOP/s，属于带宽受限区。真实值还会受缓存、利用率、同步和指令效率影响。

### 检查 5：尾延迟与批处理

batch=1 时 p50=100 ms、p99=180 ms；batch=8 时 p50=90 ms、p99=900 ms。若 SLO 是 p99≤300 ms，应该选哪个？

**答案：** 不能只看 p50 或吞吐；在该 SLO 下 batch=8 不合格。可尝试长度分桶、限制批等待、拆分优先级或增加副本，再重新测量。若业务允许不同队列，可为离线和交互请求使用不同策略。

### 检查 6：成本量纲

GPU 价格 2 美元/GPU·小时，每请求平均使用 0.08 GPU·秒。仅计算 GPU 成本，每请求约多少美元？

**答案：** 2/3600 美元/GPU·秒，再乘 0.08，约 `0.0000444` 美元，即 4.44×10^-5 美元/请求。还未包括 CPU、内存、网络、存储、空闲、重试和观测成本。

## 4.12 练习：从手算走向实验

1. **容量预算。** 某接口峰值 120 req/s，目标平均 W≤250 ms，测得服务时间 p95=80 ms。用 Little’s Law 估算平均并发，再提出至少三项尾部余量（突发、重试、故障域、长请求等）。写出你选择余量的理由。
2. **排队曲线。** 用实验 A 改写为可控到达率 λ，绘制 ρ 从 0.2 到 0.95 时的 p50/p95/p99。比较均匀到达与成批到达，解释曲线分叉。
3. **Amdahl 方案评审。** 记录一次真实请求 trace，按网关、排队、预处理、模型、后处理、网络分段。假设每段各有一种优化，计算单独优化和组合优化的端到端收益，再验证至少两项。
4. **Roofline 点图。** 选择一个矩阵乘、一个逐元素算子和一个 KV cache 访问路径，估算 FLOP、字节和 AI；用 profiler 数据替代理论字节，解释两者差异。
5. **成本敏感性。** 建立电子表格或 Python 模型，变量包括请求量、输入/输出 token、GPU 价、利用率、重试率、PUE。对每个变量做±20% 扰动，列出对每百万 token 成本影响最大的前三项。
6. **能耗实验。** 对同一个模型运行 batch=1、4、8 三种配置，在相同有效 token 量下测量 IT 能耗和 p99。找出满足 SLO 的最低能耗点，并说明测量不确定性和重复次数。
7. **失败复盘。** 选择一个“平均性能很好但线上投诉很多”的案例，写出时间线、错误指标、被忽略的分布、错误公式以及一项防回归监控。
8. **设计边界。** 写一页“何时不使用本章公式”：例如系统未稳定、请求在观察窗口内持续积压、资源被强抢占、成本价格动态变化。为每种情况指定替代测量或仿真方法。

[设计判断] 练习的评分重点不是算出唯一数字，而是说明单位、假设、样本、误差和下一步实验。一个带有不确定性范围、但可复现的估计，优于一个看似精确却无法追溯的数字。

## 4.13 来源地图：每条结论该回到哪里

本章没有把公式当作孤立口诀，建议沿下列来源和工具继续验证。阅读时区分“原始定律”“教材推导”“实现文档”和“本地测量”。

- **Little’s Law**：John D. C. Little 关于排队系统平均值关系的原始论文与排队理论教材。重点核对稳定性条件、长期平均定义和观察窗口。
- **排队模型**：M/M/1、M/G/1 与 Kingman 近似的经典排队教材。重点理解到达/服务变异性、ρ 接近 1 时的非线性，以及多服务台模型的差异。
- **Amdahl 定律**：Gene Amdahl 关于大规模计算系统并行性的原始论文。重点核对固定问题规模、串行比例和通信/同步开销。
- **Gustafson 定律**：John Gustafson 关于大规模并行计算的论文。重点理解固定时间、扩大问题规模的前提，不把它误当在线延迟保证。
- **Roofline 模型**：Williams、Waterman、Patterson 的 Roofline 论文及 Berkeley 相关教学材料。重点核对算术强度、峰值 FLOP/s、内存带宽和测量字节数。
- **硬件计数器与分析器**：CPU 的 perf、厂商 GPU profiler、框架 profiler 文档。重点查看 FLOP、内存流量、缓存命中、kernel 时间、频率和功率计数的定义。
- **百分位与可观测性**：OpenTelemetry、Prometheus histogram、HDR Histogram 等文档。重点检查客户端/服务端时间点、分桶误差、窗口聚合和高基数标签。
- **云价格与计费**：所用云厂商的实例、GPU、网络、存储和日志计费页面。每次报告记录检索日期、区域、货币、承诺折扣和最低计费粒度。
- **能耗与碳排**：设备遥测接口、数据中心 PUE 报告和当地电网碳强度数据。明确 IT 与设施边界，报告采样频率和碳强度时段。

[测量] 建议在仓库中维护 `benchmarks/` 目录：保存脚本、输入样本摘要、环境信息、原始 CSV、分析代码和结论。结果页面只展示可复现命令和 commit；不要只上传一张经过筛选的图。

## 4.14 本章小结

1. 用量纲和边界定义性能问题，防止速率、数量、时间和成本单位混淆。
2. Little’s Law `L=λW` 把吞吐、并发和平均停留时间连接起来；接近饱和时排队和尾延迟会非线性增长。
3. 平均延迟不能代替 p95/p99；流式生成要分别看 TTFT 和 TPOT，吞吐也必须说明 token 和批处理口径。
4. Amdahl 说明串行部分限制整体收益，Gustafson 说明扩大问题规模时并行价值可能不同；二者都需要真实时间占比。
5. Roofline 用算术强度判断算子更接近带宽屋顶还是算力屋顶；LLM prefill 与 decode 可能处于不同区域。
6. 成本与能耗模型要按请求、token、GPU 秒、利用率、重试、PUE 等维度归因，并进行量纲与敏感性检查。
7. 公式只是可反驳的假设。通过受控实验、分布记录、重复测量和失败复盘，才能把性能数学变成可执行的工程决策。

## 4.15 进阶排队：开放系统、封闭系统与多级队列

### 4.15.1 开放系统和封闭系统

开放系统的请求从系统外部到达，完成后离开，适合公共 API、消息入口和批处理提交。到达率 λ 由用户或上游服务决定，系统必须通过限流、排队和扩容来应对变化。封闭系统有固定数量的客户端，客户端收到响应后才发出下一次请求，常见于压测工具中的固定并发模型。封闭系统的“并发数”由客户端控制，吞吐与响应时间相互影响；只增加客户端线程，不一定增加有效吞吐。

[机制] 在封闭系统里，常用交互响应时间定律：`N = X × (R + Z)`，其中 N 是循环中的客户端数，X 是吞吐，R 是响应时间，Z 是客户端思考或发送间隔。它与 Little’s Law 相似，但把系统外等待 Z 显式分开。压测工具如果用固定并发而不是固定到达率，负载会随着响应变慢自动降低；这可能掩盖系统饱和点。

[测量] 压测报告应写明负载模型：开放式（固定 req/s）、封闭式（固定并发）、阶梯式（逐步增加）、突发式（短时峰值）还是基于真实日志回放。不同模型回答的问题不同，不能直接比较一张曲线上的数字。

### 4.15.2 多级队列和瓶颈传播

一个请求可能依次经过入口线程池、CPU 预处理队列、GPU 批调度队列、磁盘缓存和下游 API。每一级都可用局部 Little’s Law 估算，但局部队列的输出到达率会被上游阻塞和重试改变。若 GPU 队列变慢，上游连接会堆积，网关线程被占满，最终看起来像网络故障。若下游 API 超时触发重试，输入流量会被放大，形成反馈回路。

[设计判断] 对每个关键队列记录入队时间、出队时间、服务开始和完成时间；不要只记录一个总耗时。建立请求 trace 后，可计算每一级的等待比例和队列长度。告警应优先关注“队列增长速度”和“重试放大因子”，而不只是 CPU 百分比。

### 4.15.3 优先级、抢占与公平

交互请求和离线作业共享 GPU 时，先进先出未必满足业务目标。优先级队列可以降低交互 p99，却会让低优先级作业饥饿；抢占可能需要保存中间状态，增加上下文切换和缓存失效。公平调度可以按租户、用户或 token 配额分配资源，但公平不等于每类请求拥有相同延迟。

应定义清晰的调度目标：例如高优先级请求 p99<300 ms、低优先级保持每小时完成至少一批、任一租户不得占用超过 40% GPU 秒。把目标写成约束后，再比较加权公平、令牌桶、时间片或分离实例的成本。只说“优先保证线上”会留下不可测试的冲突。

## 4.16 统计严谨性：重复、置信区间与回归判定

### 4.16.1 预热和样本独立性

第一次运行可能触发导入、JIT 编译、内存映射、GPU 频率提升或文件缓存。应把预热样本单独标记，不要静默删除。若每个请求共享同一个批次、缓存或连接，样本并不独立；简单地把数千条记录当作独立样本会夸大统计置信度。

[测量] 一个可复现实验至少包含：预热次数、稳定测量时长或样本数、并发/到达率、随机种子、输入分桶、失败和超时处理、环境温度、软件版本。性能回归测试应固定这些条件，生产容量测试则应额外加入真实分布和扰动。

### 4.16.2 百分位的置信区间

p95 和 p99 由排序样本的尾部决定，样本少时波动很大。可使用 bootstrap 重采样估算百分位区间：从原样本有放回地抽取同样大小的数据，重复多次，得到 p99 的分布，再报告中位数和 5%～95% 区间。也可使用专门的 HDR Histogram 保存长尾而不把所有原始值放入内存。

[边界] 不能把同一批请求的 p99 置信区间当作跨天稳定性保证。部署、温度、邻居负载和输入分布变化会产生系统性偏差，需在多次独立运行或多时间窗口上重复。

### 4.16.3 回归阈值与实用显著性

统计显著的 1% 变化未必值得上线；统计不显著的 p99 恶化却可能违反 SLO。建立回归门槛时同时考虑：平均值或 p50 的变化、p95/p99 的变化、错误率、吞吐、成本、能耗和样本量。可以规定“p99 恶化超过 10% 且置信区间大部分为正，阻断发布；平均延迟改善但成本增加超过 20%，需评审”。阈值是治理选择，应写进 CI，而不是每次看图临时决定。

## 4.17 性能模型的反例与修正方法

### 4.17.1 非平稳流量

Little’s Law 在长期平均意义下仍有用，但短窗口内若流量持续爬坡，系统尚未稳定，`L=λW` 的瞬时解释会误导。修正方法是分段分析：在每个近似平稳窗口内计算 λ、W、L，并报告窗口边界；对爬坡过程使用离散事件仿真或直接回放时间戳。

### 4.17.2 资源共享和干扰

Amdahl 假设阶段比例固定，但多租户 GPU、NUMA 远端内存、容器 CPU 限额和后台检查点会改变阶段时间。修正方法是把干扰变量纳入实验设计，例如分别测量独占、同节点共享、网络拥塞三种条件，并为每种条件建立独立基线。

### 4.17.3 动态频率和热状态

Roofline 使用峰值 FLOP/s 与带宽，实际设备会因功耗墙、温度、风扇曲线或频率策略降速。长时间作业的后半段可能比前半段慢。修正方法是同时记录温度、时钟、功率和作业时间；报告冷启动、稳态和热稳态三段数据。若性能随时间下降，容量模型应使用稳态下限而不是瞬时峰值。

### 4.17.4 精度、压缩与质量约束

量化或压缩通常降低字节数和成本，但可能改变数值误差、输出质量和重试率。若只把模型大小代入成本公式，不记录质量门槛，节省的 GPU 秒可能被人工复核和请求重试抵消。修正方法是把质量指标作为成本模型的约束，例如在准确率、拒答率或人工通过率达到阈值后比较每百万 token 成本。

### 4.17.5 缓存命中和重复工作

请求缓存会降低平均服务时间，但命中率随输入分布、租户隔离和 TTL 变化。把缓存命中请求与未命中请求混合，会让 Amdahl 的阶段比例失真。修正方法是分别报告命中率、命中/未命中 W、缓存写入成本和失效风暴；容量规划按未命中峰值留余量。

## 4.18 建立团队级性能契约

个人实验能发现问题，团队契约才能让结果可累积。推荐每个性能报告包含以下字段：

1. **问题定义**：服务、版本、工作负载、目标 SLO、允许的质量变化。
2. **环境**：硬件、驱动、操作系统、容器资源、频率/功耗策略、区域与价格。
3. **输入分布**：请求率时间序列、输入/输出 token 分布、长短请求比例、重试和错误处理。
4. **测量点**：客户端、网关、队列、模型、设备、下游；时钟来源和是否包含网络。
5. **统计方法**：预热、样本数、百分位算法、置信区间、异常处理和随机种子。
6. **结果**：p50/p95/p99、吞吐、错误率、资源、成本、能耗、质量指标和原始数据路径。
7. **结论与边界**：支持什么决策、不能推断什么、下一步实验、回滚条件。

[设计判断] 契约的作用不是增加文档负担，而是让“快了 20%”可被另一位工程师在另一台机器上复查。对于高风险变更，要求至少一次独立复现实验；对于低风险调参，也应保留输入和命令，避免只剩截图。

可以在 CI 中加入三层检查：

- **快速单元基准**：几十秒内检查算子或序列化是否出现明显回归。
- **服务微基准**：固定负载和短时运行，检查 p95、吞吐、内存峰值和错误率。
- **夜间容量测试**：真实分布回放，检查长尾、热稳态、成本和能耗趋势。

每层都设置容许噪声，只有超过阈值才阻断；噪声范围应由历史重复实验估计。基准失败时保留环境、日志和原始样本，禁止只重跑直到“通过”。

## 4.19 迁移到生产决策的检查清单

在宣布“性能优化完成”前，逐项回答：

- 目标是降低 p99、提升吞吐、降低每 token 成本，还是降低峰值内存？是否有互相冲突的目标？
- 负载是否覆盖峰值、长上下文、突发、重试和多租户？
- 端到端时间是否拆出了排队、服务、网络和下游？
- Little’s Law 的 λ、W、L 是否来自同一观察窗口？系统是否稳定？
- Amdahl 的时间占比是否由 trace 测量，还是凭代码行数猜测？
- Roofline 的 FLOP 与 Byte 是否是实际计数，还是理论值？设备是否处于稳态频率？
- 成本是否包含空闲、重试、观测、网络、存储、折扣和最低计费粒度？
- 能耗边界是否包含 CPU、内存、风扇、PUE 和碳强度来源？
- 质量、准确率、安全拒答或人工复核是否因优化而变化？
- 是否有回滚开关、监控面板、告警阈值和容量余量？

如果其中一项无法回答，结论应标记为“待验证”，而不是写成生产承诺。工程决策可以在信息不完整时做出，但不应隐藏信息缺口。

## 4.20 术语速查与最小复盘模板

为了让跨团队讨论不被同义词拖慢，建议在报告开头写出以下术语的具体口径。**请求延迟**指客户端发出到收到完整响应；**服务时间**指服务器占用关键资源的执行区间；**排队时间**指请求等待可执行位置的时间；**吞吐**指在给定统计窗口内成功完成的工作量除以窗口时长；**并发**指同一时刻处于系统边界内的请求数；**利用率**指资源忙碌时间除以墙钟时间；**峰值**指指定窗口或指定百分位下的最大负载，而不是无限时间的绝对最大值；**成本**指明确边界内的货币消耗；**能耗**指功率对时间的积分。

最小复盘模板可以只有一页：

- 目标：在输入分布 D、到达率 λ 和版本 V 下，把 p99 从 A 降到 B，同时错误率不超过 C。
- 观测：记录 W、Q、S、TTFT、TPOT、吞吐、GPU 秒、token、功率和质量指标。
- 模型：使用 Little’s Law 估算并发，使用 Amdahl 计算可达上限，使用 Roofline 判断带宽或算力屋顶，使用成本公式估算每百万 token 费用。
- 实验：预热 H 次，稳定采样 M 个请求，重复 R 轮，保留原始数据与命令。
- 结果：给出点估计、范围、p50/p95/p99、输入分桶和失败请求比例。
- 决策：说明是否上线、需要哪些余量、如何监控、何时回滚。
- 未知：列出尚未测量的变量和对结论最敏感的假设。

把未知项显式写出来并不会削弱报告，反而让读者知道下一步应测什么。性能数学的成熟标志不是能够背出更多公式，而是能在不同系统、不同负载和不同成本约束下，快速判断哪个公式适用、哪个假设已经越界，以及用什么最小实验把争论变成证据。
