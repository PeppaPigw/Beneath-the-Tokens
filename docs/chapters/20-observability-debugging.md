# 第20章　可观测性与调试：metrics、logs、traces、profiling 与事故响应

> AI 系统出故障时，最危险的回答是“看起来 CPU 很低，所以没问题”。请求可能在网关排队、tokenizer 阻塞、GPU kernel 等待、显存页池耗尽、跨节点重试，或因安全策略拒答；平均 CPU 利用率无法区分这些状态。可观测性不是把所有数据都采集一遍，而是定义能够支持行动的信号、时间和因果关系。本章把 metrics、logs、traces、profiling、GPU telemetry 和事故响应放在同一条证据链上：先明确用户可感知的症状，再寻找边界变化，最后通过受控实验验证根因。所有示例都标注事实、机制、测量、推断和设计判断；CPU toy 只说明方法，不能证明任何生产容量或故障率。

## 20.0 一句话心智模型与前置

一句话心智模型：**可观测性是把一次请求在时间、资源、数据和决策上的因果路径压缩成可检索证据；调试是用证据淘汰假设，事故响应是先降低用户影响，再恢复可验证的正确服务。** metrics 适合看总体趋势和分位数，logs 适合记录离散事实，traces 适合关联跨组件时序，profiling 适合定位 CPU、GPU、内存和锁的成本来源。四种信号互相补足，任何单一信号都不足以解释 AI 系统。

阅读本章前，读者应理解 HTTP/gRPC、时间序列、分位数、线程与异步 stream、Kubernetes Pod、GPU 运行时和第15至19章中的队列、批处理、KV cache、拓扑、Ray 与优化栈。完成本章后，读者应能画出请求从入口到模型、工具和 GPU 的 span 图，解释 p99、错误率、饱和度和质量指标之间的关系，构造一条可重放的故障假设，并完成一个包含遏制与回滚的事故时间线。

本章默认使用四类证据标签。**事实**表示规范、官方文档或论文直接说明的行为；**机制**表示根据实现推导出的数据流；**测量**表示在声明环境中运行实验所得的数值；**推断**表示由多项证据合并得到的解释；**设计判断**表示在给定风险、预算和合规约束下的建议。标签不是形式主义：把推断写成事实，会让事故响应过早锁定错误根因。

## 20.1 AI 系统的可观测性边界

### 20.1.1 从用户症状开始

用户通常报告“响应很慢”“答案变差”“偶尔失败”“工具调用重复”或“服务不可用”。这些是症状，不是组件名。将症状拆成服务等级目标（SLO）时，至少要分请求成功率、首 token 延迟、每 token 间隔、完整响应时间、结构化输出合法率、工具成功率、拒答准确率、成本和资源使用率。对于批任务，还要记录完成时间、重试次数、丢失任务和数据质量检查。一个只跟踪 HTTP 200 的系统可能在生成错误 JSON 或错误工具参数时仍显示“健康”。

**机制**上，AI 请求经过网关认证、路由、排队、tokenizer、模型 prefill、decode、采样、工具执行、后处理和传输；每阶段都会改变延迟和失败概率。应把每阶段的开始、结束、结果类别和资源预算写入统一语义，而不是由每个团队任意命名。**设计判断**：先定义用户可感知的预算，再把预算分配到阶段；若无法说明一个指标超预算会触发什么操作，就不要采集它。

### 20.1.2 四个黄金信号的 AI 版本

经典的延迟、流量、错误、饱和度可转换为 AI 语境。延迟包括队列等待、TTFT、ITL、工具回合、完整响应和取消清理；流量包括请求数、输入 token、输出 token、批次大小、工具调用和重试；错误包括状态码、模型错误、超时、OOM、策略拒答、格式校验失败和依赖错误；饱和度包括 GPU SM、显存、HBM 带宽、KV 页池、CPU run queue、网络带宽、编译队列和日志管道积压。

“错误率下降”并不一定代表服务恢复。若流量下降是因为网关拒绝请求，错误率按完成请求计算可能变好；若模型以空答案成功返回，HTTP 指标也会变好。应同时计算到达量、接受量、完成量、拒绝量和取消量，并用同一时间窗对齐分母。分母定义必须写在指标描述中，例如“每分钟失败请求数除以接受请求数”，不要让查询者猜测。

### 20.1.3 质量、成本和安全是信号的一部分

AI 服务的质量常是延迟和错误之外的隐性维度。可用代理包括 JSON schema 合法率、检索命中率、工具参数通过率、人工抽样评分、事实性评估、拒答策略命中率和安全分类器告警。代理指标不能替代真实质量，但能在事故期间快速发现“服务在线、结果失真”。在线质量日志必须去除完整用户内容，仅保留经过同意的摘要、哈希或安全类别。

成本指标包括每请求 GPU 毫秒、输入和输出 token、显存驻留秒数、跨节点字节和外部 API 调用次数。把成本与请求 ID 或租户策略域关联，才能发现某租户因长上下文或工具重试占用大量资源。安全信号包括凭据访问拒绝、跨租户缓存命中、策略版本不一致、异常调试接口调用和审计日志丢失。**设计判断**：优先采集能同时指导稳定性、成本或安全动作的信号，避免“只看热闹”的仪表盘。

## 20.2 Metrics：语义、分位数与高基数

### 20.2.1 计数器、仪表、直方图与摘要

计数器适合累计请求、错误、重试和 token；仪表适合当前队列长度、GPU 温度、显存使用；直方图适合延迟、请求大小、批次大小和生成 token 数，因为它能在聚合后近似计算分位数；摘要型分位数在多实例聚合时容易失真，必须确认实现是否支持可合并的分位数。计数器重启后归零并不表示业务事件减少，查询时应使用速率或增量函数。

延迟直方图的桶边界决定能否回答“p99 是否超过 1 秒”。若所有样本落在一个宽桶中，分位数会过于粗糙；桶过多又增加存储和 CPU。可按业务预算设置密集边界，例如在 TTFT 预算附近细分，在超长尾使用对数增长。**测量**：先用历史样本估计分布，再验证桶误差；不要复制某个项目的默认桶并假设适合自己的长上下文流量。

### 20.2.2 标签设计与高基数陷阱

标签应描述可聚合的维度，如模型族、版本、区域、GPU 型号、路由、输入长度桶、输出长度桶和错误类别。请求 ID、完整 URL、用户文本、随机 trace ID、时间戳和无界工具名称都可能产生高基数。把这些值直接放进时间序列，会让内存、索引、查询和远端写入成本随请求数增长。

高基数不等于“永远不能记录”。将高基数值放在结构化日志或 trace 中，使用 metrics 中的低基数摘要和 exemplars 关联少量样本。对租户可先按策略域或匿名租户组聚合，必要时只在受控调试窗口采样。**设计判断**：每新增一个标签，先估算实例数乘标签组合数乘采样频率，并设置预算和自动拒绝机制；指标注册表应由审查人批准，禁止业务代码随意拼接 label。

### 20.2.3 Exemplars：从总量跳到样本

Exemplar 是附在 metrics 样本上的少量关联信息，常见是 trace ID、请求版本或测试用例摘要。它允许工程师在看到 p99 峰值时跳到一条代表性 trace，而不必把所有请求 ID 作为指标标签。exemplar 本身也需采样、过期和权限控制，不能携带 prompt、凭据或个人敏感内容。

使用 exemplar 的步骤是：先在直方图上定位异常时间窗，再选择同窗内的 exemplar，打开 trace 查看阶段分解，最后回到日志或 profile 验证设备事件。**机制**上，exemplar 只是索引，不保证该样本代表整个尾部；尾延迟常由少数形状、租户或重试构成，因此要对多个 exemplar 交叉检查。**反例**：看到一条包含 OOM 的 trace 就把所有 p99 归因于显存，忽略同时发生的网络重传。

### 20.2.4 GPU telemetry 指标

GPU 指标至少分为设备健康、利用率、内存、互联和任务关联五层。设备健康包括温度、功耗、时钟、ECC/XID、重置计数、驱动和固件版本；利用率包括 SM 活跃度、张量核心活跃度、显存读写、L2 命中和 PCIe/NVLink 流量；内存包括已分配、驻留、碎片、页池高水位、workspace 和 pinned host memory；互联包括链路状态、重传和拓扑；任务关联包括 GPU UUID、进程、容器、模型版本和 kernel 时间。

工具常提供不同时间粒度与聚合方式。设备采样可能每秒一次，短暂的 kernel 尖峰会被平均掉；进程级采样可能看不到 MIG 或共享设备的全局压力。**设计判断**：对容量监控使用低频长期采样，对事故窗口使用短期高频采样，并记录采样开销和时间同步误差。GPU telemetry 不应默认开启会影响 kernel 调度的重型 profiling。

### 20.2.5 时间与单位的一致性

指标必须明确单位和时间语义。显存用字节还是 MiB、功耗用瞬时瓦特还是窗口平均、token/s 按生成 token 还是接受 token、队列长度是请求还是 token，都应在描述中固定。跨主机时钟漂移会破坏 trace 排序；使用单调时钟测时，同时保留可转换到墙上时间的校准信息。GPU event、CPU wall clock 和日志时间戳需要一份偏移估计，不能简单比较字符串时间。

## 20.3 Logs：离散事实、结构化和采样

### 20.3.1 一条日志应回答什么问题

日志不是“把变量全部打印出来”。一条有用日志应说明事件发生在哪里、何时发生、对哪个请求、结果是什么、下一步动作是什么。字段可包含事件类型、服务、实例、版本、trace/span ID、模型摘要、输入输出长度桶、阶段、错误类别、重试序号、租户策略域、资源上下文和建议动作。完整 prompt、生成内容、访问令牌、内部路径和堆栈中的秘密不应默认记录。

结构化日志使用稳定键和枚举值，便于聚合。错误消息中的动态文本应放在受控字段中并截断；否则同一错误会被分裂成数千条字符串。对异常堆栈保存哈希和受限样本，避免日志注入与敏感数据扩散。日志级别可按版本和实例动态调整，但配置变化必须审计并自动过期。

### 20.3.2 日志采样与保留

稳定路径可按比例采样，错误、超时、策略拒答和安全事件应有独立保留策略。头部采样在请求早期决定是否记录，尾部采样可根据最终延迟和错误选择保留，但需要暂存 span 或日志直到请求结束，增加内存压力。长流式响应可能持续很久，必须设定最大缓冲大小和超时。

保留期应按用途分层：实时事故数据保存短期、脱敏性能样本保存中期、审计事件按法规和组织政策保存。删除不仅是删除对象，还要验证索引、缓存、副本和备份是否不再可查询。**设计判断**：把保留期、访问角色和删除验证写入数据契约，而不是在事故后临时清理。

### 20.3.3 日志背压与自耗尽

日志管道是系统的一部分。网络拥塞、索引限流或代理重启会导致应用线程阻塞、丢日志或内存增长。应用不应因日志后端不可用而无限等待；采用有界队列、非阻塞写入、丢弃低优先级事件和计数器告警。高优先级安全事件要有本地加密缓冲和完整性校验，恢复后按顺序补传。

事故期间临时提高日志级别可能放大负载。应先设置全局字节预算、每实例速率限制和字段脱敏，再逐步增加采样。若日志本身导致 p99 变差，必须能一键回到安全默认值。日志自耗尽是“为了观察系统而让系统崩溃”的常见二次事故。

## 20.4 Traces：跨服务时序与因果线索

### 20.4.1 Span 语义

一次请求可建根 span，并为网关、路由、排队、tokenizer、prefill、decode、工具调用、数据库、GPU 执行和输出流建立子 span。每个 span 应包含开始结束时间、状态、事件和少量低基数属性。异步任务要记录链接关系，而不是伪造父子顺序；批处理中的多个请求共享一个 GPU span 时，可用 span link 或批次事件表达成员关系。

Span 名称应表示稳定操作，如 `model.prefill`、`model.decode`、`tool.call`，不要把用户输入拼进名称。属性可记录模型版本、输入长度桶、batch size、GPU UUID、engine profile 和回退原因。完整 token 或 prompt 只应在受控、脱敏且获授权的调试通道中出现。

### 20.4.2 采样策略

头部采样适合控制成本，但可能错过长尾；尾部采样可按总延迟、错误、重试、租户策略域和质量异常保留。尾部采样需要在 collector 暂存并有上限，不能无限等待流式请求。对高风险安全事件应有强制留痕通道，和普通性能 trace 分开存储与授权。

采样概率影响误差估计。若只保留慢请求，trace 集合不再代表总体，不能直接用它计算平均延迟。报告中要同时给出样本数、采样率、选择规则和未采样指标。**推断**：如果 trace 显示慢请求多数来自某 GPU 型号，但该型号本身只保留了错误样本，结论可能是采样偏差而非硬件问题。

### 20.4.3 分布式上下文与批次

跨 HTTP、消息队列、Ray task、GPU worker 和工具服务传递 trace context 时，要定义可信边界。外部请求提供的 trace ID 不能直接作为高权限审计主键；可重新生成内部 trace，并把外部 ID 做不可逆关联。消息重试应创建新的 span，链接到原始消息，以区分一次业务操作的多次传输。

动态批处理使一个 kernel 同时服务多个请求。将每个请求的 span 直接嵌入 kernel 时间可能产生巨量事件；可记录批次 span、成员数、长度桶和每请求排队偏移，必要时对异常成员采样。解释 p99 时要区分“在批次里等待”与“kernel 本身慢”。

### 20.4.4 GPU trace 与 CPU trace 对齐

CPU 线程提交异步 GPU kernel 后可能立即返回，CPU span 结束不代表设备完成。使用 CUDA event、GPU profiler 时间线或运行时回调获取设备时间，并把流、上下文、kernel 名和批次 ID 关联。避免在生产请求路径上无条件同步；同步会改变重叠和调度，导致测量污染。

当无法获取细粒度 GPU span 时，可用阶段级近似：记录 kernel 数量、累计设备时间和同步等待时间，并标记为推断。对关键事故，在隔离副本上运行短时重型 profile 验证，完成后关闭。**设计判断**：生产默认轻量、事故按需加深、每次加深都有自动过期和回滚。

## 20.5 Profiling：CPU、GPU、内存、I/O 和 eBPF

### 20.5.1 Profiling 与 tracing 的边界

Tracing 关注一次请求跨组件的时间关系，profiling 关注进程或设备在一段窗口内把时间花在哪里。CPU profile 可以显示函数栈、线程状态和锁等待；GPU profile 可以显示 kernel、占用率、内存事务和 stream 重叠；内存 profile 显示分配、释放和泄漏；I/O profile 显示磁盘、网络、页错误。把 profile 当作 trace 的替代品会失去请求上下文，把 trace 当作 profile 会看不到函数级热点。

采样 profiler 通常比插桩开销低，但短函数、低频路径和内核态阻塞可能被漏采；插桩能给出精确阶段却增加开销。选择工具前先写问题，例如“CPU 空闲但 p99 增加，线程是否在 futex 等待？”而不是“开 profiler 看看”。窗口、采样频率、线程范围和开销都要记录。

### 20.5.2 CPU profiling 与锁竞争

Linux `perf`、火焰图和语言运行时 profiler 可显示计算热点、系统调用、锁等待、垃圾回收和解释器开销。AI 服务常见误区是把 Python CPU 占用低解释为没有瓶颈；线程可能在 GIL、futex、队列条件变量、磁盘或网络等待。运行队列、上下文切换、软中断和 cgroup CPU throttling 需要一起观察。

火焰图宽度代表采样时间，不等于单次请求延迟；异步任务和线程池会把调用栈切断。结合 trace 的 span 时间和日志中的批次 ID，才能判断热点属于哪类请求。对生产 profile 要限制权限和读取范围，避免通过内核符号、文件路径或请求参数泄露信息。

### 20.5.3 GPU profiling 与 kernel 选择

Nsight Systems 类系统级工具适合看 CPU/GPU timeline、stream 重叠、通信和同步；Nsight Compute 类工具适合看单 kernel 的占用率、内存吞吐和指令。框架 profiler 可快速关联算子，但可能将异步时间归因到错误线程。GPU profile 的结论依赖驱动、CUDA、时钟、功耗和输入形状，换一代卡或换 batch 后不能直接外推。

**机制**上，低利用率可能是 kernel 太短、并发不足、同步过多、显存带宽饱和、设备被限功率或 host 供给不足。必须同时查看 SM、内存、等待、kernel 数和 CPU 提交速率。若 profiler 让请求变慢，使用隔离副本或低采样率。任何 profile 输出都应绑定模型、engine、驱动和硬件摘要，以便复现。

### 20.5.4 eBPF：内核视角的低侵入线索

eBPF 可在内核事件、系统调用、网络、调度、块 I/O 和 cgroup 层采样，帮助回答“应用说在等待，但内核让它等什么”。常见观测包括 run queue 延迟、TCP 重传、磁盘延迟、页错误、容器 CPU throttling、进程启动和 OOM kill。工具如 bpftrace、BCC 或基于 libbpf 的 agent 具有不同开销和权限要求。

**事实**：eBPF 程序受验证器、内核版本和权限限制，不能默认在所有节点加载；生产使用需审批能力、程序签名和资源上限。**设计判断**：把 eBPF agent 视为高权限软件，限制 map 大小、采样频率、挂载点和输出字段，使用只读节点观测身份。不要让临时脚本将命令参数、socket payload 或用户内容写入共享日志。

### 20.5.5 内存与泄漏分析

AI 服务的内存问题分为堆泄漏、显存碎片、KV 页未归还、对象存储堆积、文件描述符和连接泄漏。RSS 上升不一定是泄漏，可能是分配器缓存；显存占用不下降也可能是框架缓存池。用分配/释放事件、对象生命周期、GC、页池高水位和请求结束清理计数进行区分。

在事故中先保护容量：限制新请求、拒绝超长上下文、触发可控回收或重启副本，再做详细 dump。内存 dump 可能包含 prompt、权重片段和凭据，应在隔离环境加密、设置短保留期并严格授权。任何“为了分析先上传 dump”的建议都要经过敏感数据审查。

## 20.6 因果排障：从症状到可验证假设

### 20.6.1 先建立时间线

排障第一步不是打开十个 dashboard，而是建立用户影响、开始时间、变化事件和当前范围的时间线。记录部署、配置、流量、模型、驱动、节点、证书、依赖和安全策略的变更；标出第一个违反 SLO 的指标及其分母。使用统一时间源并保留“未知”而不是猜测。

时间相关不等于因果。若 GPU 温度和错误率同时上升，可能共同由流量导致；若回滚后恢复，也要确认回滚是否改变了流量或实例数量。每个假设写成“如果 H，则应观察到 E；若没有 E，则降低 H 概率”，并指定低风险验证动作。

### 20.6.2 阶段化二分

把请求路径按边界二分：入口与依赖、排队与调度、CPU 预处理、GPU 计算、网络与输出、质量与安全。先比较健康实例和异常实例，再比较同一实例异常前后。使用对照组、固定输入、限流和只读查询，避免边排障边改变系统。

例如 p99 TTFT 上升时，可依次检查：入口时间是否上升；队列等待是否上升；tokenizer CPU 是否被 throttling；prefill GPU 设备时间是否变长；批次大小和长度是否变化；跨节点复制是否增加。若只有总延迟上升而各阶段和仍不匹配，优先查未插桩的网络、锁或时钟误差，而不是强行归因模型。

### 20.6.3 反事实和受控实验

反事实问题是“如果保持流量、模型和硬件不变，只关闭某个开关，会发生什么”。可在隔离副本禁用动态批处理、回退 engine、关闭缓存或切换驱动，再测同一输入分布。实验必须有停止条件、流量上限和回滚路径。线上直接改全局配置会把验证变成扩大事故。

使用差分中的差分时，至少保留健康对照池。例如新 engine 在两个区域发布，一处保留旧 engine；比较两处在相同流量和 GPU 型号上的变化，可减少季节和流量噪声。**推断**：若只有新 engine 区域出现 kernel 时间增加且回退后恢复，根因候选比“所有 GPU 变慢”更强，但仍需检查该区域是否有不同驱动。

### 20.6.4 常见证据错误

相关性错误：GPU 利用率高与超时同时出现，不代表 GPU 是根因，可能是重试把 GPU 填满。选择偏差：只分析报错请求，忽略成功请求的相同配置。幸存者偏差：被拒绝或取消的请求未进入延迟直方图。时间错位：日志使用墙上时间，GPU profile 使用设备时间，错误地把事件顺序反转。聚合辛普森悖论：全局 p99 变好，但长上下文租户变差。

排障笔记应记录样本选择、缺失数据、时间范围和不确定性。不要在没有证据时写“已确定根因”；可写“当前最可能假设”和下一步验证。事故结束后回顾哪些观测缺失，转化为新的指标、span 或演练场景。

## 20.7 CPU incident toy：重现队列堆积与锁竞争

### 20.7.1 实验目标与边界

本 toy 用 Python 标准库模拟一个入口线程、有限 worker、共享锁和处理队列。通过增加慢任务比例或锁持有时间，观察队列、p95 延迟、错误预算和吞吐变化。它不模拟 GPU、网络、真实模型或操作系统调度细节，任何数字只用于展示测量方法。完整脚本保存为 `ch20_cpu_incident.py`，默认不需要第三方包。

实验步骤是：固定随机种子和请求数；先运行健康基线；再运行锁竞争场景；保存每个请求的到达、开始、结束、状态和阶段；计算 p50/p95、拒绝率、队列峰值和 worker 利用率；最后比较 trace-like 事件与聚合 metrics。运行前先确认机器 CPU 余量，避免影响其他任务。

### 20.7.2 最小代码

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Lock
from time import monotonic, sleep
import random, statistics


def run_case(n=200, workers=4, slow_ratio=0.0, lock_hold=0.0, seed=7):
    rng = random.Random(seed)
    gate = Lock()
    queue_depth = 0
    samples = []

    def one(i):
        nonlocal queue_depth
        arrived = monotonic()
        queue_depth += 1
        try:
            with gate:
                started = monotonic()
                if rng.random() < slow_ratio:
                    sleep(lock_hold)
                sleep(0.002)
            finished = monotonic()
            samples.append((i, arrived, started, finished, queue_depth))
        finally:
            queue_depth -= 1

    with ThreadPoolExecutor(max_workers=workers) as pool:
        list(pool.map(one, range(n)))
    latencies = [x[3] - x[1] for x in samples]
    latencies.sort()
    p95 = latencies[max(0, int(0.95 * len(latencies)) - 1)]
    return {"count": len(samples), "p50": statistics.median(latencies),
            "p95": p95, "max": max(latencies)}
```

代码中的 `queue_depth` 不是线程安全计数器，故意保留为教学反例：真实 instrumentation 应使用锁、原子变量或队列本身提供的计数，并在 finally 路径更新。`rng` 在多个线程共享也会使事件顺序与随机消费难以重放；生产实验应为每个 worker 使用独立随机源。toy 只展示“如何从数据计算分位数”，不应直接复制到线上。

### 20.7.3 预期观察与解释

健康场景中，p50 和 p95 接近，随着 worker 增加吞吐上升；锁竞争场景中，p50 可能只略升，但 p95 和最大值显著上升，队列形成长尾。若慢任务比例提高，worker 利用率接近满载，新增请求的排队时间先增长，随后可能触发超时和拒绝。若只看平均处理时间，不会看到长尾。

**测量**：应保存原始事件，再由独立脚本计算分位数，避免在线聚合丢失证据。**推断**：若锁持有时间增加而每个任务的计算量不变，延迟增长主要来自串行化；若释放锁后 p95 仍高，可能是 worker 数不足或调度抖动。**反例**：把 toy 的 4 个 worker 线性外推到生产 GPU worker，忽略设备带宽、批处理和外部依赖。

## 20.8 事故响应生命周期

### 20.8.1 检测与分级

检测器应由 SLO、错误预算、质量代理和安全告警组合。分级考虑用户影响范围、持续时间、数据完整性、安全风险、是否需要跨团队和是否存在不可逆操作。分级不是为了责备个人，而是决定通知渠道、响应角色、更新频率和升级路径。误报可通过静默窗口和多信号确认降低，但不能为了减少告警而删除关键安全信号。

告警内容应包含症状、开始时间、受影响服务、当前值与预算、最近变更、建议的只读查询和责任角色。避免在告警中打印用户内容或访问令牌。若告警触发自动扩容、回滚或熔断，要记录自动动作和停止条件。

### 20.8.2 角色与沟通

严重事故至少需要事件指挥、技术负责人、沟通负责人和记录员。事件指挥管理优先级和授权，不亲自同时改配置；技术负责人执行遏制和验证；沟通负责人向用户、支持和管理层提供事实与下一次更新时间；记录员维护时间线、假设、命令和决定。小事故可由一人兼任，但仍要分开“执行”和“记录”。

内部更新使用统一模板：当前影响、已知事实、正在验证、已采取动作、风险和下次更新时间。对外更新只披露已确认且必要的信息，不推测根因或暴露敏感租户。任何跨组织沟通都要遵守隐私、合规和高影响通信确认要求。

### 20.8.3 遏制优先于根因

遏制目标是降低用户影响和防止数据损坏。常见动作包括停止放量、摘除异常版本、限制长上下文、降低并发、关闭高成本工具、切换到已验证 engine、隔离坏节点、启用缓存回退或返回可解释的暂时不可用。动作应可逆、有监控和有超时；不要在证据不足时批量删除数据、重置全部 GPU 或升级驱动。

回滚前确认旧版本仍可用、缓存和权重完整、容量足够且迁移不会造成第二次拥塞。若问题可能是数据完整性或凭据泄露，应隔离访问并通知安全响应，不以“恢复服务”为由跳过取证。**设计判断**：把遏制 runbook 预先演练，事故时按影响最小的步骤执行。

### 20.8.4 恢复、验证与关闭

恢复不是“错误率回到零”。要验证 p95/p99、队列、GPU telemetry、质量代理、工具结果、租户公平性和日志完整性在观察窗口内稳定。逐步放量，保留对照池和回滚按钮。若容量不足，宁可有界拒绝也不要无限排队。

关闭事故需满足明确条件：用户影响结束、数据完整性确认、监控恢复、临时开关记录、待办有负责人和期限、沟通完成。复盘用无责方式回答“哪些信号缺失、哪一步延误、自动化如何改进”，而不是只写“加强监控”。所有行动项应进入可跟踪系统，设置验收证据。

### 20.8.5 演练与混沌边界

演练应从低风险、可回滚场景开始，如模拟 GPU telemetry 丢失、单副本慢、日志后端限流、模型版本回退和节点网络抖动。每次演练定义注入、观察、停止条件和数据清理；不能在生产直接注入未审批的故障。混沌测试要限制租户、时间和资源，并防止把真实敏感数据暴露给测试工具。

演练结果包括检测时间、确认时间、遏制时间、恢复时间、误报和人力负担。指标不是越低越好：过于激进的自动回滚可能频繁抖动；过于迟钝则扩大影响。调整阈值前验证分母、采样和季节性。

## 20.9 事故案例：GPU p99 上升的证据链

假设某模型服务在新版本发布后 TTFT p99 从 450 ms 上升到 1.8 s，HTTP 错误率仍低于 0.5%。第一眼 dashboard 显示 GPU SM 利用率下降，显存使用正常。初始假设可能是 GPU 变慢，但需要证据。

第一步看入口与队列：到达量未变，接受量未变，队列等待占总延迟从 100 ms 升到 1.2 s；说明主要问题在供给不足或调度。第二步看批次：新版本把动态批处理的最大排队窗口从 20 ms 改为 200 ms，短请求在等待长请求；TTFT 上升与 batch size 和长度桶相关。第三步看 GPU trace：kernel 设备时间近似不变，CPU router 的等待 span 增加；SM 利用率下降是因为设备在等待批次形成。第四步做隔离实验：旧配置在同一 GPU 池恢复 p99，新配置在对照池复现。根因候选从“GPU 硬件变慢”更新为“排队窗口改变导致短请求等待”。

遏制动作是将窗口回滚到已验证值并逐步放量，同时保留长请求容量监控。恢复后验证短请求和长请求分层的 p99、GPU 利用率、拒绝率和质量指标。复盘新增指标：按长度桶的排队时间、批次形成等待和窗口配置变更审计；新增 canary 检查，防止单一全局 p99 掩盖长尾租户。

这个案例展示三个原则：平均 GPU 利用率不是根因；trace 必须包含排队和批次语义；回滚是验证假设的受控实验而不只是应急按钮。若没有队列 span，只能看到“GPU 低利用率”，排障会在错误方向上浪费时间。

## 20.10 观测系统本身的容量与可靠性

观测平台会消耗 CPU、网络、磁盘、索引和权限审计资源。估算成本时考虑事件大小、每秒请求、span 数、日志采样率、metrics 时间序列数、保留期和复制因子。高基数增长常是乘法效应：实例数、版本、模型、区域、租户组和错误类别每增加一维，组合迅速膨胀。

为 collector、日志代理和 metrics remote write 设置队列上限、重试上限、压缩、批大小和丢弃策略。观测后端不可用时，应用仍应遵守核心服务预算；低优先级观测可丢弃，高优先级审计事件要进有界本地缓冲。监控观测系统的自身延迟、丢弃计数、队列、存储和权限错误，避免出现“监控失明”而没有告警。

多区域部署时，优先在本地保留短期数据，跨区域异步汇总；不要把每条 token 事件同步发送到中央。跨区域故障期间，仍需在本地获得遏制所需信号。恢复后补传要有速率限制，避免重放洪峰影响在线流量。

## 20.11 隐私、安全与合规边界

### 20.11.1 数据最小化

默认不记录完整 prompt、输出、上传文件、音频、图像、凭据、访问令牌和工具请求体。指标和 trace 只保存长度桶、策略域、模型摘要、错误类别、不可逆关联 ID 和必要的时间。若排障确实需要内容，使用用户授权的短期采样、脱敏和访问审计，完成后验证删除。

匿名化不是简单哈希。低熵的用户 ID、邮箱或短文本可被字典反推；带盐哈希、令牌化和分区密钥仍需评估关联攻击。不要把敏感字段放入 metrics label，因为标签会复制到多个后端和缓存。错误堆栈、URL、环境变量和 eBPF payload 也可能泄露秘密。

### 20.11.2 访问控制与权限

按角色分离业务日志、性能 trace、安全审计和内存 dump。最小权限包括读取范围、时间窗口、租户策略域和导出能力。高风险操作如修改采样、加载 eBPF、获取 GPU dump、改变保留期和共享 trace 需要审批和审计。支持 break-glass 访问，但必须有原因、期限和事后复核。

### 20.11.3 多租户隔离与侧信道

共享指标的计数和分位数可能让租户推断其他租户流量；缓存命中、编译 profile、功耗和 kernel 时序也可能泄露活动。对敏感租户按权限域分区聚合，避免返回低样本精确分位数；必要时使用噪声、最小样本阈值或专用节点。任何隔离措施都要明确它保护的是内容、存在性、流量还是资源，不要笼统宣称“安全”。

### 20.11.4 数据保留和删除证明

保留策略应覆盖原始事件、索引、备份、缓存、exemplar、profile 和本地缓冲。删除请求需可追踪，验证后端查询不到数据，并记录失败重试。事故取证副本不应无限期保存。若法规要求不可篡改审计，使用追加式存储和完整性校验，同时将敏感内容与审计元数据分离。


### 20.11.5 观测契约与变更管理

每个信号都应有一份观测契约，写明名称、单位、分母、标签、采样、保留期、数据分类、访问角色、告警动作和删除方式。契约还要注明“未知”与“无数据”的含义：设备 agent 断开时应返回缺失状态，而不是零；没有请求时的延迟分位数应显示无样本，而不是零延迟。这样可以避免值班工程师把采集故障误当作系统健康。

信号的 schema 变更要像 API 变更一样管理。新增字段应向后兼容，修改枚举值要更新查询和告警，删除字段要经过迁移窗口。模型版本、engine 摘要、GPU UUID、区域和租户策略域等字段必须使用稳定编码；临时实验字段加前缀并设置过期时间。仪表盘和 runbook 需在预发布环境用回放数据验证，不能等生产事故才发现查询因字段改名而失效。

变更评审至少问五件事：时间序列和日志字节会增加多少；是否引入高基数或敏感数据；采样偏差如何影响 SLO；后端不可用时应用会怎样；怎样回滚并验证旧查询仍可用。若新信号的成本超过预算，应删减低价值字段，而不是无限扩容观测集群。**设计判断**：把观测看成产品接口，设置负责人和生命周期，才能避免多年积累的“僵尸指标”掩盖真正的异常。

### 20.11.6 调试数据的可信度分级

事故期间同时存在原始设备事件、应用插桩、聚合 metrics、人工笔记和第三方状态页。它们的时钟、采样和权限不同，可信度不能一概而论。可以为每条证据附上来源、时间精度、覆盖率、是否采样、是否经过重试和是否被人为过滤。设备 event 的时间精度高，但可能缺少请求语义；应用 span 有请求语义，却可能受异步和尾部采样影响；人工记录能补充决定，却容易出现回忆偏差。

当证据冲突时，不要简单选择“看起来更合理”的一条。先检查时间校准、分母、采样、重试和聚合边界，再设计能区分两种解释的实验。例如 metrics 显示 GPU 空闲而 profile 显示 kernel 很忙，可能是采样窗口错开，也可能是进程级与设备级粒度不同；通过同一时段的 GPU event、进程 ID 和 trace span 重新对齐，才能判断。复盘应记录冲突如何解决，避免下一次重复争论。

可信度分级不意味着忽略低等级证据。异常用户报告可能是最早信号，虽然缺少精确时间；单条日志可能暴露边界条件，虽然不能代表总体。将“线索”和“结论”分开，允许并行保留多个假设，直到受控实验提供足够区分度。

## 20.12 六个理解检查（含答案）

1. **为什么只看 GPU 利用率不能解释 TTFT p99？**
   - 答：TTFT 可能主要由入口排队、批次形成、CPU tokenizer、同步或网络构成；GPU 利用率是设备时间聚合，无法表示等待和分母。需结合队列、阶段 trace、批次和设备时间。
2. **什么时候把请求 ID 放进 exemplar，而不是 metrics label？**
   - 答：请求 ID 几乎无界且不可聚合，应放在少量 exemplar 或 trace 关联中；metrics 只保留低基数维度。exemplar 仍需采样、权限和脱敏。
3. **CPU profile 显示 futex 很宽，能否直接断言锁是根因？**
   - 答：不能。futex 可能来自队列等待、条件变量或运行时；需用线程状态、锁持有时间、队列深度和受控释放锁实验验证。
4. **尾部采样为什么会破坏平均延迟估计？**
   - 答：按慢请求或错误选择样本后，样本不再代表总体；必须报告采样规则、采样率，并用未采样 metrics 估计总体。
5. **事故时为什么先遏制再找根因？**
   - 答：遏制可快速降低用户影响和数据损坏，且通常可逆；在高影响状态下进行探索性改动会扩大范围。根因验证应在隔离或对照环境进行。
6. **eBPF 采样为什么需要和应用权限一样严格？**
   - 答：eBPF 可观察内核、网络和进程信息，程序错误或高基数 map 可能造成安全与性能风险；需要签名、资源上限、最小权限、字段脱敏和审计。

## 20.13 练习与实验清单

1. 为一个流式 LLM 服务写 SLO 表：TTFT、ITL、完整响应、工具成功率、质量代理和错误预算，给出分母与窗口。
2. 设计 metrics 注册表，估算模型、区域、GPU、版本、长度桶和错误类别组合的时间序列数量，提出高基数预算。
3. 为一次请求画 trace：入口、排队、tokenizer、prefill、decode、工具、输出；标出异步边界、批次关联和采样策略。
4. 运行 `ch20_cpu_incident.py` 的健康与锁竞争场景，保存原始事件，计算 p50/p95/最大值，解释为什么平均值不足。
5. 在隔离副本做 30 秒 CPU profile 和 GPU timeline，记录采样频率、输入形状、驱动、时钟和开销，比较插桩前后 p99。
6. 构造一个日志后端限流演练，验证应用是否有界丢弃、核心告警是否保留、队列是否恢复，以及删除和权限审计是否完整。
7. 写一份事故 runbook：检测、分级、遏制、回滚、恢复、沟通、关闭条件和待办验收证据，要求每步都有停止条件。
8. 对比全局 p99 和按输入长度桶、租户策略域分层的 p99，寻找一次聚合掩盖长尾的例子。
9. 为一个 eBPF 观测点写风险评估：挂载点、权限、map 上限、采样率、字段、回滚和数据保留。
10. 做一次反事实实验：固定模型、流量和硬件，只改变动态批处理窗口或缓存开关，给出支持和反驳假设的证据。

## 20.15 安全边界与上线清单

- **数据最小化**：默认不记录完整 prompt、输出、文件、音频、图像、凭据或 token；trace、日志、metrics 和 profile 使用长度桶、类别和不可逆关联 ID。
- **高基数控制**：请求 ID、随机 trace ID、动态 URL、用户文本和无界工具名不得作为 metrics label；使用 exemplars、日志和 trace 承载高基数。
- **GPU 与 eBPF 权限**：DCGM、profiler、eBPF、GPU dump 和重型 tracing 采用最小权限、签名程序、资源上限、短时窗口、审计和自动关闭。
- **租户隔离**：按策略域分区聚合，限制低样本查询，防止缓存命中、功耗、时序和 profile 泄露其他租户活动。
- **观测系统可靠性**：collector、日志代理和 remote write 有界队列、速率限制、丢弃策略和自监控；后端故障不能拖垮业务线程。
- **事故操作**：优先可逆遏制和已验证回滚；批量重置 GPU、删除数据、升级驱动、改变保留期和共享 dump 需单独授权。
- **质量与安全门禁**：恢复时同时验证延迟、错误、质量、工具结果、拒答、租户公平性和审计完整性，不能只看 HTTP 200。
- **取证和保留**：profile、内存 dump、事故 trace 和临时日志加密、限时、分角色访问，关闭后验证索引、缓存、副本和备份的删除。
- **版本与供应链**：模型、engine、驱动、eBPF 程序、collector 和仪表盘配置绑定版本摘要，变更可追踪、可回滚。
- **演练与复盘**：每季度至少演练一次检测、沟通、遏制和恢复；行动项有负责人、期限和可验证证据。

上线前请回答：用户症状能否映射到明确 SLO；每个 SLO 的分母是否稳定；p99 是否能跳到代表性 trace；GPU 时间与 CPU 时间是否校准；高基数和日志字节是否有预算；观测后端失联时系统是否有界降级；eBPF/profiler 是否能安全启停；长尾租户是否被全局平均掩盖；事故 runbook 是否在隔离环境演练；恢复是否包含质量和安全检查；以及任何调试数据是否能在保留期后被验证删除。若其中一项答不上来，系统可能“看起来有监控”却仍无法在事故中做出可信决定。
