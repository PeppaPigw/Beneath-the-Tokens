# 第40章　AI Infra 生产级 Capstone：从研究原型到可运营平台的端到端路线图

> 到这里，读者已经分别学习了执行、通信、数据、训练、服务、调度、存储、安全、可观测性、成本和评测。本章的工作不是把术语再列一遍，而是把它们放进同一个有责任人、有预算、有故障模式、有回滚按钮的系统。最终交付物不是一张“漂亮架构图”，而是一组可以在设计评审、上线审批和事故复盘中被反查的证据。

## 40.1 问题/边界：生产化到底改变了什么

### 40.1.1 研究原型和生产系统的分界线

研究原型通常优化“能不能跑”和一个代表性数据集上的质量；生产系统必须回答“谁可以调用、在什么负载下保证什么、坏了如何止损、成本由谁负责”。同一个模型权重从 notebook 进入在线 API，会新增至少九类约束：身份与租户、输入契约、资源隔离、队列与背压、状态一致性、观测与告警、隐私与供应链、预算与碳边界、以及变更审批。

本章的 capstone 场景是 **Atlas Summarize**：一个面向内部知识库的检索增强摘要服务。请求带有租户、文档引用和保密级别；服务先从文档索引取回片段，再由生成模型产生带引用的摘要。白天峰值 60 requests/s，输入长度 p50 为 1,200 token、p99 为 8,000 token，输出上限 512 token。产品承诺月可用性 99.5%，成功请求 p95 小于 300 ms（长文档另有异步路径），引用正确率不低于 95%，单月基础设施预算 12,000 美元。租户之间不能看到彼此数据；删除请求在 24 小时内从在线索引和缓存中消失。此数字是教学假设，不是任何厂商的性能或价格承诺。

边界要写在文档最前面：

1. **本章 lab 的边界**：只使用 Python 标准库和固定合成数字；不下载模型、不访问 GPU/NVML/DCGM、不访问云账单、不修改集群或用户数据。
2. **生产证据的边界**：容量、价格、功率、质量与合规结论只能在锁定硬件、版本、数据和测量方法后成立。toy 通过不能成为上线批准。
3. **责任边界**：平台团队拥有调度、节点、遥测和发布工具；模型团队拥有权重、提示和质量集；数据团队拥有索引与删除语义；产品团队拥有用户合同。任何跨边界的 SLO 必须有共同 owner。
4. **停止规则**：当关键证据缺失、错误预算耗尽、供应链 provenance 不完整、或故障演练不能自动止损时，默认 deny。不能用“先上线看看”替代风险决策。
5. **合规边界**：本章不提供法律意见；PII、受监管数据、跨境传输、版权和行业保留期要由组织的隐私、法务和安全流程裁定。

### 40.1.2 生产化的四个问题

每个设计决定都要能回答四个问题：

- **价值**：用户到底得到什么合格产出？失败时是空结果、旧结果还是人工接管？
- **机制**：哪个队列、缓存、超时、重试、锁、控制器或数据契约使它成立？
- **证据**：哪一条 trace、metric、日志、版本 digest、评测样本或账单可以证明它？
- **止损**：如果假设不成立，谁在几分钟内做什么，如何回滚，最大损失是多少？

只回答价值而没有机制是产品愿景；只有机制而没有证据是工程猜测；有证据而无止损则仍然不适合生产。

## 40.2 心智模型：把平台看作“契约—控制回路—证据图”

### 40.2.1 契约

契约不是一张 API schema，而是从输入到预算的端到端约束：请求身份、数据分类、最大 token、超时和重试；模型版本、质量门槛；节点池、配额、优先级；SLO、错误预算、月度花费；审计、删除和保留期。契约中的每个字段都应有 owner、默认值、校验器和变更方式。

以 Atlas 为例，请求契约可以写成：`tenant_id` 必填且经过授权，`doc_ids` 最多 20 个，`classification` 只能是 `internal` 或 `restricted`，`deadline_ms` 介于 100 和 5,000，`model_route` 只允许发布控制器生成。服务拒绝不合规请求，而不是悄悄截断后再声称满足质量。

### 40.2.2 控制回路

在线平台是闭环控制系统：流量和数据是输入，调度器、扩缩容、缓存、限流和回滚是控制器，推理/检索/存储是被控对象，指标和 trace 是传感器，SLO 和预算是设定值。控制回路必须有采样周期、滞后、稳定性和安全阈值。过快扩缩容会振荡，过慢采样会让尾延迟先烧完错误预算；没有 hysteresis 的路由器会在两个版本之间抖动。

一种实用分层是：

1. **快回路（秒）**：队列深度、请求超时、熔断和重试预算，保护单请求与依赖。
2. **中回路（分钟）**：副本数、批窗口、节点池和租户配额，保护 SLO 与公平性。
3. **慢回路（小时/周）**：容量采购、模型替换、索引重建、成本与碳策略，保护预算和长期可靠性。
4. **人回路（发布/事故）**：设计评审、变更审批、故障指挥和事后行动项，保护组织学习。

### 40.2.3 证据图

把证据看成有向图，而不是一堆链接：需求版本 → 设计 ADR → 数据快照 → 训练运行 → 模型 artifact → 镜像 digest → 部署 revision → 请求 trace → 指标窗口 → 评测报告 → 灰度决定 → 账单与复盘。任何节点变化都应改变 manifest 哈希。这样，事故中可以从一个 p99 异常追到具体的模型、容器、数据快照和发布操作者；研究中也能从一个质量回归追到 tokenizer、提示模板和检索索引。

## 40.3 完整 capstone 场景：Atlas Summarize 的约束与成功定义

### 40.3.1 用户路径和数据流

1. API 网关验证租户 token、请求大小、分类和 deadline，生成 `request_id`、`trace_id`。
2. 策略服务根据文档分类和租户配额选择检索索引；检索只返回授权片段，并记录 policy decision。
3. Query planner 对片段去重、截断和排序，写入带 TTL 的 prompt cache；cache key 必须包含租户、索引版本和模型路由。
4. Scheduler 将请求分为同步短请求和异步长请求，在公平队列中做 micro-batching；超出 deadline 的请求走旧结果或人工队列。
5. Model runner 执行 prefill/decode，返回结构化输出和引用；后处理器做 schema、引用存在性、安全策略和质量快速检查。
6. 结果服务写入短期审计记录和用户可见结果；删除事件传播到索引、缓存、日志和备份的相应保留层。

成功不只是“HTTP 200”。一次合格请求需满足：授权正确、引用来自允许的数据、输出 schema 有效、质量快检通过、在 p95 预算内完成、成本被正确归因，并有可采样的 trace 和版本证据。任一条件失败，要返回可解释的 reason code，并计入相应错误预算。

### 40.3.2 SLO、SLI 和错误预算

建议把 SLO 分成用户、数据和平台三组：

| SLO | SLI 分子/分母 | 目标 | 触发动作 |
| --- | --- | ---: | --- |
| 可用性 | 合法请求中返回合格结果数 / 合法请求数 | 99.5%/月 | 错误预算低于 25% 时冻结非必要发布 |
| 延迟 | 合格同步请求的 p95 端到端 ms | ≤300 ms | 连续 10 分钟超标则降级或扩容 |
| 引用质量 | 通过人工/自动引用检查的结果 / 抽样结果 | ≥95% | 质量回归门禁与索引回滚 |
| 删除时效 | 24h 内完成删除的对象 / 删除对象 | ≥99.9% | 停止新索引并启动数据事故流程 |
| 单位成本 | 成功请求基础设施成本 / 1k 请求 | ≤预算分摊 | 调整路由、批处理或配额 |

错误预算不是“可以随便失败的额度”，而是为了换取有边界的变更速度。99.5% 月可用性意味着月错误预算约 0.5%；若月合法请求 2,000,000，则最多约 10,000 次不合格结果。延迟预算应按成功请求和长短路径分别计算，不能让异步长文档掩盖同步 p95。指标定义、采样率、时钟和去重方式必须随 SLO 版本保存。

### 40.3.3 威胁、成本和容量假设

威胁模型包含越权检索、提示注入、恶意超长输入、模型/镜像篡改、日志泄露、租户侧信道和拒绝服务。成本模型包含节点、CPU、GPU/加速器、网络、索引存储、日志、备份、失败重试和 on-call；能耗边界至少记录设备功率采样、运行时、PUE/碳因子版本和估算不确定性。容量假设包含峰值到达、长度桶、缓存命中、批窗口、依赖吞吐、节点故障域和发布期间的冗余。

假设必须能被实验推翻。例如“prompt cache 命中率 40%”不是事实，直到以分桶 key、租户隔离和版本失效规则测量；“一台节点 24 QPS”不是承诺，直到在目标长度混合、p99 和故障余量下测得并锁定。假设表至少有 `id、数值、来源、置信度、验证实验、owner、过期日期`。

## 40.4 机制：从分层架构到运行时控制

### 40.4.1 分层架构和清晰边界

**体验与入口层**处理认证、限流、请求校验和幂等；不持有模型状态。**策略与控制平面**持有路由、配额、发布、版本和审计状态；控制平面故障时，数据平面使用最后一个已验证配置并进入安全模式。**数据平面**包括检索、缓存、调度、推理、后处理和结果存储；每个组件有超时、重试上限和可观测字段。**资源层**包括节点池、容器运行时、GPU/CPU、网络、对象/块/键值存储。**证据层**包括 metrics、logs、traces、评测样本、artifact registry、账单和审计仓库。

边界规则：

- 控制平面不能在每个 token 的热路径上同步调用；配置用带版本的快照分发。
- 数据平面不能直接写发布数据库；只上报事实事件，由控制器解释。
- 观测管线不能反向阻塞请求；在高压时降采样但保留错误、审计和 canary 证据。
- 多租户缓存不能只靠 hash 隔离，必须在 key、加密、访问策略和失效事件上同时隔离。
- 所有跨层调用携带 deadline、租户、trace、版本和 reason code，避免“神秘延迟”。

### 40.4.2 数据系统：质量、版本和删除是同一条链

数据层分成原始接入、清洗/去重、标注、训练集、评测集、索引构建和在线变更。每层保存 schema、统计摘要、敏感级别、来源许可、时间窗口、去重 fingerprint 和删除映射。训练数据、检索语料和评测集要有相互隔离的污染检查；模型卡与数据集说明分别记录适用范围和已知失败。

在线索引更新采用双写/双读或 shadow 索引：新版本先在隔离 namespace 构建，运行一致性和引用质量检查后再切换 pointer。删除事件用可重放的 tombstone，带有事件 ID、对象版本和完成确认；“从主库删了”不等于缓存、派生索引、日志和备份都已满足删除时限。所有派生物都应能反查来源对象和删除状态。

### 40.4.3 训练流水线：可复现、可暂停、可回滚

训练系统应把数据、代码、配置、编译器、硬件拓扑和随机种子写入运行 manifest。检查点不只是权重，还包括优化器状态、数据游标、学习率调度、混合精度 scaler、采样器和 git/container digest。分布式训练在通信超时、节点抢占和存储抖动时要区分可重试错误与可能重复写入；checkpoint 写入采用临时对象 + 校验和 + 原子指针。

晋级条件至少有：离线质量和安全集、训练/评测无污染、数值稳定、资源成本在预算、模型/数据许可证明确、可加载性验证、推理回归通过。发布 artifact 必须不可变；“latest”只能是可审计指针，不能作为部署输入。

### 40.4.4 推理和调度：把排队写进预算

推理路径将 prefill、decode、检索、后处理分段计时。调度器采用带 deadline 的公平队列：短请求不被长请求饿死，租户权重不能绕过全局保护。micro-batch 窗口、最大 token、KV cache 配额、并发上限和重试预算均为配置版本的一部分。重试只在幂等、剩余 deadline 和剩余错误预算允许时发生；否则快速失败或走降级答案。

容量规划使用保守公式：`所需节点 = ceil(峰值 QPS × (1+冗余) / 单节点有效 QPS)`。有效 QPS 应在目标长度混合、p95/p99、cache 命中与节点故障下测量。平均利用率接近 100% 不是优秀，而是没有突发、发布和故障余量。对 Atlas，toy 假设峰值 60 QPS、单节点有效 24 QPS、冗余 30%，得到 `ceil(78/24)=4` 节点；若损失一节点，剩余容量必须触发降级或扩容，而不是继续接受全部长请求。

### 40.4.5 存储和网络：带宽、尾延迟和故障域

模型和索引加载走分层存储：热层本地 NVMe/内存、温层共享块或对象、冷层归档。manifest 记录 checksum、压缩、加密、区域和生命周期策略。加载路径预热和校验不能与用户请求竞争同一带宽。网络设计明确入口、检索、模型、遥测和备份流量的队列与优先级；跨可用区复制的延迟和费用要进入 SLO/预算模型。

对网络故障，超时值应来自 deadline budget 而非“所有服务 30 秒”。熔断器记录半开探测与恢复条件；重试必须带指数退避、抖动和总预算。连接池耗尽、DNS 缓存、MTU、TLS 握手和服务发现都应在故障演练中注入，因为它们经常把一个慢依赖放大成全局尾延迟。

### 40.4.6 安全与供应链：默认拒绝和最小权限

供应链证据从源码、依赖锁文件、基础镜像、构建器、签名、SBOM 到部署 admission policy 连成一链。运行时只接受签名 artifact 与已批准 digest；依赖漏洞有严重性、可利用性、暴露面和缓解期限。密钥放在专用 secret manager，日志和 trace 做字段级脱敏；不要将完整 prompt、文档片段或 token 写入普通日志。

租户授权在检索前和结果前各检查一次，防止缓存或模型提示注入绕过 ACL。策略变更有版本和回滚；break-glass 访问必须短期、双人复核并留下原因。安全事件要能关联到 request/trace、artifact、操作者和 policy decision，但证据仓库本身也要有访问控制与保留策略。

### 40.4.7 可观测性：一个事件，多种视图

统一 `trace_id、request_id、tenant_hash、model_version、index_version、route、queue_ms、prefill_ms、decode_ms、retrieval_ms、status_reason`。指标按服务、租户类别、长度桶、版本和故障域聚合，避免高基数原始 ID 直接作为 label。日志保存结构化 reason code；trace 采样可降低成本，但错误、审计、发布和 canary 必须保留尾部采样。

Dashboard 不是终点。告警对应动作和 owner：p99 连续超标触发降级；错误预算燃烧率异常冻结发布；索引删除延迟触发数据负责人；成本偏离触发预算控制器。每个告警都要有 runbook、最近一次演练时间和可验证的恢复条件。

## 40.5 机制：成本、容量和能源的共同账本

### 40.5.1 单位经济学

推荐同时追踪三种分母：每请求、每成功请求、每合格 token。失败重试、预热、空闲、存储和遥测应按规则分摊，不能只把 GPU 小时除以请求数。月度成本可写成：

`总成本 = 计算 + 存储 + 网络 + 日志/遥测 + 备份 + 失败重试 + 人工运维分摊`

每项要有账单来源、时间窗、币种和估算误差。预算控制器只自动执行已授权的低风险动作，例如降低非关键采样或暂停实验；改变用户承诺、删除数据或购买资源需要相应审批。

### 40.5.2 容量规划流程

1. 用历史或回放流量建立到达率、长度、优先级和区域分布；标注季节性与突发。
2. 用 micro/meso benchmark 测得单节点有效服务率与尾延迟，记录冷启动、cache 命中、温度和版本。
3. 将峰值、发布冗余、N+1 故障域、维护窗口和扩容滞后写入情景矩阵。
4. 做基线、+50% 流量、丢一节点、慢依赖、cache 失效和长上下文组合实验。
5. 用 SLO/成本/能耗联合门禁选择配置，保留置信区间和未覆盖范围。
6. 设置触发器：队列、错误预算燃烧率、节点交付提前期和账单偏差；定期复盘而非等事故后才扩容。

### 40.5.3 能源与碳边界

能耗至少拆设备功率、主机/网络、存储和设施开销，明确实时遥测与估算的误差。用 `Wh / 合格请求` 和 `gCO2e / 合格请求` 而不是只报整月 kWh。碳感知调度只能在不违反延迟、数据驻留和可靠性约束时使用；把低碳区域当成无条件优先会引入跨区网络和故障风险。报告 location-based 与 market-based 方法、PUE 和电网碳因子的版本，并保留原始采样。

## 40.6 实验：CPU-only capstone lab

### 40.6.1 实验问题和假设

实验问题：给定 Atlas 的峰值、单节点有效 QPS、冗余、SLO 和月预算，容量控制器能否在基线时 admit，在流量突发、节点损失、网络分区、schema 漂移、预算超支和 canary 回归时 fail-closed？

假设：固定的容量公式、错误预算、成本公式和 rollout gate 足以在 toy 场景中区分 admit/deny；它们不证明真实模型质量、GPU 性能、云账单或生产可用性。

运行：

```bash
python3 -m py_compile labs/ch40_capstone_lab.py
python3 labs/ch40_capstone_lab.py --fault none > /tmp/ch40-none.json
for fault in traffic_spike gpu_loss network_partition schema_drift budget_breach rollback; do
  python3 labs/ch40_capstone_lab.py --fault "$fault" > "/tmp/ch40-$fault.json"
done
python3 tests/test_ch40_capstone_lab.py
```

实验输出保留 `capacity、slo、cost_energy、rollout、deny_reasons、versions、hardware、evidence`。基线使用 CPU-only generic fixture，节点、价格、功率和质量均为合成教学值；输出 JSON 仅用于检查结构和控制路径。

### 40.6.2 逐步观察

1. `capacity_plan` 将 60 QPS 乘以 30% headroom，与单节点 24 QPS 比较，得到 4 节点；同时报告利用率而不是只给节点数。
2. `slo_budget` 用 2,000,000 月请求和 99.5% 目标计算 10,000 个请求的错误预算，并同时检查 p95。
3. `rollout_gate` 比较 baseline 与 canary 的 p95、error rate、quality；任一阈值失败就返回 rollback 和 reason code。
4. `cost_energy` 将节点月费和每请求能耗转为月度成本与 kWh；预算超出即 deny。
5. `simulate` 注入六种故障，输出 fail-closed 结果；`evidence_manifest` 对规范化结果做 SHA-256，确保结果可反查。

### 40.6.3 lab 的边界和延伸

lab 没有模拟真实排队分布、GPU 内核、网络包丢失、租户侧信道、模型质量、人评、计费税费、PUE 或法务流程。生产化延伸应替换 fixture，接入实际指标和账单，保存原始事件，使用分位数置信区间和真实故障注入平台；延伸不能悄悄把合成值写成承诺。

## 40.7 故障诊所/失败：六类常见事故及止损路径

### 40.7.1 流量突发：容量公式没有余量

症状是队列快速增长、p99 超标、重试风暴。先保护已有合格请求：限制长上下文、暂停低优先级、扩容或切换异步；不要通过无限重试制造更多负载。复盘要问：峰值模型是否覆盖突发、扩容提前期是否进入 SLO、限流是否按租户公平、降级结果是否仍满足安全和引用要求。

### 40.7.2 节点或加速器损失：N+1 只是图上的数字

丢一节点时，如果剩余节点已经超过 headroom，调度器应立即停止接收非关键流量并触发路由/扩容。常见失败是 capacity controller 仍读旧节点数，或健康检查只检查进程存活而不检查模型可用、温度、内存和网络。演练必须记录检测时间、决策时间、恢复时间和错误预算消耗。

### 40.7.3 网络分区和慢依赖：重试把局部故障放大

检索依赖变慢时，固定 30 秒超时和三次重试会让同步请求全部堆积。正确做法是按剩余 deadline 计算短超时，熔断后返回缓存的已验证结果或异步任务；保留 request/trace 关联。若缓存可能泄露租户数据，宁可明确失败也不能跨租户复用。

### 40.7.4 Schema 漂移和质量回归：HTTP 200 也可能是失败

上游字段改名导致引用为空，服务仍返回 200；离线准确率没变但引用正确率下降。schema registry、契约测试、结果校验和质量抽样必须在 canary 阶段运行。质量门禁要与 p95、错误率联合，不能让“更快但错误更多”的版本晋级。

### 40.7.5 预算超支：成本告警来得太晚

月中账单偏离可能来自失败重试、日志高基数、跨区复制或实验忘记关。单位成本和资源 owner 标签应实时聚合；预算控制器先采取已授权动作，重大降级由产品 owner 决定。报告估算不确定性，避免用假精度触发不必要的停机。

### 40.7.6 灰度回滚失败：旧版本不是自动存在

回滚需要旧镜像、模型、索引、配置、schema 和迁移兼容性都可用；只保留一个“previous”指针不够。灰度期间记录最小样本、观察窗口、自动回滚条件和人工 override 过期时间。若数据库或索引已不可逆迁移，应先设计前向/后向兼容，而不是事故中临时修改。

## 40.8 灰度、回滚和变更管理

### 40.8.1 发布阶梯

1. **静态检查**：签名、SBOM、schema、权限、数据许可、artifact checksum、配置 lint。
2. **离线门禁**：质量、安全、污染、micro/meso 性能、成本/能耗估算、回归基线。
3. **shadow**：复制真实请求但不写用户状态，脱敏并限制副作用；比较质量、延迟、资源和策略决策。
4. **canary**：1% 或固定小流量，按租户和区域分层，设置最小样本和最长观察窗口。
5. **逐级扩大**：5%、25%、50%、100%；每级需通过 SLO、错误预算燃烧率和质量检查。
6. **完成与监控**：保留旧版本冷备一段时间，发布 manifest 与最终报告归档。

### 40.8.2 回滚契约

回滚条件至少包括 p95 超阈、错误率、质量、数据泄露/授权异常、成本突增、节点健康和证据管线失效。回滚动作要幂等，且在控制平面不可用时有最后安全配置。每次 rollback 记录触发 metric、阈值、时间、操作者、目标 revision 和验证结果；“命令成功”不是“服务恢复”，必须重跑合格请求和安全检查。

## 40.12 组织运行模型：人、流程与研究连接

### 40.12.1 RACI 和 on-call

平台、模型、数据、安全、产品、财务和法务不必由同一团队承担，但必须明确 RACI。on-call 手册写出告警优先级、五分钟内动作、降级开关、升级路径和证据保留；事故指挥人负责节奏与决策，技术负责人负责缓解，记录员负责时间线，联络人负责用户和利益相关者。事后复盘关注系统条件和行动项，不用“某人粗心”作为根因。

### 40.12.2 研究到产品的双向反馈

研究实验应携带 production-shaped workload、成本和故障指标；线上事故应沉淀成可复现实验和新的 benchmark case。对新 kernel、KV 压缩、量化、路由或调度策略，先在 micro/meso 验证机制，再在 shadow 观察用户指标，最后以可回滚 canary 证明长期价值。研究路线不应绕过安全、数据删除和供应链门禁。

## 40.14 练习

### 练习一：重算容量与错误预算

使用 lab 的 `ServiceSpec`，把峰值改成 110 QPS、单节点有效 28 QPS、冗余 35%，计算所需节点；再设月请求 5,000,000，目标可用性 99.9%，给出错误预算和需要的观察窗口。写出每个假设的来源与置信度。

### 练习三：事故时间线

假设 09:00 发布新模型，09:07 p99 超标，09:09 质量抽样发现引用错误，09:12 成本突增。写出从告警到回滚的分钟级时间线，标注自动动作、人动作、证据和对用户的最小通知。

### 练习四：评审与反对意见

用 40.9 模板评审“跨区低碳路由”。一半小组主张降低碳排，一半小组强调数据驻留和网络尾延迟；最后用 40.10 矩阵给出条件式决定和复审日期。

### 练习五：把故障变成研究问题

从“KV cache 失效风暴”或“长上下文公平性”中选一个，定义可证伪假设、控制变量、micro/meso/macro 指标、最小样本、停止规则和生产 rollout 保护。

## 40.15 进阶研究问题：下一代 AI Infra 的可证伪路线

1. 如何构建同时覆盖 token 级质量、尾延迟、能耗和租户公平性的多目标调度器？Pareto 边界怎样在线估计？
2. 在异构加速器与动态频率下，怎样定义跨设备可比的“合格 token/s”，并给出统计不确定性？
3. 能否让错误预算控制器根据数据/模型风险自动调整发布速率，而不产生控制振荡？

5. 如何把数据删除证明扩展到训练 checkpoint、蒸馏模型和向量索引的派生图？

9. 怎样为人评质量建立可重复、隐私保护、跨语言且能进入自动门禁的协议？

## 40.17 证据链实施细节：从事件到可审计决定

### 40.17.1 请求级证据

请求级证据的最小集合是：接收时间、tenant 的不可逆哈希、策略决定、输入/输出 token 桶、deadline、路由、模型与索引版本、各阶段耗时、状态码、reason code、重试次数和 trace 采样标志。原始 prompt 和文档正文通常属于敏感数据，应在业务日志中删除或脱敏；需要复现质量时，将受访问控制的样本仓库与请求事件通过 sample ID 关联，而不是把正文复制进多个系统。时钟以统一的 monotonic duration 和可追踪的 wall-clock 记录，避免 NTP 调整让时间线倒退。

请求事件要区分事实和推断。例如 `retrieval_ms=42` 是事实，`cache_miss=true` 是组件报告的事实，`root_cause=network` 则是事故分析阶段的推断。事件 schema 可以包含 `assertion_type` 和 `confidence`，让自动化报表不把推断冒充测量。对高风险租户，审计事件写入 append-only 存储并带 hash chain；普通性能事件可以按保留策略聚合，减少长期成本。

### 40.17.2 版本和指针证据

一次发布至少涉及代码 commit、依赖 lock、构建器、基础镜像、模型权重、tokenizer、提示模板、评测集、索引快照、配置、策略和部署 revision。把这些字段写入单个 manifest，并在部署时计算内容摘要；不要只记录人类可读的 tag。指针更新采用 compare-and-swap，防止两个发布器互相覆盖；发布控制器保留前一个可运行 revision 以及兼容性检查结果。

manifest 中还应记录“没有什么”：例如本次没有修改数据库 schema、没有改变 ACL、没有改变数据驻留区域、没有改变 tokenizer。负面声明方便评审者判断风险边界，也能在复盘中快速排除无关变量。若某字段无法锁定，状态应是 `unknown`，而不是填入 `latest` 或空字符串。

### 40.17.3 指标到决定的映射

每个自动门禁写出输入窗口、聚合方法、阈值、最小样本、延迟和动作。例如“canary p95 超 300ms”还不够，应写成：按长度桶和租户类别分层，10 分钟窗口至少 2,000 个合格请求，使用尾部延迟估计；连续两个窗口超阈或错误预算燃烧率超过 2 倍时停止扩大并恢复上一个 revision。这样，门禁既能自动运行，又能在事故中解释为什么做出决定。

门禁本身也要可观测：执行次数、输入是否完整、评估延迟、人工 override、过期时间和动作结果。评估服务故障时默认 deny 或保持当前安全流量，不能因为“门禁没有结果”就当作通过。对于低风险非生产实验，可以显式配置旁路，但旁路需要 owner、过期时间和实验环境标签。

## 40.18 多租户与公平性设计

### 40.18.1 配额、优先级和公平队列

每个租户有并发、QPS、token、存储和索引更新配额；配额变化必须有版本和审计。调度器先做全局保护（节点、KV cache、网络、错误预算），再做租户公平。优先级只在同一安全和合约等级内比较；高优先级租户不能绕过数据授权、最大 token 或全局熔断。公平指标可用加权完成率、p95 等待时间和 share-of-service 曲线表达，避免只看单一吞吐。

长请求对短请求的阻塞是常见的隐性不公平。将请求按长度和 deadline 分桶，使用 aging 防止低优先级饿死；batch 形成器记录等待原因（等 token、等租户配额、等模型 slot、等检索）并对每个原因设预算。若租户持续产生超长或失败请求，优先降低其并发和重试，而不是让全局队列崩溃。

### 40.18.2 隔离和侧信道

共享 GPU、缓存、日志和节点会带来时序、容量和错误消息侧信道。对于高敏感分类，采用专用节点池或更强的隔离策略；至少确保 cache key、加密上下文、trace 采样和错误正文不跨租户。容量和质量报表使用聚合或匿名化，避免通过某租户的 token 长度、命中率或错误率推断业务量。隔离策略要有反例测试：构造相同文档 ID、相同 cache key 前缀、并发高峰和节点迁移，确认不会读取或回显别的租户数据。

## 40.19 数据删除、保留与灾难恢复

删除契约要区分“不可再服务”“不可再检索”“不可再恢复”和“不可再训练”。在线路径可以先阻断对象，随后异步清理 cache、向量、倒排索引、日志引用和备份；每个阶段发布完成事件和证据。训练 checkpoint、蒸馏模型和统计特征可能无法逐条删除，需要在产品和法务约束下决定重训、隔离或保留；决策写进数据处理记录。

灾难恢复测试不能只启动备用服务。要验证对象存储、索引快照、密钥、策略、模型、DNS、证据仓库和租户映射是否一起恢复；测量 RTO/RPO 和恢复期间的质量/安全门禁。跨区域恢复时，先验证数据驻留和版本兼容，再切换流量。恢复后执行一小批合格请求和删除验证，避免“服务在线但返回旧权限”。

## 40.20 生产指标词典与反模式

指标名、类型、单位、分母、聚合、保留、owner 和告警阈值应集中在词典中。推荐词典字段：`metric_id`、`description`、`unit`、`good_event`、`bad_event`、`dimensions`、`sampling`、`cost_limit`、`runbook` 和 `last_reviewed`。例如 `atlas.good_result_ratio` 的分母必须是经过授权且符合 schema 的请求，而不是所有 HTTP 请求；`atlas.p95_e2e_ms` 只统计同步路径，异步任务单独统计完成时延。

常见反模式包括：用平均值代替尾延迟；用 GPU busy 代替合格产出；把重试后的成功算作一次成功而忽略失败成本；用高基数租户 ID 直接做指标标签；把日志采样当作审计保存；把“自动扩容成功”当作用户 SLO 恢复；把质量下降归咎于随机噪声而没有保存原始样本；用同一错误预算支持多个不相容的用户合同。发现反模式时，先修正定义和证据，再优化代码。

## 40.21 设计评审评分卡

为降低“架构图审美”对决策的影响，可以使用 0–2 分评分卡：0 表示无证据或不满足，1 表示有部分证据/有限边界，2 表示已演练且可反查。建议维度如下：

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 用户合同 | 没有合格产出定义 | 有 API 但错误语义模糊 | SLO/SLI/错误预算可计算 |
| 容量 | 凭经验配机器 | 有单节点测量无故障余量 | 有情景矩阵、N+1 和扩容触发器 |
| 数据 | 无 provenance/删除语义 | 有版本但派生物不全 | 端到端 lineage、tombstone 和演练 |
| 训练/模型 | 只有权重文件 | 有运行记录不可重放 | manifest、checkpoint、质量/安全门禁完整 |
| 推理/调度 | 无限重试或无背压 | 有限流但不分租户 | deadline、公平、缓存和降级可验证 |
| 安全 | 依赖人工信任 | 有扫描无 admission | 签名、SBOM、最小权限、break-glass 可审计 |
| 可观测性 | 只有日志或 CPU | 有 dashboard 无 runbook | trace/metric/log 关联且有成本边界 |
| 成本/能耗 | 只看 GPU 小时 | 有估算无对账 | 单位经济、账单、功率和碳边界完整 |
| 灰度/回滚 | 直接全量 | 手工 canary | 自动门禁、旧版本、观察窗口和演练 |
| 组织 | owner 不清 | 有 on-call 无备份 | RACI、升级路径、复盘行动项明确 |

总分不是自动批准条件。安全、数据删除、回滚、用户 SLO 中任何一项为 0，都应 deny；高风险场景需要指定维度达到 2 分并由相应 owner 签字。评分的价值在于暴露缺口，而不是制造“总分 15 就安全”的假精确。

## 40.22 逐周计划的日级执行节奏

周计划常被写成愿望清单，日级节奏可以让依赖显形。每周一确认目标、输入和风险；周二完成实现或实验；周三跑基线与故障；周四做证据整理和评审；周五决定继续、暂停或回滚，并更新 manifest。若某周的关键实验尚未达到停止规则，周五应保留在当前阶段，不为了日历强行进入下一阶段。

一个容量周的例子：周一锁定峰值和长度分布；周二测冷/热 cache 的单节点曲线；周三注入 +50% 流量和丢节点；周四把结果与账单、功率和错误预算对账；周五评审是否增加节点、改变批窗口或采用异步。一个数据周的例子：周一冻结 schema；周二构建新索引；周三做双读对比和 ACL 反例；周四演练删除和恢复；周五再决定是否切换 pointer。每个工作日结束时保存命令、环境、原始输出和未解释偏差。

## 40.23 Capstone 最终提交包

学生或团队的最终提交应包含以下互相可链接的文件，而不是一份孤立幻灯片：

1. 需求与 SLO 文档：用户路径、合格产出、SLI 分母、错误预算、数据分类和合同边界。
2. 架构与 ADR：数据/控制流、故障域、信任边界、容量假设、取舍及反对意见。
3. 运行 manifest：源码、依赖、镜像、模型、tokenizer、数据/索引、配置、硬件和时钟。
4. benchmark 包：micro/meso/macro workload、原始事件、统计方法、成本/能耗边界和未覆盖范围。
5. 安全和数据包：威胁模型、SBOM/签名、ACL、删除/保留/恢复证明、break-glass 记录。
6. 发布包：离线门禁、shadow/canary 样本、观察窗口、自动回滚 revision 和人工批准。
7. 事故包：至少两次故障演练的时间线、检测/缓解/恢复、错误预算和行动项。
8. 运营包：dashboard、告警、runbook、RACI、on-call、成本 owner 和研究 backlog。

验收者应能从任意一个数字跳到原始证据，再跳到决定和责任人；如果只能看到截图而找不到命令、版本或失败样本，提交不完整。


## 40.24 反事实分析：不要把相关性当成根因

生产系统有多个同时变化的变量：流量、长度、模型、索引、节点温度、网络路径和日志采样。事故或回归报告应列出时间对齐的反事实：如果保持旧模型但使用新索引会怎样？如果保持流量而关闭 cache 会怎样？如果只丢一个故障域而不改变发布会怎样？在不可能完整重放时，至少使用分层对照、版本一致的请求、受控 shadow 或离线回放，并明确推断强度。

因果分析的最低记录包括处理变量（发布/配置/流量策略）、结果变量（p95、合格率、成本、能耗）、混杂因素（长度、租户、区域、cache、温度）、时间窗和排除规则。不要在看到 p99 与 GPU 温度同时上升时直接宣布“温度导致延迟”；可能是长请求导致两者一起上升。先按长度和批桶分层，再做受控实验或故障注入。结果报告应包含不支持的假设，帮助下一轮实验缩小范围。

## 40.25 变化后的验证清单

任何生产变更完成后按以下顺序检查：

- 版本：部署 revision、模型/索引/配置 digest 与批准 manifest 一致；旧 revision 可启动。
- 合同：schema、ACL、删除、租户配额和错误语义没有隐式改变；契约测试通过。
- 资源：节点、队列、cache、网络、存储和日志容量覆盖峰值与故障余量；预算标签存在。
- 质量：代表性长度、租户、语言和安全样本通过；新失败样本已归类并有 owner。
- 观测：trace 字段、metrics 分母、日志脱敏、告警、runbook 和采样成本验证。
- 灰度：shadow 无副作用，canary 样本/窗口/自动回滚条件配置并实际触发过一次 dry-run。
- 复盘：风险接受者、截止日期、下一次演练和研究问题写入 backlog。

验证顺序很重要：先确认不会把错误流量导入，再确认指标是否好看。若证据管线本身失败，发布应保持在安全流量或回滚，而不是把缺少数据当作“没有问题”。

## 40.26 全书收束：工程判断的可迁移形式

全书从进程、网络和 GPU 的具体机制开始，逐步进入训练、推理、服务、调度、数据、观测、安全、成本和评测。Capstone 的共同抽象有三条：第一，把资源消耗与用户合格产出绑定；第二，把每个隐含假设变成可测量、可过期的契约；第三，把控制动作和证据保存到能回滚、能复盘的闭环。换一个模型、加一个加速器、迁移到另一云，抽象仍然适用，只是参数、故障域和责任人不同。

当你面对“要不要上线某优化”时，先问它改变哪一个控制回路、会消耗哪一类预算、如何观测副作用、何时自动止损；当你面对“研究结果提升了 10%”时，先问分母、工作负载、置信区间、质量与安全是否同样提升，以及结果能否被另一个团队重放。生产级 AI Infra 的成熟标志不是永远没有事故，而是事故发生时系统和组织都知道如何缩小爆炸半径、保留证据、恢复服务，并把教训转化为下一次更好的实验。

## 40.27 迁移与退役：平台也需要生命周期

生产路线图不能只写上线。模型、运行时、索引和硬件都会退役：供应商停止支持、漏洞无法修复、质量不再满足用户、成本超过替代方案，或数据许可到期。迁移计划要同时维护新旧 schema、模型输出兼容层、双写/双读窗口、用户通知、成本上限和删除证明。每个兼容层都应有明确的下线日期，否则系统会积累永远不敢删除的“临时路径”。

退役前先冻结新增依赖，盘点仍在使用的租户、定时任务、缓存、备份、评测集和 dashboard；再做 shadow 验证新路径，最后按租户和区域逐步切换。旧 artifact、密钥和权限按保留策略撤销，审计记录保存必要的决定和批准。若无法证明某个派生物已删除或某个用户仍在使用，先暂停销毁并升级到数据 owner。退役后运行成本、告警和证据查询应确认已停止，避免“服务删了但账单和访问仍在继续”。

## 40.28 读者自评量规

完成本章后，可用以下四级量规自评：

- **Level 1 复述**：能解释 SLO、错误预算、灰度、回滚和证据 manifest 的词义，但无法计算或演练。
- **Level 2 组装**：能按照模板画出数据/控制流，运行 toy lab，识别六种故障并给出 reason code。
- **Level 3 评审**：能用真实或脱敏 workload 做容量、质量、成本和安全联合评审，指出不确定性和 deny 条件。
- **Level 4 运营**：能在受控生产环境执行灰度、观察、回滚、故障复盘和路线图更新，让另一团队按 manifest 重放结论。

课程或团队验收应要求至少达到 Level 3；Level 4 需要真实演练、跨团队签字和周期性复审。若只完成代码测试而没有数据、权限、预算和组织证据，应明确标记为实验通过，不能叫作生产就绪。
