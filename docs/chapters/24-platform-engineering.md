# 第24章 AI Infra 平台工程与开发者体验

## 开场：平台不是一组脚本，而是一种产品

在训练、评测、推理、数据处理和 Agent 运行逐渐规模化以后，团队很容易陷入“每个项目都有一套脚本”的循环。一个脚本负责创建 GPU 实例，另一个脚本负责上传数据，第三个脚本负责启动训练，第四个脚本负责把指标抄到文档里。脚本越积越多，经验却没有沉淀成可复用的接口。新同学需要询问“正确的命令”，老同学则花大量时间处理权限、配额、镜像和网络等非业务问题。平台工程要解决的不是把脚本换成网页，而是把组织中反复出现的运维知识转化为一个可发现、可组合、可审计的产品。

AI Infra 平台尤其容易出现两种误解。第一种误解是“只要有 Kubernetes 就有平台”。Kubernetes 提供了强大的资源编排 API，但它并不了解团队的模型注册、数据血缘、评测门槛、成本预算和上线责任。第二种误解是“把所有事情都封装起来，开发者就会更快乐”。过度封装会隐藏故障原因，导致平台成为黑盒；当抽象无法覆盖新场景时，用户只能绕过平台，形成影子基础设施。

本章把平台看作一种内部产品（internal product）：有明确的用户、承诺的体验、版本化的接口、可观测的服务等级和持续的反馈回路。我们会从抽象边界讲起，逐步建立内部开发者平台（Internal Developer Platform，IDP）的架构，再讨论工作流、环境复现、配置与策略、发布门禁、插件接口、任务状态和多租户产品化。读者最终应能回答三个问题：平台替谁减少了什么认知负担？哪些约束必须在平台层强制执行？当平台自身出错时，用户如何自助定位并安全退出？

## 24.1 先定义用户旅程，再定义平台组件

平台的第一份设计文档不应是组件清单，而应是用户旅程。以“上线一个新的文本分类模型”为例，用户旅程可能包含：

1. 发现模板：选择语言、运行时、数据来源和合规等级。
2. 创建项目：获得代码仓库、镜像仓库、默认监控和文档骨架。
3. 本地运行：在与 CI 相同的依赖和工具链中完成最小训练。
4. 提交实验：声明数据版本、代码提交、超参数和预算上限。
5. 评测与审批：自动运行质量、安全、偏差和成本检查，失败时给出可执行建议。
6. 发布候选：生成可追溯的模型包和部署描述，进入逐步放量流程。
7. 运行与回滚：查看任务状态、日志、指标和血缘，必要时回滚到上一个已验证版本。
8. 退役与复盘：冻结产物，记录删除策略、费用和事故复盘链接。

每个步骤都应有一个清晰的“输入—动作—输出”契约。例如，提交实验的输入不是一串不可审计的命令，而是一个版本化的 Experiment 对象；输出不仅是一个运行编号，还包括可查询的状态、预计资源消耗和取消方式。平台设计可用“时间到首个成功运行”“从提交到可观测结果的分钟数”“用户需要手工阅读的错误日志行数”来衡量，而不是只看平台服务器的 CPU 利用率。

用户旅程还帮助平台团队区分两类能力。通用能力是任何团队都需要的，如身份认证、项目空间、日志、成本标签和发布回滚；领域能力则与具体任务有关，如图像标注、向量索引或强化学习仿真。通用能力适合进入平台核心，领域能力应通过插件或组合 API 提供，避免核心不断膨胀。

## 24.2 分层抽象：底座、控制面、体验面和产品面

一个可演进的平台通常分为四层。层与层之间通过稳定契约连接，而不是共享数据库表。

**底座层（substrate）**提供计算、存储、网络和加速器等资源。它可以是 Kubernetes 集群、批处理队列、云 API、裸机集群或边缘节点。底座关注容量、隔离、故障域和供应商差异，不直接暴露所有底层细节。

**控制面（control plane）**把用户意图翻译成底座动作。控制面维护资源对象、调度工作流、执行策略、记录状态并处理重试。理想情况下，控制面采用声明式 API：用户描述“希望存在的状态”，控制器负责不断把现实状态拉回目标状态。Kubernetes 的对象和控制器模型正是这一思想的开源实现，可参阅官方概念文档（https://kubernetes.io/docs/concepts/architecture/controller/）。

**体验面（experience plane）**包括命令行、网页门户、IDE 插件、聊天机器人和文档。体验面不应复制业务逻辑，而应把同一组 API 组织成适合不同场景的入口。命令行适合批量和自动化，门户适合发现和审批，聊天入口适合查询状态与获取下一步建议。

**产品面（product plane）**是面向团队目标的预置能力，例如“微调作业”“批量离线推理”“安全模型发布”“标注数据集版本”。产品面提供默认值、模板和护栏，隐藏不必要的自由度，同时保留专家级扩展点。

分层的一个实用原则是：越靠近底座，接口越通用；越靠近产品，接口越贴近用户任务。把供应商特定的 GPU 字段直接暴露给每个项目，会让上层产品绑定到具体云厂商。相反，产品面可以声明“需要一张 80GB 显存卡、预算每小时不超过某阈值”，由控制面选择可用实现。抽象并非抹掉差异，而是把差异放在一个可更换的位置。

## 24.3 平台抽象的设计方法：黄金路径与逃生舱

平台抽象通常从三件事开始：资源模型、操作模型和错误模型。

资源模型回答“平台里有什么”。以 AI 平台为例，常见资源包括 Project、Dataset、Experiment、Model、Endpoint、Job、Artifact 和 Policy。每种资源都应有唯一标识、所属租户、创建者、版本、生命周期和权限。资源的字段要区分用户输入、平台计算字段与外部观测字段，避免用户误写状态字段。

操作模型回答“用户能做什么”。推荐使用动词受限的操作集合，如 create、submit、cancel、promote、rollback 和 archive。一个操作要明确幂等键、超时、重试和权限检查。比如 submit 允许客户端重复发送同一个幂等键而只创建一个任务；cancel 在任务已完成时返回稳定的“已终态”结果，而不是随机报错。

错误模型回答“出错时用户如何恢复”。错误消息应包含稳定错误码、发生阶段、相关资源、建议动作、是否可重试和支持入口。不要把底层调度器的长堆栈直接当作产品错误。平台可以保存原始日志供专家查阅，但面向普通用户的摘要应告诉他是配额不足、镜像拉取失败、数据校验失败还是策略拒绝。

黄金路径（golden path）是平台对常见任务提供的最短可行路线。它应包含经过验证的模板、默认监控、默认安全策略和可复制的示例。黄金路径不等于唯一道路。逃生舱（escape hatch）允许高级用户提交底层资源描述、使用自定义容器或连接外部系统，但必须带上审计标签、责任人和失效期限。没有逃生舱的平台会被绕过；没有护栏的逃生舱则会把平台变成资源直通车。

一个好的抽象还会明确“不抽象什么”。例如，平台可以统一任务提交、日志和成本标签，却不试图统一所有深度学习框架的超参数命名。统一到无法表达领域差异的程度，会迫使用户在平台外维护第二套配置。

## 24.4 内部开发者平台（IDP）的参考架构

IDP 不是某个具体产品名称，而是一组围绕开发者自助服务组织的能力。可以把它拆成六个平面：

1. **目录平面**：登记服务、数据集、模型、所有者、依赖和文档。Backstage Software Catalog 提供了开源参考，目录实体通常由代码仓库中的描述文件声明，并可链接 TechDocs 文档（https://backstage.io/docs/features/software-catalog/）。
2. **模板平面**：把创建项目、流水线、监控和权限的步骤封装成可审计模板。模板应有版本、变更日志和迁移说明，而不是一次性脚手架。
3. **交付平面**：负责构建、测试、签名、发布、逐步放量和回滚。交付平面应能引用目录中的所有者和策略，避免流水线里出现过时的团队名单。
4. **运行平面**：提供任务、端点、日志、指标、追踪、事件和成本视图。运行平面要允许按项目、环境、提交和数据版本交叉查询。
5. **治理平面**：集中管理身份、策略、配额、审批和审计。治理平面记录“谁在何时以什么理由允许了什么动作”。
6. **反馈平面**：收集使用量、失败率、等待时间、用户满意度和支持工单，驱动平台路线图。

IDP 的关键是“自助但不孤立”。用户能自助创建资源，不代表平台团队放弃支持。模板应生成可读文档和联系人；目录应显示服务等级、最近部署和已知风险；失败任务应能够一键打开相关 runbook。平台团队的职责是降低认知负担，而不是把责任推回用户。

Backstage 的插件机制展示了如何通过前端页面、后端路由和目录实体扩展平台。插件应遵守最小权限原则：只申请所需的 API 范围，明确缓存和数据保留期限，并提供卸载路径。插件的显示名称可以变化，但实体类型、事件格式和权限声明应保持版本兼容。

## 24.5 工作流编排：把“做事”建模为可恢复的图

AI 任务往往不是单一容器，而是“准备数据→训练→评测→注册→部署→验证”的有向无环图（DAG）。工作流编排器的价值不只是启动容器，更在于提供可恢复的执行语义。

**任务节点**应包含输入引用、输出声明、资源需求、超时、重试策略和幂等键。节点不应通过隐式文件路径传递结果，而应将输出写入带版本的 Artifact，并把摘要写入元数据存储。这样，失败重试可以复用已完成的上游结果，不必从头开始。

**边与条件**表达依赖和分支。例如，评测结果低于阈值时进入人工审批，高于阈值时进入自动发布。条件应记录评估时使用的策略版本，避免策略更新后无法解释旧任务为什么走了某条路径。

**重试**必须区分暂时性错误和确定性错误。网络抖动、节点抢占和限流通常可重试；输入校验失败、权限拒绝和违反策略不应盲目重试。指数退避、最大尝试次数和熔断可以防止故障风暴。

**取消与补偿**是工作流的另一半。用户点击取消后，编排器应向所有可取消节点发送信号，并为不可取消节点记录“等待自然终止”。如果已经创建了云资源或写入了外部系统，需要定义补偿动作，例如释放临时磁盘或撤销未生效的端点。补偿不一定能完全回滚，因此状态中要区分 canceled、partially_cleaned 和 cleanup_failed。

Argo Workflows 是 Kubernetes 上的开源容器工作流引擎，支持并行步骤、参数和重试，可作为学习工作流 CRD 的实现样本（https://argo-workflows.readthedocs.io/）。即使团队不采用 Argo，也应借鉴其“工作流定义是资源对象、执行状态可查询”的设计。

工作流平台还应支持事件驱动。代码合并、数据版本发布、模型指标告警和配额恢复都可以成为事件。事件处理要具备去重、顺序和死信队列，否则一次重复投递就可能触发多次发布。事件载荷应尽量引用资源 ID，而不是复制大段配置；读取最新状态应由消费者完成。

## 24.6 环境复现：从“在我机器上能跑”到可证明的一致性

开发环境复现包含三个层次：工具版本一致、依赖内容一致、运行时行为一致。容器镜像只能解决其中一部分问题；镜像本身可能依赖未锁定的基础层、外部网络或运行时内核。

第一步是声明依赖。应用依赖应有锁文件，构建工具应固定版本，系统包应来自可验证的仓库。Nix flakes 通过锁定输入并以较纯的方式评估环境，提供了可复现开发 Shell 的一种实现（https://wiki.nixos.org/wiki/Flakes/en）。语言生态也可采用等价机制，例如 Python 的哈希锁定、JavaScript 的 lockfile、Go 的模块校验和。

第二步是隔离构建。构建过程不应读取开发者主目录中的隐式凭据，不应因为网络上某个包今天变化而得到不同产物。可以在无网络沙箱中执行构建，只允许访问预先缓存且带摘要的依赖。若必须访问网络，至少记录下载 URL、响应摘要和时间。

第三步是记录环境指纹。一个实验的指纹至少包括代码提交、数据集版本、依赖锁文件摘要、容器镜像摘要、驱动版本、随机种子和关键环境变量。指纹写入 Artifact 元数据，并在结果页展示。对于 GPU 任务，还应记录 CUDA、驱动和硬件型号，因为同一镜像在不同驱动组合下可能产生差异。

第四步是验证可复现性。对同一输入运行两次，比较产物摘要、指标容差和日志中的非确定性来源。模型训练通常包含并行归约、随机初始化和非确定性算子，平台应允许声明“位级可复现”“数值容差可复现”或“仅流程可复现”三种等级，而不是笼统声称可复现。

开发者体验上，复现按钮应重建一个隔离运行，而不是修改用户当前环境。按钮旁边显示“使用的提交、锁文件和镜像”，并允许导出命令供本地调试。任何平台自动注入的变量都要在文档中列出，避免用户在本地无法解释行为差异。

## 24.7 配置与策略：把变化和约束分开

配置是用户希望改变的参数，策略是平台允许或拒绝的边界。把两者混在同一个 YAML 文件中，会导致用户无法判断哪个字段可以自行修改，哪个字段需要审批。

配置应分为四类：静态默认值、环境覆盖、机密引用和运行时参数。静态默认值进入版本控制；环境覆盖由环境管理员维护；机密只保存引用而不保存明文；运行时参数必须经过模式校验并写入任务快照。配置解析应遵循“先合并、后校验、再渲染”的顺序，禁止模板通过字符串拼接绕过类型检查。

策略应尽量声明式、可测试、可解释。Open Policy Agent（OPA）提供了独立的策略引擎和 Rego 语言，可对 API 请求、基础设施配置和流水线输入做决策（https://www.openpolicyagent.org/docs）。一个策略决策至少返回 allow/deny、规则 ID、原因和补救提示。策略版本与任务绑定，后续更新不能改变历史审计记录的解释。

常见策略包括：生产环境必须有两名审批人；含敏感数据的任务只能在指定区域运行；GPU 预算超过阈值需要项目负责人批准；镜像必须有签名和漏洞扫描结果；模型端点必须配置健康检查和回滚版本。策略不应依赖不可观测的“团队习惯”，而应引用目录中的所有者、数据分类和成本标签。

机密管理是配置体系的安全边界。平台可以向任务注入短期令牌，但不应把长期云密钥写入日志、环境快照或 Artifact。日志脱敏应在采集端和存储端双重执行。开发者需要知道“任务拥有哪个权限”，而不是拿到一个无法解释的全能密钥。

配置演进需要兼容策略。新增字段应有默认值，删除字段要经历弃用周期，重命名应提供迁移工具。模板版本和配置版本分开管理：模板升级可以改变默认资源，而用户项目的配置快照仍应可复现旧任务。

## 24.8 发布门禁：让质量、风险和速度可组合

发布门禁不是把所有检查串成一条长流水线，而是定义可组合的证据。一个门禁可以消费代码测试报告、数据质量摘要、模型评测、漏洞扫描、许可证清单、来源证明和成本预测，并返回结构化结论。

推荐把门禁分为四级：

- **快速反馈门**：几分钟内完成的格式、单元测试、静态分析和基本数据校验，失败时阻止进入昂贵阶段。
- **可信构建门**：验证依赖锁定、镜像摘要、签名和构建来源，产出可验证的构建证明。
- **风险评估门**：运行安全扫描、偏差评测、隐私检查、红队样例和资源成本估算。
- **上线保护门**：检查审批、变更窗口、回滚版本、监控告警和逐步放量计划。

SLSA 规范定义了软件供应链来源证明和不同安全等级，可作为构建证明的参考（https://slsa.dev/spec/v1.2/）。平台不应只显示“通过/失败”，还应显示证据缺失的位置、证据新鲜度和可接受的例外范围。例外必须有责任人、理由、有效期和后续补救任务，不能用永久白名单掩盖风险。

逐步发布将风险限制在较小流量。对于模型端点，可以先分配少量租户或内部请求，观察错误率、延迟、成本和业务指标，再扩展比例。自动回滚需要事先定义阈值和冷却时间，避免告警抖动导致来回切换。回滚动作本身也要经过权限和审计检查。

门禁设计应避免“指标游戏”。例如，只看测试覆盖率会鼓励无意义的测试；只看延迟平均值会掩盖尾延迟；只看成本总额会忽略单租户异常。平台应提供指标定义、窗口、采样和计算版本，并允许用户查看原始样本。

## 24.9 插件接口：扩展能力而不复制核心

插件是平台应对领域差异的主要手段。设计插件接口时，可采用“稳定核心 + 可选能力”的结构。核心接口包括身份上下文、资源 ID、事件格式、日志协议和错误码；可选能力通过能力发现（capability discovery）声明，例如是否支持 GPU 预留、批量取消或自定义评测。

插件生命周期至少包括安装、配置、健康检查、升级、禁用和卸载。每个插件要声明版本兼容范围、所需权限、外部依赖、数据留存和迁移步骤。升级应支持并行运行新旧版本，失败时能回滚。插件不得直接写平台核心数据库，应通过 API 或事件提交变更。

Backstage 插件可以作为门户层扩展，但后端插件仍需遵守租户隔离和审计要求。工作流插件则应把任务提交映射到标准 Job 资源，而不是返回一套私有状态。这样，用户可以在门户、命令行或聊天界面看到同一任务。

OpenFeature 展示了“规范化 API + 可替换 Provider”的另一种扩展模式。其规范定义了与供应商无关的特性开关 API，Provider 负责从具体系统解析旗标值（https://openfeature.dev/specification/sections/providers/）。类似思想可以用于 AI 平台的模型路由、评测器和成本估算器：应用依赖稳定接口，平台根据环境选择实现。

插件接口还要考虑失败隔离。第三方插件超时不能阻塞核心控制面；调用应有预算、熔断和降级值。插件返回的数据要带来源和时间戳，避免过期缓存被当作事实。对于高风险插件，平台可以要求沙箱运行和只读权限。

## 24.10 任务状态与可观测性：让每一步都能被解释

任务状态不是一个字符串，而是一个受约束的状态机。一个训练任务可以经历 pending、validated、queued、running、succeeded、failed、cancel_requested、canceled、cleanup_failed 和 expired。状态转换必须有前置条件，非法转换应被拒绝并记录原因。

状态机设计要区分“事实”和“判断”。事实包括调度器返回的 Pod 已启动、存储已挂载、输出已写入；判断包括策略通过、预算足够、可发布。事实由系统观测，判断由策略引擎计算。把判断写死在 UI 会造成不同入口显示不一致。

每次转换记录事件：事件 ID、任务 ID、旧状态、新状态、触发者、时间、控制器版本、原因和关联日志。事件流可以驱动通知和审计，状态快照则用于快速查询。恢复控制器启动时应从事件或外部系统重建状态，不能依赖进程内存。

可观测性要遵循统一语义。OpenTelemetry 的语义约定定义了跨追踪、指标和日志的常用属性名，方便在不同组件之间关联信号（https://opentelemetry.io/docs/concepts/semantic-conventions/）。平台应为每个任务生成 trace ID，并将其注入工作流节点、容器日志和外部 API 请求。用户点击某个失败步骤时，应能跳到对应的日志、指标和策略决策。

“任务完成”不等于“任务成功”。成功指标应包括结果可用性、证据完整性、成本是否在预算内和清理是否完成。平台可以定义完成度：产物已写入但监控未启用时为 partial_success；主任务失败但补偿成功时为 failed_cleanly。细分状态能减少支持团队从日志猜测发生了什么。

## 24.11 团队协作：平台要管理认知负荷，而不仅是资源

平台工程常被误认为基础设施团队的单向交付。实际上，平台的质量取决于平台团队与使用团队之间的协作机制。

首先要定义服务边界。平台团队承诺控制面可用性、模板维护窗口、门禁响应时间和数据保留；应用团队承诺提供健康检查、资源预算和故障联系人。服务等级目标应以用户旅程衡量，例如“提交后五分钟内看到可解释的排队原因”，而不只是“API 99.9% 可用”。

其次要建立反馈渠道。每个黄金路径都应有轻量反馈按钮，记录用户卡在哪一步、错误是否可理解、是否绕过平台。平台团队每个迭代周期公开改进清单和已知限制，避免用户在聊天群里重复提问。

再次要维护文档和示例。目录条目应显示所有者、依赖、运行手册、最近一次验证时间和弃用日期。文档采用 docs-as-code 时，示例应在 CI 中执行，防止“文档能看不能跑”。Backstage TechDocs 的做法是从仓库构建文档并在门户中展示，可作为实现参考（https://backstage.io/docs/next/techdocs/generated-index/）。

平台还应帮助团队管理认知负荷。模板把复杂选择压缩为少量有意义的选项；高级配置可以折叠，但不能隐藏关键风险。错误消息应包含下一步，而不是要求用户理解调度器内部术语。对于长期运行的实验，平台可提供摘要和订阅，减少用户频繁刷新页面。

## 24.12 多租户平台产品化：隔离、公平和可计费

当平台服务多个团队时，租户不只是一个标签，而是隔离和治理的边界。租户模型至少要回答：资源属于谁、谁能看见、谁能修改、谁承担成本、谁负责数据删除。

**身份隔离**需要将用户、服务账号和工作负载身份分开。请求中的租户上下文不能只由客户端传入，应由经过验证的令牌和目录关系计算。后台任务必须携带原始发起者和服务账号，便于审计。

**资源隔离**包括命名空间、网络策略、存储前缀、加速器配额和节点池。共享集群可以通过资源配额和优先级实现公平，但对高敏感数据应提供物理或逻辑上更强的隔离。平台要防止跨租户日志、缓存和指标标签泄漏。

**公平调度**不等于平均分配。可以根据租户预算、优先级、等待时间和历史用量计算权重，同时设置每租户上限，避免单个大任务拖垮系统。排队页面应显示预计等待和阻塞原因，用户可以选择更小的资源或错峰运行。

**计费与成本治理**需要稳定的成本事件。每个任务记录资源类型、使用时长、单价版本和租户标签；汇总结果可与云账单对账。平台可以在提交时给出估算，在运行中显示累计，在超预算前发出可操作的警告。成本数据属于敏感业务信息，应限制可见范围并保留更正流程。

**数据生命周期**应支持保留、归档和删除证明。租户删除项目后，平台要说明哪些缓存、日志、备份会在何时清除。对于跨区域复制和第三方插件，删除请求必须传播并可审计。

多租户产品化还包括套餐和版本管理。不要用“企业版”作为模糊权限集合；应把并发额度、保留期、支持等级和可用插件写成可验证的能力。版本升级要提供迁移检查，避免租户在没有通知的情况下被迫改变行为。

## 24.13 标准库可运行实验：一个可恢复的门禁工作流

下面的实验只依赖 Python 标准库，模拟一个带策略检查、幂等提交、重试和状态查询的 AI 任务平台。它不是生产实现，却可以帮助读者观察控制面最小闭环：声明任务、校验策略、执行状态转换、记录事件并从事件重建摘要。

将以下代码保存为 `platform_lab.py`，使用 Python 3.11 或更高版本运行。代码不访问网络，也不会创建真实云资源。

```python
#!/usr/bin/env python3
import argparse, json, pathlib, time, uuid
from dataclasses import dataclass, asdict

TERMINAL = {"succeeded", "failed", "canceled"}
ALLOWED = {
    "pending": {"validated", "failed", "canceled"},
    "validated": {"queued", "failed", "canceled"},
    "queued": {"running", "failed", "canceled"},
    "running": {"succeeded", "failed", "cancel_requested"},
    "cancel_requested": {"canceled", "failed"},
    "failed": set(), "succeeded": set(), "canceled": set(),
}

@dataclass
class Event:
    task_id: str
    old: str
    new: str
    reason: str
    ts: float
    event_id: str

class Store:
    def __init__(self, path="platform-events.jsonl"):
        self.path = pathlib.Path(path)
    def append(self, event):
        with self.path.open("a", encoding="utf-8") as f:
            f.write(json.dumps(asdict(event), ensure_ascii=False) + "\n")
    def events(self, task_id=None):
        if not self.path.exists(): return []
        out = []
        for line in self.path.read_text(encoding="utf-8").splitlines():
            e = Event(**json.loads(line))
            if task_id is None or e.task_id == task_id: out.append(e)
        return out
    def state(self, task_id):
        state = "pending"
        for e in self.events(task_id): state = e.new
        return state

def policy(args):
    if args.gpu > 2 and args.tenant != "research":
        return False, "POLICY_GPU_QUOTA: non-research tenants may request at most 2 GPUs"
    if args.budget <= 0:
        return False, "POLICY_BUDGET: budget must be positive"
    return True, "policy accepted"

def transition(store, task_id, new, reason):
    old = store.state(task_id)
    if new not in ALLOWED.get(old, set()):
        raise RuntimeError(f"invalid transition {old} -> {new}")
    store.append(Event(task_id, old, new, reason, time.time(), str(uuid.uuid4())))
    return new

def submit(store, args):
    ok, why = policy(args)
    task_id = args.idempotency_key or str(uuid.uuid4())
    if store.events(task_id):
        print(json.dumps({"task_id": task_id, "state": store.state(task_id), "idempotent": True}, ensure_ascii=False))
        return
    if not ok:
        store.append(Event(task_id, "pending", "failed", why, time.time(), str(uuid.uuid4())))
        print(json.dumps({"task_id": task_id, "state": "failed", "reason": why}, ensure_ascii=False))
        return
    transition(store, task_id, "validated", why)
    transition(store, task_id, "queued", "capacity reserved")
    transition(store, task_id, "running", "worker started")
    # 用 --fail 模拟确定性失败；生产系统应将该错误分类为不可重试
    if args.fail:
        transition(store, task_id, "failed", "EVAL_THRESHOLD: score below gate")
    else:
        transition(store, task_id, "succeeded", "artifact and report committed")
    print(json.dumps({"task_id": task_id, "state": store.state(task_id)}, ensure_ascii=False))

def main():
    p = argparse.ArgumentParser()
    p.add_argument("command", choices=["submit", "status", "events"])
    p.add_argument("--tenant", default="team-a")
    p.add_argument("--gpu", type=int, default=1)
    p.add_argument("--budget", type=float, default=10)
    p.add_argument("--idempotency-key")
    p.add_argument("--id")
    p.add_argument("--fail", action="store_true")
    p.add_argument("--store", default="platform-events.jsonl")
    args = p.parse_args(); store = Store(args.store)
    if args.command == "submit": submit(store, args)
    elif args.command == "status": print(json.dumps({"task_id": args.id, "state": store.state(args.id)}, ensure_ascii=False))
    else: print(json.dumps([asdict(e) for e in store.events(args.id)], ensure_ascii=False, indent=2))

if __name__ == "__main__": main()
```

运行示例：

```bash
python platform_lab.py submit --tenant team-a --idempotency-key demo-1
python platform_lab.py status --id demo-1
python platform_lab.py submit --tenant team-a --gpu 8 --idempotency-key denied-1
python platform_lab.py submit --tenant team-a --idempotency-key demo-1
python platform_lab.py events --id demo-1
```

第一次提交会经过 validated、queued、running、succeeded；第二个任务因 GPU 策略进入 failed；第三次提交使用相同幂等键，不会重复执行。观察 `platform-events.jsonl` 可以看到状态转换和原因。请尝试把代码中的 `ALLOWED["running"]` 删除 `succeeded`，再运行实验，理解为什么状态机必须显式声明合法转换。

实验改进建议：为事件加入租户和代码提交字段；实现指数退避的重试；把策略从 Python 函数移到独立 Rego 文件；增加“取消请求”命令；让状态摘要从事件重建而不是读取内存。完成这些改动后，再思考哪些字段属于平台核心契约，哪些只是实验实现细节。

## 24.14 失败案例：平台为什么会被绕过

**案例一：模板生成了无法维护的仓库。**某团队为了“一键创建服务”，模板同时生成十几个配置文件、三套 CI 工作流和一套私有脚本。半年后，模板升级困难，项目之间出现分叉。根因是模板承担了平台所有历史决策，却没有版本和迁移策略。修复方法是把模板拆成稳定骨架和可更新组件；生成的仓库记录模板版本，平台提供迁移检查；对于非关键文件，改用运行时引用而不是复制。

**案例二：门禁只返回红叉。**模型评测失败后，门户显示“Quality gate failed”，用户只能找平台团队。根因是门禁输出没有结构化原因，也没有链接到失败样本。修复方法是为每个规则定义错误码、证据链接和最小复现命令；把常见修复建议加入文档，并统计用户从失败到再次提交所需时间。

**案例三：重试风暴导致配额耗尽。**底层节点短暂不可用，编排器对所有任务立即重试，队列持续膨胀，正常任务也无法运行。根因是没有区分暂时性和确定性错误，也没有全局退避。修复方法是错误分类、指数退避、租户级并发上限和熔断；对重试次数和排队时间设置告警。

**案例四：插件泄漏跨租户日志。**一个监控插件在缓存键中遗漏租户 ID，导致用户能看到其他团队的任务名称。根因是插件接口只约定了资源 ID，没有强制租户上下文。修复方法是把租户上下文设为不可变请求字段，在网关和插件 SDK 双重校验；编写跨租户访问的负向测试；缓存默认按租户分区。

**案例五：平台把所有人锁在黄金路径。**研究团队需要自定义编译器和网络拓扑，平台拒绝任何例外，团队于是建立独立集群。根因是把标准化误当成统一化。修复方法是提供有期限、可审计的逃生舱；平台收集例外用法，评估是否值得升级为新的产品能力；高风险例外需要额外审批，但不应让普通任务承担同样复杂度。

**案例六：成功任务没有清理。**任务状态显示 succeeded，但临时磁盘和云端 IP 未释放，月底成本超预算。根因是“任务成功”只关注主产物，没有把补偿和清理纳入状态机。修复方法是将清理作为显式子流程，定义 cleanup_failed 状态和重试；成本报表按任务和资源核对；上线门禁要求存在清理策略。

**练习七：插件契约测试。**定义一个评测器插件接口，要求支持能力发现、超时、错误码和版本协商。编写一个故意返回旧字段的插件，观察客户端如何兼容或拒绝。

**练习八：多租户压测。**模拟三个租户提交不同优先级和资源大小的任务，比较无配额、固定配额和加权公平调度的等待时间。输出每个租户的 p50、p95 等待时间和成本。

**项目题：构建最小 IDP。**用任意语言实现一个本地服务，提供项目创建、任务提交、策略检查、事件查询和文档链接五个 API。要求：所有变更写事件日志；状态可从事件重建；插件可独立升级；跨租户访问有负向测试；README 给出五分钟内成功运行的步骤。

## 24.18 安全边界清单

平台工程的便利性不能越过安全底线。上线前至少检查以下边界：

- 身份、租户和服务账号经过独立验证，客户端不能自行声明高权限租户。
- 机密使用短期令牌或引用，绝不进入日志、事件载荷、镜像层和错误堆栈。
- 跨租户查询、缓存、指标和日志都有负向测试，默认拒绝而不是默认共享。
- 策略决策带版本、原因和证据；例外有责任人、范围、有效期和撤销方式。
- 构建产物带来源证明、签名和依赖摘要；发布只接受可验证的产物。
- 插件权限最小化，运行在隔离边界内；超时、熔断和降级不会绕过授权。
- 取消、回滚和删除是可审计操作；不可恢复的数据删除需要额外确认和保留证明。
- 成本、数据分类和用户活动等敏感信息按最小可见范围展示，并遵守保留期限。
- 逃生舱不会绕过核心身份、审计和安全扫描；临时例外到期后自动失效。
- 平台故障时，用户仍能导出任务定义、日志和产物元数据，避免被锁定在黑盒中。

## 小结：把平台当作持续演进的内部产品

AI Infra 平台的核心产物不是一个漂亮门户，而是一套让团队能够安全、自助、可复现地完成工作的方法。平台抽象把底座差异放在可更换的位置；IDP 用目录、模板、交付和反馈平面降低认知负荷；工作流和状态机让任务可恢复、可解释；环境复现和来源证明建立信任；策略、门禁和多租户治理把速度与安全放在同一条路径上；插件和逃生舱则让平台在面对新需求时保持弹性。

平台团队应持续问三个问题：用户今天还需要手工完成哪一步？哪条规则只能靠口头约定？当平台失败时，用户能否在没有平台工程师值班的情况下理解、恢复或安全退出？如果答案不断改善，平台就从基础设施集合成长为真正的内部产品。

## 24.19 设计评审清单：从接口草图到运营现实

在平台立项评审时，可以用下面的顺序逐层追问，避免会议只停留在组件选型。第一问是用户目标：这个能力对应哪个用户旅程，成功的最小结果是什么，多久能得到反馈？如果只能回答“我们要一个统一入口”，说明问题还没有被具体化。第二问是资源边界：输入、输出、所有权、生命周期和数据分类分别是什么？资源是否能在没有门户的情况下通过 API 创建和查询？第三问是状态语义：哪些状态由外部系统观测，哪些状态由策略判断，状态转换是否幂等，重启控制器后能否重建？第四问是失败恢复：每一种可预期故障是否有明确的错误码、重试策略、补偿动作和人工接管路径？第五问是证据链：用户能否看到代码、数据、镜像、策略和审批的版本，是否能在三个月后复现这次发布？第六问是成本与容量：提交前是否给出估算，运行中是否有预算护栏，租户之间如何公平，成本异常由谁收到通知？第七问是安全：请求身份从哪里来，机密如何注入，插件能看到哪些数据，跨租户访问如何被拒绝并留下证据？第八问是退出机制：用户能否导出任务定义和产物，平台或插件下线时如何迁移，删除请求是否能证明完成？

评审材料最好包含一份“反例走读”。让评审者模拟以下情况：提交请求重复到达；底层节点在写产物时宕机；策略在任务执行中升级；租户达到配额但已有任务正在运行；插件返回未知字段；用户在发布后立即请求回滚；日志系统延迟十五分钟才恢复。逐个反例走完，平台团队会发现很多隐含假设，例如“状态一定按顺序到达”“所有错误都可以重试”“目录信息永远新鲜”。将这些假设写成显式契约，才能在测试和监控中验证。

平台版本化也值得单独评审。API 版本只解决字段兼容，不解决语义变化。一个默认 GPU 类型的改变可能不破坏 JSON 模式，却会改变成本和性能。因而每次改变默认值、调度权重、策略阈值或日志字段，都应在变更说明中写出影响范围、迁移建议和回滚方式。对于模板，推荐维护“支持窗口”：当前版本提供完整支持，旧版本只接受安全修复，过期版本只能导出配置并迁移。对于插件，建议提供契约测试套件和兼容性矩阵，让插件作者在升级平台前自行验证。

运营上，平台应建立几个高信号指标：从创建项目到首个成功任务的时间；任务从失败到再次成功的时间；因为不可解释错误而打开支持工单的比例；黄金路径使用率与逃生舱使用率；策略例外的数量、逾期率和重复原因；跨租户访问拒绝次数；每个任务的清理成功率；成本估算与实际账单的偏差。指标不能只用于考核平台团队，也要用来发现产品设计问题。例如逃生舱使用率突然升高，可能说明黄金路径过时；支持工单减少但取消率升高，可能说明用户放弃了任务而不是问题被解决。

最后，平台要给自己设定“可逆性预算”。任何自动化动作都应尽量可暂停、可重试、可回滚或可导出。不可逆动作，例如删除数据、公开端点或跨区域复制，应提高确认等级并扩大审计信息。可逆性不是降低速度，恰当地设计补偿和快照后，团队反而能更快尝试新能力。把可逆性当作平台的质量属性，能在面对未知需求和新模型时保持行动空间。

## 24.20 章节回顾卡片

如果读者只保留一页笔记，可以记住以下对应关系：资源模型决定平台谈论什么；操作模型决定用户如何改变世界；状态机决定系统如何解释变化；工作流决定复杂任务如何恢复；环境指纹决定结果能否复现；策略与门禁决定什么被允许；事件和遥测决定问题能否定位；插件和逃生舱决定平台能否演进；租户模型决定组织如何共享而不互相伤害；指标和反馈决定平台是否真正改善开发者体验。它们共同组成一个闭环：用户提交意图，控制面验证并执行，系统记录证据，体验面展示状态，反馈面推动下一版抽象。缺少任何一环，平台都可能退化为不可解释的自动化脚本。
