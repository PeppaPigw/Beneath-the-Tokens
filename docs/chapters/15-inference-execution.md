# 第15章　推理执行：prefill、decode、KV cache 与可控调度

> 语言模型推理的难点并不是把一次前向传播调用起来，而是让数千个长短不同、优先级不同、随时可能取消的请求，在有限的计算、显存、带宽和功耗预算内共同前进。一次请求有一段可以高度并行的 prefill，也有一段每次只生成一个或少量 token 的 decode；它们争抢同一块显存和同一条设备队列。KV cache 让 decode 不必反复计算历史，却把序列长度直接变成内存占用。连续批处理让新请求在旧请求尚未完成时加入，但也会把调度、取消、分页、碎片、尾部延迟和公平性问题暴露出来。本章把推理服务当作一个可观测的实时系统：每个阶段都有明确的资源账本、可验证的假设和停止条件。

本章的例子先用纯 Python 标准库构造 CPU toy 模拟器。模拟器不声称复现某个 GPU 内核的真实性能，尤其不代表真实矩阵乘、通信、量化或显存行为。它的价值在于把抽象概念变成可运行的状态机：请求何时进入、何时预填充、何时占用 KV 页、何时产生 token、何时被拒绝或取消。迁移到生产前，必须在目标硬件、目标模型、目标流量和目标安全边界上重新测量。

## 15.1 一次请求的两种节奏：prefill 与 decode

### 15.1.1 Prefill 是把上下文一次读完

请求通常先携带系统提示、历史对话、检索片段和用户问题。prefill 阶段把这串输入 token 一次送入 Transformer，计算每层的 query、key、value 和注意力结果，最终得到最后一个位置的 logits。虽然注意力在长序列上仍有二次项，但 token 维度上的并行性很高，矩阵乘可以填满大部分算力。prefill 的首要指标是首 token 延迟，也就是从请求进入到第一个可展示 token 的时间；在流式产品里，这个时间往往比完整回答时间更影响“是否卡住”的感知。

prefill 的成本受输入长度、层数、隐藏维度、批大小和实现影响。批量把多个请求的输入对齐后，可以提升算力利用率，但填充的空位置会浪费计算，尤其当一个请求有几千个 token、另一个只有几十个 token 时。生产调度器通常会按长度分桶、限制单批 token 总数，或者采用不需要整齐填充的变长内核。长度分桶本身也有公平性代价：短请求可能等待一个长桶，长请求可能因为桶稀疏而无法凑满批次。

### 15.1.2 Decode 是重复的小步迭代

decode 阶段每次生成一个新 token，下一步再把这个 token 送入模型。因为历史 token 的 key 和 value 已经保存在 KV cache 中，当前步只需计算新位置的 query、key、value，并让 query 与历史 key 做注意力。算力工作量看起来比 prefill 小，但每一步都要读整个历史的 KV，且 kernel 启动、调度和内存访问开销占比变高。对单个请求而言，decode 常常受显存带宽和同步延迟约束，而不是受矩阵乘峰值约束。

decode 生成的 token 数量不可预知。用户可能在第 5 个 token 停止，也可能生成 2,000 个 token；工具调用、结构化输出和停止词会改变生命周期。因此系统不能只为平均长度做预算，必须对最大上下文、最大新 token、每租户并发和全局页池设上限。达到上限时应返回清晰的截断或拒答原因，不能静默丢掉系统消息或安全约束。

### 15.1.3 两阶段不是两条孤立队列

将 prefill 和 decode 拆成两个服务可以让它们分别扩缩容，却会增加 KV 的转移、版本一致性和跨节点调度成本。合并服务则便于共享显存，容易出现长 prefill 阻塞正在 decode 的请求。实践中常见三种模式：

1. **同一实例、轮转调度**：每轮限制 prefill 的 token 预算，再为所有活跃请求各解码一步，简单且不需要搬运 KV。
2. **分离式 prefill/decode**：prefill 节点负责生成 KV，decode 节点接管并持续生成，适合大量长上下文和稳定的跨节点网络，但需要高效 KV 传输与故障重试。
3. **分层池**：短请求走共享池，超长请求进入长上下文池；池之间有独立并发和内存预算，避免一个异常大请求拖垮全部用户。

选择模式时要看瓶颈在哪里。若输入 token 占大头且解码很短，分离 prefill 可能更有效；若输出很长且网络带宽紧张，搬运 KV 可能抵消收益。不要只看平均吞吐，应同时比较首 token 延迟、每 token 间隔、p95/p99 尾延迟、拒绝率和每请求能耗。

### 15.1.4 端到端时间线

可以把请求看成一条带资源占用的时间线：排队等待、准入检查、prefill、首 token、重复 decode、停止判定、释放 KV、日志和计费。每段都应打点，并把同一 `request_id` 贯穿设备事件和调度事件。仅记录总耗时无法区分“排队太久”“prefill 太慢”还是“decode 受长上下文拖慢”。在流式接口中，还要记录首 token 到达时间、相邻 token 间隔和最后一个 token 时间；用户看到的卡顿常常来自中间长间隔，而非总时长。

## 15.2 KV cache：用内存换重复计算

### 15.2.1 每个 token 到底占多少字节

对每层注意力，KV cache 至少保存一个 key 向量和一个 value 向量。若 batch 中序列长度为 S，层数为 L，键值头数为 H_kv，每头维度为 D，数据类型每元素 B 字节，则近似容量为：

```text
bytes_per_sequence ≈ 2 × L × S × H_kv × D × B
```

这里的 2 是 K 与 V 两份。若模型使用多查询注意力或分组查询注意力，H_kv 会小于 query 头数，KV 容量显著下降；若使用 float16，B 为 2；采用 int8 或更低精度则可进一步降低占用，但需要校准和质量验证。实际实现还会有页元数据、对齐、临时 workspace、采样缓冲区和通信缓冲区，因此不能把公式结果直接当作可用显存。

一个直观例子：假设 32 层、8 个 KV 头、每头 128 维、float16，一个 token 的 K/V 大约是 2 × 32 × 8 × 128 × 2 = 131,072 字节，也就是约 128 KiB。上下文为 8,000 token 时，一条序列仅 KV 就接近 1 GiB，还没算模型权重和激活。这个数量级解释了为什么上下文长度和并发数常常比参数量更快成为服务瓶颈。

### 15.2.2 KV 生命周期与所有权

KV 不是“缓存命中就永远保留”的普通缓存，而是推理正确性的一部分。请求创建时获得一个句柄，prefill 写入前缀页，decode 逐步追加新页；请求完成、取消、超时或发生节点故障时，句柄必须原子地释放或转移。释放过早会导致后续步读到脏数据，释放过晚则形成泄漏，最终表现为无关请求被拒绝。

应为每个页记录所有权和版本，例如租户、请求、逻辑 token 区间、模型版本、量化格式、校验摘要和最近访问时间。日志里不必保存 token 原文；页号、长度和版本通常足以排障。共享前缀时必须采用引用计数或不可变快照，不能让一个请求的 decode 覆盖另一个请求仍在使用的页。若前缀来自不同权限域，即使文本相同也不应无条件共享，以免出现跨租户数据推断。

### 15.2.3 复用前缀的收益与陷阱

系统提示和常用模板往往相同，可以把它们的 KV 作为只读前缀复用，缩短 prefill。复用键应包含完整的模型权重版本、tokenizer 版本、模板版本、精确 token 序列和权限上下文。仅用字符串前缀哈希是不够的：相同的用户可见文本，在不同系统指令、工具权限或租户策略下，语义上下文可能不同。前缀页还要设置容量和生命周期，防止热门模板挤占活跃请求的动态页。

缓存命中并不自动等于安全。攻击者可以通过测量首 token 延迟或页分配行为，推断某个秘密前缀是否存在。对高敏感前缀应关闭跨用户复用、加入时间和大小抖动，或只在同一信任域内共享。缓存统计要按权限域聚合，避免把租户名、文档标题或用户问题写进公共指标。

### 15.2.4 KV 量化和压缩

KV 量化可以把 float16 压到 int8、int4 或混合格式，减少内存和带宽，但误差会累积到每个 decode 步。长上下文、稀有语言、代码和严格 JSON 输出对误差更敏感。可靠做法是先建立未量化对照，按上下文长度、语言、任务和安全提示分层评测；若质量下降超过预算，退回更高精度或只量化较早的层。不要仅凭总体平均准确率批准，因为少量高风险请求的失败可能被平均值掩盖。

## 15.3 Paged memory：把连续序列映射到固定大小的页

### 15.3.1 为什么连续分配会碎片化

最朴素的实现为每条序列分配一块连续 KV 缓冲区，长度增长时扩容并复制。面对长短混合请求，显存会出现外部碎片：总空闲容量足够，却找不到一段连续区域容纳新序列。扩容复制还会暂停 decode，造成尾部延迟尖峰。若提前按最大长度分配，则短请求浪费大量空间，实际并发被最坏情况锁死。

paged memory 把 KV 切成固定 token 数的页，例如每页 16、32 或 64 token。逻辑序列维护页表，页池按需分配物理页。相邻逻辑 token 不必占用连续物理地址，注意力内核根据页表读取。请求完成时只归还使用过的页，减少外部碎片。页大小越小，内部浪费越少，但页表更大、地址转换和内核元数据开销更高；页大小越大，读取更规整，却可能在短序列尾部浪费更多空间。

### 15.3.2 页池、配额和碎片指标

页池设计应至少有全局池、租户配额、优先级保留池和紧急回收池。全局剩余页不代表某租户可立即使用，因为公平性和资源隔离需要先检查租户配额。建议记录以下指标：

- 已分配页、空闲页、保留页、不可用页以及各类页的高水位
- 页内部未使用 token 数和按长度桶统计的碎片率
- 页表查找次数、读放大、跨节点页访问次数
- 因页不足而拒绝、排队、截断、取消和回收的请求数
- 从释放到再次可用的延迟，以及异常回收次数

碎片率不能只用“空闲页占比”表示。内部碎片可以定义为已分配页中未写入的 token 槽位除以总槽位；外部碎片在固定页模型下较少，但会以不同内存池之间无法借用的形式出现。监控应按模型版本和租户分层，否则一个大租户的健康状态会掩盖小租户的持续拒绝。

### 15.3.3 页面迁移、抢占和重算

当高优先级请求到来而页池不足时，有三种常见动作：等待、抢占低优先级请求，或释放部分 KV 后重算。等待最安全但可能违反 SLA；抢占需要保存请求状态并保证恢复时模型版本一致；重算省下内存却增加 prefill 成本。抢占不等于删除请求：应把请求放回可恢复队列，保留已生成文本、随机种子、采样参数和安全策略版本，并在恢复时验证上下文仍然有效。

抢占策略必须避免“抖动”：如果每轮都在同一批请求之间抢来抢去，系统会花大量时间搬页和重算，却几乎不生成 token。可以设置最小运行配额、冷却时间和最大抢占次数；超过次数则降级到低并发长队列或返回可重试错误。对正在执行工具调用的请求，抢占边界还要尊重工具事务状态，不能在外部副作用已提交而内部文本未记录时重复执行。

## 15.4 Continuous batching：每一步都允许批次变化

### 15.4.1 静态批处理的浪费

静态批处理在开始时收集 N 个请求，所有请求一起跑到最长序列结束。短请求完成后，批次里的位置变成填充，算力和 KV 槽位被浪费；长请求会把整个批次的完成时间拖长。面对流式服务和长度高度离散的流量，静态批处理会造成排队和尾延迟。

连续批处理把调度点放到每个 decode step 或小窗口：已完成的请求退出，新准入的请求进入；每一步只为活跃序列产生一个 token。批次形状和页表可以动态变化，资源账本按 token 预算而不是固定请求数管理。这不是“无限插队”，因为新请求仍要通过准入检查，并预留未来 decode 需要的页和时间配额。

### 15.4.2 单轮决策的四个输入

每轮调度至少需要四类输入：

1. **活跃状态**：每个请求的阶段、已生成 token、剩余上限、页数、最近一次服务时间和取消标记。
2. **资源状态**：可用页、计算 token 预算、设备队列深度、通信带宽和临时 workspace。
3. **策略状态**：租户配额、优先级、SLA、deadline、重试次数和安全降级级别。
4. **候选动作**：继续 decode、插入新 prefill、暂停、迁移、释放、拒绝或请求澄清。

调度器应先做硬约束过滤，再在可行集合中优化目标。硬约束包括不会超出页池、不会超过单请求最大长度、不会让已取消请求继续产生外部输出、不会把不同模型版本的 KV 混入同一请求。软目标可以综合首 token 延迟、每 token 间隔、吞吐、公平性和能耗，但需要固定权重并记录决策理由。

### 15.4.3 Token 预算比请求数更有意义

“同时处理 32 个请求”没有说明它们是 32 个短问题还是 32 个 32k 上下文。更可比的做法是为每轮设定最大输入 token、最大输出 token 和最大活跃页数。调度前估算新增 prefill 的计算量、每个活跃请求下一步所需的读写量以及安全余量。估算不能假设所有请求都在平均长度处停止，应保留尾部预算，并在达到阈值前停止接纳新的长请求。

输入和输出预算要分开。一个请求可能 prefill 很长但只输出一句话，另一个输入很短却会生成大量代码。若只看总 token，会让长输入挤占 decode 服务，造成正在流式输出的请求长时间没有下一个 token。常见策略是为 decode 保留最低服务份额，每轮先为活跃请求完成一次步进，再用剩余预算执行新 prefill。

### 15.4.4 公平性、优先级与 deadline

优先级是策略，不是把低优先级请求永久饿死的理由。可以使用带老化的优先级：等待越久，调度分数逐步增加；或者为每租户维护令牌桶，令牌用尽后进入公平队列。deadline 请求应提供可接受的降级路径，例如更小的最大输出、较低采样复杂度或转到轻量模型；不能为了满足一个 deadline 让所有其他租户的 p99 失控。

高优先级也要经过安全和配额检查。管理员标记不能绕过数据权限、内容安全或审计。队列中的敏感请求不应通过错误日志打印完整 prompt；调度原因可记录成分类标签，如 `quota_exceeded`、`memory_pressure`、`deadline_risk`，而不是记录原始文本。

## 15.5 Admission control：先保证系统可活，再追求吞吐

### 15.5.1 准入是资源承诺

准入控制回答“这条请求现在能否开始”，不是简单的排队长度判断。一个请求至少带来输入 token、预期输出上限、KV 页、临时激活、采样缓冲、日志和可能的重试成本。准入时应计算最坏但合理的承诺，并为已有请求留出 decode 预算。若只按当前页数判断，几个长输出请求同时增长时会把系统推入不可恢复的 OOM。

可以把准入看成三道门：

- **策略门**：认证、租户、模型权限、内容政策、区域和数据驻留要求。
- **资源门**：模型权重已加载、KV 页、临时显存、CPU 线程、网络和限流令牌。
- **体验门**：预计等待和首 token 延迟是否仍在请求级 SLA 内，是否会破坏已有请求。

任一门失败都应给出可操作的结果：排队并带预计等待、降级到允许的模型、缩短上下文、要求用户减少输出，或返回明确的可重试错误。模糊的 500 会让客户端盲目重试，形成重试风暴。

### 15.5.2 背压与重试协议

服务端必须有背压，否则连接数会比模型吞吐增长得更快。可以在网关处限制并发流、在排队处限制总 token、在模型池处限制页和设备队列。拒绝响应应包含稳定的错误类别、建议等待时间和是否安全重试的标志。客户端只对幂等请求按指数退避重试；流式输出已经部分发送时，重试可能生成重复内容，必须由上层决定是否拼接。

重试策略要有抖动、上限和租户级预算。若下游页池短暂紧张，几十毫秒后的重试可能成功；若模型权重未加载或策略拒绝，盲目重试只会放大压力。服务端可以返回一个不包含内部拓扑的 `retry_after_ms`，并用监控验证客户端是否遵守。

### 15.5.3 取消、超时与客户端断线

用户关闭页面不代表服务器自动知道。应监听流式连接断线和显式取消，设置很短的检测周期，并在安全边界释放 KV。取消释放不能在设备仍有未完成 kernel 时粗暴复用同一页；需要等待事件完成或使用代际标签，避免旧 kernel 写入新请求的页。

超时分为排队超时、prefill 超时、单步 decode 超时、总请求超时和空闲流超时。每种超时的处置不同：排队超时可直接拒绝，单步超时可能说明设备故障需要摘除实例，总请求超时应记录已生成 token 并安全关闭流。工具调用或外部事务要有独立的提交状态，不能让模型请求超时后自动重放不幂等操作。

## 15.6 Speculative decoding：用便宜模型猜，再由目标模型验

### 15.6.1 基本流程

投机解码使用一个较小、更快的草稿模型先生成一段候选 token，再由目标模型并行验证。若目标模型接受候选前缀，就一次提交多个 token；在第一个不接受的位置，保留目标模型给出的替代 token，后面的猜测丢弃。理想情况下，目标模型每轮验证多个 token，减少昂贵模型的迭代次数。

接受率是核心变量，受草稿模型质量、领域、温度、采样策略和上下文长度影响。接受率高时可以明显降低每 token 延迟；接受率低时，草稿模型的计算、KV 和管理开销反而拖慢系统。必须用目标流量分层测量，而不是只在通用基准上测一次。

### 15.6.2 采样一致性与验证边界

贪心解码比较简单，因为目标模型总是选择最高概率 token。随机采样需要更谨慎：草稿模型提出的 token 不能改变目标分布。常见做法是基于目标和草稿概率计算接受概率，并在拒绝位置按修正分布采样。实现中的浮点误差、温度、top-k、top-p、重复惩罚和随机数种子都可能影响一致性。若产品要求可重放，应记录采样参数、模型版本和随机种子，并验证投机路径与非投机路径的统计分布一致。

结构化输出和安全过滤是额外边界。草稿模型可能猜出不符合 JSON schema 的 token，目标模型验证后拒绝；若在验证前把草稿 token 发给用户，就会暴露不应出现的片段。安全分类器、工具参数校验和外部副作用必须放在最终接受之后。投机不能绕过系统提示、权限检查或内容安全。

### 15.6.3 草稿模型的资源账本

投机不是免费的“加速开关”。草稿模型占权重显存、KV 页、算力和调度槽位。准入时需要同时预算目标和草稿两套资源；在内存压力高时，关闭投机可能比抢占活跃请求更合理。草稿长度也应动态调整：接受率高且页富余时增加猜测步数，接受率下降或尾延迟上升时缩短；调节必须有上下限和冷却时间，避免振荡。

可以按请求类型选择是否投机。短输出请求的管理开销可能不值得；代码和严格格式任务的接受率可能高，也可能因一个标点差异导致频繁拒绝；多语言和稀有领域需要独立测量。不要把整体平均加速写成所有租户的 SLA 承诺。

## 15.7 Memory planning：从权重、KV 到临时缓冲的总账

### 15.7.1 四类内存

推理实例至少要为四类内存留预算：

1. **静态权重**：模型参数、量化缩放因子、词表和常驻查找表。
2. **动态 KV**：按活跃请求和生成长度增长的页池，包括共享前缀和抢占快照。
3. **临时激活与 workspace**：矩阵乘、注意力、归约、采样和通信所需的短时缓冲。
4. **系统与碎片余量**：运行时元数据、页表、驱动保留、对齐浪费和故障降级空间。

总预算不能刚好等于设备标称容量。应为临时峰值和碎片留出安全百分比，并用压力测试验证。多个模型共存时，权重和 workspace 可能在同一设备争用；加载/卸载会触发显存碎片和页迁移，不能只按权重大小叠加。

### 15.7.2 静态上限与动态估算

静态上限包括最大上下文、最大新 token、每租户最大并发、页大小、单批 token 和最大草稿长度。动态估算根据活跃请求的真实长度、剩余上限、分页碎片和历史拒绝率调整。估算结果要保守且可解释：例如“加入该请求后，最坏 KV 将增加 384 页，低优先级保留池仍剩 128 页”。若只返回一个神秘分数，值班人员无法判断该降低哪个参数。

可以把预算公式写成：可用动态页 = 设备容量 − 权重 − 临时保留 − 安全余量。单请求承诺页 = ceil((输入 token + 最大新 token) / 页大小) × 每 token 每层 KV 字节，再加页表和对齐。实际采用共享前缀或重算时可降低平均占用，但准入仍需防止最坏情况；只按平均值接纳会在长尾输入同时到来时崩溃。

### 15.7.3 规划与压测的闭环

先用离线长度分布估算页需求，再用合成最坏流量压测。压测要包含：所有请求都长、输入和输出同时长、频繁取消、模型切换、投机开关切换、租户突发和设备温度下降。观察页高水位、p99 单步间隔、拒绝率和恢复时间；如果只看平均 tokens/s，很容易错过偶发 OOM 或某租户饥饿。

规划参数应有版本和回滚。修改页大小、KV 量化、最大批 token 或保留池比例都可能改变 SLA；先在旁路或小流量实例验证，再逐步放量。运行时读取配置要有校验，不能让错误单位（MiB 与 MB、token 与字符）悄悄把上限放大。

## 15.8 CPU toy 模拟器：把调度状态机跑起来

下面的实验只使用 Python 标准库，模拟页池、prefill、decode、连续批处理和简单准入控制。它把每个 token 当作一个离散时间单位，不模拟真实 FLOP，但能观察短请求、长请求和优先级混合时的完成顺序与尾部等待。代码故意保持可读，生产系统应替换为真实设备事件和线程安全的数据结构。

```python
from dataclasses import dataclass, field
from collections import deque
import random

@dataclass
class Req:
    rid: int
    tenant: str
    prompt: int
    output: int
    priority: int = 0
    arrival: int = 0
    phase: str = "queued"
    seen: int = 0
    generated: int = 0
    first_token: int | None = None
    done: int | None = None
    pages: int = 0
    cancelled: bool = False

class ToyEngine:
    def __init__(self, page_tokens=8, total_pages=64,
                 prefill_budget=32, decode_slots=8):
        self.page_tokens = page_tokens
        self.total_pages = total_pages
        self.free_pages = total_pages
        self.prefill_budget = prefill_budget
        self.decode_slots = decode_slots
        self.now = 0
        self.q = deque()
        self.active = []
        self.finished = []

    def admit(self, req):
        worst = (req.prompt + req.output + self.page_tokens - 1) // self.page_tokens
        if worst > self.free_pages:
            return False
        req.phase = "queued"
        req.pages = worst
        self.q.append(req)
        self.free_pages -= worst
        return True

    def step(self):
        # 先为活跃请求各生成一步，确保 decode 不被长 prefill 饿死
        for req in list(self.active)[:self.decode_slots]:
            if req.cancelled:
                req.done = self.now
                req.phase = "cancelled"
                self.active.remove(req)
                self.free_pages += req.pages
                continue
            req.generated += 1
            if req.first_token is None:
                req.first_token = self.now
            if req.generated >= req.output:
                req.done = self.now + 1
                req.phase = "done"
                self.active.remove(req)
                self.finished.append(req)
                self.free_pages += req.pages

        # 剩余预算用于 prefill，按优先级和到达时间排序
        budget = self.prefill_budget
        self.q = deque(sorted(self.q, key=lambda r: (-r.priority, r.arrival, r.rid)))
        while self.q and budget > 0 and len(self.active) < self.decode_slots:
            req = self.q[0]
            need = req.prompt - req.seen
            take = min(need, budget)
            req.seen += take
            budget -= take
            req.phase = "prefill"
            if req.seen == req.prompt:
                req.phase = "decode"
                self.active.append(req)
                self.q.popleft()
        self.now += 1
```

### 15.8.1 实验一：长度混合与连续批处理

构造 20 个请求：输入长度从 8 到 128 token，输出长度从 4 到 64 token，按泊松式到达时间加入。分别运行静态批处理和连续批处理的简化版本，记录首 token、完成时间、总生成 token、页高水位和拒绝数。要注意：toy 的一个时间步不等于毫秒，比较的是相同工作量和相同调度规则下的相对趋势。

```python
random.seed(7)
reqs = [Req(i, "t1" if i % 3 else "t2",
            prompt=random.choice([8, 16, 32, 64, 128]),
            output=random.choice([4, 8, 16, 32, 64]),
            priority=1 if i < 3 else 0,
            arrival=i // 2)
        for i in range(20)]
eng = ToyEngine(page_tokens=8, total_pages=96,
                prefill_budget=32, decode_slots=4)
for r in reqs:
    while eng.now < r.arrival:
        eng.step()
    print("admit", r.rid, eng.admit(r))
while eng.q or eng.active:
    eng.step()
print("finished", len(eng.finished), "time", eng.now,
      "p99 first", sorted(r.first_token for r in eng.finished)[-1])
```

观察点有三个。第一，连续批处理通常较早让短请求完成，因为短请求完成后马上退出，不必等待最长请求；第二，长 prefill 仍可能造成首 token 延迟，如果每轮 prefill 预算没有上限，decode 会被饿死；第三，按最坏输出预留页会降低接纳率，却避免动态增长时 OOM。可以把 `prefill_budget` 改成 8、32、128，绘制首 token 与总完成时间的变化，理解吞吐和交互延迟的冲突。

### 15.8.2 实验二：页大小与内部碎片

为不同页大小运行同一长度分布，计算分配页槽位与实际 token 的差额。页大小 4 通常降低内部碎片，但页表和调度操作更多；页大小 32 减少元数据，却让短请求的尾页浪费明显。真实内核还受内存合并访问影响，因此不能仅凭碎片率选参数。

```python
def fragmentation(lengths, page_tokens):
    slots = sum(((n + page_tokens - 1) // page_tokens) * page_tokens
                 for n in lengths)
    used = sum(lengths)
    return 1 - used / slots

lengths = [3, 7, 9, 15, 17, 31, 33, 65]
for p in [4, 8, 16, 32]:
    print(p, round(fragmentation(lengths, p), 3))
```

实验结果不应被写成“页越小越好”。当页表过大、访存不连续或跨节点迁移频繁时，小页可能增加每 token 开销。应把内部碎片、页表占用、kernel 吞吐、p99 单步延迟和工程复杂度一起评估。

### 15.8.3 实验三：准入拒绝与背压

把总页数从 96 逐步降到 16，保持请求长度不变，比较三种策略：一律排队、一律拒绝、按优先级保留池。记录高优先级请求的首 token、低优先级请求的等待时间、拒绝率和页高水位。若一律排队，系统可能在客户端连接上堆积大量无法服务的请求；若一律拒绝，突发流量下用户体验差但资源可预测；保留池在两者之间提供更好的高优先级 SLA，却需要公平性和配额审计。

不要把 toy 的 `free_pages` 当作真实显存。真实系统还要扣除权重、workspace、碎片和驱动保留；toy 实验只能帮助验证调度逻辑。实验日志应保存随机种子、参数、代码版本和结果摘要，才能复现失败。

## 15.9 失败案例：看似合理的优化为何会反噬

### 15.9.1 案例 A：最大上下文预分配导致低并发

团队把每条请求按 32k 上下文预分配 KV，担心动态扩容带来碎片。上线后短问答的平均延迟尚可，但并发一上升就大量返回“容量不足”。根因是每个请求占据了远超实际使用的页，活跃请求数被最坏长度锁死。修复方案是分页按需分配、以最大新 token 做保守承诺，并把长上下文请求路由到独立池；同时保留足够安全余量，避免把所有节省的空间再次接纳掉。

### 15.9.2 案例 B：连续批处理吞吐上升、p99 恶化

把新请求加入每一步后，tokens/s 增长了 25%，但流式用户看到 token 间隔偶发数秒。分析发现 prefill 没有限制单轮 token，长输入占满设备，活跃 decode 请求连续多轮得不到服务。修复是在每轮先为活跃 decode 保留预算，再限制 prefill token；必要时把超长 prefill 放入分离池。成功标准同时包含吞吐、首 token、p95/p99 单步间隔和取消释放延迟。

### 15.9.3 案例 C：KV 前缀共享造成跨租户推断

为了减少系统提示计算，团队按文本哈希跨租户复用前缀 KV。某租户通过测量相同请求的首 token 时间，推断另一个租户是否使用了特定政策片段。即使没有直接读到文本，缓存命中侧信道仍泄露了存在性。修复是将信任域、模型版本、权限策略纳入缓存键，敏感域关闭共享，并对高风险缓存做时间和容量抖动。监控只输出聚合命中率，不暴露具体前缀。

### 15.9.4 案例 D：投机解码提前流出未验证 token

为了让 UI 更快显示，工程师把草稿模型的 token 立即发送给客户端，等待目标模型稍后纠正。结果是草稿输出了一个不该出现的工具参数和一段被安全策略禁止的内容，虽然目标模型最终拒绝了它。修复是把草稿 token 视为内部候选，在目标模型验证和安全过滤完成后再提交；若需要更低首 token 延迟，可缩短草稿步数、使用更快的目标 kernel，不能把未验证内容当作可见输出。

### 15.9.5 案例 E：取消信号迟到导致页泄漏

移动端用户频繁切换页面，连接断开后服务端没有及时收到取消。请求仍在生成，页池逐渐耗尽；重启实例才恢复。修复包括心跳和空闲流超时、设备事件完成后的代际页标签、取消计数器和泄漏告警。要测试的是“取消发生在 prefill、decode、抢占、工具调用各阶段”时的行为，而不是只测正常完成。

### 15.9.6 案例 F：重试风暴把过载变成雪崩

网关在 `RESOURCE_EXHAUSTED` 时立即重试三次，多个客户端叠加后排队长度翻倍，健康实例也被拖垮。修复是服务端返回稳定的重试类别和带抖动的等待建议，客户端只对幂等请求退避，达到上限就向用户报告可操作错误。压测要注入页耗尽、设备重启、模型加载和网络抖动，验证系统在失败时会减压而不是放大负载。

## 15.10 可观测性与排障顺序

### 15.10.1 最小指标集

按请求、实例、租户和模型版本分层记录：排队时长、prefill 时长、首 token 延迟、平均与 p95/p99 token 间隔、总生成速度、输入输出 token、KV 页高水位、页碎片、抢占与重算次数、准入拒绝类别、取消释放延迟、草稿接受率和每请求成本。指标标签要有限，避免把用户文本或高基数 id 直接放进时间序列系统；详细事件可写入受控审计日志并设置保留期。

体验指标和资源指标要关联。首 token 变慢可能是排队变长、prefill 变重或设备降频；token 间隔变长可能是 KV 读带宽、页表查找、抢占重算或长 prefill 插队。把 `trace_id` 连接到设备事件，才能从一次慢请求定位到具体阶段。

### 15.10.2 排障的先后顺序

第一步先确认是否有资源硬错误：OOM、页泄漏、设备重置、权重版本不一致。第二步看准入与队列：拒绝是否集中在某租户，等待是否与输入长度相关。第三步分解 prefill 与 decode：只慢首 token 还是每个 token 都慢。第四步检查页表、KV 量化、抢占和投机的开关，做一次可回滚的对照实验。第五步检查模型和采样质量，确认优化没有改变分布、结构化输出或安全过滤。

任何开关变更都要有时间戳、操作者、旧值、新值和回滚命令。不要在高峰同时修改页大小、批预算和投机长度，否则无法归因。先关闭可选优化恢复基线，再逐一打开。若涉及安全策略或权限逻辑，优先回退到保守路径，不要为了吞吐延长实验窗口。

## 15.10.1.1 事件时间与资源时间的对齐

排查推理延迟时，墙上时钟、设备事件时钟和客户端观测时钟经常不同步。客户端收到首 token 的时间包含网络缓冲和代理排队；服务端的请求时间包含网关、准入和模型队列；设备事件只覆盖 kernel 和通信。若没有统一的单调时钟和 trace 关联，团队可能错误地把网络抖动归因于 decode，或把设备降频归因于客户端。建议在请求进入网关、通过准入、开始 prefill、完成 prefill、提交每轮 decode、发出 token、释放页时分别记录单调时间，并给设备事件附上逻辑步号。日志中同时保留时间单位和采样来源，避免把微秒和毫秒混算。

对于流式输出，客户端可能把多个 token 合并成一个网络包，也可能因为代理缓冲延迟显示。服务端应记录“生成时间”和“发送时间”两个点，网关再记录“转发时间”。当用户报告卡顿时，先比较三段时间的差值：若生成本身快而发送慢，优化模型没有用；若发送及时而客户端显示慢，应检查代理和应用层；若生成间隔抖动与页高水位同步，则回到 KV 和调度。这个分解也帮助设置合理的 SLO，避免把不可控的公共网络延迟硬塞进模型预算。

## 15.10.1.2 质量、性能与成本的联合实验

推理优化常常把一个指标换成另一个指标。降低 KV 精度可能减少带宽，却让长上下文的事实一致性下降；增大连续批次可能提高吞吐，却让交互请求的 p99 变差；投机解码可能减少目标模型步数，却让草稿模型占用更多显存。实验设计应把质量、性能、成本放在同一张对照表中，并明确不可接受的底线。至少要有未优化基线、单项优化、组合优化和关闭开关后的回归结果四组。

质量评估不能只看一个离线分数。按输入长度、语言、任务类型、输出长度、结构化约束和安全类别分层，检查答案正确性、格式有效率、引用支持率、拒答准确率和越权率。性能侧记录首 token、每 token 间隔、p95/p99、完成时间、拒绝率、页峰值和设备能耗。成本侧估算权重常驻、草稿模型、重算、跨节点传输和日志存储的增量。每组实验保存配置哈希和随机种子，允许在同一流量重放；若优化只在理想短输入上有效，就不应宣称是通用加速。

## 15.10.1.3 运行时状态机的可验证不变量

复杂调度器容易出现“状态看起来合理、组合起来错误”的 bug。可以为请求和页池写出不变量，并在 toy 模拟器和生产影子流量中检查。每个请求最多处于一个阶段；请求标记完成、取消或拒绝后不再生成可见 token；一个物理页的引用计数不能为负；页的模型版本、精度和信任域必须与持有它的请求一致；活跃请求承诺的最坏页数加上保留池不超过总容量；设备事件完成前，旧代请求不能把页归还给新代请求。

不变量失败时要保留最小重放信息：请求阶段序列、页分配和释放事件、调度轮次、配置版本和错误类别。不要为了重现 bug 保存所有敏感 prompt；可以保存脱敏后的 token 数、摘要和伪造的长度模式。对于涉及权限的异常，再由受控审计流程取最小必要证据。把不变量检查当作开发期和压测期的断言，上线后可采样执行并在失败时立即停止有风险的优化路径。

## 15.11 六个理解检查（附答案）

### 检查 1：为什么 prefill 通常更偏算力，而 decode 更容易受带宽影响？

答案：prefill 同时处理大量输入位置，矩阵乘和注意力有更高的并行度，设备能保持较高算力利用率；decode 每次只新增一个位置，却需要读取随序列长度增长的历史 KV，并承担 kernel 启动和同步开销，因此内存带宽和延迟占比上升。具体模型、批大小和内核可能改变结论，必须用目标硬件测量。

### 检查 2：若 KV 每 token 每层的字节数不变，把最大上下文从 8k 加到 16k 会怎样？

答案：单序列最坏 KV 约翻倍，可容纳的并发序列在同一页预算下大致下降；实际还受权重、workspace、分页碎片和调度策略影响。若采用共享前缀、重算或量化，平均占用可能低于线性翻倍，但准入不能忽略长尾。

### 检查 3：连续批处理为什么不能只追求每秒 token？

答案：新 prefill 或长输出可能占满设备，使已有流式请求的 token 间隔和 p99 变差；吞吐上升不代表交互体验和公平性变好。应同时监控首 token、单步间隔、尾延迟、拒绝率、取消释放和租户配额。

### 检查 4：paged memory 解决了什么，没解决什么？

答案：它把连续增长的 KV 拆成固定页，降低外部碎片、扩容复制和短请求的过度预留；但它不能消除总容量不足、内部尾页浪费、页表开销、跨节点带宽和错误的准入策略。页大小仍需在碎片与访存效率之间测量。

### 检查 5：投机解码接受率低时，为什么可能比普通解码更慢？

答案：草稿模型额外消耗算力、权重显存、KV 页和调度时间；若目标模型频繁拒绝候选，验证收益不足以抵消这些成本。应按请求类型和流量分层测量接受率、每 token 延迟、尾延迟和质量一致性，并允许动态关闭。

### 检查 6：为什么准入时不能只看当前空闲页？

答案：当前空闲页没有包含已接纳请求未来增长的承诺。如果已有请求都达到最大输出，动态 KV 会继续增加；新请求若把剩余页全部占用，会让老请求在下一步无法前进并触发 OOM。准入需预留未来 decode、workspace、碎片和故障余量，并有租户和优先级配额。

## 15.12 练习

1. **容量推导**：给定 48 层、8 个 KV 头、每头 128 维、float16，估算 1 token 和 16k token 的 KV 字节数，再加入 15% 页表与对齐开销。比较采用 int8 KV 后的理论节省，并列出需要验证的质量指标。
2. **调度策略**：在 toy 模拟器中实现带老化的优先级队列，要求低优先级请求最长等待不超过高优先级请求的某个倍数。报告不同 prefill 预算下的首 token p95 和吞吐。
3. **分页实验**：加入共享只读前缀和动态页分配，测量页命中、内部碎片、释放延迟以及取消发生在不同阶段时的页回收正确性。
4. **投机一致性**：实现一个小词表的草稿/目标模型，比较贪心和随机采样下的接受率。固定随机种子，检查投机路径与逐 token 路径的输出分布是否接近，并记录拒绝位置。
5. **准入控制**：设计错误类别和 `retry_after` 规则，模拟客户端指数退避与立即重试，比较两者在资源耗尽时的队列长度和恢复时间。
6. **安全审计**：列出 KV 前缀共享、日志 trace、抢占快照和投机候选可能泄露的数据，分别提出最小化、隔离、保留期和审计措施。
7. **容量演练**：构造输入长度长尾、输出长尾和租户突发的三种流量，验证实例在 OOM 前是否拒绝新请求、是否保留高优先级服务、是否能在取消后恢复页池。

练习报告必须包含随机种子、硬件/软件版本、配置、原始日志摘要和失败样本。不要只提交平均值；至少给出 p50、p95、p99、最大值和拒绝类别。若使用真实用户数据，先脱敏并确认保留和访问策略，优先使用合成或已获授权的离线集合。

## 15.14 安全边界与上线清单

推理执行服务承载用户输入、系统提示、检索内容和可能的工具调用，性能优化不能越过这些边界：

- **权限边界**：模型、KV 页、前缀缓存、日志和指标都必须按租户、区域、数据分类和模型权限隔离。相同文本不意味着可以跨域共享。
- **机密边界**：不在公共日志写入完整 prompt、输出、token、页内容、访问令牌或工具参数。调试采样要脱敏、限时、审批和可追踪。
- **完整性边界**：页版本、模型版本、tokenizer、采样策略和安全策略必须一致；抢占恢复不能混入旧页或重复外部副作用。
- **可用性边界**：任何优化都要有关闭开关和保守回退；页耗尽、设备重置和投机失败应产生可操作错误，而不是静默截断或无限重试。
- **内容边界**：草稿 token 在目标模型与安全策略验证前不可见；结构化输出、工具参数和高风险建议要经过独立校验。
- **公平边界**：配额、优先级和老化规则应可解释、可审计，不能用隐藏的租户特征决定资源；紧急通道也不能绕过合法性和安全检查。

上线前逐项确认：模型和 tokenizer 版本固定；权重、KV、workspace 和安全余量有预算；prefill/decode 指标分离；页池有高水位和泄漏告警；连续批处理有 decode 保留份额；准入和重试有背压；取消和超时经过每个阶段测试；投机默认关闭或有明确质量门槛；长上下文和租户突发有隔离池；日志最小化且保留期明确；所有动态开关可回滚；压测覆盖最坏长度、设备故障、网络抖动、客户端断线和恶意长输入。

## 15.15 小结：把每个 token 当作一次资源决策

prefill 负责把上下文转成可用状态，decode 负责在每一步追加一个可验证的 token；KV cache 省下重复计算，却让长度、并发和权限成为显式内存问题。paged memory 用固定页降低碎片，连续批处理让批次随请求生命周期变化，准入控制和背压保证系统在压力下仍能前进。speculative decoding 可以减少目标模型迭代，但只有在接受率、资源成本、采样一致性和安全验证都满足门槛时才值得启用。memory planning 则把权重、KV、workspace、页表和安全余量放进同一账本。

真正可靠的推理系统不会只报一个吞吐数字。它能回答每个请求何时进入、为何等待、占用了哪些资源、何时产生首 token、为何被抢占或拒绝、怎样释放页，以及在优化关闭后是否仍能安全服务。把这些答案写进状态机、指标、实验和回滚路径，才是从“模型能跑”走向“服务可运营”的关键。
