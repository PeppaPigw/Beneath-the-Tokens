# 第22章　AI Infra 安全、隐私与供应链：从身份到事故证据

> AI 基础设施的安全边界不是模型 API 的边界。一个请求携带的提示词可能进入网关日志、批处理队列、KV cache、检索索引、GPU 显存、遥测系统和训练回放；一个看似普通的模型更新可能同时替换权重、tokenizer、CUDA 扩展、容器镜像和数据处理脚本。攻击者不必“攻破模型”才能造成影响：盗取一个过宽的工作负载令牌、将恶意依赖塞进镜像、在共享 GPU 上观察侧信道、把租户 A 的文档写入租户 B 的向量索引，都足以造成数据泄露、财务损失或错误决策。

本章采用与前章一致的证据标记。**事实**来自标准、官方文档、论文或开源项目明确的语义；**机制**是根据调用和数据流还原的因果链；**测量**是实验脚本在声明环境中的观测；**推断**由测量和模型得到；**设计判断**是在假设和约束下的工程选择。示例中的哈希、签名、令牌和隔离都是教学用具，不能替代 KMS、HSM、硬件根信任、集群准入或合规评估。每个控制都要写出保护的资产、信任假设、失败时的默认行为，以及它明确不能保证什么。

## 22.1 先定义安全问题：资产、主体、边界和失败语义

### 22.1.1 资产清单比攻击清单更重要

安全评审从资产开始，而不是从工具开始。AI infra 至少有八类资产：

1. **身份与授权材料**：用户会话、服务账户、OIDC 令牌、SPIFFE SVID、云角色、KMS 解密权限和集群管理员凭据。
2. **模型工件**：原始权重、量化权重、LoRA/适配器、tokenizer、配置、编译后的 CUDA kernel、模型评测结果和发布指针。
3. **数据工件**：原始数据、去标识数据、训练样本、检索文档、向量、标签、删除清单和数据处理脚本。
4. **运行时状态**：GPU 显存、KV cache、批处理队列、临时文件、检查点、随机状态、缓存和故障转储。
5. **供应链证据**：提交哈希、依赖锁文件、容器层、SBOM、构建日志、来源证明、签名、许可证和漏洞扫描结果。
6. **控制平面**：Kubernetes API、调度器、准入策略、镜像仓库、模型注册表、特性开关、DNS、证书和密钥轮换作业。
7. **观测与审计**：访问日志、工具调用、策略决策、脱敏后的提示词摘要、指标、trace、告警和取证副本。
8. **业务承诺**：租户的数据驻留、删除期限、模型版本、质量阈值、成本上限、人工复核和监管报告。

资产清单不能只写“机密性、完整性、可用性”三个词，还应写恢复和归属。模型权重可公开下载，但内部微调适配器是商业秘密；日志通常不含原文，但时间、租户 ID 和输出长度可以拼出用户行为；一个可恢复的旧检查点可能满足可用性，却违反删除请求。**设计判断**：为每个资产记录所有者、分类、保存期限、允许的处理区域、备份位置和销毁证据。

### 22.1.2 主体和信任边界

把主体分成五类有助于避免“服务到服务都是可信的”这一误区：

- **人类主体**：终端用户、标注员、开发者、值班工程师、管理员和外部审计员。人类身份应有强认证、职责分离和可追溯操作。
- **工作负载主体**：网关、检索服务、训练 worker、评测 job、模型 server、清理任务和 sidecar。工作负载身份应与节点身份、镜像身份和部署环境分离。
- **基础设施主体**：Kubernetes API、节点代理、GPU 设备插件、镜像仓库、对象存储、KMS、CI 构建器和日志平台。这些系统能代表其他主体，必须单独审计。
- **数据主体**：租户、员工、客户、患者、学生等信息的所有者。数据主体不一定登录系统，却承担泄露和错误决策后果。
- **对手**：外部匿名请求者、被盗账号、恶意租户、供应链维护者、被入侵的依赖、恶意提示词作者和有节点权限的内部人员。

信任边界应画在数据流上。例如，网关到模型 server 的 TLS 只保护传输，不证明模型 server 得到的是哪个租户；向量库同一索引里的 namespace 过滤只是一条应用条件，除非服务端真正把租户约束绑定到身份并在存储层执行。节点上的两个 pod 共享内核和部分设备状态，因此“不同 namespace”不自动等于“互不观察”。

### 22.1.3 威胁建模矩阵

可以用 STRIDE 风格的六列矩阵快速审查一条 AI 请求路径：主体、动作、资源、信任边界、攻击手段、证据与控制。比如“租户 A 的 agent 调用导出工具”这一行：主体是 `agent-a`，动作是读取对象并上传，资源是 A 的文档，边界是 agent 到工具 API，攻击手段包括提示注入、令牌混用和路径穿越，证据包括带请求 ID 的工具审计和对象访问日志，控制包括工具级 capability、目的地 allowlist、大小上限和人工确认。

矩阵要包括非恶意事故。配置错误、镜像回滚、训练数据重复、GPU 驱动升级和密钥过期会产生同样的影响。安全控制若只针对攻击者，往往无法解释“合法管理员错误地把生产 bucket 挂到测试 pod”这种真实事件。**设计判断**：把误操作纳入威胁模型，给高影响操作增加双人审批、短期授权、模拟执行和自动回滚。

### 22.1.4 安全目标必须写成可验证的句子

模糊目标如“保护隐私”无法驱动测试。把它改写为带对象、条件和证据的句子：

- 在生产推理日志中，不保存原始提示词、原始检索片段和完整输出；抽样调试须在隔离存储中以短期访问令牌读取，访问记录与工单关联。
- 一个训练 worker 只能读取已分配租户、版本和时间窗口的数据对象；尝试读取其他前缀在授权层被拒绝，拒绝事件可在五分钟内检索。
- 只有经过签名验证、来源证明满足最小构建级别、SBOM 无阻断漏洞的模型包才能进入发布 namespace；验证失败默认拒绝而不是“先运行再告警”。
- 删除请求完成后，在线索引、备份、缓存、检查点和日志中的数据在声明期限内不可被业务读取，并有每层清理或例外理由的证据。

这些句子同时定义了“不能保证”。例如，脱敏规则不能证明模型没有记忆训练语料；容器签名不能证明运行时没有被节点管理员替换；网络策略不能证明 pod 内的应用不会把数据编码到允许的出站域名。

## 22.2 身份、权限和可撤销的工作负载认证

### 22.2.1 人、服务账户和工作负载不要共用一个秘密

最常见的权限事故是把三种身份混成一个长寿命 API key：开发者把 key 写入环境变量，CI 复制到镜像，推理 pod 继承后可以读生产数据。正确做法是分层：人通过企业 IdP 获取短期会话；CI 通过 OIDC 联邦取得一次性构建权限；运行中的工作负载通过节点证明或工作负载身份服务获取短期凭据。每层凭据的受众、作用域、有效期和撤销路径不同。

人类访问生产控制面应采用强认证、设备和网络条件、最小角色、just-in-time 提权与会话录制。管理员执行 `kubectl exec`、读取 Secret、修改准入策略和发布模型要分别授权，不能以“cluster-admin 方便排障”为默认。紧急破窗账号可以存在，但应放在密封流程中，使用后自动失效并触发复盘。

工作负载身份应绑定部署属性，而不是 Pod IP 或镜像标签。SPIFFE 定义了可在动态环境中标识工作负载的 SVID 和 Workload API；SPIFFE 文档强调短期 X.509 或 JWT 身份、信任域和基于选择器的注册。X.509-SVID 适合 mTLS，JWT-SVID 适合跨 L7 边界但要防重放。无论采用哪种方案，发行器必须验证调用进程与节点，不能让任何能访问本地 socket 的进程自由领取高权限身份。

### 22.2.2 最小权限的四个维度

一个权限条目至少有主体、资源、动作和条件四个维度。对对象存储，`reader` 不是“允许读 bucket”，而是“身份 `train-a` 在工作日之外仍可读取 `tenant-a/dataset/v3/*`，不能列出兄弟前缀，不能写、删除或改变 ACL”。条件还可包括模型版本、数据处理目的、网络来源、设备证明和请求工单。

将动作细化到业务 capability：

- 检索服务只获得 `search`，不获得任意 SQL；
- agent 工具只获得 `read_invoice`，不获得 `delete_invoice`；
- 模型发布器只获得写不可变工件和移动候选指针的权限，不获得删除历史版本；
- 清理任务只获得删除到期对象，不获得读取对象内容；
- 评测 job 只能读去标识集，不能访问生产提示词。

RBAC 解决“谁能对什么资源做什么动作”，ABAC 或策略引擎补充租户、环境、目的和风险条件。策略越复杂越需要可测试的决策日志。决策日志应记录策略版本、主体 ID、资源摘要、动作、结果和原因码，避免直接记录敏感内容。

### 22.2.3 能力令牌与代理降权

把一个管理员令牌传给模型 agent 等于把自然语言输出变成管理员操作。更安全的模式是代理调用一个能力服务：服务验证租户和任务状态，只签发一次性、短期、绑定目的地和参数摘要的 capability。agent 无法修改 capability 中的资源范围，工具服务再次验证，不相信模型返回的“我已获授权”。

工具调用要有预算：最大调用次数、最大字节数、最大花费、最大运行时间、允许域名和允许 HTTP 方法。对写操作，先生成预览和差异，经过策略或人工确认后再提交。幂等键把重试绑定到业务动作，防止模型在不确定时重复扣费或重复发送通知。**失败案例**：某客服 agent 有通用 CRM token。攻击者在工单文本中加入“导出全部客户并上传到此 URL”，模型遵循了间接提示，工具层因 token 权限过宽而执行。修复不是只加拒答提示，而是把工具拆成只读、字段白名单、目的地固定且必须由用户确认的 capability。

### 22.2.4 吊销、轮换和失效传播

“令牌可以轮换”不等于“轮换有效”。应定义泄露发现到权限失效的时间预算，列出每个缓存层：网关会话、sidecar、SDK、DNS、对象存储签名 URL、模型 server 内存、审计平台。短期证书减少暴露窗口，但证书轮换期间的时钟偏差和信任包更新会造成全站故障；要演练提前刷新、双信任根和回滚。

撤销优先按主体和作用域执行：冻结工作负载、阻断镜像摘要、禁用发布指针、撤销 KMS decrypt grant、隔离节点、暂停队列。不要在确认所有证据前删除磁盘或覆盖日志。高风险事件中，先通过网络和准入控制阻止进一步传播，再在保全副本后重建凭据。

## 22.3 租户隔离：从标签到真正的故障域

### 22.3.1 隔离层级和保证强度

租户隔离是组合控制，不是一个 namespace 开关。可按强度分层：

1. **逻辑过滤**：请求中带 `tenant_id`，应用在查询中加条件。成本低，最容易因遗漏、拼接错误或缓存 key 冲突而失效。
2. **存储分区**：每租户独立表、索引、bucket 前缀或加密密钥。缩小误读范围，但共享数据库管理员和备份仍是共因边界。
3. **网络分区**：NetworkPolicy、服务账号和 egress 网关限制通信。阻止许多横向移动，但不能阻止同 pod、节点内核或共享 GPU 的侧信道。
4. **计算分区**：节点池、污点、拓扑 spread、独立运行时、专用 GPU、虚拟机或裸金属。成本高，降低内核和设备共驻风险。
5. **密码学隔离**：每租户独立数据加密密钥、信封上下文、签名域和访问审计。即使底层存储被复制，没有密钥授权也无法解密；密钥管理服务本身仍是高价值边界。
6. **物理或机密计算隔离**：独立主机、TEE、受证明的 VM。可减少云运维者或宿主机窥视，但要核对证明链、驱动支持和侧信道假设。

隔离设计必须针对攻击者能力。若威胁模型包含恶意租户可提交任意容器，那么“同一节点不同 namespace”不应被当作机密隔离；若只防止应用层查询漏租户，则存储分区和自动化策略可能已足够。记录每一层隔离的强度、成本、性能影响和失效方式。

### 22.3.2 Kubernetes 控制与盲点

Kubernetes 官方安全文档把 Pod Security Standards、NetworkPolicy、准入控制、Secret 加密和 RBAC 列为关键机制。Restricted 级别通常要求非 root、禁止特权容器、收紧 capabilities、只读根文件系统和受限卷类型；但 Pod Security Admission 只验证对象字段，不能检测应用在运行时是否把数据发往允许的域名。NetworkPolicy 是允许/拒绝通信的声明策略，具体效果取决于 CNI 实现，且通常是 L3/L4，不理解 HTTP 语义。

AI workload 常见危险字段包括 `hostNetwork`、`hostPID`、`hostPath`、`privileged`、未限制的 `CAP_SYS_ADMIN`、设备挂载、Docker socket 和可写的共享 PVC。GPU operator 或设备插件需要访问 `/dev`、驱动和节点目录，不能简单套用普通 Web pod 策略；应把 GPU 管理组件放在单独 namespace、锁定镜像摘要和准入例外，并限制它们能代表的身份。

**失败案例**：团队为模型 server 开启 `privileged: true` 以修复一个 CUDA 初始化错误，后来同节点的恶意 pod 通过共享内核和宿主路径读取了 kubelet 凭据。修复是先定位所需设备和 capability，使用专用 RuntimeClass、seccomp/AppArmor、只读宿主挂载和专用节点；“整 pod 特权”是未审计的扩大权限。

### 22.3.3 GPU 隔离、显存清理和侧信道

GPU 隔离有设备分配、时间切片、MIG/虚拟化、进程上下文和物理卡独占等多种语义。设备可见不等于显存可读；同一物理卡上的上下文切换、缓存、编解码器和驱动接口可能有侧信道。模型 server 在请求结束后应显式释放或覆盖包含敏感 token 的缓冲区，避免把 KV cache、错误转储和 profiler trace 写入共享位置。但覆盖本身不保证物理显存立即清零，也不能阻止恶意驱动或宿主机管理员读取。

高敏感租户应使用专用 GPU 或机密计算能力，并禁用不需要的调试接口、持久化 profiler 和远程桌面。多租户时间切片要有可测量的性能和泄露风险评估：比较同卡共驻与独占时的尾延迟、显存峰值、上下文长度和错误率，记录驱动、固件、CUDA、设备插件版本。**设计判断**：不能用“GPU utilization 低”证明资源隔离；应检查设备句柄、cgroup、调度记录、显存归还和租户标识在 trace 中是否一致。

### 22.3.4 配额、舱壁和成本安全

隔离还保护可用性和账单。租户应有并发、令牌、最大上下文、GPU 秒数、存储、检索次数和工具花费配额。令牌桶或漏桶限流要在入口和每个昂贵阶段分别实施；只在网关限流会让恶意任务填满检索、GPU 或日志管道。舱壁把租户的队列、线程池、GPU stream、缓存和错误预算分开，防止一个租户的长请求挤掉另一个租户。

拒绝服务可能表现为“denial of wallet”：攻击者构造高成本上下文、反复触发工具或诱导模型生成超长输出。成本指标应按主体、租户、模型、工具、地区和请求来源聚合，但不要把原文放入高基数标签。异常成本触发降级、人工确认或暂时冻结，不应静默从其他租户的配额借资源。

## 22.4 密钥、加密和秘密生命周期

### 22.4.1 三种加密目标

传输加密保护网络中的窃听和篡改；静态加密保护磁盘、对象存储、备份和快照丢失；使用中保护需要在内存或 GPU 中处理的数据。TLS 证书和对象存储 SSE 不能解决“日志平台合法读取了原始提示词”或“训练进程把 secret 打印到 stdout”。因此密钥策略必须与数据流和权限策略一起设计。

### 22.4.2 信封加密与上下文绑定

对大模型权重和数据，常用信封加密：数据由一次性数据密钥（DEK）加密，DEK 再由密钥加密密钥（KEK）在 KMS/HSM 中包裹。对象包含密文、nonce、算法和加密上下文（例如租户、用途、版本和对象 ID）。读取时，服务只有在主体、上下文和策略都满足时才能解包 DEK。

上下文绑定很关键。若只要能调用 KMS `Decrypt` 就能解密任何对象，租户隔离会退化为应用自律。使用 AEAD（如 AES-GCM 或 ChaCha20-Poly1305）时，关联数据应包含租户、工件摘要、环境和用途；任何字段被替换都会导致认证失败。不要把密钥、nonce 或 tag 拼接格式自创却没有版本号和测试。

### 22.4.3 Kubernetes Secret 不是“加密后的保险箱”

Kubernetes Secret 对象默认在 API 中以 base64 表示；是否在 etcd 静态加密、谁能读取、是否进入审计、备份和诊断包，取决于集群配置和访问策略。把云访问密钥放进 Secret 后挂载给每个 pod，会扩大泄露面。优先使用工作负载身份和外部 secrets manager，短期注入只读文件，并限制进程、namespace、路径和轮换通知。禁止把 Secret 放进镜像层、Git、Helm values、训练日志、异常堆栈和 notebook 输出。

### 22.4.4 轮换、备份、吊销和灾难恢复

密钥轮换有四个状态：当前写入、新旧并读、旧密钥停止写入、旧密钥撤销/销毁。模型和数据迁移要支持一段时间的双读，否则轮换会变成一次性停机。备份必须同时保护密文和密钥版本映射；只备份 bucket 没有 KMS 恢复路径等于不可用。对删除和合规擦除，要记录哪些副本使用了哪个密钥版本，销毁密钥通常不能替代对业务数据的删除证明。

密钥泄露响应顺序：识别受影响主体和范围；冻结发行和解密；保全审计与证明；切换到干净身份和密钥；扫描日志、镜像、构建缓存和对象访问；验证旧令牌确实失效；再恢复服务。不要先删除日志或重启所有节点，造成证据丢失。

## 22.5 模型、代码、数据和基础镜像供应链

### 22.5.1 AI 供应链的扩展攻击面

传统软件供应链关注源代码、依赖、构建和发布。AI 供应链还包含数据采集器、清洗规则、标注工具、数据切分随机种子、训练配置、基础镜像、CUDA/cuDNN、编译扩展、模型权重、tokenizer、评测脚本、检索索引和发布路由。攻击者可以：

- 抢占或仿冒模型仓库中的同名包；
- 在 Python 依赖或 CUDA 扩展中执行任意代码；
- 利用 pickle 等不安全序列化在加载模型时执行代码；
- 投毒训练样本或标签，让模型在触发器出现时产生后门；
- 交换 tokenizer，使输入边界和安全过滤错位；
- 修改量化脚本、合并 LoRA 或配置温度，造成隐蔽行为漂移；
- 伪造评测结果或删除失败样本；
- 在构建缓存、镜像层或模型转换器中注入恶意文件。

供应链控制必须对“内容”和“过程”都做证明。仅对最终权重签名，不能说明它由哪个数据集、代码提交和构建器产生；只有 SBOM，也不能证明没有人篡改构建过程。

### 22.5.2 SBOM：知道包里有什么

SBOM 是机器可读的组件清单，至少记录组件名称、版本、包管理器、许可证、依赖关系、文件哈希、来源和生成工具。容器 SBOM 应覆盖基础镜像、系统包、Python/Node/Rust 依赖、CUDA 库和自编译插件；模型 SBOM 可扩展记录权重分片、tokenizer、配置、转换工具和数据摘要。SBOM 不等于漏洞扫描结果，也不等于安全；它让事件响应能够回答“哪些运行中的模型使用了受影响的库”。

版本必须尽量固定到 digest 或 commit。`latest`、浮动 semver、未锁定的 Git URL、构建时在线下载和本地工作站打包都会削弱可重现性。若必须下载动态数据或模型，保存 URL、响应头、内容摘要、许可和下载时间，并把工件复制到受控仓库。对外部模型，要记录许可、作者、训练数据声明（若有）、已知限制和允许用途，不因“开放权重”而忽略合规。

### 22.5.3 SLSA、来源证明和签名

SLSA 1.0 将构建轨道分为递进级别：L1 有来源证明，L2 由托管平台生成并签名，L3 要求强化构建平台，避免构建间相互影响且不让用户步骤接触签名秘密。当前规范已迭代到更新版本，阅读时必须锁定版本；本章只借用“来源证明和构建抗篡改”这一概念，不把级别名称当作通用认证。

来源证明至少回答：输入提交是什么，构建器是谁，构建命令和参数是什么，依赖和环境是什么，输出摘要是什么，谁签发了证明。验证方应把期望写成策略，例如：构建器必须是受信 CI；源提交必须来自受保护分支；构建步骤不得联网下载未锁定依赖；输出摘要必须与模型注册表中的候选版本一致。签名验证通过只证明签名与信任根匹配，不能证明内容安全或评测质量。

Sigstore/cosign、in-toto、TUF 等开源项目提供签名、透明日志、声明和更新保护的组合模式；应遵照目标项目版本和信任模型。密钥无论由硬件、OIDC 短期证书或密钥管理服务保护，都要有信任根轮换、构建隔离和撤销演练。**失败案例**：镜像签名密钥放在 CI 的普通环境变量里，攻击者通过依赖脚本读取并签发恶意镜像。修复需让签名发生在隔离服务中，构建步骤只能请求“为这个摘要签名”，不能导出私钥。

### 22.5.4 数据血缘和投毒防护

数据集 manifest 应有不可变版本、对象摘要、来源、许可、采集目的、处理脚本 commit、去重规则、标注者版本、删除映射和质量指标。训练前进行重复样本、异常标签、触发器、域外内容和极端分布检查；对高影响领域保留人工抽样和可追溯的拒收原因。投毒检测不能只靠一个分类器，因为攻击者可以模仿正常分布；把数据审查、模型行为测试和上线后的漂移监控组合起来。

删除请求是供应链问题。若样本进入多个 shard、缓存、特征库、检查点和蒸馏模型，必须有数据 ID 到工件的反向索引，或明确“无法证明逐样本删除”的限制。加密分区和密钥销毁可作为补充，但不能在法律或业务要求需要实际删除时偷换概念。

## 22.6 推理隐私：提示词、检索、缓存与模型记忆

### 22.6.1 数据最小化和目的绑定

推理服务只应接收完成任务所需的字段。先在边缘做格式校验、字段分级和令牌化，再把必要内容发送到模型。用户 ID、工单号和手机号等标识可用稳定的内部别名，减少下游日志暴露；但别名映射表仍是敏感资产，必须单独授权。不要为“以后可能调试”而永久保留全量 prompt 和 output。

目的绑定意味着同一文本不能无声地从客服回答流入训练集、评测集和供应商分析。若用户同意范围不同，使用标志和数据标签控制传播；服务端记录数据使用目的，不依赖模型自己“记住不要训练”。第三方模型 API、外包标注和遥测 SDK 都是数据接收方，需核对保留、地域、训练使用和删除接口。

### 22.6.2 日志、trace 和错误信息的泄露

敏感文本常从主日志泄露到别处：HTTP 访问日志记录 query string，trace attribute 记录 prompt，异常堆栈打印 token，重试队列序列化整个请求，GPU profiler 保存 kernel 参数，调试 dump 把 KV cache 写磁盘。建立日志分层：生产默认只记录请求 ID、租户、策略版本、长度桶、模型摘要和结果类别；受控调试记录经过脱敏和截断的样本，短期保留并强制工单关联。

脱敏要避免“只替换数字”。姓名、地址、代码片段、自由文本和罕见实体仍可能识别个人。对高敏感域，使用结构化字段白名单和不可逆摘要，宁可少记也不把未知文本放入指标。统计输出还要防止小群体重识别；高基数标签应聚合或采样。

### 22.6.3 RAG、缓存和跨租户污染

检索增强生成（RAG）将隐私边界拆成文档存储、embedding 服务、向量索引、元数据过滤、reranker、prompt 拼装和缓存。必须在检索服务端执行租户和文档 ACL，而不是只在 prompt 中告诉模型“不要看别人的文档”。向量本身可能泄露语义，邻近搜索结果和相似度分数也会透露敏感信息；删除文档要同步索引、缓存和备份。

缓存键应包含租户、主体、模型版本、策略版本、语言和数据新鲜度；否则公共缓存会把 A 的回答返回给 B。对于流式输出，取消请求要立即切断下游读取和清理缓冲；“客户端关闭连接”不是隐私删除。工具结果和 agent memory 也应有租户和目的边界，不能把系统提示或内部文档写入跨用户长期记忆。

### 22.6.4 差分隐私、联合学习和机密计算的边界

差分隐私（DP）用隐私预算量化单个记录加入或删除对输出分布的影响。NIST SP 800-226 强调评估 DP 保证时要看隐私预算、相邻数据定义、机制、实现和常见陷阱；“加了噪声”不是自动得到 DP。训练中使用 DP-SGD 还会影响效用、偏差、收敛和成本，必须记录采样率、裁剪范数、噪声乘子和预算会计器版本。 经典的 DP-SGD 论文 [Abadi 等，2016](https://arxiv.org/abs/1607.00133) 给出了深度学习中的裁剪与噪声机制；[Shokri 等，2017](https://arxiv.org/abs/1610.05820) 的成员推断研究提醒我们，模型接口本身可能泄露训练成员关系。论文是机制和威胁模型的起点，不是对本系统配置的安全证明。

联合学习减少原始数据集中，但梯度和更新仍可能泄露；安全聚合和客户端认证不能消除投毒、成员推断或服务器窥视。TEE/机密 VM 可以降低宿主窥视风险，需要验证远程证明、固件、驱动、密钥释放策略和侧信道模型。它们不替代应用层授权、日志最小化、数据删除和模型输出审查。模型反演、成员推断、提示词窃取和训练数据记忆应通过红队测试和抽样评估持续测量，而不是只在发布时做一次。

## 22.7 GPU 与 Kubernetes 的安全基线

### 22.7.1 节点、驱动和设备插件

GPU 节点同时承载内核、驱动、设备插件、容器运行时和模型进程，版本耦合比 CPU 节点更强。锁定节点镜像、内核、GPU 固件、驱动、CUDA、NVIDIA container toolkit、设备插件和模型 server 的兼容矩阵；维护可回滚的黄金镜像。禁止在生产节点临时安装驱动或用 root notebook 调试。设备插件应只暴露需要的 GPU 资源，记录分配、释放、错误复位和设备 UUID。

将训练和推理节点分池，通过 taint/toleration、nodeSelector 和拓扑约束防止任意工作负载落到带敏感数据的节点。控制平面和日志节点不应混跑 GPU 任务。节点启动时用远程证明或配置签名确认引导链和镜像摘要；若证明失败，节点进入隔离池，不接受敏感租户。

### 22.7.2 Pod 和容器运行时

默认使用非 root、只读根文件系统、删除不需要的 Linux capability、seccomp、AppArmor/SELinux、禁止特权和 host namespace。设置 CPU、内存、临时磁盘、进程数和 GPU 配额；对长时间训练使用显式 checkpoint 目录和最小卷权限。镜像使用不可变 digest，入口点不执行下载脚本，启动时校验模型和配置摘要。

AI 框架经常需要共享内存、IPC 或高速网络，不能因为性能需求就跳过所有隔离。为每个例外写出：所需字段、替代方案、允许的 namespace、生命周期、监控和撤销条件。`hostPath`、Docker socket、可写 `/sys`、可访问云 metadata 服务通常是高风险，应以网络和准入策略阻断。

### 22.7.3 准入、策略和运行时检测

准入策略在对象进入集群前检查：镜像 digest 和签名、来源证明、SBOM 阻断规则、Pod Security、服务账户、资源配额、租户标签、网络策略、数据分类和 GPU 节点池。策略代码要有单元测试、审计模式和版本；切换为强制前先观察拒绝样本，避免管理员临时关掉策略。

运行时检测关注异常进程、出站域名、设备访问、Secret 读取、shell 执行、模型工件变更和显存错误。eBPF、审计日志和云流量日志可互补，但不会看到加密 payload 里的业务语义。检测规则应按主体和基线建模，避免把模型加载产生的大量文件读误报成数据窃取。高置信度事件触发隔离而不是自动删除，保全证据后再重建。

## 22.8 事故响应：安全、可靠性和隐私联动

### 22.8.1 准备阶段

准备清单包括资产和数据分类、值班表、决策权限、供应商联系人、密钥和证书撤销路径、镜像/模型阻断机制、隔离节点池、干净构建环境、备份与恢复演练、法律和隐私通报流程。为常见场景写 playbook：令牌泄露、模型工件篡改、租户串读、GPU 节点入侵、训练数据投毒、日志暴露、供应商服务异常。

演练必须有停止条件和安全边界。不要在真实租户数据上测试“删除”；在隔离环境注入带标记的 canary 记录和模型版本。每季度验证一次从干净提交重建镜像、生成 SBOM、验证签名、恢复索引和轮换 KMS；记录耗时、失败点和人工步骤。

### 22.8.2 检测与分级

信号来自身份异常（不常见的主体、地域、设备、权限）、供应链差异（摘要、SBOM、来源证明变化）、数据访问（跨租户、批量读取、夜间峰值）、模型行为（触发器、格式漂移、工具调用链异常）、GPU/节点（新设备句柄、驱动崩溃、出站异常）和隐私管道（日志字段突然出现原文）。把安全信号与前章可靠性信号关联：错误率低但对象读取暴增可能是静默窃取；p99 上升且重试放大可能是攻击或过载。

分级应按影响而非告警数量：S0 可能暴露跨租户或高影响数据，立即冻结和通报；S1 影响单租户或模型完整性，限制发布并进入取证；S2 可疑配置或低敏感事件，修复后复盘。每级定义响应时间、可自动化动作、需要谁批准以及何时升级法律/隐私团队。

### 22.8.3 遏制、证据和根除

遏制是让影响停止并保留状态：撤销高风险身份、暂停队列、阻断模型摘要、隔离节点、关闭出站、冻结对象版本和发布指针。不要一上来删除 pod，因为它可能抹掉内存、临时文件和连接信息。先保存 API 审计、对象访问、容器运行时、GPU 错误、模型 manifest、签名证明、DNS/流量和时间同步信息，并记录证据哈希与保管链。

根除要从干净来源重建，不在被怀疑的工作站或节点上“修补后继续用”。重新生成依赖锁文件和 SBOM，验证来源证明和评测，轮换相关密钥，清理缓存和镜像，检查同一工件在其他环境的部署。若怀疑数据投毒，冻结训练和评测结果，回退到最后已知良好数据版本，比较行为差异而不是只看 loss。

### 22.8.4 恢复、通知和复盘

恢复顺序通常是信任根和身份、控制平面、存储和索引、模型 registry、推理服务、训练任务和异步工具。每一步有健康、完整性、隐私和租户隔离门禁。恢复旧模型要明确质量、知识新鲜度和删除请求影响；在高影响场景增加人工复核和只读模式。

通知内容要可证实：受影响资产、时间窗口、已确认数据类型、未知部分、遏制措施、用户行动和后续时间点。不要在事实未定时发布具体攻击者或数据量。复盘关注系统性原因：为什么令牌能读过宽前缀，为什么准入例外无过期，为什么监控没有租户维度，为什么备份没有删除索引。把修复项转成可验证的控制和演练，而不是“加强安全意识”。

## 22.9 失败案例：控制存在但边界错误

### 案例一：签名通过，模型仍被篡改

团队对权重签名，但 tokenizer 和 `generation_config` 通过未签名 URL 加载。攻击者只替换 tokenizer，即可改变分词边界并绕过长度和安全规则。修复：把模型包、tokenizer、配置和转换脚本放进同一不可变 manifest，签名 manifest 摘要；发布器验证所有成员，而不是只验证最大文件。

### 案例二：租户过滤在缓存层丢失

检索服务查询时带租户条件，应用缓存却只使用 `hash(prompt)` 作为键。A 的回答被 B 命中。修复：缓存键包括租户、用户授权版本、模型/索引摘要、策略版本和数据新鲜度；对跨租户缓存使用独立密钥和显式允许列表。增加 canary 文档验证串读，不能只做单租户单元测试。

### 案例三：短期令牌被长时间缓存

SPIFFE 或云身份发行短期凭据，但 SDK 在进程内缓存并在过期后重试旧 token；轮换后部分 worker 仍能访问。修复：实现提前刷新、时钟容差、令牌受众校验和撤销后的缓存清空；在演练中缩短 TTL，证明失效传播。

### 案例四：GPU 调试端口成为横向入口

为分析 OOM，团队暴露 profiler 和远程 shell 端口。该端口绕过网关身份，允许读取进程和显存统计。修复：调试功能默认关闭，使用短期、审计、只读会话；专用节点和网络策略隔离；将采样结果脱敏并设置到期时间。

### 案例五：删除完成但备份仍可恢复

数据库和在线索引删除了客户记录，旧 checkpoint 和对象快照仍包含原文。恢复脚本默认会把快照挂载到生产。修复：建立数据 ID 到备份/模型工件的血缘，删除或加密隔离全部副本，恢复前执行删除清单过滤；若做不到逐样本删除，必须在产品承诺中披露限制。

### 案例六：CI 被依赖脚本窃取签名能力

构建任务安装未锁定的包，安装脚本读取 CI 环境并调用签名命令。签名服务只验证“任务成功”，没有绑定输出摘要和构建身份。修复：构建步骤无权取得签名私钥，只能提交摘要；签名服务验证来源证明、提交保护状态和 SBOM，且每次签名带工件用途和环境。

## 22.10 标准库实验：可验证的小型安全控制

实验不连接云、不操作真实集群，使用 Python 标准库演示五件事：哈希和 HMAC 的完整性校验、不可变 manifest、租户队列与配额、敏感字段脱敏、事件时间线和供应链篡改检测。它不实现真正的数字签名、KMS、容器隔离或差分隐私；实验结果只能证明 toy 的状态转移和测试断言。

运行：

```text
python3 ch22_security_lab.py
```

预期输出包括：manifest 摘要、完整性校验通过与篡改后的失败、A/B 租户配额统计、脱敏后不含原始邮箱/手机号、来源证明缺失被拒、事件按时间排序以及最终安全边界提示。脚本在 `/workspace/scratch/4dcc55129e39/ch22_security_lab.py`，仅使用 Python 3.10+ 标准库。

实验观察要点：

1. HMAC 证明的是“持有同一共享密钥的验证者看到的消息未被修改”，不证明密钥未泄露，也不提供不可否认性。真实供应链应使用签名和独立信任根。
2. 租户配额只有在每个资源入口都执行时才有意义；脚本故意把全局队列和每租户队列分开，展示全局容量不足时不会自动借用别人的配额。
3. 脱敏会损失调试上下文，且简单正则有漏报和误报。输出中只保留字段类别和不可逆摘要，不能据此宣称满足任何法律删除或匿名化要求。
4. manifest 篡改检测依赖规范化序列化；若不同语言对字段顺序、浮点或 Unicode 处理不同，必须使用明确的 canonical 格式。

### 22.10.1 实验脚本

```python
#!/usr/bin/env python3
"""Chapter 22 CPU-only security lab; Python standard library only."""
from __future__ import annotations

import base64
import hashlib
import hmac
import json
import re
import time
from collections import defaultdict, deque
from dataclasses import dataclass
from typing import Any


def canonical(obj: Any) -> bytes:
    return json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")


def digest(obj: Any) -> str:
    return hashlib.sha256(canonical(obj)).hexdigest()


def mac(obj: Any, key: bytes) -> str:
    return hmac.new(key, canonical(obj), hashlib.sha256).hexdigest()


def verify_mac(obj: Any, tag: str, key: bytes) -> bool:
    return hmac.compare_digest(mac(obj, key), tag)


EMAIL = re.compile(r"(?i)\b[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}\b")
PHONE = re.compile(r"(?<!\d)(?:\+?86[- ]?)?1[3-9]\d{9}(?!\d)")


def redact(text: str) -> str:
    text = EMAIL.sub("[EMAIL]", text)
    text = PHONE.sub("[PHONE]", text)
    return text


@dataclass
class Job:
    tenant: str
    job_id: str
    cost: int
    text: str


class TenantLimiter:
    def __init__(self, per_tenant: dict[str, int], global_limit: int) -> None:
        self.per_tenant = dict(per_tenant)
        self.used: defaultdict[str, int] = defaultdict(int)
        self.global_limit = global_limit
        self.global_used = 0
        self.accepted: deque[Job] = deque()
        self.rejected: list[Job] = []

    def submit(self, job: Job) -> bool:
        allowed = (
            job.tenant in self.per_tenant
            and self.used[job.tenant] + job.cost <= self.per_tenant[job.tenant]
            and self.global_used + job.cost <= self.global_limit
        )
        if not allowed:
            self.rejected.append(job)
            return False
        self.used[job.tenant] += job.cost
        self.global_used += job.cost
        self.accepted.append(job)
        return True


def main() -> None:
    key = b"toy-demo-key-do-not-use-in-production"
    manifest = {
        "model": "demo-1.0",
        "weights_sha256": "a" * 64,
        "tokenizer_sha256": "b" * 64,
        "source_commit": "deadbeef",
        "builder": "ci.example/build@v3",
        "sbom": ["python:3.12", "numpy:2.0"],
    }
    tag = mac(manifest, key)
    print("manifest sha256:", digest(manifest))
    print("hmac verified:", verify_mac(manifest, tag, key))
    altered = dict(manifest, weights_sha256="c" * 64)
    print("tampered hmac rejected:", not verify_mac(altered, tag, key))

    limiter = TenantLimiter({"tenant-a": 5, "tenant-b": 5}, global_limit=7)
    jobs = [
        Job("tenant-a", "a1", 3, "alice@example.com asks for 13800138000"),
        Job("tenant-a", "a2", 3, "second expensive request"),
        Job("tenant-b", "b1", 3, "bob@example.com asks for 13900139000"),
    ]
    for job in jobs:
        accepted = limiter.submit(job)
        print("quota", job.job_id, "accepted" if accepted else "rejected")
    print("accepted cost by tenant:", dict(limiter.used))
    print("rejected jobs:", [j.job_id for j in limiter.rejected])

    raw = "contact alice@example.com or 13800138000; tenant=tenant-a"
    clean = redact(raw)
    print("redacted:", clean)
    assert "alice@example.com" not in clean and "13800138000" not in clean

    events = [
        {"ts": 3, "kind": "admission_denied", "reason": "missing_provenance"},
        {"ts": 1, "kind": "token_issued", "subject": "train-a", "ttl_s": 300},
        {"ts": 2, "kind": "tenant_quota_reject", "tenant": "tenant-a"},
    ]
    print("incident timeline:")
    for event in sorted(events, key=lambda e: e["ts"]):
        print(json.dumps(event, ensure_ascii=False, sort_keys=True))

    # A toy admission rule: provenance and SBOM must be present before release.
    candidate = {"provenance": True, "sbom": True, "signature": True}
    print("admission:", "allow" if all(candidate.values()) else "deny")
    candidate["provenance"] = False
    print("missing provenance:", "deny" if not all(candidate.values()) else "allow")

    print("BOUNDARY: HMAC is not a digital signature; quotas are not kernel isolation;")
    print("BOUNDARY: regex redaction is not anonymization; a manifest is not a safety proof.")


if __name__ == "__main__":
    main()
```

代码块之外的复现实验可逐项改变：把 `global_limit` 从 7 调到 10，观察租户 A 的第二个任务仍因每租户预算拒绝；把同一 job 的 `tenant` 改成未知值，确认默认拒绝；在 manifest 中改变字段值，确认 HMAC 失败；将邮箱改成 Unicode 或分行，观察正则脱敏的漏报并记录为实验限制。不要把 demo key 或脚本中的信任逻辑复制到生产。

## 22.11 理解检查（含答案）

### 检查一：签名和来源证明有什么区别？

**问题**：镜像签名验证通过，是否说明镜像由受信源代码构建且没有已知漏洞？

**答案**：不说明。签名只把摘要绑定到签名身份和信任根；来源证明才描述输入、构建器和过程，SBOM/扫描才提供组件与漏洞视图。即使三者都满足，也不能证明运行时配置、模型行为或未知漏洞安全。

### 检查二：namespace 隔离是否能承受恶意租户？

**问题**：两个租户在同一 Kubernetes 节点、不同 namespace、不同 ServiceAccount，是否可直接承诺机密隔离？

**答案**：不能。namespace 和 RBAC 限制 API 对象，NetworkPolicy 限制部分网络，仍共享内核、节点、驱动和可能的 GPU。恶意租户模型应使用更强的节点/VM/专用 GPU/机密计算边界，并对侧信道和运维者能力做明确假设。

### 检查三：为什么短期令牌仍需撤销设计？

**问题**：令牌只有五分钟有效期，泄露后是否可以等它自然过期？

**答案**：不一定。五分钟可能足以读取大量数据或签发下游凭据，且缓存、长连接、签名 URL 和复制任务可能延长影响。应先冻结主体、撤销授权和阻断出站，再等待 TTL；演练失效传播时间。

### 检查四：缓存键缺租户字段会怎样？

**问题**：RAG 结果缓存只按 prompt 哈希索引，A 和 B 的 prompt 相同但权限不同，会发生什么？

**答案**：B 可能拿到 A 的检索结果或回答。缓存键必须包含租户/主体授权版本、模型与索引摘要、策略版本和新鲜度；服务端仍应再次校验文档 ACL。不要把 prompt 内容相同当成权限相同。

### 检查五：脱敏后的日志是否可以放到公开仓库？

**问题**：已替换邮箱和手机号的 trace 是否可公开？

**答案**：不能直接推断。时间、长度、罕见实体、错误文本、租户 ID 和上下文拼接可能重新识别；脱敏规则还可能漏报。公开前要做数据分类、攻击者重识别评估、最小化和审批，最好只公开合成或明确无敏感字段的样本。

### 检查六：删除请求为什么需要模型血缘？

**问题**：删除数据库行和向量后，为什么还要查 checkpoint 和蒸馏模型？

**答案**：训练和蒸馏可能把记录的信息编码进参数、梯度、缓存或评测工件；恢复旧 checkpoint 又会重新暴露。必须有数据到工件的血缘和删除/隔离策略；如果无法证明逐样本删除，要明确限制并降低承诺。

### 检查七：GPU 利用率能证明租户隔离吗？

**问题**：监控显示 GPU 利用率和显存都正常，能否说明没有跨租户泄露？

**答案**：不能。利用率只描述资源忙闲，不覆盖显存残留、设备句柄、侧信道、驱动和 profiler 访问。应结合设备分配、清理、节点共驻、出站、运行时审计和专门攻击测试。

### 检查八：事故时为什么先保全证据再重启？

**问题**：怀疑节点被入侵，立即删除并重建最快，为什么不这样做？

**答案**：删除会丢失内存、临时文件、进程、连接和时间线，无法判断影响范围和是否需要通知。先隔离网络和身份、做合规的取证快照并记录哈希，再从干净来源重建；若有生命或大规模泄露风险，按 playbook 在保全与遏制之间作明示取舍。

## 22.12 练习：从检查到设计

1. **资产图**：为一个含网关、RAG、模型 server、工具 API、KMS 和审计平台的系统画数据流。给每条边标出主体身份、数据分类、加密、日志和失败默认。
2. **权限矩阵**：为训练 worker、评测 job、发布器、清理任务写最小权限矩阵，至少包含对象动作、条件、TTL、审计字段和撤销路径。找出一个必须人工确认的高影响动作。
3. **租户攻击**：实现一个故意缺少租户缓存字段的 toy，构造 A→B 串读；加入授权版本、索引摘要和拒绝默认后重复测试。
4. **供应链**：为模型包设计 manifest 和 SBOM。列出代码、数据、tokenizer、权重、配置、转换器、基础镜像、CUDA 版本、评测结果和许可；定义哪些变化必须重新签名。
5. **SLSA 策略**：比较 L1/L2/L3 的威胁覆盖。针对一个可接受的实验环境和一个高影响生产环境，选择级别并解释构建成本、信任根和失败动作。
6. **隐私评估**：列出 prompt、embedding、KV cache、trace、错误堆栈、GPU profiler、备份和 checkpoint 的保留期与删除方法。为每个来源设计一个 canary，验证数据没有越过允许边界。
7. **Kubernetes 审查**：检查一个模型 Deployment 的 securityContext、ServiceAccount、NetworkPolicy、Pod Security、资源配额、GPU 设备和准入例外。把每个例外改写成带到期日期和证据的策略。
8. **事故演练**：模拟签名密钥泄露和租户串读两条事件，分别写检测信号、前 15 分钟动作、证据清单、恢复顺序、用户通知和复盘项。注明哪些动作需要安全、隐私或业务负责人批准。
9. **隐私预算**：给出一个 DP 训练实验的采样率、裁剪范数、噪声乘子和预算会计器版本；对三种预算目标测量质量、训练时间和成员推断风险。不要把一次实验的 epsilon 当成所有模型的保证。
10. **GPU 边界**：比较同卡时间切片、MIG、专用卡、VM 和裸金属的隔离保证、吞吐、成本和侧信道假设。为高敏感租户选择方案，并列出需要实测的驱动/固件项目。

## 22.13 安全边界与伦理约束

本章的控制不能授权读取、导出或推断他人的敏感数据。只在隔离环境使用合成或获授权的 canary；不在真实租户、公共集群、第三方模型服务或未批准的节点上做渗透和故障注入。漏洞复现遵循负责任披露和组织审批，不能把实验脚本改造成扫描器或凭据窃取器。

身份、日志和取证包含高度敏感信息。最小化访问者、用途、保留期和复制范围；对员工、患者、未成年人、财务和身份数据遵守适用法律与组织政策。不要为“调试方便”关闭审计、TLS、准入或隔离。高影响领域的模型输出不能因为通过签名、SLO 或安全扫描就自动获得决策资格，仍需领域专家、人工复核和申诉渠道。

安全控制也可能损害可用性和公平性。强隔离提高成本，严格删除降低可回放性，噪声和拒答影响不同语言和边缘群体，令牌限额可能让资源有限的租户更难使用。设计时记录谁承担成本、错误和延迟，使用分层配额和申诉机制，而不是把安全例外默认为特权。

## 22.15 总结与下一依赖

AI infra 安全是一条端到端链：资产和信任边界决定威胁模型；身份和最小权限决定主体能做什么；租户、节点、GPU 和密码学隔离决定失败影响范围；密钥、SBOM、来源证明和签名决定工件能否被追溯与阻断；数据最小化、日志分层、RAG ACL、DP/TEE 和删除血缘决定隐私承诺；准入、运行时检测和事故响应决定控制能否在错误或入侵后及时生效。

没有单一工具能覆盖这条链。签名无法替代运行时授权，namespace 无法替代节点隔离，脱敏无法替代数据最小化，短期令牌无法替代撤销，GPU 利用率无法替代侧信道评估，SLO 也无法替代安全和隐私门禁。工程结论只有在写出假设、证据、失败默认和恢复路径后才有意义。

下一章可在本章身份、来源和租户边界上继续讨论成本、容量和治理：每个租户的 GPU 秒数如何计量，安全扫描和签名验证怎样进入发布延迟预算，隐私删除如何影响 checkpoint 与缓存，事故预算怎样和可靠性错误预算联合决策。把安全控制当作系统状态和数据流的一部分，才能避免“上线前检查一次，运行时无人负责”的断裂。
