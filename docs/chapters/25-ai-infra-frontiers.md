# 第25章　AI Infra 前沿与研究方法：加速器、稀疏、边缘、隐私、长上下文与绿色计算

> 本章讨论的是“下一代基础设施如何被证明可用”，而不是罗列芯片名称。AI Infra 的新方向常把一个瓶颈移到另一个瓶颈：加速器提高矩阵吞吐，却受到显存容量和通信限制；MoE 减少每 token 的算术量，却增加路由、跨卡 all-to-all 和尾部负载；边缘部署降低网络往返，却引入功耗、热设计和固件碎片；联邦学习减少原始数据汇聚，却需要安全聚合、客户端掉线处理和隐私预算；长上下文扩大窗口，却把 KV cache、内存带宽和质量评估推到前台。读者需要一套能拒绝夸大宣传的研究方法。

本章延续全书的证据标记。**事实**表示标准、芯片厂商文档、公开协议或论文明确给出的语义；**研究结果**表示同行评审论文或复现实验报告中的统计结论，适用范围必须保留；**测量**表示本章 CPU toy 或目标环境的直接观测；**机制**表示根据数据流和状态机还原出的因果关系；**设计判断**表示在目标、约束和风险已知时的工程取舍；**前瞻推断**表示由已知趋势推演的可能结果，不是已发生的事实；**未知**表示当前证据不足，不能用经验填空。一个 toy 只能验证公式和控制流，不能证明某个芯片在生产流量上的优势。

## 25.1 先建立全景图：算力不是单一资源

### 25.1.1 六种前沿与共同问题

可以把本章的前沿分为六类。第一类是新型加速器与存算，把矩阵乘、向量访存、通信和能耗重新映射到芯片或封装；第二类是 MoE 与稀疏，用选择性计算减少每个 token 的激活参数；第三类是边缘与异构，把 CPU、GPU、NPU、DSP、FPGA 和传感器放进同一条工作流；第四类是联邦与隐私计算，使数据留在客户端或受控域内；第五类是长上下文与新内存，重新安排 KV cache、权重、激活和分层存储；第六类是绿色计算，要求同时报告能量、碳、材料和使用率。

**事实**：这些方向互相耦合。模型的算子图决定加速器利用率，精度格式决定内存和通信，路由策略决定网络拓扑，数据驻留要求决定联邦和边缘边界，能耗限制又反过来决定 batch、频率和服务等级。**设计判断**：评估一个新方案时，不要先问“理论 TOPS 多少”，而要先写出端到端工作单元，例如“每个用户请求生成 256 token，包含检索、prefill、decode、审计写入，延迟 p99 小于 1 秒，功耗上限 250 W，数据不能离开区域”。没有工作单元，峰值指标没有分母。

### 25.1.2 研究问题模板

每个前沿问题都可以用五句模板表达：

1. **瓶颈**：系统在什么阶段被算力、带宽、容量、同步、能耗或隐私约束卡住？
2. **干预**：新硬件、算法或协议改变哪个状态转移？是否只是把成本移到别处？
3. **基线**：与哪个固定版本、相同精度、相同质量门槛和相同故障预算比较？
4. **证据**：测量什么指标、多少重复、哪些置信区间、哪些失败样本，怎样复现？
5. **边界**：在什么模型规模、序列长度、拓扑、温度、租户或合规条件下结论失效？

**研究结果**：许多系统论文的速度提升在 microbenchmark 中显著，在端到端任务中却被输入管线、同步、编译时间或数据准备抵消。原因不是论文“错”，而是测量对象不同。读者应把算子级、设备级、节点级和用户级结果分开。

### 25.1.3 数量级心算

对 dense GEMM，算术强度可粗略写成 FLOPs/byte。若矩阵乘重用不足，带宽而非乘加单元会决定速度；若激活、权重和 KV cache 不能驻留高速内存，理论吞吐会坍缩。对生成 decode，单 token 的矩阵乘通常要读取大量权重和历史 KV，算术强度低于 prefill；因此“训练吞吐高”不能直接推出“交互延迟低”。

一个请求的粗略内存预算可以写成：

\[
M_{total}=M_{weights}+M_{optimizer}+M_{activations}+M_{KV}+M_{workspace}+M_{replication}。
\]

推理时 optimizer 常为零，但 KV cache 随 batch、层数、头数、每头维度、序列长度和元素字节数线性增长。**测量**：本章实验用 Python 计算这个公式，并把整数四舍五入、分页和碎片化的误差显式打印出来。**前瞻推断**：随着上下文窗口扩大，系统优化的中心可能从“再堆矩阵单元”转向“管理可变工作集和跨层内存”。这不是预测某个产品，而是由容量与带宽公式得到的条件推断。

## 25.2 新型加速器与存算：从峰值算力回到数据移动

### 25.2.1 加速器层次结构

**事实**：现代 AI 加速器通常包含矩阵或张量单元、向量/标量单元、片上 SRAM、片外高带宽内存和高速互连。不同供应商对单元名称、精度支持和调度方式不同，但层次结构相似：越靠近计算单元，容量越小、延迟越低、带宽越高；越靠近主机或网络，容量更大但移动成本更高。官方规格可以确认峰值吞吐、内存容量、互连带宽和支持的数值格式，却不能单独证明某模型的端到端性能。

**机制**：编译器或 kernel 选择 tile 大小，把权重、激活和累加器在 SRAM、寄存器与 HBM 之间搬运；当 tile 不适配、转置频繁或算子融合失败时，空闲的计算单元并不表示系统异常，而是说明数据路径成为瓶颈。内核融合可以减少写回，但会增加寄存器压力和编译复杂度；量化可以减少字节数，却可能引入反量化开销和质量损失。

**研究结果**：FlashAttention 一类工作证明，通过分块和在线归一化减少高带宽内存读写，可以在不改变注意力数学结果（数值误差在实现允许范围内）的情况下提升实际速度和降低内存占用。这个结果的可迁移部分是“IO 感知算法”思想，具体倍数依赖 GPU、序列长度、精度和实现版本，不能跨硬件照搬。

### 25.2.2 PIM、near-memory 与存内计算

“存内计算”包含多种不同架构，不能用一个词掩盖差异。**事实**：near-memory 把计算单元放在内存附近，缩短数据移动距离；processing-in-memory（PIM）把有限逻辑放进内存阵列或封装；模拟存内计算可能利用电荷或电导完成近似乘加。它们的共同目标是减少数据搬运，但精度、可编程性、写入寿命、校准和软件栈各不相同。

**研究结果**：公开论文在向量搜索、低比特矩阵乘和推荐模型上展示过能效提升，但常以特定模型、静态权重、批量访问和定制编译器为前提。实验经常排除主机调度、数据重排、编程时间和错误校正。正确的复现应至少补上：端到端数据搬运、编译/映射时间、热稳态、故障率、精度分布和更新权重的成本。

**设计判断**：PIM 适合访问模式稳定、带宽占主导、可接受受限算子集合的工作负载；对频繁变权重、动态控制流和需要复杂调试的服务，应保留通用 CPU/GPU 路径。生产接入要有 shadow 运行和回滚：同一批请求在通用路径计算参考输出，只在质量和尾延迟都通过后逐步提升 PIM 流量。

### 25.2.3 精度、量化与数值边界

精度不是越低越好。**事实**：FP32、BF16、FP16、FP8、INT8、INT4 等格式在指数范围、有效位、舍入和硬件支持上不同；训练常需要更宽动态范围或损失缩放，推理量化则需要校准数据、异常值处理和算子级混合精度。一个“支持 INT4”的规格可能只对部分矩阵单元成立，激活、累加器和归一化仍使用更高精度。

**机制**：量化误差沿残差、注意力 logits、softmax 和采样链传播；校准集覆盖不足时，罕见 token、长文本或多语种输入会暴露异常。**研究结果**：后训练量化与量化感知训练在许多公开模型上可接近 FP16 质量，但质量差异依赖校准集、任务、生成长度和实现。必须报告每个任务的置信区间和最坏切片，而不是只报平均准确率。

**前瞻推断**：当硬件支持更细粒度的混合精度和稀疏格式时，最优策略可能是“按层、按 token、按温度动态选择格式”。推断成立的前提是切换开销小于节省的内存和算力，并且质量监控能发现异常；若格式切换引入同步，结论会相反。

### 25.2.4 实验设计：从峰值到屋顶线

屋顶线模型（roofline）把算术强度与峰值算力、峰值带宽放到同一图上。实验步骤如下：先固定模型、输入形状、精度、编译器和 batch；测量 kernel 时间、有效 FLOPs、实际字节数和设备功率；计算 arithmetic intensity；再增加融合、重排或量化干预，观察瓶颈是否从带宽移到计算。**测量**必须区分热启动与冷启动，并报告 p50、p95、p99 和温度稳定时间。

不要用一个“平均 tokens/s”掩盖 prefill 与 decode。对服务还要记录排队时间、数据传输、tokenizer、采样和日志开销。**失败模式**：研究者把输入复制到 GPU 的时间放在基线里，却在优化实现中缓存输入；或只测最大 batch，忽略真实服务的小 batch 和尾部请求。解决方法是发布脚本、固定命令行、保存原始 trace，并让第三方运行同一基线。

## 25.3 MoE 与稀疏：少算不等于少系统成本

### 25.3.1 稀疏的几种含义

“稀疏”至少有四种含义：权重稀疏（固定或结构化零值）、激活稀疏（只有部分神经元被激活）、路由稀疏（MoE 每 token 选择少数专家）、输入或检索稀疏（只读取少量上下文）。它们减少的资源不同。非结构化零值若硬件无法跳过，可能只减少存储，不减少时间；结构化 N:M 稀疏需要编译器和矩阵单元共同支持；MoE 仍需保存全部专家权重并承担路由通信。

### 25.3.2 MoE 数据路径

典型稀疏 MoE 层包含路由器、top-k 选择、容量限制、token 重排、专家计算、跨设备 all-to-all、逆重排和聚合。**事实**：Switch Transformer 等工作把 top-1 路由作为降低通信和负载的方案；GShard 等工作展示了专家并行与路由的扩展方式。论文的具体质量与扩展结果应按模型和训练设置引用，不能推断所有 MoE 都稳定。

**机制**：路由器产生 logits，softmax 后选择专家。若某专家过热，容量因子会导致 token 丢弃、二次路由或 padding；若专家分布不均，最慢专家决定 step 尾延迟。all-to-all 对拓扑和拥塞敏感，跨节点通信可能抵消省下的 FLOPs。训练中的负载均衡损失会改变梯度，推理中的硬容量上限则可能改变答案质量，二者不能混为同一个参数。

**测量**：实验应记录每层每专家 token 数、丢弃率、路由熵、all-to-all 字节、最慢专家时间和质量切片。只报告总吞吐而不报告 p99 专家负载，会把尾部掩盖在平均值中。

### 25.3.3 稀疏失败案例

案例一：把 dense checkpoint 直接拆成专家，得到“激活参数少”的宣传数字，但所有专家仍在同一张卡上，显存和加载时间不降。根因是只改变计算路径，未改变权重驻留和内存布局。修复是区分总参数、激活参数、驻留字节和每请求通信。

案例二：训练集分布改变后，路由器把新领域 token 集中到两个专家，其他专家空闲。根因是负载均衡正则在旧分布上调优，部署域漂移后失效。修复是在线监控路由熵和专家占用，设置回退到 dense 层或重新校准路由的门槛。

案例三：top-2 比 top-1 质量略高，但跨节点 all-to-all 使 p99 翻倍。根因是用离线 perplexity 代替用户延迟目标。修复是按质量-延迟前沿选点，并给通信预算设硬上限。

### 25.3.4 动态稀疏的前瞻推断

**前瞻推断**：未来的稀疏系统可能把路由、精度和内存层级联合优化，例如把常用专家放在本地 HBM，把冷专家放在 CXL 或远端内存；根据租户和上下文动态选择 top-k；在质量下降前回退到 dense。推断依赖于快速预测专家热度、稳定的缓存命中和可解释的质量探针。若路由抖动使缓存频繁失效，动态策略可能比静态分配更慢，因此必须以稳态 trace 和最坏窗口验证。

## 25.4 边缘与异构：把模型放到数据发生的地方

### 25.4.1 为什么边缘不是“缩小版云”

**事实**：边缘节点通常受功耗、温度、内存、网络不稳定、更新窗口和物理访问限制约束；硬件异构程度高，驱动和编译器版本组合更多。云端可以用统一镜像和高速网络扩容，边缘常需要离线运行、断点更新和本地降级。**设计判断**：边缘架构应把网络断开当作常态路径而非异常，定义本地模型、缓存、策略和恢复顺序。

典型工作流分成四段：传感器或客户端预处理、边缘推理、云端聚合/重训练、策略和模型下发。每段都有数据驻留与版本边界。模型版本、tokenizer、预处理、量化参数和硬件编译产物必须作为不可变 bundle 发布；只更新其中一个文件会造成“模型与前处理不匹配”的静默错误。

### 25.4.2 异构调度与切分

把模型切到 CPU、GPU、NPU 或 DSP 时，要写清楚张量何时跨设备、是否复制、是否异步、谁负责内存回收。流水线并行可以隐藏传输，但会增加缓冲和尾延迟；算子卸载可以节能，却可能触发频繁同步。**测量**应包括 PCIe/CXL/共享内存传输、编解码、线程唤醒和设备电源状态切换，而不仅是 kernel 时间。

一个可运行的异构调度策略至少有：设备能力向量（峰值、带宽、可用内存、功耗）、请求特征（token 数、优先级、截止时间）、队列和可回退路径。调度目标可写为加权成本：

\[
C = w_l L_{p99}+w_e E_{token}+w_c C_{cloud}+w_f P_{failure},
\]

其中 (L_{p99}) 为尾延迟，(E_{token}) 为每 token 能耗，(C_{cloud}) 为回传成本，(P_{failure}) 为超时或质量失败概率。权重应来自产品和安全约束，不能为了好看的图随意调整。

### 25.4.3 边缘失败案例

失败案例一：边缘设备在实验室持续 20°C，部署到户外后温度升高触发降频，p99 从 150 ms 变成 800 ms。根因是未测热稳态；修复是把热循环、风扇故障和降频事件纳入基准，并设置温度相关 SLO。

失败案例二：离线设备在 72 小时后模型过期，但本地策略仍接受高风险输入。根因是把“离线可用”误当成“策略永不过期”。修复是给模型和策略设置过期时间，过期后仅允许低风险模式或转人工。

失败案例三：OTA 更新只校验压缩包哈希，不校验模型、tokenizer 和硬件编译版本的绑定。根因是工件清单不完整。修复是签名 manifest、原子切换、双分区回滚和启动自检。

### 25.4.4 前瞻推断：联邦边缘与稀疏协同

**前瞻推断**：边缘设备可能只训练或上传稀疏增量、低秩适配器或梯度草图，把全量模型留在受控仓库。这样可以减少带宽和隐私暴露，但会引入适配器组合、版本冲突和恶意更新问题。要把推断变成研究结果，至少需要跨设备异构基准、掉线和非独立同分布数据、攻击注入以及端到端能耗测量。

## 25.5 联邦学习与隐私计算：减少集中数据，不等于自动隐私

### 25.5.1 威胁模型先于协议

**事实**：联邦学习把训练数据留在客户端或组织边界，服务器聚合更新。它降低原始数据集中化的风险，但更新本身可能泄露成员信息或被反演；恶意客户端可以投毒，服务器也可能观察单个更新，客户端掉线和重连会改变统计。安全聚合隐藏单个客户端更新，不能保证模型不泄露，也不能阻止服务端拒绝服务。

写威胁模型时至少回答：服务器是否诚实但好奇？客户端是否会串谋？攻击者能观察多少轮？是否有可信执行环境？数据跨境和删除请求如何处理？什么是可接受的成员推断风险？如果问题没写清楚，“隐私增强”只是口号。

### 25.5.2 联邦平均与非独立同分布

McMahan 等人的 Federated Averaging 以本地多步更新后加权平均为核心。**研究结果**：在通信受限且客户端数据近似独立同分布时，本地多步可以减少通信轮数；在强非 IID、客户端规模差异大或标签偏斜时，收敛和公平性会恶化。论文结果依赖模型、客户端采样、学习率和聚合权重，不能把一个数据集的轮数当作通用结论。

实验必须报告每轮参与客户端数、掉线率、客户端样本量分布、聚合权重、局部 epoch、通信字节和各群体指标。平均准确率可能上升，但小群体或新设备质量下降。**设计判断**：把公平性和最坏切片作为门禁，不用全局均值掩盖客户端间的不平等。

### 25.5.3 差分隐私与预算会计

差分隐私用 \(\epsilon\)（隐私损失）和 \(\delta\)（极小失败概率）刻画相邻数据集输出分布的可区分程度。DP-SGD 常对每个样本梯度裁剪，再加入高斯噪声；多轮组合会消耗总预算。**事实**：较小的 epsilon 通常意味着更强隐私但更大噪声，质量损失依赖裁剪阈值、批量、采样率和轮数。不能只报一个 epsilon 而不报会计方法、采样假设和邻接定义。

**研究结果**：隐私会计工具能够比简单线性相加给出更紧的组合界，但界限是数学保证，不是对具体攻击的实测概率。生产上线仍应做成员推断、更新反演和投毒测试。不要把“加噪后准确率还行”误写成“不会泄露”。

### 25.5.4 安全聚合与故障语义

安全聚合通常利用掩码，使服务器只能看到总和；客户端掉线时需要恢复或取消掩码。**机制**：协议增加握手、密钥交换、分片和重试，通信字节和失败状态比普通平均更多。若掉线恰好集中在某个群体，参与样本会偏移；若协议超时，服务器可能反复请求更新，增加客户端能耗。

**失败案例**：团队把安全聚合阈值设得过高，低在线率时一轮无法完成；为了“保住吞吐”又降低阈值，单轮只剩两个客户端，隐私保护明显变弱。修复是把最小参与数、群体覆盖、超时和退出条件写入策略，并在 UI 和审计日志中记录本轮实际参与者范围，而不是只写“secure=true”。

## 25.6 长上下文与新内存：工作集管理成为一等公民

### 25.6.1 长上下文的三个成本

长上下文增加至少三类成本：prefill 的注意力和输入处理时间、decode 阶段持续增长的 KV cache、检索/重排和安全扫描的额外读取。稀疏注意力、滑动窗口、摘要和检索可以减少计算，但会改变可见信息集合，质量不能假定保持。

**事实**：标准全注意力的中间工作量随序列长度增长很快；KV cache 在自回归生成中随历史 token 线性累积。具体常数由层数、头数、头维度、是否 GQA/MQA、元素字节数和 batch 决定。工程师应从模型配置和实际 token 计数推导容量，而不是使用“每百万 token 多少显存”的宣传平均值。

### 25.6.2 KV cache 公式与分页

以每层 key、value 各一份为例，单序列 KV 字节数近似为：

\[
M_{KV}=2\times L\times T\times H_{kv}\times D\times B,
\]

其中 (L) 是层数，(T) 是历史 token 数，(H_{kv}) 是 KV 头数，(D) 是每头维度，(B) 是每元素字节。若使用 GQA，(H_{kv}) 小于 query 头数，可显著降低缓存，但要在质量和 kernel 支持上验证。batch、beam、并发流和复制会再乘上相应因子。

分页 KV cache 把缓存切成固定块，按需分配并回收，减少长短请求之间的外部碎片。**机制**：分页增加块表、地址转换和可能的非连续读取；块越小，碎片少但元数据和访存间接层越大；块越大，kernel 更简单但尾部浪费更多。实验应扫描块大小、并发、请求长度分布，报告容量利用率和 p99。

### 25.6.3 长上下文质量评估

“上下文窗口支持 1M token”只说明接口或位置编码允许更长输入，不证明模型在最远位置仍能检索、推理和拒绝提示注入。**研究结果**：长上下文基准常发现位置、干扰内容、任务类型和训练分布会影响召回；needle-in-a-haystack 只是单一检索测试，不能替代多跳推理、事实一致性、成本和安全测试。

评估矩阵至少包含：近端与远端信息、单跳与多跳、重复与冲突、不同语言、恶意指令、长输出、截断和流式取消。记录输入 token、有效上下文、命中位置、答案质量、首 token 延迟、每 token 延迟、内存峰值和能耗。**设计判断**：把长上下文作为能力档位，超过内存或质量门槛时显式切换到摘要、检索或人工复核，而不是静默截断。

### 25.6.4 CXL、HBM 与分层内存

**事实**：HBM 提供高带宽但容量和封装成本受限；DDR 容量更大但带宽和延迟不同；CXL 允许在特定平台上扩展或共享内存，具体协议、设备和一致性语义取决于实现。将冷 KV、专家权重或检查点放到较慢层级可能提升容量，但远端访问延迟、拥塞和故障域必须计入。

**前瞻推断**：如果分页缓存和压缩能稳定识别热块，分层内存会让“容量不足”变成“热度预测问题”。推断的风险是工作集突变造成抖动：缓存抖动会同时恶化尾延迟和能耗。生产设计需要热点采样、迟滞阈值、限流和快速回退到短上下文模式。

## 25.7 绿色计算：把能量、碳与公平成本放进指标

### 25.7.1 能耗测量不是乘一个 TDP

**事实**：TDP 是热设计参考，不等于每次请求的实际能耗。能耗应尽量从设备遥测、机架电表或可校准的功率计获得，并与时间、利用率、温度和任务标签对齐。CPU 的 RAPL、GPU 的功率接口和机架级电表各有采样频率、权限和误差。没有直接测量时可以用模型估算，但必须标为估算并给出假设。

请求级能量可粗略写成：

\[
E_{request}=\int_{t_0}^{t_1}P(t)dt / N_{completed},
\]

其中应说明是否包含待机、冷启动、网络设备、存储和失败请求。仅用完成请求做分母会低估重试和超时浪费；同时报告每 token、每成功请求和每单位质量的能耗更有意义。

### 25.7.2 碳强度与时间迁移

碳排估算还需要电网碳强度、地点、时间和 PUE 等假设。**事实**：同一工作在不同地区和时段的碳强度可能不同；把批处理迁移到低碳时段需要考虑数据驻留、延迟、备用容量和公平性。**设计判断**：对于可延迟训练，报告“能量”和“碳”两个指标，不用低碳调度掩盖高能耗；对于在线请求，先满足延迟和安全 SLO，再在可行窗口内做功率限制。

### 25.7.3 绿色优化的失败案例

失败案例一：用更低精度降低单请求能耗，却因质量下降触发重试和人工复核，整体能耗上升。修复是把能耗按“成功且质量通过的请求”统计，并记录重试链。

失败案例二：为了 PUE 漂亮，把工作迁移到远端低碳区域，网络传输和冷却延迟使 p99 超标。修复是对端到端能耗和延迟做联合预算，不把机房指标当作用户指标。

失败案例三：只优化满载吞吐，低流量时设备频繁唤醒和睡眠，尾延迟与能耗都恶化。修复是测量不同利用率区间，比较保持温热副本、批处理和功率上限的前沿。

### 25.7.4 前瞻推断：能耗成为调度维度

**前瞻推断**：当碳价、功率上限和 GPU 稀缺性同时存在，调度器会把能耗和可靠性预算一起优化，例如为低优先级训练选择可中断实例，为在线服务预留热副本。推断成立需有可观测功率、可预测工作量和可恢复检查点；否则能耗权重会导致不可解释的抢占和质量波动。

## 25.8 研究基准与实验设计：让数字可以被复查

### 25.8.1 基线冻结

基线是实验的法律文本。冻结模型 commit、数据版本、tokenizer、精度、编译器、驱动、硬件 SKU、拓扑、线程、batch、序列长度分布、随机种子和功率模式。记录 warm-up、缓存状态和后台进程。**事实**：MLPerf 等基准规定了任务、质量门槛和提交规则；它们用于可比性，但不能覆盖每个生产工作负载。引用基准时说明使用了哪一套规则和是否偏离。

### 25.8.2 端到端分解

把一次请求分解为排队、预处理、设备传输、prefill、decode、后处理、网络和日志。每段用 trace id 对齐，并报告服务级 p50/p95/p99。对于训练，分解数据加载、前向、反向、通信、检查点和空转；对联邦，分解客户端计算、上行、聚合、下行和掉线重试。**研究结果**：平均值容易被短请求和空闲阶段稀释，尾部常由少数长请求、最慢 rank 或重传决定。

### 25.8.3 统计与显著性

重复实验至少覆盖冷启动和热稳态，使用固定或分层随机种子。报告样本量、均值、中位数、分位数、置信区间和离群处理规则。对质量指标优先使用配对比较，让同一输入在基线和变体上评估；对延迟用 bootstrap 或非参数方法，而不是假设正态分布。若测试很多模型、数据集和阈值，应说明多重比较与预注册，否则“挑最好一次”会产生乐观偏差。

**失败模式**：只运行三次，选最好的结果；把编译时间排除在新方案却包含在基线；用不同 tokenizer 导致 token 数不同；质量下降一个百分点却用吞吐倍数宣传。修复是发布原始日志、命令、环境摘要和失败样本，并让独立人员复跑。

### 25.8.4 反事实和消融

消融要一次只改变一个关键因素，或使用因子实验估计交互项。例如比较 MoE 时分别固定总参数、激活参数、网络字节和质量门槛；比较量化时固定 tokenizer、采样参数和评估切片；比较边缘时固定输入和温度曲线。反事实问题是：“如果没有这个优化，其他条件相同，结果会怎样？”没有反事实就无法归因。

## 25.9 从论文到生产：一条可回滚的迁移链

### 25.9.1 论文阅读清单

阅读论文先提取四张表：

- **工作负载表**：模型、参数、序列、batch、数据分布、任务和质量门槛；
- **系统表**：硬件、拓扑、驱动、编译器、并行方式、故障假设；
- **指标表**：吞吐、延迟、内存、能耗、通信、成本和统计方法；
- **限制表**：未测场景、失败案例、代码和数据可获得性、与基线的差异。

**事实**和**研究结果**必须保留原文适用范围。若论文只测合成输入，生产迁移要补真实输入长度和错误分布；若论文只测单节点，跨节点通信和故障域必须重测。不要把摘要里的“up to”当成平均提升。

### 25.9.2 原型阶段：影子流量与差分日志

原型先接入不影响用户的 shadow 流量，保留参考路径输出摘要、延迟、能耗和质量判定。差分日志应避免保存完整敏感文本，只记录安全的哈希、结构化错误和可重放的最小样本。对生成模型，使用固定随机种子或 deterministic 解码做功能差分，再用真实采样评估分布差异。

### 25.9.3 灰度、回滚与版本绑定

每个新硬件或稀疏策略都要有版本化 manifest：模型、tokenizer、算子编译产物、驱动、固件、量化校准、路由配置、内存块大小和安全策略。灰度按租户、区域、请求长度和模型版本分桶，设置质量、p99、错误预算、功率和泄露告警。回滚应只切换到已验证的完整 bundle，不能临时拼文件。

### 25.9.4 生产门禁与退出条件

门禁包括：端到端 p99 不超过预算、质量切片无不可接受回归、内存无泄漏、热稳态通过、断网/掉卡/掉线可恢复、隐私和数据驻留符合要求、功率和成本在上限内。退出条件要提前写，例如连续两个窗口的尾延迟超标、路由丢弃率超过阈值、隐私预算耗尽、碳强度迁移造成 SLA 风险时自动回退。

### 25.9.5 生产失败案例

失败案例一：论文中的 4-bit 量化在短英文基准上几乎无损，生产多语种长文本出现事实错误。根因是校准集和切片不覆盖。修复是按语言、长度、领域重建校准集，并设置质量回退阈值。

失败案例二：MoE 原型单机吞吐翻倍，部署到跨区集群后 all-to-all 成为主要时间。根因是拓扑和通信字节未冻结。修复是把拓扑写入基线，增加通信仿真和跨节点压测。

失败案例三：边缘 NPU 推理功耗降低，固件更新后算子回退到 CPU，能耗和延迟突然恶化。根因是只绑定模型版本，不绑定编译器、驱动和固件。修复是启动时验证能力矩阵，异常时拒绝静默回退并报警。

## 25.10 综合架构练习：一个长上下文边缘联邦服务

设想一个工业巡检系统：摄像头和传感器在工厂边缘，边缘 NPU 运行视觉编码器，云端 MoE 语言模型生成维修建议；原始图像默认不离开工厂，只上传裁剪后的特征或加噪梯度；维修文本需要保留 128k token 历史；训练采用联邦聚合。这个场景把本章所有前沿连在一起。

第一步画数据流：传感器→预处理→NPU→本地缓存→云端路由→专家→审计与人工复核。为每个箭头标注数据类型、版本、加密、保留期和故障后动作。第二步写资源预算：NPU 内存、云端 HBM、KV cache、跨边缘网络、设备功耗、碳强度和联邦通信。第三步写质量与安全门禁：视觉误报、危险维修建议、提示注入、模型过期、策略无法更新时分别做什么。第四步设计实验矩阵：短/长上下文、热/冷设备、在线/离线、正常/恶意客户端、dense/MoE、不同隐私预算和功率上限。

**机制**：任一层的回退都会改变另一层。云端不可达时，边缘只能给出低风险分类；KV cache 超限时应切换摘要或检索，而不是丢弃最旧安全指令；联邦参与者不足时应跳过本轮并保留旧模型，不能为凑数量放宽阈值；功率过高时降低并发或质量档位，但不能关闭审计。**设计判断**：将“安全不可降级”与“性能可降级”写成策略表，并在实验中注入每种故障。

## 25.11 标准库 CPU 实验：前沿概念的最小可运行模型

本节的实验不模拟真实 GPU、NPU 或隐私安全证明，而是用 Python 标准库展示四种可复查的因果：稀疏 top-k 如何影响负载，异构设备如何按延迟/能耗调度，联邦平均与裁剪加噪如何改变更新，长上下文 KV cache 与碳排估算如何随参数变化。完整脚本保存为 `ch25_frontiers_lab.py`，只依赖 Python 3.10+ 标准库。

运行：

```bash
python3 ch25_frontiers_lab.py --seed 7 --tokens 20000 --experts 8 --clients 12
```

脚本输出 JSON，包含基线和变体的专家负载、p95 调度延迟、联邦更新范数、KV cache 字节数、能耗与估算碳排。建议至少重复三个 seed，并把原始输出保存到实验目录。**测量**只对 toy 的随机分布有效；不要把数字写成某硬件的性能承诺。

核心代码（完整版本见同名文件）：

```python
from dataclasses import dataclass
import argparse, json, math, random, statistics

@dataclass
class Device:
    name: str
    latency_ms: float
    joule_per_token: float
    capacity: int

def route(tokens, experts, top_k, rng):
    loads = [0] * experts
    for _ in range(tokens):
        scores = [rng.random() for _ in range(experts)]
        for idx in sorted(range(experts), key=lambda i: scores[i], reverse=True)[:top_k]:
            loads[idx] += 1
    return loads

def kv_bytes(layers, tokens, kv_heads, head_dim, bytes_per):
    return 2 * layers * tokens * kv_heads * head_dim * bytes_per

def fedavg(clients, clip, noise, rng):
    clipped = []
    for vec in clients:
        norm = math.sqrt(sum(x*x for x in vec))
        scale = min(1.0, clip / max(norm, 1e-12))
        clipped.append([x * scale for x in vec])
    dim = len(clipped[0]); n = len(clipped)
    return [sum(v[j] for v in clipped) / n + rng.gauss(0, noise) for j in range(dim)]
```

实验问题一：固定 tokens 和 experts，比较 top-1 与 top-2 的最大/最小专家负载和负载变异系数。若 top-2 的总激活量翻倍但路由更均匀，不要直接称其“更快”；还要模拟专家计算和通信字节。

实验问题二：把三类设备（高延迟低能耗、低延迟高能耗、容量小的边缘设备）放入调度器，分别以延迟权重和能耗权重运行。观察一个权重改变会怎样迁移 p95、每 token 能耗和拒绝数。调度器只接受容量内请求，超限请求进入回退队列。

实验问题三：为客户端生成不同均值的更新，运行无裁剪、裁剪和裁剪加噪的聚合。记录聚合向量范数与客户端均值差异；这说明非 IID 与隐私噪声如何同时影响更新，但不能证明真实攻击成功率。

实验问题四：扫描序列长度和 GQA 的 KV 头数，绘制内存阶梯。把结果与可用内存和并发相乘，找出第一次超限的长度；然后加上 20% 碎片余量，比较保守门槛。最后用功率×时间×碳强度估算能耗与碳，显式标注这是模型估算。

最小验证清单：随机种子固定时输出哈希稳定；top-k 增大时总路由计数单调增加；KV 字节数对 tokens 和 kv_heads 单调；裁剪后单个更新范数不超过 clip 加噪前；容量拒绝数在设备容量降低时不减少。若这些性质失败，先修实验再谈前沿结论。

## 25.12 失败案例复盘：看似创新，实际越过了边界

### 25.12.1 “峰值 TOPS 翻倍，所以服务翻倍”

观察：设备规格的理论 TOPS 翻倍，线上 tokens/s 只提高 12%。调查发现 decode 受权重带宽和 KV cache 限制，新增矩阵单元空闲。教训：报告算子级占用、实际带宽、内存命中、排队和质量；把“峰值”标为事实，把“端到端提升”标为测量。

### 25.12.2 “激活参数少，所以 MoE 更便宜”

观察：激活参数下降，显存和跨节点流量却增加。根因是所有专家仍驻留、top-2 路由和 padding 放大通信。教训：同时统计总驻留参数、激活 FLOPs、路由字节、padding、最慢专家和每成功 token 能耗。

### 25.12.3 “联邦=数据不出端，所以隐私安全”

观察：服务器从更新中恢复了训练样本特征。根因是未定义服务器威胁模型、未用安全聚合或差分隐私。教训：原始数据留端只是数据驻留属性，隐私需要威胁模型、协议、预算、攻击测试和删除语义。

### 25.12.4 “长上下文窗口等于长记忆”

观察：接口接受长输入，但远端事实召回率下降且 KV OOM。根因是把位置编码上限、有效质量和内存容量混为一谈。教训：按位置、任务、干扰、内存、延迟和安全切片评估，并在超限时显式降级。

### 25.12.5 “低碳调度总是更绿色”

观察：迁移到低碳区域后网络和重复计算增加，总能耗上升。根因是只看电网碳强度，不看迁移、空转、重试和 PUE。教训：把能耗、碳、延迟、可靠性和数据驻留放入同一实验矩阵。

## 25.13 六个理解检查（含答案）

### 检查一：为什么 decode 常比 prefill 更受带宽影响？

**问题**：prefill 一次处理长输入，decode 每次生成一个 token。为什么同一模型在 decode 的算术强度可能更低？

**答案**：prefill 可在批量矩阵中重用激活，计算量和数据重用较高；decode 每步只新增少量激活，却要读取大量权重和历史 KV，字节/FLOP 比例上升。具体结论仍取决于 batch、GQA、缓存命中和 kernel，必须测量而非套用定律。

### 检查二：top-2 一定比 top-1 好吗？

**问题**：top-2 让每个 token 访问两个专家，质量通常更高，因此生产应默认 top-2 吗？

**答案**：不能。top-2 增加专家计算、路由字节和尾部负载，可能超过质量收益；应在相同质量门槛、拓扑和 p99 预算下比较，并监控丢弃率和最慢专家。

### 检查三：安全聚合解决了什么，没解决什么？

**问题**：启用安全聚合后，服务器看不到单个更新，是否就不会有成员推断？

**答案**：安全聚合主要隐藏单个更新，减少诚实但好奇服务器的直接观察；它不自动防止聚合结果泄露、串谋、投毒、低参与人数和模型成员推断。通常还需差分隐私、阈值策略和攻击评估。

### 检查四：KV cache 何时超限？

**问题**：层数、KV 头数、头维度和元素字节数都不变，token 数翻倍会怎样？

**答案**：理想公式下 KV 字节数线性翻倍。实际还要考虑分页块浪费、并发、beam、复制和碎片，因此容量门槛应留余量并通过压力测试确认。

### 检查五：碳排估算的分母是什么？

**问题**：只用“成功请求数”做分母会遗漏什么？

**答案**：会遗漏超时、重试、失败推理、冷启动和预热等消耗，导致每成功请求能耗被低估。应同时报告每尝试、每完成、每质量通过请求以及每 token 的指标，并说明边界。

### 检查六：论文到生产的第一道门禁是什么？

**问题**：论文速度提升很大，是否应直接灰度 50% 流量？

**答案**：不应。先冻结环境和基线，复现实验，做真实输入的 shadow 流量，验证质量、p99、内存、功率、故障恢复和数据驻留；只有在门禁通过后才逐级灰度，并保留完整 bundle 的回滚。

## 25.14 练习：从复述到研究计划

1. **基线表**：为一个 7B 级生成服务列出设备、精度、上下文、batch、网络、功率、质量和 SLO；说明哪些数字是事实、哪些需要测量。
2. **屋顶线**：选一个矩阵乘和一个 decode kernel，估算 FLOPs、字节和算术强度；设计三个 tile 大小并预测瓶颈，再用 profiler 验证。
3. **MoE 消融**：在 toy 脚本中加入容量因子和 token 丢弃，分别测 top-1/top-2 的质量代理、通信字节、最大专家负载和 p99。
4. **边缘热循环**：设计 20°C、40°C、60°C 和降频事件的实验，定义温度、功耗、延迟和错误预算门禁；写出 OTA 失败的回滚动作。
5. **联邦隐私预算**：给定客户端采样率、裁剪阈值、噪声和轮数，选择一个隐私会计方法，报告 epsilon、delta、假设和最坏群体指标。
6. **长上下文**：构造近端、远端、冲突和提示注入四类样本，扫描 8k、32k、128k token；同时记录质量、KV 峰值、TTFT、ITL 和能耗。
7. **新内存分层**：模拟 HBM、DDR、CXL 三层延迟和容量，加入热点突变；比较静态放置、LRU 和带迟滞的热度预测，在 p99 超限时回退。
8. **绿色调度**：用两个地区的时变碳强度和网络成本，安排可延迟训练；证明在可靠性、数据驻留和检查点 RPO 约束下的可行解。
9. **论文审查**：选择一篇加速器、MoE、联邦或长上下文论文，填四张表并列出三条无法从论文推出的生产结论。
10. **迁移计划**：写一页从 shadow、1%、5%、25% 到 100% 的灰度门禁，包括自动回滚、人工复核和安全事件停机条件。

## 25.15 安全边界与伦理约束

新硬件和新协议不能绕过既有安全控制。加速器遥测、边缘日志、联邦更新和长上下文缓存可能包含个人数据、商业机密、位置、设备指纹或模型权重。只采集完成实验和审计所需的最小字段，访问按租户和研究角色隔离；不要把原始提示、图像、梯度或密钥放入高基数指标、公开 notebook 或论文附件。

隐私计算不是豁免。联邦训练仍需数据主体同意、删除和跨境政策；差分隐私的预算、邻接定义和会计假设应向数据控制者解释；安全聚合阈值不应为了吞吐被静默降低。对医疗、金融、身份、教育和政府场景，模型质量和人工复核门槛不得因边缘离线或功耗不足而消失。

边缘设备的 OTA、固件和驱动是安全关键路径。签名、回滚、最小权限、双分区和供应链证明要纳入发布；禁止用未验证的第三方 kernel、绕过安全启动或关闭审计来追求 benchmark。新型存算器件可能产生侧信道、故障注入和寿命问题，应在独立隔离环境测试。

长上下文扩大了提示注入和数据外泄面。检索、摘要和缓存都要标记来源、权限和过期时间；跨租户缓存必须证明隔离，无法证明时采用保守清空。对高影响建议，超时、内存超限或策略过期时应拒绝或转人工，不可静默使用旧模型和旧数据。

绿色优化也要公平。把可延迟训练迁移到低价时段不能牺牲低带宽地区的服务，也不能把噪声、热量或电子废弃物外部化给资源有限的社区。报告能耗时尽量披露测量误差、设备寿命和硬件制造边界，避免用单一碳数字做道德结论。

## 25.16 总结：前沿工作的可证伪链条

本章的核心方法可以压缩为一条链：先写真实工作单元和失败成本，再定位算力、带宽、容量、通信、隐私、功耗或碳的瓶颈；选择改变瓶颈的数据路径，定义固定基线和质量门槛；用分解 trace、重复实验和消融区分事实、研究结果、测量、设计判断和前瞻推断；在 shadow 流量、热稳态、故障注入、隐私攻击和长上下文切片上复现；最后把版本、manifest、回滚、观测和安全边界一起迁移到生产。

加速器的峰值、MoE 的激活参数、边缘的低延迟、联邦的留端、长上下文的窗口和绿色的低碳都只是局部属性。系统价值取决于端到端成功请求、质量、尾延迟、能耗、隐私和可恢复性。一个诚实的研究结论应同时告诉读者“在哪些条件下有效”和“在哪些条件下未知”。当证据不足时，最专业的答案不是补一个更大的数字，而是设计下一个能推翻自己的实验。
