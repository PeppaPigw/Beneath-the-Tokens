# 第21章　AI 可靠性工程：SLO、错误预算、重试、容错与灾备

> AI 系统的可靠性不是“服务返回了 200”这一种健康。一次回答可以在 HTTP 层成功，却读取了旧的检索索引；训练任务可以在调度器中显示为 Running，却把最后一个检查点截断成了不可恢复的半文件；重试可以把短暂网络错误变成请求风暴，也可以把一次扣费或一次数据写入执行两遍。本章把可靠性定义为一组可验证的用户和数据契约：在给定时间窗口和故障假设下，系统以足够的正确性、及时性、新鲜度和完整性完成工作，并且在失败时以有界的损失恢复。重点不在背诵某个云厂商按钮，而在于把契约、状态机、证据和回滚路径写出来。

本章沿用全书的证据标记。**事实**指标准、官方文档或论文直接支持的语义；**机制**指根据组件调用、数据流和状态转移还原出的因果链；**测量**指 CPU 实验在声明环境中的观测；**推断**指由测量和公式得到的结论；**设计判断**指在目标、约束和风险清楚时的工程建议。一个 toy 实验不证明生产集群的可用性，一个绿色探针不证明业务成功。每个承诺都应有对应的观测、故障演练和恢复证据。

## 21.1 为什么 AI 系统需要独立的可靠性工程

### 21.1.1 失败不只发生在进程层

传统 Web 服务常把失败理解成进程崩溃、连接超时或数据库错误。AI 系统增加了模型权重、分词器、KV cache、检索索引、GPU 显存、异步队列、长时间生成和训练状态。这些状态有不同的生命周期和恢复成本。一个推理副本可以继续接受请求，却在热更新后加载了错误的 tokenizer；一个 GPU 进程可响应健康探针，却因为显存碎片在长上下文请求上持续 OOM；一个训练 worker 可继续执行，却丢失了数据游标，重启后重复消费样本，导致指标看似平滑而数据统计已经偏移。

可靠性因此要同时看四类信号：服务是否回答、回答是否在时限内、回答是否满足任务正确性和策略、不可逆的副作用与状态是否只发生一次。设一次请求的业务结果为四元组 \(R=(a,t,q,i)\)，其中 \(a\) 是可达性，\(t\) 是时效，\(q\) 是质量或正确性，\(i\) 是完整性。只有当四个分量都通过门槛，才可把请求计入成功事件。**设计判断**：SLO 不能只使用进程级 uptime；必须至少在用户协议中声明业务成功和正确性如何被采样与审计。

### 21.1.2 可靠性是端到端属性

模型服务器、网关、向量库、对象存储、节点网络、GPU 驱动和训练数据源构成依赖图。一个组件的高可用不会自动相乘成端到端高可用。若请求必须同时通过五个独立依赖，每个依赖在窗口内可用率分别为 0.999、0.999、0.9995、0.999 和 0.999，且无冗余、无并行替代，理想串联系统的上限约为这些概率的乘积，已经低于任意单个组件的数字。真实系统还存在共因故障，例如同一可用区断电、同一镜像签名错误或同一配置推送导致所有副本异常，因此乘积只是粗略上界。

**机制**上，请求路径还包括排队和资源竞争。某个延迟正常的检索服务若在流量峰值时占满连接池，会让生成 worker 等待；重试又会把排队中的请求复制，进一步消耗 GPU。可靠性设计必须画出数据平面和控制平面：数据平面负责请求和张量，控制平面负责发布、扩缩容、证书、检查点索引和路由。控制平面失效时，已有数据平面是否继续服务、服务多久、以何种降级运行，是必须写出的故障模式，而不是留给默认配置。

### 21.1.3 “看起来健康”的失败

最危险的故障往往不是红色告警，而是结果仍然有值却已经失去契约。以下案例在值班页上可能全部显示绿色：

1. 探针只发送短提示词，GPU 对长上下文请求的显存泄漏没有触发。
2. 网关收到上游 200 就计算成功，忽略响应中的 `degraded=true`，把降级答案当作正常质量。
3. 检查点目录中有最新时间戳文件，但权重文件只写了一半，恢复代码自动回退到更旧版本却没有告警。
4. 重试中间件对 POST 请求没有幂等键，客户端看到一次超时，后端却执行了两次数据写入。
5. 错误率保持低位，因为客户端在达到超时后自行取消；服务器仍占用 GPU 完成被丢弃的生成。

每个案例都说明“指标没有错，指标覆盖的对象错了”。本章后文会要求为每个 SLI 写出排除条件、采样偏差和无法证明的事情。

## 21.2 前置知识、学习结果与一句话心智模型

读者应熟悉 Linux 进程、信号和文件系统，理解网络超时与队列，能阅读第10章的训练作业和第16章的模型服务状态机，并能使用第20章的指标、日志和 trace。无需先安装 Kubernetes、云数据库或 GPU；本章的实验使用 Python 标准库在 CPU 上演示相同的状态与故障逻辑。生产实现阅读部分会指向容器编排、对象存储和训练框架，但不把任何工具的默认行为当作可靠性保证。

完成本章后，读者应该能够：

- 从用户旅程定义可计算的 SLI，选择窗口、分母、排除项和采样方法；
- 从 SLO 推导每月或每个批次的错误预算，用它决定发布、实验和债务偿还节奏；
- 画出带超时、预算、幂等键和状态转移的重试路径，证明不会制造无限风暴；
- 解释熔断器何时打开、如何探测恢复、什么请求可以降级，以及舱壁怎样隔离 GPU、CPU 和租户；
- 检查一个检查点是否原子、可识别、可校验、与数据游标一致，说明恢复后可能重复或遗漏什么；
- 用 RTO（恢复时间目标）和 RPO（恢复点目标）选择备份、复制和演练频率；
- 为故障注入写出假设、停止条件、回滚动作、观测指标和安全边界。

一句话心智模型：**把一次 AI 工作看作一条带版本状态的有向路径；可靠性工程就是给路径上的每个状态转移设定可观测契约、有限重试和可逆恢复，并用故障演练证明损失不会超出预算。**

后文将使用符号。请求数为 \(N\)，成功事件数为 \(S\)，失败事件数为 \(F=N-S\)；窗口长度为 \(W\)；错误预算为 \(B\)；单次操作的幂等键为 \(k\)；重试次数为 \(r\)；指数退避初始等待为 \(d_0\)，上限为 \(d_{max}\)，抖动随机量为 \(J\)。每次使用符号都会先说明其意义，不把 SLO 的百分比、延迟分位数和业务质量混成一个数字。

## 21.3 SLI、SLO、SLA 与错误预算的第一性原理

### 21.3.1 先写事件，再写百分比

服务等级指标（Service Level Indicator，SLI）是一个可计算的比值、分布或集合属性。对在线生成服务，成功率 SLI 可以定义为

\[
SLI_{success}=\frac{\#\{请求满足业务成功条件\}}{\#\{纳入统计的请求\}}。
\]

业务成功条件至少包含：请求被授权、模型版本正确、输出在截止时间内、输出格式和安全策略通过、依赖数据新鲜度满足要求。分母要写清楚是否包含客户端取消、超载拒绝、已知非法输入和维护窗口。若把所有 4xx 都排除，攻击流量和误用就可能被人为移出分母；若把明显无效的请求纳入，服务团队又会为用户错误承担不合理预算。**设计判断**：排除项必须可审计、稳定并在 SLA 中公开，不能在事故发生后才修改。

延迟 SLI 不是“平均响应时间”。可为每个请求记录是否在阈值 \(T_{target}\) 内：

\[
SLI_{latency}=\frac{\#\{T_i\leq T_{target}\}}{N}。
\]

流式生成还应分别定义首 token 延迟（TTFT）、每 token 间隔（ITL）和完成时间。短请求快速返回会掩盖长上下文的 p99；只看 p50 会把少数但重要的超时视为噪声。对长任务和训练作业，可把“在截止时间前产生有效检查点”或“恢复后丢失的有效工作不超过目标”作为事件型 SLI。

### 21.3.2 SLO 是目标，SLA 是外部承诺

服务等级目标（SLO）是工程团队在窗口内希望达到的内部目标，例如一个月内 99.9% 的有效请求在 2 秒内返回第一个 token，且格式校验通过。服务等级协议（SLA）是对外承诺，通常还包含补偿、责任范围和维护条款。SLO 可以比 SLA 严格，以便为发布和异常留出缓冲；把二者写成同一个数字会让团队在内部目标被击穿前没有操作空间。

延迟目标要绑定请求类别。把聊天、批量摘要、工具调用和长上下文放在同一个 SLO，服务会通过拒绝长请求“优化”数字。更好的做法是按租户、模型、上下文长度、优先级和是否流式分桶，每桶单独计算分子和分母，再报告全局加权结果。分桶不应成为掩盖问题的手段；必须同时报告总体成功率和最高流量桶的尾部。

### 21.3.3 错误预算的推导与使用

如果目标可用性为 \(A\)，窗口内预算近似为 \(B=(1-A)\times W\)。例如 30 天窗口约有 43200 分钟，99.9% 目标允许约 43.2 分钟的不可用或不满足条件的时间。对请求型指标，若分母为 \(N=10^7\)，99.9% 目标允许约 10000 个失败事件。预算单位必须与 SLI 一致，不能拿分钟预算直接抵扣质量错误或数据丢失，除非协议明确规定转换。

预算的价值不只是“还有多少分钟”。它是发布与风险的控制信号：预算充足时，团队可在隔离环境进行压力测试和渐进发布；预算快速消耗时，暂停高风险变更，优先修复回归和增加容量。**设计判断**：错误预算政策应提前写出自动动作、人工阈值和豁免理由。例如，连续一个小时消耗掉日预算的 50% 时停止扩大灰度；达到月预算的 100% 时进入变更冻结，除安全修复和恢复动作外不再发布。

一个常见误解是“预算归零后只要等窗口滚动即可”。如果根因仍在，滚动窗口会让新预算很快耗尽；如果把预算用于未经控制的混沌实验，用户流量可能受到不必要影响。实验应使用独立的合成 SLI 或标记流量，并把用户预算和实验预算分开计量。

### 21.3.4 可靠性与质量的二维平面

模型服务至少有两个轴：系统可靠性和模型输出质量。系统可靠而质量错误，用户仍然受损；质量高但经常超时，用户也无法使用。可以把请求分类到二维矩阵：及时且正确、及时但错误、超时但最终正确、超时且错误。指标面板要保留四格计数，不要只显示“成功/失败”一个布尔值。安全拒答、策略降级和检索过期也要有显式类别。

对质量 SLI，随机抽样人工评审、规则验证、结构化字段校验和离线回放各有偏差。人工评审成本高、延迟大；规则验证覆盖窄；离线回放不能代表实时依赖和提示注入。**设计判断**：将质量 SLI 分为快速门禁和慢速审计两层，快速层阻止明显格式与安全错误，慢速层用带版本的抽样和盲评估校准快速层的误报与漏报。

## 21.4 从请求到硬件：可靠性控制流

### 21.4.1 预算必须沿调用链传播

一次在线请求可能经过客户端、边缘网关、鉴权、路由、检索、模板渲染、模型 prefill、decode、内容过滤和计费。若每层都使用独立的 30 秒超时，失败请求会在后端继续运行数分钟。正确做法是给请求携带截止时间 \(D\)，每个子调用计算剩余时间 \(D-now-\epsilon\)，其中 \(\epsilon\) 是序列化和回收余量。子调用超时必须触发取消，释放 GPU、连接和队列槽位。

**机制**上，超时传播需要同时经过线程、协程、RPC 和 kernel 边界。很多 GPU kernel 不能在任意指令处安全取消；服务层的取消信号可能只能阻止下一个 decode step，已提交的 kernel 仍要完成。**设计判断**：为每个阶段记录“可取消点”和最坏清理时间，并在 admission control 中预留这段时间。若无法可靠取消，应把请求隔离到有界队列，避免被取消请求拖垮活跃请求。

### 21.4.2 资源舱壁和公平性

舱壁（bulkhead）把资源划分成互不吞噬的池。例如把长上下文、短聊天、批处理和管理请求放入不同的 GPU worker 池或 CPU 线程池；为每个租户设置并发、KV 页和带宽配额。没有舱壁时，一个租户上传超长文档即可占满 KV cache，让所有租户的 p99 变差。

舱壁不是简单的进程数量。还要隔离对象存储、网络连接、日志写入、编译缓存和检查点带宽。**反例**：聊天 worker 与训练数据预取使用不同 Deployment，CPU 和 GPU 指标看似隔离，但共享同一块节点本地盘；训练预取写满磁盘后，聊天服务无法创建临时文件，两个池仍然互相影响。资源图必须包含共享硬件和控制面依赖。

### 21.4.3 降级的契约

降级不是把任意错误文本返回给用户。一个可验证的降级结果应带有模式、版本和原因，例如使用缓存回答、较小模型、无检索回答、同步转异步任务或明确拒绝。客户端需要知道结果是否可用于自动决策；下游写入应拒绝把 `degraded=true` 当作正常证据。

设计降级路径时要回答四个问题：哪类故障触发；最大持续时间；哪些用户或请求不允许降级；恢复后如何重新验证。若模型版本加载失败而回退到旧模型，必须在响应元数据和审计日志中记录版本，不能静默改变行为。金融、医疗、身份和权限判断等高影响场景应优先拒绝或转人工，而不是无提示地降级。

## 21.5 重试、幂等性、超时与退避

### 21.5.1 重试解决什么问题

重试只能解决部分瞬态失败，例如连接重置、短暂 503、节点迁移或可恢复的限流。它不能修复确定性 bug、无效输入、权限拒绝、数据校验失败或已耗尽配额。先按错误类别建立重试矩阵：可重试、不可重试、需要人工检查、可改用降级路径。任何“遇到异常就重试”的通用装饰器都把业务语义丢掉。

重试增加的是系统尝试次数，不是成功概率的免费倍增。若单次调用失败概率为 \(p\)，最多尝试 \(r+1\) 次且各次独立，理论成功概率是 \(1-p^{r+1}\)；实际故障往往相关，所有副本可能同时受同一配置或区域问题影响。更重要的是，后端负载约按尝试次数增加。若每个客户端以速率 \(\lambda\) 发送，平均尝试次数为 \(E[K]\)，后端到达率约为 \(\lambda E[K]\)。当错误由过载引起时，重试会形成正反馈。

### 21.5.2 幂等键和状态机

幂等意味着同一个逻辑操作执行一次或多次，最终外部状态相同。最实用的实现是让调用方生成唯一幂等键 \(k\)，服务端在持久存储中记录 \(k\)、请求摘要、状态和结果。第一次请求进入 `PENDING`，成功后变为 `COMMITTED`，确定失败变为 `FAILED`；再次收到同一 \(k\) 时，如果摘要不一致则拒绝，摘要一致则返回已记录状态或结果。

幂等键记录必须有生命周期。过期太快会让延迟重试重复执行；保存太久会占用存储并阻止合法的新操作。生命周期应覆盖最大客户端重试窗口、消息重复投递窗口和灾难恢复的回放窗口。键值存储的写入也需要原子条件，例如“仅当不存在时创建”；先查询再写入会产生竞态。

**例子**：将一批训练样本写入特征库时，`batch_id` 可作为幂等键，但只有在输入清单摘要、schema 版本和目标分区一致时才可复用。若同一批次被重新计算出不同摘要，服务必须标记冲突并停下来，不应悄悄覆盖。

### 21.5.3 超时分层

连接超时、请求超时、阶段超时和总截止时间是不同概念。连接超时限制建立连接，读取超时限制一次读操作，请求超时限制一次 RPC，总截止时间限制整条调用链。只有设置总预算，才能阻止多个串联重试突破用户期望。每层应记录配置值和实际消耗，避免把一个“30 秒超时”误读为总耗时上限。

超时不是可靠恢复。超时后，服务器可能仍在执行；客户端重试会造成并发重复。对不可中断的操作，先设计查询状态接口，采用“提交返回操作 ID，后台执行，查询结果”模式。提交阶段使用幂等键，查询阶段可安全重试。对生成请求，应在取消后等待 worker 确认释放 KV 页，再把槽位重新分配。

### 21.5.4 指数退避与抖动

指数退避可写成 \(d_i=\min(d_{max},d_0 2^i)\)，其中第 \(i\) 次重试的基础等待不超过上限。抖动让客户端在一个区间随机等待，例如全抖动 \(D_i\sim Uniform(0,d_i)\)，避免大量客户端同时醒来。还要设置单请求重试预算 \(R_{retry}\) 和全局预算，不能仅依赖次数。若剩余截止时间小于等待和最小处理时间，则立即失败或降级。

**测量建议**：记录首次尝试和每次重试的原因、等待时间、结果、幂等键、租户和剩余预算。只看最终成功率会漏掉重试风暴；必须同时看尝试率、重试放大倍数、后端队列、拒绝数和副作用冲突数。把重试次数作为高基数标签直接放入指标可能造成监控成本，应在日志和直方图中采用有界桶。

## 21.6 熔断器、限流、舱壁和负载 shedding

### 21.6.1 熔断器的状态机

熔断器（circuit breaker）保护调用方不持续撞击已失败的依赖。最小状态包括 `CLOSED`、`OPEN` 和 `HALF_OPEN`。`CLOSED` 统计滑动窗口内的失败率、超时率或连续失败数；达到阈值后进入 `OPEN`，快速拒绝或转降级；经过冷却时间后进入 `HALF_OPEN`，只允许少量探测；探测成功则回到 `CLOSED`，失败则回到 `OPEN`。

阈值不能只写一个百分比。低流量时 100% 失败可能只是一次请求，若立即熔断会造成抖动；高流量时 5% 的尾部失败可能已经耗尽预算。应同时设置最小样本数、连续失败上限、冷却时间、半开并发、最大打开时间和按错误类别的白名单。探测必须使用真实但无副作用的请求，不能拿未认证的空请求证明业务依赖健康。

熔断器是调用方本地状态，多个副本会各自决定，可能造成同步振荡。全局限流和共享错误信号可以改善，但也引入控制面依赖。**设计判断**：先用本地熔断保护线程和连接，再用网关或服务网格做粗粒度全局预算；不要把所有实时决定都集中到一个可能成为单点的控制器。

### 21.6.2 限流与负载 shedding

限流控制进入系统的速率或并发。令牌桶按速率 \(\rho\) 产生令牌、桶容量为 \(C\)，允许短时突发但限制长期平均；漏桶以固定速率处理，延迟更可预测。并发限流直接限制活跃请求数量，适合 GPU decode 和 KV 页这类容量受限资源。速率限流和并发限流不能互相替代：长请求会在低速率下仍占满并发。

负载 shedding 是在系统已接近饱和时主动拒绝低优先级工作，以保住高优先级 SLO。拒绝应快速、可解释并带重试提示；若客户端立即无抖动重试，shedding 反而变成风暴。可以按租户、请求类型、上下文长度和截止时间做准入，优先保留有足够剩余预算且可在 deadline 前完成的请求。

### 21.6.3 让流式服务可回收

流式输出把一次请求变成多次发送和多个可能的取消点。代理断开后，服务器必须收到取消、停止新的 decode step、释放 KV 页、归还并发额度并记录终止原因。只在 HTTP 写失败时记录错误，而不释放模型状态，会形成隐形资源泄漏。

**失败看起来健康**：网络层显示客户端断开率很低，因为代理重用连接；GPU 显存和 decode 队列却持续增长。修复应在 worker 内部记录活动请求的最后心跳、客户端取消、阶段完成和资源回收，并设置孤儿请求的硬上限。回收动作也要幂等，重复取消不能把共享前缀或其他租户的页释放两次。

## 21.7 检查点完整性：从“有文件”到“可恢复状态”

### 21.7.1 检查点的组成

训练检查点不是一个权重文件，而是一个状态快照。至少包括模型参数、优化器状态、学习率调度器、随机数状态、数据分片游标、全局 step、配置和代码/数据版本摘要。推理服务的模型工件还需要 tokenizer、量化校准摘要、engine 或编译缓存信息。缺少任何会影响语义的成员，恢复后都可能得到“可运行但不可继续”的状态。

把检查点写成目录或对象前缀时，要区分临时前缀和已提交前缀。例如先写入 `step-100.tmp-uuid` 下的所有对象和 manifest，再计算每个分片的大小与校验和，最后用原子 manifest 或指针更新把它发布为 `step-100`。读者只信任 manifest 中列出的对象和整体摘要，不按目录时间戳猜测最新状态。

### 21.7.2 原子性、校验和与一致性

文件系统上的原子 rename 只保证同一文件系统和元数据语义下的名字切换；跨挂载点、对象存储前缀或分布式文件系统不一定具有相同保证。对象存储的分片上传也可能先可见部分对象，再最终提交。**事实**：具体一致性和条件写语义随存储产品和 API 版本变化，必须以目标平台文档为准。**设计判断**：用带版本和条件匹配的 manifest 指针，写入后读回验证，并在恢复前对每个分片做长度和强校验和检查。

校验和只能发现传输或存储中的比特变化，不能证明权重来自可信构建、配置与权重匹配或模型质量正确。应同时记录内容摘要、签名、来源身份、生成代码提交、数据集版本和评估结果。若摘要不匹配，恢复流程应停止或转入明确的旧版本回退，而不是“尽力加载”。

### 21.7.3 分布式检查点的一致切片

数据并行训练中，每个 rank 可能拥有不同的 optimizer shard 和数据游标。若 rank 0 先发布 manifest，而其他 rank 仍在写入，恢复时会读到混合 step。可以使用两阶段提交：第一阶段所有 rank 写临时 shard 并发送完成标记；协调者验证 rank 数、shape、dtype、摘要和 step 全部一致；第二阶段发布提交记录。协调者故障时，旧 manifest 仍有效，新临时目录由垃圾回收器按租约清理。

“最后一个完成的 rank”不等于“最后一个安全检查点”。慢 rank 可能持有更晚的数据游标，快 rank 若提前发布会造成重复或遗漏。训练恢复策略要声明是允许最多重复 \(D\) 个样本、允许丢失哪些未提交样本，还是必须达到近似 exactly-once。后者成本很高，通常需要外部事务日志和可重放数据，不能靠 `torch.save` 文件名实现。

### 21.7.4 检查点恢复演练

恢复演练至少注入四种故障：写入中断、单分片截断、manifest 损坏、发布后部分副本不可读。演练要测量 RTO、恢复后 step、重复样本数、丢失样本数和评估指标漂移。一个只测试“进程能启动”的演练没有证明训练状态正确。

## 21.8 混沌工程与故障注入

### 21.8.1 混沌实验的假设结构

混沌工程不是随机破坏生产，而是用可控实验验证系统在已知故障下是否满足稳态假设。每个实验应写出：

1. 稳态假设，例如“99% 有效请求在两秒内得到首 token，重复副作用为零”。
2. 故障注入，例如杀死一个模型副本、延迟检索 500 毫秒、截断临时检查点或撤销一个网络路径。
3. 观测窗口和样本量，包含基线、注入期和恢复期。
4. 停止条件，例如用户错误预算消耗超过实验预算、GPU 温度或队列超过安全阈值。
5. 回滚与清理动作，确保实验结束后没有残留规则、脏对象或已损坏的副本。
6. 证据位置：指标、trace、日志、检查点 manifest、事件时间线和复盘结论。

“随机杀 Pod”只有在明确副本、状态、重试、预算和停止条件后才是有意义的实验。实验不能绕过安全、隐私或数据删除控制；生产注入需要变更审批和可见的责任人，普通用户流量不应被当作免费测试数据。

### 21.8.2 故障模型覆盖范围

AI 服务常见故障模型包括：进程崩溃、GPU Xid 或显存不足、节点断电、网络分区、DNS 延迟、对象存储读写错误、依赖返回慢但不报错、错误配置全量发布、模型工件损坏、时钟漂移、队列消息重复、租户突发流量和控制面不可用。每种故障都要说明检测延迟、是否可重试、状态是否持久、恢复时可能重复什么。

故障注入的粒度从函数级异常到区域级隔离逐渐扩大。先在单元和集成测试中注入确定性异常，再在隔离环境验证控制器和备份，最后进行小流量生产演练。跨区域演练成本高、风险大，必须先证明依赖清单、DNS、证书、身份和数据复制都能在预定 RTO 内切换。

### 21.8.3 负面结果同样重要

如果实验没有触发告警、队列保持稳定、恢复比预期更快，这是结果而不是“没有发生什么”。要记录实际注入是否成功、是否命中正确路径、是否有无意的旁路。一个注入网络延迟却未改变任何请求，可能是流量没有经过被注入的接口；一个杀掉 worker 却没有看到失败，可能是请求都在另一个池。

## 21.9 灾难恢复：RTO、RPO 与依赖图

### 21.9.1 两个目标的定义

RTO 是从灾难发生到恢复服务或关键功能的最大允许时间。RPO 是可接受的数据回退窗口，即灾难后最多丢失多长时间内已确认的数据或进度。若训练每小时上传一次检查点，理论 RPO 至少接近一小时，还要加上传和发现故障时间；若只复制模型权重而不复制数据游标，权重 RPO 很小，训练语义 RPO 仍然很大。

RTO 和 RPO 是业务选择，不是存储系统的默认数字。热备份降低 RTO 但持续消耗 GPU 和同步带宽；异步跨区域复制降低主路径开销，却使 RPO 依赖复制延迟；冷备份便宜，但恢复需要拉取镜像、权重、tokenizer、索引和权限配置。应按功能分级：在线生成、批处理、训练、审计日志和离线评估通常有不同目标。

### 21.9.2 依赖清单和恢复顺序

灾备计划要列出代码镜像、模型权重、tokenizer、量化 engine、配置、密钥引用、数据库 schema、向量索引、对象存储、DNS、证书、监控和人工联系人。恢复顺序通常是：建立身份和网络边界，验证镜像和工件签名，恢复元数据和 manifest，恢复或重建索引，启动最小数据平面，执行能力探针和质量探针，逐步放量。先启动模型副本而没有正确的 tokenizer 或权限，会产生看似成功却无法解释的输出。

控制面与数据面要分别演练。即使 Kubernetes API 或发布系统不可用，已运行的服务是否能继续处理现有请求？若不能，用户需要看到明确维护状态，而不是无限重试。恢复脚本必须可重复执行，使用版本化输入和幂等操作；手工复制文件和临时改 DNS 可能让第二次演练无法复现。

### 21.9.3 恢复后的验证

恢复成功不是端口打开。验证至少包括：路由到正确版本，读取一组已知输入得到期望摘要或质量范围，检查检索新鲜度和权限隔离，提交一个带幂等键的合成请求，确认取消和回收，读取最近一个检查点并比较 step、shape、dtype、摘要和数据游标。最后要确认观测、告警和审计仍然写入正确目的地，否则系统会在下一次故障中再次失明。

## 21.10 最小实现：CPU 故障恢复 toy

本章提供 `ch21_reliability_lab.py`，只使用 Python 标准库，模拟一个带幂等键的任务提交器、随机瞬态故障、指数退避、熔断器和带 manifest 的检查点。它不是生产队列、数据库或分布式锁的替代品，而是把状态转移暴露出来，方便逐行观察。

### 21.10.1 模型与代码路径

实验任务把整数区间切成批次。每个批次有 `batch_id`、输入摘要和输出摘要。提交器先以条件写入的方式记录 `PENDING`，调用 worker；worker 可能在“写结果前”或“写结果后”注入异常。写前异常可安全重试，写后异常必须依赖幂等键查询，避免再次产生副作用。成功后写入 `COMMITTED` 并更新 manifest。熔断器在连续失败达到阈值时打开，冷却后允许半开探测。

检查点写入临时目录，内容包括当前 step、已提交批次列表、配置摘要和每个文件的 SHA-256。写入中断时不发布 manifest；恢复器只接受完整 manifest，验证所有文件长度与摘要，并从最后一个提交批次继续。实验会刻意截断一个临时文件，观察恢复器拒绝它而不是静默加载。

### 21.10.2 运行方法

在仓库根目录运行：

```bash
python3 ch21_reliability_lab.py --seed 7 --batches 12 --fail-before-commit 0.18 --fail-after-commit 0.12 --checkpoint-every 3
```

脚本输出每批次的尝试数、最终状态、重试等待、熔断状态、检查点 step、恢复起点和重复副作用计数。可改变 `--fail-before-commit` 与 `--fail-after-commit`，比较“写前失败可重试”和“写后失败必须幂等”的差异；设置 `--truncate-checkpoint` 验证校验和保护；设置较小的 `--breaker-threshold` 观察熔断和半开。

**测量**应记录：成功批次比率、总尝试次数、重试放大倍数 \(E[K]\)、平均和最大恢复时间、RPO（最后提交 step 与故障 step 的差）、重复副作用数、熔断打开时长和被快速拒绝的请求数。**推断**：如果写后失败没有增加重复副作用，说明幂等记录覆盖了重试窗口；这不证明真实数据库的事务和网络分区语义，仍需在目标存储上做集成测试。

### 21.10.3 期望观察与解释

当 `fail-before-commit` 较高时，尝试次数增加但提交批次数不应重复；若所有请求都在写前失败，熔断器应在阈值后快速拒绝，降低后端负载。提高 `fail-after-commit` 会看到“客户端认为失败、服务端已提交”的事件；幂等键查询应返回已提交结果，而不是再执行。截断检查点后，恢复器应选择上一个完整 manifest，RPO 等于未发布的批次数。

一个常见误读是把“零重复副作用”理解成 exactly-once。toy 的副作用记录在同一个进程内存和本地文件中；真实系统还需面对数据库提交成功但响应丢失、跨区域复制延迟、时钟和租约过期。实验只证明状态机的必要条件，不证明所有外部系统的充分条件。

## 21.11 生产实现阅读：把控制面承诺对齐到组件

### 21.11.1 Kubernetes 与服务编排

Kubernetes 的 liveness、readiness 和 startup probe 目的不同。liveness 失败可能触发重启，readiness 失败只应把实例从流量中摘除，startup 保护长时间加载模型的初始化。若把昂贵的生成请求放进 liveness，模型慢就会被反复杀死；若 readiness 只检查端口，未加载权重的副本会收到流量。探针要包含版本、权重摘要、基本推理和资源回收检查，但要设置严格超时，避免探针本身成为负载源。

Deployment 的滚动更新保证 Pod 替换策略，不保证模型质量、检查点完整性或跨区域 RPO。PodDisruptionBudget 可限制自愿中断，却不能阻止节点断电或区域故障。GPU 节点升级前应把实例摘流、等待请求和 KV 回收、验证新 Pod 能力探针，再逐步恢复。发布控制器必须把 SLO 和错误预算信号接入，而不是只看 ReplicaSet 是否 Available。

### 21.11.2 训练框架与检查点

训练框架通常提供保存和加载 API，但完整恢复依赖应用自己保存 optimizer、调度器、随机状态和数据游标。分布式 sharded checkpoint 需要记录 world size、rank 映射、参数分片规则和版本；改变并行策略后能否重分片是能力问题，不应靠文件名猜测。恢复后应先用小批次 replay 检查损失、梯度范数和数据顺序，再继续长任务。

抢占、抢修和自动重启会放大检查点频率与 I/O 带宽。把检查点写在训练关键路径上，可能让 GPU 长时间空转；异步保存需要复制或冻结一致的参数视图，否则保存的不同分片来自不同 step。设计判断是为检查点设置 I/O 舱壁和优先级，并把“可恢复但稍旧”的策略和“阻塞训练直到提交”的策略分别计入 RPO 与吞吐预算。

### 21.11.3 对象存储、队列和数据库

对象存储适合大权重和不可变工件，但要使用版本、条件写和完整性摘要；队列通常至少一次投递，消费者必须幂等；数据库事务可以保证一组记录的原子性，却不能自动包住 GPU 计算和外部对象。跨系统工作流应使用 outbox、状态表或可重放事件，把“计算完成”和“副作用提交”分开。

不要把消息队列的 offset 当成业务提交点。消费者先提交 offset 再写结果会丢失；先写结果再提交 offset 会重复。正确方案是结果写入使用幂等键，offset 提交可以重复，恢复时重复消费只返回已提交状态。若结果本身不能幂等，应采用支持事务的消息与存储组合，或把任务改成查询型异步操作。

### 21.11.4 观测与事件时间线

可靠性指标需要关联请求 ID、幂等键摘要、模型版本、检查点 manifest、租户和故障事件。高基数内容（完整提示词、权重路径、用户数据）不应直接作为指标标签，避免泄露和成本爆炸；可在受控日志中记录脱敏摘要。事件时间线要同时显示客户端、网关、worker、依赖和存储的时钟，处理时钟漂移和延迟写入。

## 21.12 失败诊所：十个反例与修复

### 21.12.1 重试把过载变成雪崩

现象：依赖响应慢，客户端超时后重试，网关 QPS 翻倍，GPU 队列持续增长。根因：没有全局尝试预算和并发限流，所有实例使用同一退避时间。修复：按错误类别重试，传播 deadline，使用全抖动，设置总重试预算和负载 shedding，监控放大倍数。

### 21.12.2 POST 重复扣减配额

现象：用户看到一次超时但配额减少两次。根因：服务端没有幂等键或键在响应前才写入。修复：请求入口生成或验证键，条件创建 `PENDING`，提交与结果绑定，重试先查询状态；对冲突摘要返回明确错误。

### 21.12.3 熔断器永远半开

现象：探测请求成功，真实大 batch 仍失败；熔断器反复关闭和打开。根因：半开只允许短探针，未覆盖主要形状和租户资源。修复：分桶探针，限制半开并发，记录探针形状与资源峰值，按错误类型和样本量决定回闭。

### 21.12.4 检查点时间戳最新但不可读

现象：恢复脚本挑到最新目录，读取某 rank 分片时报 EOF。根因：把目录可见时间当提交协议。修复：临时前缀、完整 manifest、长度和摘要验证、原子指针发布，恢复时选择最后一个完整版本并告警。

### 21.12.5 质量错误未计入 SLO

现象：格式错误和过期检索答案比例上升，但可用率仍为 99.99%。根因：SLI 只统计 HTTP 200。修复：把业务成功条件写成结构化事件，单独统计质量和新鲜度，抽样校准自动规则。

### 21.12.6 取消后 KV 未回收

现象：客户端取消率正常，显存逐渐耗尽，长请求 OOM。根因：取消信号未到达 decode worker，或共享页引用计数错误。修复：显式取消确认、孤儿请求硬上限、页回收审计、定期泄漏测试；将释放动作设计为幂等。

### 21.12.7 灾备只复制权重

现象：区域切换后模型能启动，但训练指标跳变、检索结果为空。根因：未复制 tokenizer、索引、数据游标和配置。修复：用依赖清单和 manifest 描述可运行工件，按顺序恢复并执行已知输入探针，记录实际 RPO。

### 21.12.8 混沌实验破坏生产预算

现象：注入延迟没有停止条件，用户错误预算被消耗完。根因：把“实验成功”定义为故障可见，而未定义用户安全边界。修复：独立实验流量、预算、责任人和自动停止，先在隔离环境复现，实验后验证规则清理。

### 21.12.9 训练异步检查点损坏

现象：GPU 利用率高，恢复后某些 rank 的 loss 异常。根因：保存时参数视图被下一 step 修改，分片来自不同逻辑时刻。修复：冻结一致快照或使用框架保证的异步快照，提交前校验 step 和跨 rank 摘要。

### 21.12.10 告警绿色但控制面失明

现象：数据平面仍返回缓存结果，监控和审计日志无法写入；故障持续到缓存过期才被发现。根因：只监控数据面，不监控观测依赖和控制面。修复：为指标、日志、trace、配置、证书和告警通道设置 SLO，加入合成事件和“观测不可用”告警。

## 21.13 权衡与拒绝的替代方案

### 21.13.1 “所有请求无限重试”

拒绝理由：无法证明副作用安全，放大过载，延迟无上界。替代方案：按操作类型划分重试矩阵，使用幂等键、deadline、抖动和预算；不可重试操作改成异步状态查询。

### 21.13.2 “提高副本数就可靠”

拒绝理由：共因故障、错误配置、共享节点、共享存储和容量不足不会因副本数自动消失。替代方案：拓扑分散、舱壁、独立工件、分级降级和演练；对关键依赖设置冗余但明确故障域。

### 21.13.3 “检查点越频繁越安全”

拒绝理由：I/O 争用会降低有效训练吞吐，异步写不一致会制造伪安全。替代方案：依据抢占率、恢复成本和 RPO 计算频率，进行带宽预算和恢复演练；保留少量经过验证的完整版本。

### 21.13.4 “混沌就是随机杀实例”

拒绝理由：随机并不等于有证据，可能没有命中关键路径或越过安全边界。替代方案：稳态假设、最小故障、明确停止条件、可回滚注入和可审计结果。

### 21.13.5 “exactly-once 可以靠消息队列开关”

拒绝理由：跨网络、存储和副作用的端到端 exactly-once 很难，队列的投递语义不能包住外部系统。替代方案：至少一次投递加幂等提交、事务 outbox、可重放事件，或者接受并量化重复与丢失边界。

## 21.14 论文、规范与仓库综合

Google 的 SRE 书籍和《Site Reliability Engineering Workbook》提供 SLI、SLO、错误预算和基于预算的发布治理框架；它们强调用户旅程和可操作的指标，而不是机器健康计数。Brandon Gregg 等人的尾延迟和排队分析提醒我们，平均值无法代表共享资源在高分位的体验。论文《Exponential Backoff and Jitter》类的工程实践说明，随机抖动是避免同步重试的重要机制，但具体窗口仍需结合服务容量测量。

分布式系统教材对幂等、至少一次投递、日志和一致性边界的讨论说明，消息重复是正常故障模型，不是罕见例外。两阶段提交、事务 outbox、补偿事务和可重放事件各有成本，不能把“恰好一次”当成 API 语法。可靠性设计应先明确业务能接受的重复、丢失和乱序，再选择机制。

训练系统和检查点仓库的共同启示是：保存模型参数只是最小子集，恢复需要 optimizer、随机状态、数据分片和版本元数据；分片格式和并行策略必须写进 manifest。Kubernetes、Ray Serve、TensorRT-LLM、vLLM 等官方文档可用来确认探针、滚动、批处理和恢复选项的版本语义，但不能替代在目标硬件、模型和流量上的演练。阅读仓库时优先查找状态机、持久化边界、超时默认值、重试条件、版本矩阵和测试中的故障注入。

**研究方法**：对每条外部声明保留来源、版本和访问日期；把“文档写明”与“本实验测得”分开。若源码与文档冲突，先记录版本和最小复现，再在升级决策中锁定行为。没有可复现环境时，将结论标为未知，不用个人经验填空。

## 21.15 六个理解检查（含答案）

### 检查一：为什么 99.9% 可用率不能代表回答可靠？

**问题**：服务一个月 99.99% 的 HTTP 200，但 2% 的响应使用过期索引，另有 0.5% 的 JSON 字段不符合协议。可以宣称满足业务 SLO 吗？

**答案**：不能。HTTP 200 只是可达性事件，业务成功还需新鲜度和格式正确。应把有效请求定义、分桶和质量 SLI 纳入分子，重新计算错误预算；如果质量采样不是全量，必须报告抽样置信度和漏检边界。

### 检查二：重试放大倍数如何计算？

**问题**：客户端原本每秒发送 100 个请求，平均每个请求尝试 1.4 次。后端实际收到多少尝试每秒？

**答案**：约 140 次每秒，放大倍数为 1.4。真实系统还要区分被本地限流、网关重试和下游重试的多层放大，并监控相关故障下的峰值，而不能只看平均。

### 检查三：写后超时为何不能盲目重试？

**问题**：数据库写入已提交，但响应在网络中丢失。客户端超时后再次提交，怎样避免重复？

**答案**：第二次请求必须携带同一幂等键和相同摘要；服务端以原子条件记录键和状态，查询到 `COMMITTED` 就返回已有结果，摘要不一致则拒绝。没有持久幂等记录时，客户端无法区分“未执行”和“已执行但响应丢失”。

### 检查四：熔断器为何需要最小样本数？

**问题**：只有一个请求失败就按失败率 100% 打开熔断器，会有什么问题？

**答案**：低流量下单次偶发错误会造成误熔断，流量在开关之间抖动。最小样本数、连续失败阈值和冷却时间能减少这种噪声；高影响依赖仍可用单次致命错误直接保护，但必须单独定义错误类别。

### 检查五：RTO 与 RPO 如何影响检查点频率？

**问题**：训练任务最多容忍 15 分钟工作丢失，恢复环境启动需 10 分钟。检查点每小时一次是否满足目标？

**答案**：通常不满足。检查点间隔至少要小于 15 分钟，还要扣除上传、发现故障和复制延迟；RTO 还要求恢复脚本、镜像和工件在 10 分钟内可用。应在真实存储上测量端到端恢复，而不是只看上传时间。

### 检查六：混沌实验的成功标准是什么？

**问题**：杀死一个模型副本后，其他副本继续返回 200，就能判定实验成功吗？

**答案**：不能仅凭 200。要验证稳态假设，包括 p99、质量、新鲜度、错误预算消耗、重试放大、状态恢复和副本重建时间；还要确认故障确实命中目标路径，且实验结束后注入规则和临时资源已清理。

## 21.16 练习：从回忆到设计

1. **回忆**：列出一次流式生成请求的至少六个阶段，并为每阶段写出可取消点和最坏清理动作。
2. **推导**：给定 30 天窗口、99.95% 成功 SLO 和 2,000,000 个纳入请求，计算请求错误预算，并设计一个按小时滚动的预算消耗告警。
3. **实现**：扩展 CPU toy，加入两种租户和并发限流；测量无舱壁与有舱壁时高负载租户对低负载租户 p95 的影响。
4. **诊断**：构造“客户端错误率低、后端重试率高、GPU 队列增长”的时间线，判断是超时传播、重试风暴还是观测缺失，并写出三条可证伪假设。
5. **检查点实验**：让一个 rank 在 manifest 发布前崩溃，验证恢复器不读取混合 step；再让恢复器从上一个完整版本继续，记录 RPO 和重复数据量。
6. **设计**：为包含检索、生成和审计写入的医疗摘要服务写 SLI/SLO、降级和安全边界；明确哪些结果必须转人工，哪些日志不能包含原始敏感文本。
7. **灾备演练**：画出区域故障依赖图，标注每个工件的复制方式、RPO、RTO、负责人和验证探针；说明控制面不可用时数据面是否继续服务。
8. **审查**：选择一个常用 Serving Engine，阅读指定版本的重试、健康探针、检查点或模型加载文档，找出至少三个默认值，并在目标版本上用实验确认其中两个。

## 21.17 安全边界与伦理约束

可靠性机制不能成为绕过安全控制的借口。幂等日志、请求摘要、检查点和故障事件可能包含用户输入、模型输出、租户标识或训练数据线索；应最小化采集、脱敏、加密并限制访问。不要把完整提示词、医疗文本、凭证或密钥写进高基数指标和公共日志。故障注入不得在未经授权的系统、第三方租户或高影响决策链上执行。

降级模型、缓存答案和跨区域副本会扩大数据传播范围；在恢复计划中明确数据驻留、删除、保留期和密钥可用性。若系统用于医疗、金融、身份、教育或政府决策，可靠性通过不等于合规授权，质量和人工复核要求仍然有效。对安全关键操作，宁可快速拒绝或转人工，也不要用未验证的旧模型、旧索引或不完整检查点继续自动决策。

混沌实验的权限应最小化并可撤销，实验账号与生产账号分离，注入操作有双人审查或自动审批门槛。恢复脚本不得把调试模式、临时凭证和宽泛网络规则永久带回生产。每次演练结束后检查临时对象、访问策略、DNS、队列和告警路由，形成可审计清单。

## 21.18 总结与下一依赖

本章的核心不是某个熔断器库或备份命令，而是一条可复核的推理链：先定义用户和数据真正关心的成功事件，再写 SLI、SLO、SLA 和错误预算；沿请求和训练状态传播 deadline、幂等键、重试预算和资源舱壁；对检查点使用临时写入、完整 manifest、校验和、版本和两阶段发布；用混沌实验验证稳态假设、停止条件和恢复动作；最后按 RTO、RPO 和依赖顺序演练灾备，并把证据回写到发布和容量决策。

可靠性不是“永不失败”。它是失败可检测、影响有界、状态不悄悄损坏、恢复可重复、用户知道结果语义。一个返回降级答案并清楚标记、且在预算内恢复的系统，可能比偶尔返回高质量但无法解释和无法回滚的系统更可靠。第22章将在这些状态和依赖边界之上讨论身份、隔离、供应链和数据外泄；安全控制会反过来改变幂等日志、灾备副本和故障演练的允许范围。
